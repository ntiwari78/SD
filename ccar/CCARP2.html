Core idea

Evaluation, Testing & Optimization
Core idea
Decide what success means, in numbers, before you build.

  • Prefer volume over perfection in a test set, and automate grading where you can: exact match and code-based checks first, then an LLM grader with an explicit rubric, then human review.

Q01 Stakeholders Answered correctly

An architect is reviewing a draft implementation guide for a multi-turn assistant built on the Messages API. The draft instructs engineers to send only the newest user message after the first request completes. What correction should the architect make to the guide?

  • A State that the API is stateless, so each request must resend the full conversation history. Correct · you chose this

    This is correct because the Messages API does not retain conversation state between requests. Every request must include all prior user and assistant turns for Claude to have context, so the guide as drafted would produce an assistant that appears to forget everything after the first exchange.

  • B Recommend rebuilding the assistant on Claude Managed Agents so earlier turns persist automatically. Distractor

    This is incorrect because re-platforming is an unnecessary overhaul when the actual fix is a client-side change to how requests are assembled. Managed Agents is a different build path suited to long-running asynchronous work, and switching to it does not correct the guide's misunderstanding of how the Messages API handles conversation history.

  • C Recommend enabling prompt caching so the server retains earlier turns between requests. Distractor

    This is incorrect because prompt caching changes what you pay for repeated prefix tokens, not whether they must be sent. Cached content still has to appear in every request and still occupies the context window, so caching does not make the API stateful.

  • D Advise selecting a model with a larger context window so prior turns are retained automatically. Distractor

    This is incorrect because context window size determines how much a single request can hold, not whether the server remembers anything between requests. A larger window does not change the requirement to resend the conversation history.

Why this is the answer

The Messages API is stateless: nothing about a conversation persists on the server between requests. Each call is a complete, self-contained prompt, and the application is responsible for accumulating the conversation (every user turn, every assistant response, and any tool results) and sending the whole history with each new request. A guide that tells engineers to send only the latest message will produce an assistant that answers the first question normally and then loses all context, which is one of the most common integration mistakes for teams new to LLM APIs. This is exactly the kind of property an implementation guide must state explicitly, because engineers coming from session-based web APIs reasonably assume the opposite.

The design tradeoff behind statelessness is control: because the client owns the history, the application can edit, truncate, summarize, or inject synthetic turns before each request, which is what makes context-management strategies like compaction and context editing possible at all. The mental model to teach is that the message list is the conversation, and the server sees only what you send.

The distractors map to predictable misconceptions. Migrating to Claude Managed Agents is a disproportionate response: that is a distinct build path (a pre-built agent harness for long-running, asynchronous work), and swapping platforms neither fixes the guide nor teaches the team how the API they chose actually works. Prompt caching is a pricing and latency optimization on repeated prefixes, not server-side memory: cached turns must still be included in the request and still count toward the context window. And a larger context window enlarges what a single request can carry, but it does not cause anything to be retained across requests. See Working with Messages and Prompt caching.

Q02 Stakeholders Answered correctly

An architect is presenting a recommended solution architecture to a client's steering committee for sign-off. Evaluation results meet the agreed targets overall, but testing revealed a known weakness on one rare input category. How should the architect handle this in the presentation?

  • A Postpone the sign-off until testing shows the weakness has been eliminated. Distractor

    LLM-based systems are probabilistic, so residual error on rare inputs can rarely be driven to zero, and waiting for perfection stalls delivery indefinitely. The professional approach is to quantify the risk and manage it, not to treat elimination as a precondition for approval.

  • B Disclose the weakness with its measured impact and the planned mitigation. Correct · you chose this

    This is correct because the committee is accountable for the decision and needs full information to approve it responsibly. Quantifying how often the weakness occurs and pairing it with a mitigation and monitoring plan turns a risk into a managed trade-off, and it protects trust when the issue eventually appears in production.

  • C Report only the aggregate performance metrics showing the targets are met. Distractor

    Aggregate metrics can hide failure modes that matter to specific users or processes, and withholding a known weakness deprives the accountable stakeholders of material information. When the weakness surfaces in production, the omission damages credibility far more than an upfront disclosure would have.

  • D Raise the weakness only if a committee member asks about edge cases. Distractor

    Making disclosure contingent on the right question being asked shifts responsibility for discovering risk onto stakeholders who may not know what to ask. Material limitations should be volunteered proactively so the approval is genuinely informed.

Why this is the answer

Architectural decisions about AI systems are ultimately risk acceptance decisions, and only the accountable business stakeholders can accept a risk they have been told about. Because large language models are probabilistic, a solution that meets its aggregate targets will still carry residual error, often concentrated in rare or unusual input categories. The architect's job in a sign-off presentation is therefore not to prove the system is flawless but to make the trade-off legible: state what the weakness is, quantify how often it occurs and what it costs when it does, and show the mitigation, whether that is a human review path, a guardrail, targeted evaluation coverage, or production monitoring with an agreed threshold for revisiting the design.

This approach works for a practical reason as well as an ethical one. A weakness disclosed with a plan reads as engineering maturity; the same weakness discovered in production after a silent sign-off reads as concealment, and it undermines every future recommendation the architect makes. Anthropic's guidance on defining success criteria reflects the same mental model: success for an LLM system is expressed as measurable thresholds and acceptable error rates tied to business risk, not as the absence of failure.

The alternatives each fail this standard. Reporting only aggregate metrics buries a known failure mode inside a passing average and withholds material information from the decision-makers. Postponing sign-off until the weakness is eliminated treats a probabilistic system as if it could be made deterministic, delaying value indefinitely for a goal that may be unreachable. Disclosing only on request outsources risk discovery to stakeholders who lack the technical context to ask the right question, which means the approval they give is not genuinely informed.

Q03 Architecture Answered correctly

A customer-service application receives requests that fall into a few well-separated categories, each best served by different instructions and a different model tier. A single general prompt has degraded quality: tuning it for one category worsens the others. Which orchestration pattern most directly addresses this?

  • A Use an orchestrator that dynamically decomposes each request and delegates subtasks to workers. Distractor

    Orchestrator-workers earns its complexity when subtasks cannot be predicted in advance and must be decomposed dynamically. Here the categories are known and well separated, so dynamic decomposition adds coordination overhead without addressing the prompt-conflict problem.

  • B Chain the categories as sequential prompt steps so each set of instructions is applied in turn. Distractor

    Prompt chaining decomposes one task into fixed sequential steps where each builds on the last. A request belongs to a single category, so passing it through every category's instructions in sequence wastes tokens and reintroduces the instruction conflicts the team is trying to eliminate.

  • C Send every request through all specialized handlers in parallel and select the best output. Distractor

    Running all handlers on every request multiplies cost and latency for no benefit when the correct category can be determined up front. Parallel voting is meant for aggregating diverse attempts at the same task, not for dispatching between known categories.

  • D Classify each request up front and dispatch it to a category-specific prompt and model. Correct · you chose this

    This is the routing pattern: an initial classification step separates concerns so each category gets a handler optimized for it, including a cheaper or faster model where appropriate. It directly resolves the stated conflict where improving one category degrades another.

Why this is the answer

The scenario describes the textbook trigger for the routing workflow: inputs fall into distinct categories that are handled better separately, and a shared prompt forces a compromise where optimizing for one input type hurts performance on others. Routing adds a lightweight classification step at the front, then hands each request to a downstream prompt, toolset, and model chosen for that category. Because the dispatch happens per request, each handler can be tuned aggressively without side effects on the others, and easy categories can be served by a smaller, cheaper model while hard ones go to a more capable tier.

A useful mental model is separation of concerns applied to prompts. Anthropic's guidance in Building Effective Agents distinguishes routing from the other patterns by what is known in advance: routing assumes the categories are enumerable and a classifier can assign them accurately, whereas orchestrator-workers exists for the opposite situation, where subtasks cannot be predicted and a central model must decompose the work dynamically. Choosing orchestrator-workers here would pay for planning flexibility the problem does not need. Parallelization in its voting form runs the same task multiple times to gain confidence from diverse outputs; broadcasting one request to every specialized handler inverts that idea into pure waste, since only one handler's answer was ever relevant. Prompt chaining sequences steps of a single task, so threading a request through every category's instructions in turn recreates the very instruction interference the redesign is meant to remove.

Architecturally, routing also keeps the system evolvable: adding a new category means adding a classifier label and a new handler, not renegotiating a shared prompt that every existing category depends on. The classifier itself should be validated with an evaluation set, since routing quality is bounded by classification accuracy.

Q04 Governance Answered correctly Select two

A platform must guarantee that no policy-violating assistant response ever reaches readers. Its automated content filter occasionally times out. Which TWO design choices uphold that guarantee?

  • A Deliver the response with a disclaimer whenever the filter cannot return a verdict in time. Distractor

    This is a fail-open design: during every timeout, unscreened content reaches readers, which directly breaks the stated guarantee. A disclaimer is notice, not a control, and does not prevent the harm.

  • B Treat a filter timeout as a rejection, withholding the response until screening succeeds. Correct · you chose this

    Failing closed means the absence of a verdict is handled the same way as a negative verdict. This preserves the guarantee during outages, trading availability for safety, which is the correct trade when the requirement is absolute.

  • C Place the filter as a blocking gate in the delivery path, so unscreened responses cannot ship. Correct · you chose this

    A guarantee that violating content never reaches readers requires the filter to sit inline, where delivery is impossible without a passing verdict. Any architecture that lets a response route around the check turns an absolute requirement into a best effort.

  • D Run the filter asynchronously after delivery and retract any responses it later flags. Distractor

    Post-delivery scanning is a detective control, so violating content is visible to readers during the window before retraction. A requirement that content never reach readers cannot be satisfied by catching it afterwards.

Why this is the answer

An absolute safety requirement, one phrased as never, demands a preventative guardrail, and a preventative guardrail is defined by two properties working together: its placement and its failure mode. Placement means the check sits synchronously in the delivery path, so a response physically cannot reach the user without a passing verdict. Failure mode means the system fails closed: when the check cannot complete, whether from a timeout, a crash, or a network fault, the response is withheld rather than waved through. Either property alone is insufficient. An inline gate that passes traffic on timeout leaks during every outage; a fail-closed check that runs outside the delivery path can simply be bypassed.

The distractors illustrate the two classic ways this design gets weakened. Delivering with a disclaimer on timeout is a fail-open posture: it optimizes availability at the expense of the guarantee, which may be acceptable for advisory checks but not for a regulatory or brand-safety absolute. Asynchronous post-delivery scanning converts the control from preventative to detective: it can measure how often violations occur and support remediation, but the harm has already landed by the time it fires. Detective controls are valuable as a second layer for monitoring and audit, not as the mechanism that enforces a never-before-display rule.

The engineering tradeoff is deliberate: failing closed reduces availability during filter outages, so teams pairing this design in production typically add health monitoring and alerting to keep those outages short, and reserve fail-open behavior for checks whose requirements are soft. Matching the failure mode to the severity of the requirement is a core part of implementing guardrails. Q05 Evaluation Answered correctly

A team runs an A/B test comparing two prompt variants for a multi-turn support assistant. Each incoming message is independently assigned to a variant, so a single conversation often mixes both prompts. Which design change makes the comparison valid?

  • A Alternate variants deterministically on every other message so both arms receive equal exposure. Distractor

    This is incorrect because alternating still mixes both prompts inside a single conversation. Equal exposure does not create independence; each variant's outcomes remain influenced by the other variant's earlier turns.

  • B Randomize assignment at the conversation level so each session uses one variant throughout. Correct · you chose this

    This is correct because the unit of randomization must match the unit where the treatment acts. Assigning a whole conversation to one variant keeps each arm's outcomes attributable to a single prompt, so the measured difference reflects the variants rather than a blend of both.

  • C Replace the online test with a rerun of the offline evaluation suite for each variant. Distractor

    This is incorrect because it abandons the production measurement rather than repairing it. Offline evaluations are useful and can even include multi-turn test cases, but rerunning them does not fix the flawed A/B design and is not a substitute for measuring live user outcomes when that is the goal of the experiment.

  • D Increase the traffic allocation to the treatment arm so results accumulate faster. Distractor

    This is incorrect because more traffic only adds volume to a contaminated measurement. When both variants appear within the same conversations, the arms are not independent, and no sample size fixes that attribution problem.

Why this is the answer

The unit of randomization in an A/B test must match the unit at which the treatment operates. A prompt variant for a multi-turn assistant shapes an entire conversation: each response conditions the user's next message and the model's subsequent turns. If individual messages are assigned to arms independently, every conversation becomes a blend of both variants. Each arm's metrics are then contaminated by the other arm's behavior, a form of interference that biases both estimates toward each other and destroys attribution. The fix is to randomize at the conversation (or user) level, so every session experiences exactly one variant from start to finish and outcomes can be cleanly credited to it.

This is why neither more traffic nor deterministic alternation helps: both leave the contamination in place. Statistical power addresses noise, not bias; a biased comparison stays biased at any sample size. Alternating messages guarantees mixing rather than preventing it. Retreating to the offline evaluation suite is also not a repair: offline evaluations are valuable and can include multi-turn, context-dependent test cases, but the experiment's goal here is to compare performance against a baseline on live production traffic, and replacing the online test forfeits that measurement rather than fixing its design.

A useful mental model for architects: an A/B test is only as trustworthy as its isolation between arms. Choose the randomization unit first, based on where the treatment's effects can leak, then set traffic split, duration, and guardrail metrics on top of that foundation. Q06 Architecture Answered correctly

A team processes inbound customer messages in three distinct categories: billing disputes, outage reports, and plan changes. Each category needs different instructions and tools, messages can be classified accurately up front, and one generalist prompt performs poorly across all three. Which architectural pattern is most appropriate?

  • A Use an orchestrator LLM that decomposes each message into dynamically chosen subtasks. Distractor

    Orchestrator-workers fits complex tasks where the needed subtasks cannot be predicted in advance. Here the handling path for each category is known and stable, so dynamic decomposition adds cost and unpredictability without solving the stated problem.

  • B Keep one generalist prompt and add more few-shot examples covering every category. Distractor

    The scenario states the single generalist prompt already performs poorly across the three categories, which signals that one prompt is overloaded. Adding examples for all categories makes the prompt longer and more diluted rather than giving each category the focused instructions and tools it needs.

  • C Add a classification step that routes each message to a category-specific prompt and toolset. Correct · you chose this

    This is the routing pattern: classify the input, then hand it to a specialized downstream handler. It fits exactly when inputs fall into distinct categories that can be classified accurately, letting each handler use focused instructions and tools without the categories interfering with one another.

  • D Run all three specialized handlers on every message in parallel and select the best output. Distractor

    Parallel execution is less appropriate here because each message can be classified accurately before processing, so running every handler triples the work and adds a selection step for no benefit. Parallelization earns its cost when subtasks genuinely need to run together or multiple outputs improve the result.

Why this is the answer

This scenario matches the routing pattern: a classification step directs each input to a specialized downstream process. Routing is a form of separation of concerns for prompts. Instead of one prompt trying to cover billing, outages, and plan changes at once (where instructions for one category can degrade performance on the others), each handler carries only the instructions, examples, and tools relevant to its category. The pattern is appropriate precisely under the conditions the scenario states: the categories are distinct, and classification can be done accurately up front. If classification were unreliable, routing errors would send messages to the wrong handler, and a different design would be worth considering.

Running all specialized handlers in parallel on every message is a workable design in some situations, but it is a poor fit here: because the category is knowable before processing, routing avoids paying for two unnecessary handler runs per message and eliminates the need for aggregation or selection logic afterward. Parallelization is better reserved for cases where independent subtasks must all execute, or where multiple outputs genuinely improve the result. Orchestrator-workers is also mis-scoped: its defining trait is that a central model dynamically decides what subtasks are needed, which pays off when the work cannot be predicted in advance; here the per-category workflow is stable and known. Finally, enlarging the single generalist prompt is the anti-pattern the scenario is already suffering from: cross-category instructions compete for the model's attention, and more examples deepen the dilution rather than fixing it.

The broader principle is Anthropic's guidance to choose the simplest pattern that satisfies the requirements. Routing keeps each path predictable, individually testable, and cheap, and it composes cleanly: each downstream handler can itself be a single augmented call, a chain, or an agent as its category demands. Q07 Dev Productivity Answered correctly

A team's Claude Code workflows depend on three MCP servers: an issue tracker, a database, and a monitoring service. New members currently configure each server by hand, and configurations drift over time. What most effectively standardizes these connections for the team?

  • A Commit a project-scoped MCP configuration file to the repository so every clone loads the servers. Correct · you chose this

    This is correct because MCP servers support a project scope stored in a checked-in configuration file, so every team member who clones the repository gets the same server definitions automatically. Version control keeps the configuration consistent and lets changes propagate to the whole team through normal review and pull workflows.

  • B Document the server setup commands in the project's CLAUDE.md for developers to follow. Distractor

    CLAUDE.md carries instructions and context for Claude at session start; it does not configure or connect MCP servers. Developers would still perform the setup manually from the documentation, leaving the same room for drift and inconsistency.

  • C Distribute an onboarding shell script that each new member runs once to register the servers. Distractor

    A one-time script registers servers at onboarding but does not keep configurations synchronized afterward: when the team changes a server, existing members drift until they rerun the script. Project-scoped configuration in version control updates everyone automatically without a separate distribution step.

  • D Have each developer add the three servers to their personal user-level configuration. Distractor

    User-level configuration applies only to the individual machine where it was set up, which is essentially the current state that produced the drift. It gives the team no shared source of truth and no mechanism for propagating changes.

Why this is the answer

Claude Code resolves MCP server configuration from three scopes: local (private to one developer on one machine), user (all of that developer's projects), and project. The project scope lives in a .mcp.json file at the repository root, designed to be checked into source control. Because the file travels with the codebase, every clone of the repository yields identical server definitions, and updating a server becomes a normal code change that reaches the whole team on the next pull; this is exactly the mechanism that eliminates configuration drift.

The design also anticipates team realities: the file supports environment variable expansion such as ${API_KEY} or ${VAR:-default} in URLs, headers, and commands, so a shared configuration never needs to embed machine-specific paths or secrets. Claude Code additionally prompts for approval before using project-scoped servers from a repository, which protects developers from a compromised or malicious checked-in configuration.

The mental model to carry is that each configuration mechanism has a distinct job: user-level and local scopes exist for personal, machine-specific setups and cannot serve as a team's source of truth; CLAUDE.md shapes Claude's behavior through instructions but performs no configuration at all, so documenting commands there still leaves humans doing manual setup; and one-time onboarding scripts freeze a snapshot that decays as the server list evolves. Standardization at team scale comes from putting configuration where the code lives, in version control, so consistency is inherited rather than maintained by hand.

Q08 Architecture Answered correctly

A team runs two Claude workloads: interactive customer queries under a committed response-time SLA, and nightly summary reports with no urgency. Leadership wants inference costs reduced without breaching the SLA. Which recommendation best aligns cost optimization with the performance commitment?

  • A Batch the nightly reports and keep interactive queries synchronous. Correct · you chose this

    This is correct because it applies the cost lever exactly where latency does not matter: asynchronous batch processing carries a 50 percent discount and its processing window is acceptable for overnight reports. The interactive traffic stays synchronous, so the committed SLA is untouched while overall spend drops.

  • B Submit both workloads through batch processing to maximize the discount. Distractor

    This is incorrect because batch processing is asynchronous with a processing window measured in hours, which is incompatible with a committed response-time SLA for interactive queries. Maximizing the discount by breaching the SLA trades one value pillar away to serve another when both can be satisfied.

  • C Switch both workloads to the smallest model tier to reduce token spend. Distractor

    This is incorrect because changing model tier alters capability, not just cost, and nothing in the scenario indicates the accuracy of either workload has been evaluated on a smaller model. It risks quality regressions on both workloads instead of applying a cost lever that leaves output quality unchanged.

  • D Renegotiate the SLA so interactive traffic can also be processed in batches. Distractor

    This is incorrect because it sacrifices a committed performance pillar to serve the cost pillar when the two are not actually in conflict here. The nightly workload alone can absorb the batch discount, so weakening the customer-facing commitment is an unnecessary concession.

Why this is the answer

Business value pillars such as cost and performance SLAs are not interchangeable, and an architect's job is often to satisfy several at once by mapping each optimization to the workload where it fits. The key insight in this scenario is that the two workloads have fundamentally different latency profiles: one carries a committed response-time SLA, the other runs overnight with no urgency. That segmentation is what unlocks savings without a tradeoff.

The Message Batches API processes requests asynchronously at a 50 percent discount on both input and output tokens, with results delivered within a 24-hour processing window. That pricing model exists precisely because the platform can schedule batch work flexibly; the customer trades immediacy for cost. Nightly report generation is the textbook fit, while interactive traffic under an SLA is the textbook non-fit. Batching everything would breach the commitment, and renegotiating the SLA gives up a promised pillar the business never needed to concede. Downgrading the model tier is a different lever entirely: it changes capability, and the disciplined version of that move (choosing the smallest model that meets an accuracy target) requires evaluation evidence the scenario does not provide.

The general pattern for architects: before pulling a cost lever, classify workloads by their latency and quality requirements, then apply asynchronous discounts, caching, or model right-sizing only where the affected requirement can absorb it. Q09 Models & Context Answered correctly

A team runs two endpoints: one performs multi-step fraud-pattern analysis on claims, the other extracts three fields from a standardized form. Both prompts instruct step-by-step reasoning before answering. The extraction endpoint's latency and cost have risen with no accuracy gain. What change is most appropriate?

  • A Keep step-by-step reasoning for the fraud analysis and remove it from the field extraction. Correct · you chose this

    Chain-of-thought reasoning earns its extra tokens on multi-step analytical tasks, where the fraud endpoint shows real benefit. On a simple, bounded extraction task it adds output tokens, latency, and cost without improving accuracy, so the technique should be applied per task based on measured benefit.

  • B Lower the temperature on the extraction endpoint so the reasoning text becomes shorter. Distractor

    Temperature controls sampling randomness, not how many reasoning tokens the model produces. It does not remove the instructed step-by-step output, so latency and cost remain inflated.

This division exists because accurate relevance scoring is too costly to run over an entire corpus, but perfectly affordable over 20 candidates.

The scenario is the textbook signature for adding the second stage. Recall is already solved (the correct chunk is nearly always retrieved), and the constraint is the context budget, so the whole problem reduces to ordering. Anthropic's published evaluation of this pattern reports that reranked Contextual Embeddings plus Contextual BM25 reduced the top-20 retrieval failure rate by 67% relative to the baseline, with the reranking step providing the final gain over the unreranked hybrid system; see Introducing Contextual Retrieval.

The other approaches each miss the failure mode. Enlarging the candidate pool improves recall, which is not deficient here. Thresholding on embedding similarity filters by the very signal that is misordering results, and raw similarity scores are not calibrated enough to serve as a reliable relevance cutoff. Shrinking chunks changes how many passages fit, not which ones are chosen, and fragments the meaning each passage carries. For guidance on embedding-based retrieval and pairing it with rerankers, see the Embeddings documentation. The one real cost of reranking is added latency per query, which is why the sound engineering habit is to quantify that cost against response-time requirements before adopting it.

    A model mismatch shows up as a capability gap, such as shallow reasoning on complex tasks, not as oscillation between two styles the model can clearly produce. A more capable model still cannot satisfy two instructions that contradict each other, so the defect would persist.

  • C Add retrieval grounding so responses stay anchored to source documents. Distractor

    Retrieval grounding is a mitigation for hallucination, where the model fabricates content not supported by source data. The symptom here is inconsistent response style, not fabricated facts, so grounding addresses a failure mode the system is not exhibiting.

  • D Review the system prompt for conflicting instructions about response length and style. Correct · you chose this

    Inconsistent behavior on similar inputs, following a prompt that accumulated edits from multiple contributors, is the classic signature of a prompt failure caused by contradictory instructions. When the prompt simultaneously demands brevity and thoroughness, the model resolves the conflict differently on each request, producing exactly this oscillation.

Why this is the answer

Diagnosing a degraded LLM system starts with matching the observed symptom to the right failure class. Prompt failure shows up as behavior the model is capable of but applies inconsistently or wrongly, often because instructions conflict, are ambiguous, or have drifted through accumulated edits. Hallucination shows up as confident content ungrounded in the provided data or tool results. Model mismatch shows up as a genuine capability gap: the task exceeds what the chosen model tier can do even under a well-structured prompt.

Here the telltale details are in the stem: the model, tools, and retrieval are unchanged, the prompt has been edited by several contributors, and the output oscillates between two styles the model can clearly produce. A prompt that says both "be concise" in one section and "explain each step in detail" in another forces the model to pick a winner per request, and which instruction dominates can vary with the specific query, so the assistant looks erratic. The first diagnostic step is therefore an audit of the prompt itself, reconciling or removing the contradiction, then re-testing against the evaluation suite.

The distractors each misdiagnose the failure class. Escalating the model tier treats an instruction conflict as a capability gap; a stronger model follows instructions more faithfully, which does not resolve two instructions that cannot both be satisfied. Lowering temperature reduces sampling randomness but leaves the contradictory guidance in place. Retrieval grounding targets fabrication, a failure the system is not showing. Anthropic's guidance makes the broader point explicit: not every failure is best fixed at the same layer, and effective prompt engineering presumes you have identified where the defect actually lives before changing anything.
