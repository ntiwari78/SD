Q1

Choosing the Correct Subagent for Exploration and Editing

Claude Code Configuration & WorkflowsCI/CD code review pipeline
Scenario · CI/CD code review pipeline

You are integrating Claude Code into your Continuous Integration/Continuous Deployment (CI/CD) pipeline. The system runs automated code reviews, generates test cases, and provides feedback on pull requests. You need to design prompts that provide actionable feedback and minimize false positives.

A pipeline stage delegates a dependency survey to the Explore subagent and also instructs it to fix the outdated import statements it finds. The survey summary comes back, but no files were changed. What is the correct adjustment?

  1. Correct

    Explore is designed for searching and analyzing codebases. Its tool restrictions prevent it from modifying files. A general-purpose subagent can investigate the code and make the required edits when given the appropriate tools.

  2. Incorrect

    The model affects reasoning capability and cost, not the tools an agent is permitted to use. Even a more capable model cannot modify files without write-capable tools.

  3. Incorrect

    Thoroughness controls how deeply Explore searches and analyzes. It does not change its permissions or grant Write and Edit access.

  4. Incorrect

    Subagents do not generally discard their file changes. A general-purpose subagent with write access can make persistent modifications. The problem is Explore's specific read-only configuration.

Correct answer: A

Overall explanation

Claude Code's built-in subagents are specialized by their available tools, not merely by their prompts.

Explore is useful for broad, read-only investigation. Its restrictions let the main agent delegate noisy discovery work without allowing the Explore subagent to alter the repository. When the task requires both discovery and modification, use a general-purpose subagent or separate the workflow into exploration followed by editing.

The key distinction is between what an agent can reason about and what actions its tool permissions allow. Changing the model or thoroughness cannot override a tool restriction.

Understanding Tool Use During Plan Mode

Claude Code Configuration & WorkflowsCustomer support resolution agent
Scenario · Customer support resolution agent

You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to backend systems through custom Model Context Protocol (MCP) tools: get_customer, lookup_order, process_refund, and escalate_to_human. Your target is 80%+ first-contact resolution while knowing when to escalate.

A developer refactoring the agent's escalation logic enters plan mode and notices Claude running git log and grep shell commands before any plan has been presented. What should the developer do?

  1. Incorrect

    Plan mode relies on active exploration. Reading files and running commands helps Claude understand the codebase before proposing changes. Blocking all tools would force it to plan without adequate evidence.

  2. Incorrect

    Running exploratory shell commands does not mean Claude has left plan mode. The mode restricts edits, not all command execution. Restarting would also discard useful investigation.

  3. Incorrect

    Plan mode defers source edits until approval; it does not rely on staging edits in a temporary worktree. Worktrees isolate filesystem state for separate work, but they are not necessary to make plan mode read-only.

    Plan mode allows Claude to inspect files and run exploratory commands to understand the task. The developer should review the proposed plan before approving execution. The presence of read-only investigation is expected and does not indicate a problem.

Correct answer: D

Overall explanation

Plan mode separates research and planning from implementation. Claude can inspect the repository, trace dependencies, and run exploratory commands before it proposes a plan. Source modifications wait until the developer approves that plan.

This is particularly valuable for changes to complicated workflows, such as escalation logic, where a developer wants to understand the current behavior before committing to an implementation.

Do not confuse the restriction on editing with a restriction on exploration. The purpose of planning is to gather evidence first, propose an approach, and obtain approval before making changes.

Reconciling Research Findings That Change Over Time

Context Management & ReliabilityMulti-agent research system
Scenario · Multi-agent research system

You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

Two research subagents return dated findings on a CI vendor's job concurrency limit: a source published in 2023 states 20 jobs, and a source published in 2025 states 60. The synthesis step currently flags this as an unresolved contradiction. How should the final report handle these values?

  1. Incorrect

    Escalation is appropriate when credible sources conflict in a way the available evidence cannot resolve. Here, the publication dates offer a plausible explanation: the vendor's limit may have changed over time. A human review is not necessary merely because historical and current values differ.

  2. Incorrect

    A coverage gap means the information could not be obtained. In this case, the system retrieved two values with dates. Omitting both would lose useful historical and current information.

  3. Incorrect

    Recency is not an automatic override rule. Removing the older value destroys historical context and hides the fact that the limit may have changed. The older figure could still be relevant to users investigating earlier configurations.

  4. Correct

    The publication dates provide temporal context. A limit of 20 jobs in 2023 and 60 in 2025 plausibly indicates that the vendor increased its limit. Presenting both values with their dates preserves provenance while identifying the newer value as current.

Correct answer: D

Overall explanation

Research synthesis must distinguish a genuine contradiction from a change over time. Two sources can report different values without either being wrong if the underlying fact changed between publication dates.

The solution is to carry dates and source metadata through the entire research pipeline. Subagents operate in separate contexts and return summaries, so the coordinator cannot reliably infer missing dates later. The output schema should preserve publication or data-collection dates alongside each finding.

The guiding principle is dates are interpretive metadata, not a tiebreaker. Use them to explain a likely historical change, but do not automatically discard older evidence. Escalate only when the available metadata cannot reasonably resolve a disagreement.

Scenario · Customer support resolution agent

You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to backend systems through custom Model Context Protocol (MCP) tools: get_customer, lookup_order, process_refund, and escalate_to_human. Your target is 80%+ first-contact resolution while knowing when to escalate.

You define a billing-investigation subagent with an AgentDefinition. It needs to read customer and order data, but must be structurally unable to call process_refund. Which configuration achieves this guarantee?

  1. Incorrect

    The description field helps Claude decide when to delegate work to the subagent. It does not restrict the tools available after the subagent has been invoked. The refund tool would still be callable if it remained in the subagent's toolset.

  2. Incorrect

    allowedTools controls which tools are pre-approved; it does not define which tools exist or are available. A tool not listed there can still be called subject to the normal permission handling.

  3. Correct

    The tools field in AgentDefinition controls the subagent's available capabilities. When specified, the subagent receives only the listed tools. Because process_refund is absent, the billing-investigation subagent cannot invoke it.

  4. Incorrect

    Prompt instructions are behavioral guidance, not an access-control guarantee. The model may still call a tool that remains available, so the tool should be removed from the subagent's capabilities entirely.

Correct answer: C

Overall explanation

An AgentDefinition separates three concerns:

  • Description: Helps Claude decide when to delegate to the subagent.
  • Prompt: Explains how the subagent should perform its assigned work.
  • Tools: Determines which actions the subagent is capable of taking.

Only the tool configuration creates the required structural restriction. A billing investigator needs read access to customer and order information, not the ability to issue refunds. Giving it only get_customer and lookup_order enforces that separation regardless of the model's generated decisions.

This is an important security principle: remove unnecessary capabilities rather than relying on instructions not to use them. It is especially important for consequential operations such as refunds.

Handling Frustrated Developers in Automated Code Reviews

Context Management & ReliabilityCI/CD code review pipeline✗ Recorded incorrect
Scenario · CI/CD code review pipeline

You are integrating Claude Code into your Continuous Integration/Continuous Deployment (CI/CD) pipeline. The system runs automated code reviews, generates test cases, and provides feedback on pull requests. You need to design prompts that provide actionable feedback and minimize false positives.

A developer replies to one of the pipeline's review comments: “This warning is wrong, it keeps blocking my PRs, and it's really frustrating.” The flagged finding is one the system can re-evaluate. How should the response flow be designed?

  1. Incorrect

    Sentiment analysis is an unreliable proxy for whether human intervention is necessary. A negative tone does not necessarily mean a problem is beyond the system's capabilities. This approach may escalate easily resolvable disputes while overlooking calmly expressed but genuinely complex cases.

  2. Correct

    Acknowledge the developer's frustration, use the additional context to re-evaluate the disputed finding, and escalate only if the developer reiterates their objection after the resolution attempt. Frustration alone is not an explicit request for human intervention.

  3. Incorrect

    Removing a finding merely because someone disputes it is silent suppression. The warning may identify a real problem. The system should reassess the evidence rather than suppress the finding to avoid conflict.

  4. Incorrect

    Frustration does not establish that the case exceeds the system's capabilities. Immediate escalation is appropriate when a human is explicitly requested; otherwise, the system should attempt a reasonable resolution first.

Correct answer: B

Overall explanation

The key principle is to distinguish frustration from an explicit request for human intervention.

A reliable workflow should:

  1. Acknowledge the developer's frustration.
  2. Re-evaluate the finding using the developer's additional context.
  3. Explain the result and the evidence supporting it.
  4. Escalate if the developer continues to object after the re-evaluation, or if human intervention is explicitly requested.

This balances automation efficiency with trust. Escalating every frustrated response overwhelms human reviewers, while automatically dismissing disputed findings undermines the integrity of the review process.

Sentiment scoring does not solve the problem because emotional tone is not a dependable measure of task complexity. Observable actions—such as explicitly requesting a human or reiterating an objection after a resolution attempt—provide better escalation signals.

The important distinction is that a schema controls the shape of the output, while validation checks whether the output is meaningful and correct.

Refreshing Stale Findings in a Resumed Session

Agentic Architecture & OrchestrationCI/CD code review pipeline✓ Recorded correct
Scenario · CI/CD code review pipeline

You are integrating Claude Code into your CI/CD pipeline. The system runs automated code reviews, generates test cases, and provides feedback on pull requests. You need to design prompts that provide actionable feedback and minimize false positives.

A nightly re-review job wants to reuse yesterday's review session after a developer pushes a few new commits touching a handful of files. Most of the prior analysis remains valid. How should the job proceed?

  1. Incorrect

    Compaction summarizes conversation history; it does not compare previous tool results with the current repository. Stale findings can therefore survive compaction, merely in summarized form.

  2. Incorrect

    A fresh review can be appropriate when extensive changes invalidate most of the previous analysis. Here, only a few files changed, so starting over wastes useful investigation that can be preserved by refreshing the affected evidence.

  3. Correct

    Resuming preserves the prior conversation and analysis, while explicitly re-reading changed files replaces the relevant stale evidence. This approach retains the useful bulk of the earlier work and refreshes the parts that may no longer be accurate.

  4. Incorrect

    Session resumption restores conversation history; it does not automatically refresh earlier file reads. Without explicit instructions to re-read changed files, the model may rely on outdated code and conclusions.

Correct answer: C

Overall explanation

A session should be understood as a conversation transcript, not a snapshot of the repository. It retains prompts, tool calls, tool results, and model responses. Earlier tool results remain in that history even if files change afterward.

The appropriate recovery strategy depends on the amount of change:

  • Limited changes: Resume the session, identify modified files, and re-read them before relying on previous conclusions.
  • Extensive changes: Consider starting a fresh session with a structured summary of the still-relevant prior findings.
  • Compaction: Use it to manage context size, not as a method for refreshing stale evidence.

The goal is to preserve valid work while explicitly updating the evidence that may have become outdated.

Evaluating Competing Strategies from the Same Baseline

Scenario · CI/CD code review pipeline

You are integrating Claude Code into your CI/CD pipeline. The system runs automated code reviews, generates test cases, and provides feedback on pull requests. You need to design prompts that provide actionable feedback and minimize false positives.

A session has completed a thorough baseline analysis of a large pull request. The team wants to evaluate two competing review-prompt strategies from that identical baseline, with neither evaluation influencing the other. What should they do?

  1. Correct

    Forking on resume creates a new session from a copy of the original conversation history, with its own session ID. Each review strategy starts from the same baseline, but subsequent messages and analysis remain isolated in their respective branches.

  2. Incorrect

    Both evaluations would accumulate in the same conversation history. Asking the model to ignore the first evaluation does not remove that evaluation from its context, so the second strategy may still be influenced by it.

  3. Incorrect

    A manually written summary is a lossy approximation of the original analysis. It can omit important details, and the two summaries may differ. Forking preserves the complete baseline history without requiring the analysis to be repeated or manually summarized.

  4. Incorrect

    Git worktrees isolate filesystem state, not conversation history. Separate sessions in separate worktrees do not automatically inherit the original session's analysis. Worktrees may be useful for filesystem isolation, but they do not solve the context-isolation requirement in this question.

Correct answer: A

Overall explanation

The objective is to conduct a controlled comparison: both strategies must begin with the same baseline, and neither strategy's subsequent analysis should influence the other.

The fork_session mechanism supports this by creating independent session branches from the original history. The original baseline remains unchanged, and each branch can develop its own conclusions.

Remember the distinction:

  • Session history contains the conversation and analysis available to the model.
  • Filesystem state contains the repository files being examined.
  • Forking a session isolates subsequent conversation histories while preserving the shared starting context.
  • Git worktrees isolate working directories, but do not copy conversation history into a new session.

For a fair comparison, fork the baseline once per strategy and let each branch proceed independently.

Its backend MCP tools include get_customer, lookup_order, process_refund, and escalate_to_human. The target is 80%+ first-contact resolution while knowing when to escalate.

The process_refund tool rejects an out-of-window refund with:

  • isError: true
  • errorCategory: "business"
  • isRetryable: false
  • message: "ERR_RB_221: refund_window_check failed"

The agent then tells customers an unspecified internal error occurred. What change fixes the customer communication?

  1. Incorrect

    This duplicates knowledge already held by the tool, consumes prompt tokens, and can become outdated when policy codes change. The explanation should be provided where the failure is identified.

  2. Incorrect

    Exposing raw internal details does not make the response more useful. Rule identifiers and internal thresholds may be inappropriate for customers and do not necessarily help the agent explain the decision.

  3. Correct

    The error metadata already indicates that the operation failed and should not be retried. A clear, human-readable message gives the agent the information it needs to explain the policy decision accurately.

  4. Incorrect

    A deterministic returns-window violation will not be resolved by retrying the same request. Marking it retryable encourages unnecessary calls without adding useful information.

Correct answer: C

Overall explanation

The error response needs to communicate both what happened and what the agent should do next.

In this case, the existing fields describe a non-retryable business-rule rejection. The missing piece is a message that explains the reason in understandable language.

A better message might say that the order falls outside the permitted returns window. The agent can then communicate the refusal accurately instead of inventing a reason or claiming an unspecified internal error occurred.
