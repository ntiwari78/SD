How to attack a question

  1. Find the deciding fact. Look for words like must or never, a hard deadline, “unattended”, “the prompt already failed”, “every subagent succeeded” or “files changed”.
  2. Guarantee or tendency? Hard guarantees need a programmatic control (hook, permission, tool scope, tool_choice, schema). Everything else can be shaped by prompts and examples.
  3. Where is the earliest effective point? Before the side effect, before context fills up, before the plan is approved, at decomposition.
  4. What does each party actually see? Subagents, humans, new sessions and CI runs see only what they are handed.
  5. Cross out the distractor smells below. What remains is usually the specific, minimal fix aimed at the root cause.

10 universal decision rules

  • Guarantees go in code, tendencies go in prompts

    If it says must, never or always and is about money, security or compliance, choose hooks, deny rules, tool scoping, tool_choice or schemas. Prompts, descriptions, few-shot and IMPORTANT only shift odds.

  • Act at the earliest point that prevents the problem

    PreToolUse before irreversible actions; trim before context; isolate discovery instead of compacting later; fix the plan before approval; fix decomposition, not synthesis.

  • Use the simplest structure that fits the uncertainty

    Direct execution for a one-sentence diff; a fixed prompt chain for known steps; plan mode or dynamic decomposition only when scope must be discovered.

  • Nothing is shared unless you pass it

    Subagents, humans, fresh sessions, CI runs and batch results see only what you hand them, so make handoffs explicit and self-contained.

Domain 1

Agentic Architecture & Orchestration

How agents, subagents and coordinators share work, context and control, and where hard rules are enforced.

51 questions12 principles
1.1

Subagents start empty, so hand off explicitly

7 questions

A non-fork subagent sees only its own system prompt, tools, CLAUDE.md and the delegation prompt. It never sees the parent’s history, tool results or system prompt.

✓ Pick this

  • Put the retrieved data, findings and full request context directly in the delegation prompt
  • Hand off a compact structured summary (IDs, amounts, decisions made), not a raw transcript
  • Static conventions every subagent must follow → project CLAUDE.md; runtime findings → delegation prompt

✗ Reject this

  • “The subagent will inherit the conversation / see earlier tool results”
  • Referencing parent tool_use IDs, or spawning “in a later turn” so it can see history
  • Writing runtime findings into CLAUDE.md or the AgentDefinition system prompt
  • Giving the subagent the lookup tools so it re-fetches what the parent already has
  • A bigger context window (the data was never sent)
EvidenceS1·Q6S1·Q21S2·Q7S2·Q13S2·Q25S2·Q29S3·Q36
1.2

The coordinator is the hub: it routes, filters and owns recovery

3 questions

In hub-and-spoke, results flow back to the coordinator, which decides what each next agent needs. Spokes don’t talk to each other.

✓ Pick this

  • Coordinator passes each subagent only the results its task requires
  • Coordinator collects findings from agent A and includes the relevant ones in agent B’s prompt
  • Failures go back to the coordinator with context; it retries, re-delegates or proceeds with partial results

✗ Reject this

  • Forwarding every accumulated output downstream
  • Adding a summariser subagent to shrink an over-stuffed handoff
  • Subagent-to-subagent shortcuts that bypass the coordinator
  • Aborting the whole workflow on one failure
  • Returning an empty “success” so the flow keeps going

1.3

Decomposition sets the ceiling on coverage

3 questions

If a concern never becomes a subtask, nothing downstream can recover it. When every subagent succeeds but the answer is incomplete, fix decomposition.

✓ Pick this

  • Coordinator enumerates every stated concern and delegates one bounded subtask per concern
  • Partition overlapping work up front (security / tests / style) so parallel agents don’t duplicate

✗ Reject this

  • Reordering the synthesis input
  • Passing the full history to every worker
  • A dedupe pass after the fact, or a shared “focus log” between agents
  • Rewriting tool descriptions when routing isn’t the problem
EvidenceS2·Q26S2·Q58S2·Q40
1.4

Parallel when independent, sequential when dependent

2 questions

Independent subtasks run concurrently only if their Task calls are emitted in the same assistant response. A subtask that needs another’s output waits for it.

✓ Pick this

  • Run independent subagents in parallel, then start the dependent step once its input returns
  • Emit both Task calls in one coordinator response
  • Give each parallel worker its own complete context (customer ID, its own issue)

✗ Reject this

  • Consecutive turns (that serialises them)
  • Letting one subagent spawn the dependent subagent itself
  • Spawning a dependent task in parallel before its input exists
  • Merging everything into one subagent

1.5

Match the workflow structure to the task’s uncertainty

6 questions

Use the simplest structure that works. Known, repeatable steps get a fixed prompt chain; scope that must be discovered gets dynamic, adaptive decomposition.

✓ Pick this

  • Recurring audits and weekly briefs → fixed prompt chain with programmatic gates between steps
  • Unfamiliar systems → map entry points and data flows first, rank by impact, adapt the plan
  • Large reviews → per-file pass, then a separate cross-file pass (beats attention dilution)
  • Incomplete output → evaluator-optimizer loop: detect nulls, re-delegate targeted extraction, re-assemble
  • Exploration → start broad and short, then narrow toward specific call sites

✗ Reject this

  • An autonomous agent loop for a predictable pipeline
  • One giant request for everything
  • A fixed uniform sequence for open-ended security work
  • Bigger context windows, extended thinking or majority-vote reruns for attention problems
  • Making fields required to “force” completeness

1.6

Description chooses the agent; the tool list bounds it

3 questions

Subagent and tool selection is driven by descriptions and the whole context. Capability is bounded by the tools each agent is given.

✓ Pick this

  • Distinct, specific subagent descriptions + a coordinator told to invoke only the matching ones
  • Least privilege: remove process_refund from a read-only analysis subagent’s toolset
  • Remove system-prompt wording that wrongly pairs a topic with a tool (e.g. “billing” ↔ escalation)

✗ Reject this

  • Keyword classifiers in app code
  • Naming every subagent so all of them always run
  • “Never call X” prompt rules or after-the-fact reversal
  • Hooks that block a symptom created by your own prompt

1.7

Enforce critical rules in hooks, at the right lifecycle point

9 questions

Prompts, descriptions and few-shot examples are probabilistic. Business-critical rules belong in code that runs before the side effect. Keep model-driven tool choice for the flexible parts.

✓ Pick this

  • PreToolUse hook to block a call (refund > limit, no verified customer ID) and route it to escalation
  • PreToolUse returning updatedInput to sanitise a call that should still run (strip a codename)
  • Shell hook exit code 2 to block in unattended runs (exit 1 is non-blocking; ask needs a human)
  • PostToolUse to transform results: normalise formats, trim verbose MCP fields
  • Matchers for MCP tools use the full name mcp__<server>__<tool>

✗ Reject this

  • PostToolUse to stop an irreversible action (too late)
  • System-prompt rules or tool descriptions for hard guarantees
  • Replacing the whole agent loop with a fixed decision tree
  • Extra “convert” or “trim” tools the model must remember to call

1.8

Honour the tool-use contract

4 questions

Claude requests tools; your code runs them. Every tool_use needs exactly one matching tool_result (by tool_use_id) in the next single user message.

✓ Pick this

  • Append the assistant tool_use message, then one user message carrying all tool_result blocks
  • Report a failed call as its own tool_result with is_error: true and details

✗ Reject this

  • Split results across messages, or send them in an assistant/“tool role” message
  • Plain text in place of a tool_result
  • Leaving a call unanswered (400 error) or waiting on retries before answering
  • Assuming the API runs client tools server-side

1.9

A session is a transcript, not a filesystem snapshot

8 questions

Resuming restores old tool results as if they were still true. How you continue depends on how much has changed.

✓ Pick this

  • Few files changed → resume, name the changed files, re-read before reusing findings
  • Major change (e.g. framework migration) → fresh session seeded with a structured summary of conclusions + claim-to-source mapping
  • Compare alternatives from one baseline → fork_session per branch
  • Automate refresh on resume → SessionStart hook listing changed files
  • Come back to long work → /rename now, --resume <name> later

✗ Reject this

  • Assuming resume reconciles files
  • /compact to “remove” stale results
  • Seeding a new session with stale raw tool results
  • Discarding everything for a two-file change
  • --continue when other sessions may intervene

1.10

Recover locally, escalate with context

1 question

Errors are handled at the lowest level that can resolve them. Only unresolved failures travel up, with enough context to decide.

✓ Pick this

  • Bounded local retry with backoff, then report failure type, attempted queries and partial results

✗ Reject this

  • Infinite retries inside the subagent
  • Forwarding every timeout immediately
  • Reporting partial results as success

1.11

Keep provenance inside the data

4 questions

Information loses context at every handoff. Pair each claim with its source in the same structured unit.

✓ Pick this

  • Structured findings: claim + quote + URL + document + date
  • Wrap each excerpt with its own <source> tag
  • Search agent returns a structured evidence report; coordinator passes it to synthesis

✗ Reject this

  • Separate bibliographies or a master registry
  • Order-based matching of excerpts to a path list
  • Running search and synthesis in parallel when synthesis needs search output

1.12

Keep measuring autonomous quality

1 question

Autonomous resolutions leave escalation-based QA. Only ongoing sampling across the whole population shows their error rate.

✓ Pick this

  • Stratified random sample of autonomous resolutions, reviewed continuously

✗ Reject this

  • A one-off audit then stopping
  • Complaint or reopen rates as the only signal
  • Agent self-rated confidence to choose what gets checked

How tools are described, scoped and connected, and how they report errors so agents can act on them.

2.1

Descriptions are the routing signal

3 questions

Claude picks tools mainly from their descriptions. Near-identical descriptions cause misrouting, so fix the interface contract itself.

✓ Pick this

  • State what it returns, when to use it, when not to, input format, an example and limits
  • Rename a tool when the name misleads (scan_code → run_security_scan)

✗ Reject this

  • Few-shot routing examples in the system prompt
  • Keyword classifiers + forced tool_choice
  • Merging tools behind a mode parameter
  • A rename alone, or minimal descriptions plus validation errors

2.2

Bound capability through the interface and tool list

4 questions

A tool’s interface is its capability surface. Narrow tools and scoped toolsets beat rules about how to use broad ones.

✓ Pick this

  • Replace a raw run_query with get_billing_history(customer_id, dates)
  • Subagent tools field lists only what its role needs
  • A scoped helper (fetch_source_snippet) for frequent checks; route heavy work via the coordinator

✗ Reject this

  • Filtering results after the fact
  • Description or prompt rules (“always filter by customer”)
  • Removing from top-level allowedTools (that is pre-approval, not restriction)
  • Granting a whole other agent’s toolset, or a routing tool

2.3

Errors must say what happened and what to do next

7 questions

isError alone says nothing about recovery. Add structured metadata and a plain-language message.

✓ Pick this

✗ Reject this

  • Raw payloads or stack traces
  • Prompt mappings of error codes
  • Blanket retries or escalating everything
  • Empty “success” for a failure; isError for a genuine empty result

2.9

Use built-in tools incrementally and precisely

4 questions

Search first, then read only what matters. Edit needs an anchor that matches exactly once.

✓ Pick this

  • Grep in content mode with escaped regex metacharacters for literal calls
  • Ambiguous Edit → widen the anchor with surrounding lines; else Read + Write the whole file

✗ Reject this

  • sed via Bash, shortening the anchor, or deleting duplicates
  • Writing only the changed line with Write

Ask: who should get it (me or the team), and where (one repo or all)?

Rules and CLAUDE.md guide. Permission rules and modes enforce. A skill’s allowed-tools grants pre-approval for that turn; it does not restrict.

✓ Pick this

  • Relying on omission from allowed-tools

3.4

Plan mode vs direct execution

6 questions

If you can describe the diff in one sentence, skip the plan. Plan when scope is uncertain, multi-file or unfamiliar, or there are competing approaches.

✓ Pick this

  • One-line fix → direct, with the stack trace / repro command and tests as the check
  • Library migration with two viable approaches → plan mode, review, then implement
  • Plan mode still reads files and runs exploratory commands; only edits wait
  • Plan missing something → keep planning and revise before approval

✗ Reject this

  • Plan mode or Explore for a trivial fix
  • Approving an incomplete plan and fixing it during execution
  • “Let the changes reveal the design” for big migrations

✗ Reject this

  • Longer prose specs or IMPORTANT markers
  • A few I/O examples when you don’t know the questions

Keep the main context clean

5 questions

Prevention beats recovery: isolate noisy discovery. Recover with focused compaction only when needed.
