Q1

Guaranteeing Exactly One Tool Call

Tool Design & MCP IntegrationMulti-agent research system
Scenario

You are building a multi-agent research system using the Claude Agent SDK. A coordinator delegates work to specialized subagents that search the web, analyze documents, synthesize findings, and generate reports.

A document-extraction pipeline's first Messages API request forces extract_metadata by name. The request also includes enrichment tools that will be used later. On long documents, Claude sometimes returns three extract_metadata calls in one response, one per section. The pipeline requires exactly one metadata record before enrichment begins.

Which request change guarantees exactly one extract_metadata call?

  1. Incorrect
    • Why it is incorrect: The flag is real, but it belongs inside the tool_choice object, not at the top level of the request.
    • Key distinction: A valid setting placed at the wrong level will not enforce the intended behavior.
  2. Correct
    • Why it is correct: Forcing the tool by name ensures that Claude calls extract_metadata. Setting disable_parallel_tool_use to true within tool_choice prevents multiple parallel calls, providing the required single-call behavior.
    • Why this matters: The pipeline needs an API-level guarantee rather than a behavior that merely tends to occur.
  3. Incorrect
    • Why it is incorrect: Prompt instructions guide model behavior but cannot guarantee that only one tool call will be emitted. The model may still produce multiple calls on some documents.
    • When it helps: Prompt instructions can clarify the intended extraction scope, but they should not replace a deterministic API control when call count is critical.
  4. Incorrect
    • Why it is incorrect: This can constrain the response to exactly one tool call, but it does not guarantee that the call will be extract_metadata. Since enrichment tools are also available, Claude could select one of those instead.
    • Key distinction: Limiting the number of calls is not the same as forcing the correct tool.
Correct answer: B

Overall explanation

Two separate requirements must be satisfied:

  1. Tool identity: Force extract_metadata using the named-tool form of tool_choice.
  2. Tool-call count: Set disable_parallel_tool_use: true inside tool_choice.

Parallel tool use is enabled by default. Forcing a tool's identity alone does not prevent Claude from emitting several calls to that tool in the same response.

The top-level parameter approach fails because the flag is misplaced. The prompt-only approach fails because instructions are not a hard API constraint. Using any constrains the call count but leaves the tool identity ambiguous.

Important limitation: Forced tool selection is not supported in every configuration, including certain combinations involving extended thinking. The scenario explicitly specifies a model that supports forced selection.

Quick revision

  • tool_choice with a named tool → forces the intended tool.
  • disable_parallel_tool_use: true inside tool_choice → prevents parallel calls.
  • Prompt instructions → guidance, not a guarantee.
  • any → does not guarantee a particular tool when several tools are available.

Distinguishing a Real Contradiction from Change Over Time

Agentic Architecture & OrchestrationMulti-agent research system
Scenario

A research coordinator delegates work to search, document-analysis, synthesis, and report-generation subagents.

The synthesis subagent reports a contradiction between two statistics published a year apart. The newer figure reflects genuine growth. Currently, subagents pass each finding as only a value and a source name.

How should the system be changed?

  1. Incorrect
    • Why it is incorrect: The synthesis agent cannot distinguish a time-related change from a genuine conflict if the dates are missing.
    • Additional risk: The instruction may suppress legitimate contradictions between sources that actually disagree.
  2. Incorrect
    • Why it is incorrect: Escalating an actual contradiction with attribution is reasonable, but the scenario describes a temporal difference rather than a genuine disagreement.
    • Root problem: The coordinator receives the same incomplete data and cannot resolve the issue without publication dates.
  3. Incorrect
    • Why it is incorrect: The older statistic is useful evidence of change over time. Discarding it removes the growth trend from the report.
    • Additional problem: Without dates, the synthesis agent cannot reliably determine which source is newer.
  4. Correct
    • Why it is correct: Publication dates supply the missing temporal context. The synthesis agent can recognize that the statistics describe change over time rather than automatically interpreting them as contradictory.
    • Implementation principle: Keep values, source attribution, and dates as distinct structured fields.
Correct answer: D

Overall explanation

In a multi-agent system, each subagent operates with its own context. Information reaches the next agent only when it is explicitly included in the handoff.

If a finding contains only a value and a source name, downstream agents may lose important metadata such as the publication date. Prompting cannot reliably recover information that was never supplied.

A more useful finding structure would be:

{
  "metric": "Example metric",
  "value": 125,
  "source": "Example report",
  "publication_date": "2025-06-15"
}

This is an illustrative schema, not a claim about the exact format required by the API.

With the dates available, the synthesis agent can explain the increase and cite both sources. For genuine disagreements, it should preserve the conflicting evidence and report the uncertainty rather than automatically choosing one value.

Quick revision

  • Missing metadata → fix the handoff structure.
  • Publication dates → distinguish temporal change from contradiction.
  • Do not discard older statistics when the trend matters.
  • Do not suppress genuine conflicts with blanket prompt instructions.
  • Structured fields preserve context more reliably than prose-only handoffs.

Resuming a Named Claude Code Session

Agentic Architecture & OrchestrationMulti-agent research system
Scenario

A team runs overnight research jobs using claude -p and the --no-session-persistence flag to prevent transcripts from being saved to disk.

An engineer wants to reopen a specific run the following morning using --resume with a name.

Which change to the launch command enables this?

  1. Incorrect
    • Why it is incorrect: --continue targets the most recent conversation in the directory rather than a specific named run.
    • Critical limitation: The original run was launched without session persistence, so there is no saved transcript to reopen.
  2. Incorrect
    • Why it is incorrect: Headless runs can be resumed by name when the session is saved and appropriately named.
    • Critical limitation: Capturing an ID does not restore a transcript that was never persisted.
  3. Correct
    • Why it is correct: Resuming by name requires a saved session and a name associated with that session. Removing the persistence-disabling flag allows the transcript to be saved; adding --name provides the label used to identify the run later.
    • Result: The next morning, the engineer can target the specific saved session by name.
  4. Incorrect
    • Why it is incorrect: Naming a session does not save its transcript. The run remains unavailable for resumption because session persistence is disabled.
    • Key distinction: A session name identifies a saved session; it cannot substitute for the saved session itself.
Correct answer: C

Overall explanation

Session resumption depends on persisted conversation data. Claude Code normally saves session transcripts, allowing the CLI to reopen a conversation by session ID or name.

The --no-session-persistence flag disables that saving behavior. Consequently, none of the resume mechanisms can recover a transcript that was not written to disk.

For a named overnight run, the correct design is to:

  1. Enable session persistence by removing --no-session-persistence.
  2. Assign a distinct label with --name.
  3. Resume that specific session using --resume and its name.

The alternatives fail because they either target the wrong session, assume a missing transcript can be recovered, or name a session without saving it.

Quick revision

  • --name → labels a session.
  • --resume → reopens a saved session.
  • --no-session-persistence → prevents the transcript from being saved.
  • --continue → targets the most recent conversation, not necessarily the desired run.
  • Always check whether session persistence is enabled before designing a resume workflow.

Enforcing Domain Restrictions Across Tools

Agentic Architecture & OrchestrationClaude Code workflows (general)
Scenario

Licensing terms prohibit retrieving content from certain publisher domains. A PreToolUse hook matching WebFetch denies requests to those domains, but a search subagent can still download the same pages by running curl through Bash.

Which change enforces the licensing policy?

  1. Incorrect
    • Why it is incorrect: The hook still matches only WebFetch, not Bash. The curl command bypasses the hook entirely.
    • Key distinction: Changing the decision on an existing hook does not extend its coverage to another tool.
  2. Correct
    • Why it is correct: The policy violation occurs through a different tool surface. Adding a Bash matcher allows the pre-execution hook to inspect shell commands that could retrieve restricted content.
    • Why timing matters: PreToolUse runs before the action, allowing the system to block the prohibited retrieval rather than merely hide its output afterward.
  3. Incorrect
    • Why it is incorrect: A system prompt provides behavioral guidance but does not deterministically prevent a tool call.
    • Security principle: Rules with contractual or compliance consequences should be enforced at the tool-execution boundary.
  4. Incorrect
    • Why it is incorrect: A post-execution hook runs after the command has executed. By then, the prohibited content has already been retrieved.
    • When post-processing helps: Redaction or normalization after execution can be useful when retrieval itself is permitted, but it cannot prevent a prohibited retrieval.
Correct answer: B

Overall explanation

A hook matcher determines which tool calls trigger the hook. A hook matching WebFetch does not automatically cover Bash, even when both tools can access the same website.

To enforce a domain restriction, the policy must cover all relevant execution paths. Here, the existing WebFetch hook should remain, and the deny logic should also cover Bash commands that could use curl or another command-line downloader to retrieve restricted pages.

The distinction between pre- and post-execution enforcement is essential:

  • PreToolUse: Intercepts the call before it executes.
  • PostToolUse: Runs after tool execution and can process the resulting output, but cannot undo the retrieval.

A prompt-only rule is insufficient when the policy must hold consistently.

Implementation note: A robust Bash policy should inspect or constrain the actual command execution path rather than relying only on a simple substring match. Shell commands can be composed in ways that evade naïve text matching, so strict licensing enforcement may also require sandboxing, network-level domain restrictions, or a controlled fetch proxy.

Quick revision

  • Hook matchers define the scope of enforcement.
  • WebFetch and Bash are separate tool paths.
  • PreToolUse is appropriate for blocking prohibited actions.
  • PostToolUse is too late to prevent retrieval.
  • Prompt instructions are not a substitute for deterministic enforcement.

Targeted Follow-Up Analysis of Revised Documents

Agentic Architecture & OrchestrationClaude Code workflows (general)
Scenario

A document-analysis pipeline runs headlessly using claude -p. After its first analysis run, several unrelated headless sessions are started in the same project directory, and three source documents are revised.

The pipeline needs to perform a targeted follow-up analysis of those revised documents while preserving the original analysis context.

How should the script run the follow-up?

  1. Incorrect
    • Why it is incorrect: Resuming restores the previous conversation and tool results, but it does not guarantee that revised files will be read again from disk.
    • Risk: Claude may continue using stale document contents captured during the first run.
  2. Correct
    • Why it is correct: The session ID identifies the intended analysis session, even when other sessions have subsequently run in the same directory. Explicitly naming the changed documents tells Claude which sources must be refreshed before continuing.
    • Benefit: The pipeline retains the useful prior analysis while focusing additional work on the files that changed.
  3. Incorrect
    • Why it is incorrect: Several unrelated sessions have been started since the original analysis. --continue may therefore select the wrong conversation.
    • Better approach: Use the original session's ID to target the correct analysis run.
  4. Incorrect
    • Why it is incorrect: This discards the opportunity to reuse the existing analysis and repeats work on documents that have not changed.
    • When a fresh run may be appropriate: If the prior session is unavailable, corrupted, or no longer suitable for the task, a new run may be necessary. Those conditions are not stated here.
Correct answer: B

Overall explanation

The workflow has two distinct requirements:

  1. Resume the correct conversation. Use the session_id returned by the initial headless run. This avoids accidentally continuing one of the unrelated sessions created afterward.
  2. Refresh the changed sources. Explicitly tell Claude to re-read the three revised documents before continuing the analysis.

Resuming a session restores conversational context, not a guarantee that every earlier tool result will be refreshed against the current filesystem. A previous Read result may still describe the older version of a document.

The targeted approach is therefore more efficient and reliable than either blindly continuing the latest session or restarting the entire corpus analysis.

Quick revision

  • Capture the original session_id when running headless automation.
  • Use --resume with that ID to target the intended session.
  • --continue is not reliable when multiple sessions have run in the same directory.
  • Name revised files explicitly and instruct Claude to re-read them.
  • Resuming preserves context; it does not automatically refresh stale file contents.

Correctly Ordering Tool Results in the Messages API

Agentic Architecture & OrchestrationMulti-agent research system
Scenario

A multi-agent research system uses a manual tool loop. The search subagent returns a single user message containing guidance text followed by tool_result blocks. The API rejects the request with an invalid tool-result ordering error. The loop must also log every tool call before execution.

What is the correct fix?

  1. Incorrect

    The documented pattern is to return all results for a single assistant tool-use turn together in one user message. Splitting the results across messages does not fix the underlying ordering error.

  2. Incorrect

    Each result must retain the tool_use_id of its original tool call. These identifiers establish the pairing between requests and results; changing them breaks that association.

  3. Incorrect

    Not the best answer for this scenario. The Tool Runner can manage tool execution and result formatting automatically, but the system specifically requires logging each tool call before it runs. A manual loop preserves this level of control.

  4. Correct

    The results must immediately follow the assistant's tool-use turn, with all tool_result blocks preceding ordinary text in the user message. This fixes the message structure while preserving the custom logging requirement.

Correct answer: D

Overall explanation

When using client-side tools, the application is responsible for completing the tool-use cycle correctly. Claude issues tool calls, the application executes them, and the results must be returned using the identifiers and message structure the API expects.

The critical detail is that the result blocks must come before ordinary text in the response message. Adding guidance text before them violates the expected ordering.

The alternatives fail for different reasons: splitting results changes the documented response pattern, changing IDs breaks request-result matching, and switching to the Tool Runner sacrifices the explicit control the application needs for pre-execution logging.

Key takeaway: Fix the message structure rather than changing tool IDs or abandoning a manual loop that provides necessary control.

Q7

Preventing Infinite Refinement Loops

Agentic Architecture & OrchestrationMulti-agent research system
Scenario

A coordinator agent delegates research to specialized subagents and repeatedly evaluates report coverage. For some topics, a subtopic has no published sources. The coordinator repeatedly delegates the same gap query, and the run never finishes.

What change fixes this?

  1. Incorrect

    Broader queries can help when the original query is poorly phrased. They cannot solve a gap caused by the genuine absence of published sources. The loop remains unbounded.

  2. Correct

    A retry limit gives the system a guaranteed exit. An explicit annotation preserves transparency about what could not be established, without preventing the rest of the report from being completed.

  3. Incorrect

    maxTurns controls the number of tool-use rounds within an individual subagent run. Increasing it does not fix the coordinator's unbounded retry loop or create sources that do not exist.

  4. Incorrect

    This lowers the standard for all reports, including topics where another targeted search could have filled the gap. It also risks concealing the limitation from readers.

Correct answer: B

Overall explanation

A refinement loop needs both a success condition and a failure path. If it continues until every gap is filled, it can run forever when a gap is genuinely unfillable.

Repeated delegations also cost time and tokens. Each new subagent may repeat searches without retaining the previous subagent's working context.

The robust design is to use bounded retries and graceful degradation. After a defined number of attempts, the system completes the report and clearly identifies the unavailable evidence.

This preserves quality better than either endlessly repeating searches or silently lowering the coverage standard.

Key takeaway: Every iterative agent workflow needs a bounded stopping rule and an honest way to report unresolved gaps.

Agentic Architecture & OrchestrationMulti-agent research system
Scenario

Before a refactor, the coordinator must locate every call site of five exported functions and record exact locations. It currently launches one search subagent per function, but the runs are slow and return vague summaries.

What should change?

  1. Incorrect

    This reduces the number of subagents but still relies on a summary. The requirement is to identify every call site with exact locations, not merely describe where functions appear.

  2. Correct

    Grep searches file contents and can provide the raw match information needed for the refactor. These straightforward searches do not justify the extra delegation overhead.

  3. Incorrect

    Structured output could improve precision, but it does not eliminate the cost of running five separate subagents. Direct Grep calls are simpler and faster for these small searches.

  4. Incorrect

    Glob matches file paths against patterns; it does not search the contents of files for function calls. Grep is the appropriate tool for finding call sites inside source files.

Correct answer: B

Overall explanation

Subagents are useful when work is substantial, independent, or likely to overwhelm the main conversation with verbose exploration. They are not automatically the best choice for every search.

Delegation introduces overhead: each subagent runs in its own context, consumes tokens, and typically returns a summary rather than every raw result.

Here, the work consists of five small, precise content searches. Running Grep directly lets the coordinator retain the exact matches and locations needed for the refactor.

Key takeaway: Use direct tools for short, precise searches when you need their raw output. Delegate when the work benefits meaningfully from isolation or parallel investigation.

Freeing Context While Preserving Decisions

Context Management & ReliabilityClaude Code workflows (general)
Scenario

A Claude Code session debugging a synthesis subagent's citation logic has nearly filled its context window. The next task involves changing report-generator code that depends on decisions made during that debugging session.

Which command best fits this situation?

  1. Incorrect

    This setting adjusts when automatic compaction occurs. Increasing it does not free space in a context window that is already nearly full.

  2. Incorrect

    /clear starts a fresh conversation. That is useful for unrelated tasks, but here the next task depends on decisions from the current conversation.

  3. Correct

    /compact condenses the conversation history to free context while retaining a summary of important decisions. The same session can then continue with the related task.

  4. Incorrect

    Rewinding rolls back the conversation to an earlier checkpoint and can discard the debugging conclusions needed for the next task.

Correct answer: C

Overall explanation

The deciding factor is whether the next task depends on the existing context.

  • /compact reduces the context used by the conversation while preserving a summarized record of the important work.
  • /clear removes the active conversation context and is more appropriate when moving to an unrelated task.
  • /rewind is for backing out of a previous direction, not for safely compressing a conversation whose conclusions remain useful.
  • autoCompactWindow affects when automatic compaction is triggered rather than increasing the model's fixed context capacity.

Compaction is particularly useful after lengthy debugging sessions, where the decisions and conclusions matter more than retaining every verbose intermediate output. Optional focus instructions can help preserve the details that the next phase requires.

Key takeaway: When the next task depends on the current conversation, compact it rather than clearing or rewinding it.

Scenario

A multi-agent research system has a coordinator and specialized subagents for web search, document analysis, synthesis, and report generation. Subagents operate with isolated contexts. The system must preserve coordinator visibility into the information passed between agents and handle subagent failures without unnecessarily terminating the entire run.

Which approach meets these requirements?

  1. Incorrect

    Each subagent has an isolated context. Findings must be included explicitly in the downstream subagent's input.

  2. Incorrect

    Not appropriate when the architecture requires a single coordinator to maintain visibility over all handoffs. Agent teams are a separate mode that permits direct inter-agent communication and changes that centralized control model.

  3. Incorrect

    This can transfer information, but it creates a side channel. Findings may move between subagents without the coordinator explicitly observing or controlling the handoff, which undermines the stated visibility requirement.

  4. Correct

    The coordinator should include relevant findings in the next subagent's input and inspect the result returned. If a subagent times out or fails, the coordinator can decide whether to retry, delegate elsewhere, or continue with partial findings and annotate the limitation.

Correct answer: D

Overall explanation

Core concept

The coordinator must explicitly pass findings into downstream subagents and handle their returned results or failures centrally.

Explanation

Subagents do not automatically share their conversation histories or intermediate findings with one another. The coordinator is responsible for passing relevant information across each delegation boundary.

For example, if a web-search subagent discovers important evidence, that evidence does not automatically become available to the synthesis subagent. The coordinator must include the search findings in the synthesis subagent's prompt or input.

This explicit handoff allows the coordinator to preserve attribution, track the information being used, and decide what happens when a subagent fails.

Overall explanation

The coordinator acts as the control and information-flow hub. Each subagent receives a task and the context supplied to it, then returns its result to the coordinator. This architecture makes information transfer explicit rather than automatic.

The coordinator also has the broadest view of the run. A timeout in one subagent should therefore be treated as a recoverable outcome when possible, not as an automatic reason to abort all research.

Depending on the failure, the coordinator can retry the task, redirect it, or finalize the report with a clear statement about the missing evidence.

Key takeaway: In a coordinator-based multi-agent architecture, make handoffs explicit and keep failure recovery at the coordinator level.

Scenario

A research system has four specialized subagents, each receiving the same catalog of 16 tools. The team has already improved the tool descriptions with clear instructions about their intended boundaries, but the synthesis agent still calls web-search tools.

Which change most reliably stops this misuse?

  1. Incorrect

    Better descriptions are usually a strong first step because they help the model select the appropriate tool. However, the descriptions already contain clear boundary language and the misuse continues. Adding more examples does not reduce the number of tools available to the synthesis agent.

  2. Incorrect

    According to the source, allowedTools controls which tool calls are automatically approved; it does not determine which tools the agent can see. Tools outside the allowlist can still be selected and may trigger permission handling.

  3. Incorrect

    Prompt instructions influence behavior, but they do not remove tools from the available set. The agent can still select an inappropriate tool.

  4. Correct

    The tools field limits the subagent to the tools explicitly listed. Tools excluded from its definition are unavailable in that session, making misuse structurally impossible rather than merely discouraged.

Correct answer: D

Overall explanation

This question tests the difference between behavioral guidance and architectural constraints.

Tool descriptions and system prompts influence what the model chooses. Tool configuration determines what the model can choose from in the first place.

When a synthesis agent sees 16 tools, including web-search tools that do not belong to its role, it must repeatedly make the correct selection among unnecessary options. Restricting its tool set reduces this decision complexity and prevents it from calling tools it should never use.

  • tools controls which tools are available.
  • allowedTools controls permission behavior and automatic approval.
  • Tool descriptions help the model decide when an available tool is appropriate.
  • System prompts provide behavioral instructions but do not enforce tool availability.

Key takeaway: When unwanted tool use persists despite clear descriptions and prompts, restrict the agent’s actual tool set.

Fixing Exact-String Edit Failures

Tool Design & MCP IntegrationClaude Code workflows (general)Select TWO
Scenario

A report generator needs to rename a citation tag everywhere in findings.md. The Edit call fails because the tag occurs 14 times. A second Edit call reports no match even though the target text appears to be present.

Which TWO actions fix these failures? (Select TWO.)

  1. Incorrect

    Incorrect for the requested global rename. Adding context is a valid way to resolve an ambiguous match when only one occurrence should change. Here, the tag must change everywhere, so a unique-context edit would update only one occurrence and leave the other 13 unchanged.

  2. Correct

    Edit uses literal string matching. Differences in whitespace, indentation, or other characters can cause a no-match error even when the text looks similar. Copying the exact text from the file avoids this problem.

  3. Correct

    By default, Edit expects old_string to match a unique location. The replace_all: true option allows the same replacement to be applied to every matching occurrence, which is precisely what a global citation-tag rename requires.

  4. Incorrect

    The Edit tool does not interpret old_string as a regular expression. It searches for the literal text supplied, so a regex pattern will not provide regex-based matching.

Correct answer: B and C

Overall explanation

The Edit tool is designed around exact, predictable string replacement. Two separate issues are being tested.

Problem 1: Multiple matches. The target appears 14 times, and the requested change applies to all 14. Use replace_all: true. Adding unique context would solve the ambiguity only by narrowing the edit to one occurrence.

Problem 2: No match. The target looks present, but the supplied string does not match it exactly. Read the file and copy the target verbatim, preserving indentation and whitespace.

If a change cannot be safely performed with a targeted edit, reading the file and rewriting the modified content is a heavier fallback. But it is unnecessary for these two cases.
