Evaluation, Testing & Optimization
Core idea
Decide what success means, in numbers, before you build.
  • Success criteria must be specific and measurable. Even hazy dimensions such as tone, ethics, or safety can and should be quantified before you design against them.
  • Prefer volume over perfection in a test set, and automate grading where you can: exact match and code-based checks first, then an LLM grader with an explicit rubric, then human review.

Q01 Architecture Answered correctly

A trust-and-safety team uses Claude to flag policy-violating posts on a community forum. Single assessments of borderline posts are inconsistent, and the business needs higher confidence in each verdict than one model judgment provides. The latency budget allows several model calls at once. Which architectural pattern best fits?

  • A Deploy an autonomous agent that decides its own review steps per submission. Distractor

    Autonomous agents are justified when the number and nature of steps cannot be predicted in advance. Assessing a single post against a fixed policy is a bounded, known task, so agent autonomy adds cost and unpredictability without improving verdict confidence.

  • B Chain sequential calls where each step reviews and refines the prior verdict. Distractor

    Prompt chaining decomposes a task into fixed sequential subtasks, with each call processing the previous step's output. Moderating a post is not a decomposable multi-step task, and sequential calls add latency without producing the independent judgments that build confidence.

  • C Run the same assessment several times in parallel and aggregate the verdicts. Correct · you chose this

    This is the voting variant of parallelization: identical tasks run independently and their diverse outputs are combined for a higher-confidence result. It directly addresses inconsistent single judgments, and because the calls run simultaneously it fits within the stated latency budget.

  • D Have one call generate a verdict and a second call critique and revise it. Distractor

    This is the evaluator-optimizer pattern, which suits outputs that measurably improve through iterative refinement against clear criteria. A moderation verdict is a judgment call, not a draft to polish; a single critique loop does not deliver the multiple independent perspectives the problem calls for.

Why this is the answer

Anthropic's pattern taxonomy documents parallelization in two variants: sectioning, where independent subtasks run simultaneously for speed, and voting, where the same task runs multiple times to produce diverse outputs that are then aggregated. Voting is the documented fit when multiple perspectives increase confidence in a result, which is exactly the gap here: individual judgments on borderline content vary, so several independent assessments combined by a rule (majority vote, or flag-if-any-flags when false negatives are costlier) give a more reliable verdict than any single call. Because the calls are independent, they run concurrently, so the confidence gain costs extra tokens rather than extra latency.

The distinctions among the distractors are worth internalizing because they look superficially similar. Prompt chaining trades latency for accuracy by splitting a decomposable task into easier sequential steps; it assumes the task has stages, which a single moderation verdict does not. Evaluator-optimizer pairs a generator with a critic in a refinement loop; it improves the quality of one output rather than reducing the variance of a judgment, and its two calls are dependent, not independent. An autonomous agent earns its cost only when the steps cannot be hardcoded in advance; a fixed policy check per post is the opposite case, and Anthropic's guidance is to use the simplest viable pattern because agentic autonomy adds cost and compounding-error risk.

The general mental model: choose sectioning when subtasks differ and are independent, voting when the task is identical but confidence matters, chaining when steps are known and sequential, and agents when the path itself is unknowable up front. Q02 Stakeholders Answered correctly

An architect starts discovery for an AI assistant meant to speed up insurance claims handling. All requirements so far have come from senior managers who do not process claims themselves. What should the architect do next?

  • A Send managers a feature checklist to rank before any design work begins. Distractor

    This is incorrect because ranking features presumes the right features are already known. Discovery has not yet established the underlying problem or workflow, and a checklist keeps the input confined to the same secondhand perspective that created the gap.

  • B Finalize the requirements from management input, since managers own the process and budget. Distractor

    This is incorrect because owning the budget does not mean managers know the operational detail of claims handling. Requirements built solely on secondhand descriptions frequently miss edge cases and daily realities, producing a solution that fails the people who must use it.

  • C Interview and observe frontline claims handlers to learn how the work is actually done. Correct · you chose this

    This is correct because structured discovery requires understanding the real workflow from the people who perform it. Managers often describe an idealized or outdated version of the process, so frontline interviews and observation surface the true pain points, exceptions, and constraints that the solution must handle.

  • D Build a prototype from the management requirements and gather feedback during testing. Distractor

    This is incorrect because prototyping against unvalidated requirements anchors everyone to a possibly wrong solution and defers the cost of discovering the mismatch until build time. Validating the workflow first is far cheaper than reworking a prototype built on flawed assumptions.

Why this is the answer

Structured discovery exists to establish what the work actually is before anyone decides what an AI system should do about it. The people who describe a process from above (managers, sponsors, executives) tend to report the intended process: the documented happy path, the metrics they see in reports. The people who do the work daily know the actual process: the exceptions, workarounds, tribal knowledge, and where the time is really lost. When every requirement so far comes from one layer, the architect's next move is to close that gap by interviewing and observing frontline claims handlers directly. This is the same principle as sample discovery activities like interviewing frontline staff to understand how quotes are produced today.

This matters especially for LLM-based systems because their value depends on how well prompts, tools, and workflows mirror real task structure. Anthropic's guidance on building effective agents stresses starting from the actual task and its variability before choosing patterns like fixed workflows or autonomous agents; you cannot make that architectural judgment from a manager's summary of the process. A claims workflow that looks linear from above may in practice branch on fraud signals, missing documents, or legacy-system quirks that only handlers know.

The distractors each shortcut discovery in a familiar way. Locking requirements to management input mistakes accountability for operational knowledge. A feature checklist asks stakeholders to prioritize solutions before the problem is understood, and it polls the same audience whose view is already overrepresented. Prototyping early feels like progress but anchors the engagement to unvalidated assumptions, so errors surface as expensive rework rather than cheap conversation. Q03 Governance Answered correctly Select two

A team handling regulated customer data operates under a zero-data-retention arrangement with Anthropic. Which TWO design decisions correctly account for how the platform retains data?

  • A Keep regulated data out of features that store inputs and outputs server-side, such as batch processing. Correct · you chose this

    Asynchronous batch processing requires server-side storage of both requests and results to support processing and result retrieval, and it is not ZDR eligible; results remain available for 29 days after batch creation. Routing regulated data away from such features is the architectural control that keeps the workload consistent with the retention obligation.

  • B Rely on the automatic expiry of stored batch results to satisfy the workload's retention obligation. Distractor

    Batch results remaining available for a fixed window before expiring is a retention schedule, not the absence of retention. Data that is stored and later expires has still been retained, which is exactly what the obligation prohibits.

  • C Verify each feature's retention behavior and ZDR eligibility before adding it to the design. Correct · you chose this

    Zero data retention is scoped per feature, not granted platform-wide. Some capabilities, such as batch processing and Agent Skills, store data under standard retention policies even when an organization has a ZDR arrangement, so each feature must be verified before it touches regulated data.

  • D Treat the organization-wide ZDR arrangement as automatically covering every feature the workload uses. Distractor

    A ZDR arrangement applies only to features that are ZDR eligible. Features like batch processing retain data according to their standard retention policy regardless of the arrangement, so assuming blanket coverage leaves regulated data stored without the team realizing it.

Why this is the answer

A zero-data-retention arrangement is not a switch that covers everything an organization sends to the platform; it is a property evaluated feature by feature. The mental model to hold is that some capabilities are architecturally stateless (the request is processed and the response returned, with nothing stored afterward), while others are inherently stateful: batch processing requires server-side storage of both inputs and outputs to support asynchronous processing and result retrieval, and results remain available for 29 days after batch creation regardless of when they are downloaded. A stateful feature cannot honor zero retention because storage is what makes it work, which is why the documentation marks features individually as ZDR eligible or not.

For an architect, this turns a legal commitment into a design constraint: before regulated data flows through any capability, verify that capability's retention classification, and route data with strict retention obligations only through ZDR-eligible paths. Assuming the arrangement blankets every feature is the classic failure mode, because the system works perfectly while quietly storing data the organization promised not to retain. Relying on automatic expiry of batch results confuses bounded retention with no retention; expiring data was still stored, so the obligation is already breached during the storage window. The same reasoning generalizes to other regimes: HIPAA and GDPR analyses must trace where data actually persists, not what the headline agreement says.

Q04 Governance Answered correctly

An agent executes SQL against a production database to build reports. Its system prompt instructs it to run only SELECT statements, yet adversarial testing shows crafted inputs can occasionally make it issue UPDATE statements. Which control most reliably prevents data modification?

  • A Rewrite the system prompt with stronger, capitalized warnings against write statements. Distractor

    This is incorrect because system prompt instructions are probabilistic guidance, not enforcement. The testing already demonstrated that adversarial inputs can override the existing instruction, and stronger wording reduces but cannot eliminate that failure mode.

  • B Connect the agent through a database account granted only read permissions. Correct · you chose this

    This is correct because a read-only credential enforces the constraint at the execution layer, where the model's behavior cannot override it. Even a fully successful adversarial manipulation cannot modify data the account has no permission to write. It converts a probabilistic instruction into a deterministic boundary.

  • C Log every executed query and review the logs for violations weekly. Distractor

    This is incorrect because logging is a detective control: it identifies violations after the data has already been modified. The requirement is to prevent modification, which a retrospective review cannot do.

  • D Set temperature to zero so the model follows instructions deterministically. Distractor

    This is incorrect because temperature controls sampling randomness, not adherence to instructions under adversarial input. A deterministic model can still be steered by a crafted prompt into producing a write statement.

Why this is the answer

The core principle here is the difference between advisory controls and enforced controls. A system prompt instruction such as "run only SELECT statements" shapes the model's behavior probabilistically: it works most of the time, but a sufficiently crafted adversarial input can override it, exactly as the testing revealed. Prompt wording, however emphatic, cannot provide a guarantee, because the model's compliance is itself the thing under attack.

Enforcement belongs at the layer the model cannot influence: the tool and credential boundary. Connecting the agent through a database account that holds only read permissions applies the principle of least privilege. The database itself rejects any UPDATE, INSERT, or DELETE, regardless of what the model generates. This is the same architectural idea behind restricting an agent's toolset so that a successful prompt injection has no destructive action available to trigger; the injection may still succeed at the language level, but its blast radius is capped at zero writes. Anthropic's own agent tooling reflects this pattern: subagents can be granted a deliberately narrowed set of capabilities, and command validation hooks can gate what a tool is permitted to execute.

The distractors each fail the "prevents" test. Stronger prompt wording is more of the same advisory layer that already failed under adversarial pressure. Query logging with weekly review is a detective control that surfaces violations days after production data was changed. Temperature affects randomness in token sampling, not instruction adherence; a zero-temperature model can be manipulated just as reliably, and sometimes more reproducibly, by the same adversarial input.

In practice, mature designs layer these controls: least-privilege credentials as the hard boundary, prompt instructions to keep routine behavior on track, and logging for audit. But when the requirement is that modification must never occur, the deterministic permission boundary is the control that carries the guarantee. Q05 Architecture Answered correctly

A team is designing a system that handles complex code-change requests. The number of files to modify and the supporting analyses required cannot be enumerated in advance and differ for every request. Which orchestration pattern is most appropriate?

  • A A prompt chain that processes every request through the same fixed sequence of steps. Distractor

    Prompt chaining suits tasks that decompose into a stable, known sequence identical across requests. Here the work varies per request, so a fixed chain would either miss needed steps or waste effort on irrelevant ones.

  • B An orchestrator that decomposes each request into subtasks, delegates to workers, and synthesizes results. Correct · you chose this

    This is the orchestrator-workers pattern, which is designed for exactly this situation: a central model determines the subtasks dynamically at runtime, farms them out to worker models, and combines the outputs. It fits when the required subtasks cannot be predicted before the work begins.

  • C A parallelization design that runs a predefined set of independent subtasks concurrently and merges outputs. Distractor

    Parallelization requires the subtasks to be defined before execution so they can be dispatched concurrently. The scenario states that the subtasks cannot be enumerated in advance, so there is nothing fixed to dispatch.

  • D An evaluator-optimizer loop where one model drafts changes and another critiques them iteratively. Distractor

    Evaluator-optimizer improves a single output through repeated generate-and-critique cycles when clear evaluation criteria exist. It refines quality; it does not address the core problem of dynamically breaking a variable task into subtasks.

Why this is the answer

Anthropic's guidance on agentic systems distinguishes several composable orchestration patterns, and the discriminator between them is how much of the work's structure is known before execution begins. In the orchestrator-workers pattern, a central model examines each incoming task, decides at runtime what subtasks it requires, delegates those subtasks to worker models, and synthesizes the workers' outputs into a final result. Coding tasks are the canonical example: which files need editing, what analyses are needed, and how many workers to spawn all depend on the specific request, so the decomposition itself must be a model decision rather than a design-time one.

This is what separates orchestrator-workers from parallelization, which it superficially resembles because both fan work out to multiple calls. In parallelization (whether sectioning, which splits a task into independent pieces, or voting, which runs the same task several times), the subtasks are fixed in code before any request arrives. In orchestrator-workers, the subtasks emerge per request. Prompt chaining occupies the opposite end of the spectrum: a fixed sequence of steps, valuable precisely when every request follows the same path and intermediate outputs can be checked between steps. Evaluator-optimizer is a quality-refinement loop, pairing a generator with a critic when clear evaluation criteria exist; it improves one output iteratively rather than structuring variable work.

The architectural mental model: choose the least dynamic pattern the problem allows, because predefined code paths are cheaper, more predictable, and easier to audit. Reach for orchestrator-workers only when the flexibility is genuinely required, as it is when the shape of the work is unknowable in advance. Q06 Stakeholders Answered correctly

A sponsor wants the service agreement for a new AI assistant to state only that responses will be "fast and accurate." What should the architect do before the SLA is finalized?

  • A Accept the wording as written, since loose terms give the delivery team room to maneuver. Distractor

    This is incorrect because ambiguity in an SLA does not protect the delivery team; it guarantees a later dispute in which the sponsor's private interpretation of fast and accurate becomes the de facto standard. Vague criteria make it impossible to demonstrate compliance or diagnose shortfalls.

  • B Commit to the vague wording for launch and quantify performance targets only after production data accumulates. Distractor

    This is incorrect because deferring measurability means the system launches under an agreement no one can evaluate, and expectations harden around unstated assumptions. Production data can refine agreed thresholds, but baseline targets should be negotiated before the commitment is signed.

  • C Translate the wording into measurable targets, such as percentile latency and accuracy thresholds. Correct · you chose this

    This is correct because an SLA only functions if both parties can verify whether it is being met, which requires specific, measurable targets. Converting vague language into quantified thresholds, agreed with the sponsor, aligns expectations before delivery and gives the feedback loop something concrete to measure against.

  • D Set the SLA to guarantee zero errors so the sponsor's accuracy concern is fully covered. Distractor

    This is incorrect because LLM systems are probabilistic and no responsible architect can guarantee zero errors. Signing an unachievable absolute converts an alignment problem into an inevitable breach of contract rather than resolving the expectation gap.

Why this is the answer

An SLA is only useful when every commitment in it is specific, measurable, achievable, and relevant. Phrases like "fast and accurate" fail all four tests: they cannot be monitored, cannot be breached or satisfied objectively, and leave each party free to hold a different mental model of what was promised. The architect's job at this stage is expectation alignment: sit with the sponsor and convert the intent behind the words into quantified targets, for example a percentile latency bound such as 95% of responses under a defined threshold, a task-accuracy rate on a representative evaluation set, and an uptime figure. Anthropic's guidance on defining success criteria makes exactly this point, listing operational metrics like response time and uptime percentage alongside quality dimensions such as task fidelity, consistency, and tone, and noting that most real use cases need multidimensional criteria rather than a single vague target.

This translation step also powers the ongoing feedback loop. Once thresholds exist, production monitoring and evaluation sets can report against them, breaches become detectable early, and fortnightly stakeholder reporting speaks the language the SLA established rather than raw token counts.

The alternatives all fail in characteristic ways. Keeping the wording loose feels safe but actually cedes interpretation to whoever complains loudest later. Deferring quantification until after launch means the system goes live against criteria nobody agreed; production data should calibrate targets, not substitute for them. And promising zero errors converts a probabilistic system's normal behavior into contractual breach, the same trap as agreeing to "100% accuracy" during discovery. The professional pattern is consistent across the lifecycle: replace absolutes and vagueness with measurable acceptance criteria proportionate to business risk, and get sponsor sign-off on those numbers before they become commitments.

Q07 Integration Answered correctly

A publishing team runs a nightly pipeline that sends each new manuscript summary to Claude for a single genre classification. The pipeline is deterministic, owned entirely by one team, and no other application will consume the connection. Which integration mechanism is most appropriate?

  • A Call the model directly through the Messages API inside the pipeline's own code. Correct · you chose this

    This is correct because the call is deterministic, tightly scoped, and confined to a pipeline one team owns. A direct API integration is the simplest mechanism that satisfies the requirement, with no discovery or protocol layer to build and maintain.

  • B Register a company-wide MCP toolset so future applications can reuse the connection. Distractor

    Building for hypothetical future consumers contradicts the stated situation, where no other application will use the connection. Standing up shared infrastructure speculatively adds operational cost now for reuse that may never materialize; the integration can be migrated to MCP later if real demand appears.

  • C Expose the pipeline's data through an MCP server for standardized tool access. Distractor

    MCP earns its overhead when multiple applications need discoverable, reusable access to a system, or when tools change frequently across team boundaries. Here there is exactly one consumer, one owner, and one fixed call, so a discovery layer adds maintenance without any benefit.

  • D Wrap the classification step as an autonomous agent using agent-to-agent communication. Distractor

    Agent-to-agent communication is designed for coordination between independently operated agents, typically across organizational trust boundaries. A single deterministic classification call inside one team's pipeline involves no second agent and no boundary to mediate.

Why this is the answer

Choosing a connection mechanism starts with the shape of the consumer, not the technology. The Model Context Protocol (MCP) is an open standard that exists to solve a many-to-many problem: many AI applications needing standardized, discoverable, reusable access to many systems, each maintained by its own team. When those conditions hold, an MCP server pays for itself because each system is wrapped once and every present and future agent can connect. When they do not hold, the standard's discovery and tooling layer is pure overhead.

This scenario is the opposite shape: one deterministic call, one owning team, one consumer, and no model-driven tool selection involved in deciding whether to call. That is the textbook case for direct API integration, where the pipeline invokes the Messages API as an ordinary service dependency inside code the team already controls. There is nothing to discover, no catalogue to browse, and no other application whose reuse would justify a server.

Agent-to-agent communication addresses a third, distinct shape: autonomous agents operated by different parties that must coordinate without exposing internal systems across a trust boundary. A batch classification step has neither autonomy nor a boundary. Pre-building a company-wide MCP toolset "for later" is the speculative-infrastructure anti-pattern: architecture should follow demonstrated need, and a well-factored direct integration can be lifted behind an MCP server later if multiple consumers actually emerge.

Q08 Governance Answered correctly

A team is building an agent that sends supplier emails and updates billing records through tools. Compliance requires that a human approve each external action before it occurs. Where in the architecture should this approval step be implemented?

  • A Add an instruction in the system prompt directing the model to ask permission before acting. Distractor

    Prompt instructions are advisory, not enforced. The model may usually comply, but a compliance requirement that every external action be approved needs a control the model cannot bypass, which a prompt alone does not provide.

  • B Implement the approval gate in the application layer before executing the model's tool request. Correct · you chose this

    Claude never executes client-side tools itself; it emits a structured request that the application must carry out. Placing the approval gate at that seam makes the human check a hard architectural control: no action can occur unless the application, after approval, actually executes it.

  • C Record every executed action in an audit log that compliance reviews on a weekly cycle. Distractor

    An audit log is a detective control: it reconstructs what happened after the fact. The requirement is that a human approve actions before they occur, so a weekly retrospective review arrives after the emails are sent and the records changed.

  • D Prompt the model to self-assess the risk of each action in its reasoning and pause whenever uncertain. Distractor

    Self-assessment leaves the gating decision to the model's own judgment, which can err or be manipulated. The requirement is unconditional human approval of every external action, not approval only when the model decides an action seems risky.

Why this is the answer

The key to this question is understanding the tool-use contract. When Claude decides to act, it does not act directly: it pauses and emits a structured tool request naming the tool and its arguments. Your application then extracts those arguments, performs the operation, and returns the result so the model can continue. That handoff is not incidental; it is the deliberate architectural seam where governance controls belong. Because nothing happens until your code executes the request, inserting a human approval step there turns the compliance requirement into a guarantee rather than a hope. This is also why Anthropic advises using a manual orchestration loop rather than fully automatic tool execution when human-in-the-loop approval, custom logging, or conditional execution is needed.

The distractors each fail a different way. A system-prompt instruction to "ask before acting" is guidance the model usually follows but can be worded around, forgotten under long context, or subverted by injected content; it is not an enforcement layer. A weekly audit log is a monitoring-and-audit control, valuable for reconstruction and trend detection, but it reviews actions after suppliers have received the emails. Model self-assessment of risk delegates the gate to the very component being governed, so approval happens only when the model judges it necessary, which does not satisfy an unconditional pre-action approval requirement.

The general mental model: prompts shape behavior, but architecture enforces it. Controls that must hold under all circumstances belong in the layer that actually executes actions. See How tool use works and Tool runner for the execution seam and the guidance on when to keep the loop manual.

Q09 Evaluation Answered correctly Select two

A real-time RAG assistant sends many retrieved passages per request, and most traffic is simple, repetitive questions. Which TWO optimizations reduce latency and cost without degrading quality?

  • A Apply a sharply reduced output token cap to every request regardless of task. Distractor

    A blanket output cap truncates responses that legitimately need more length, cutting answers off mid-thought. It reduces tokens indiscriminately rather than targeting waste, so it violates the requirement that quality not degrade.

  • B Route all requests through asynchronous batch processing to capture discounted token pricing. Distractor

    Batch processing offers a significant discount but is asynchronous, with results returned over minutes to hours rather than immediately. It is designed for non-time-sensitive workloads and is incompatible with users waiting on each response.

  • C Lower reasoning effort for simple, high-volume queries after validating quality on evals. Correct · you chose this

    Reducing how much internal reasoning the model spends on straightforward requests cuts output tokens, which lowers both latency and cost. Gating the change on evaluation results ensures quality does not silently degrade on the affected traffic.

  • D Trim retrieved context so each request contains only passages relevant to the query. Correct · you chose this

    Input tokens dominate both cost and time-to-first-token in retrieval-heavy requests. Sending only relevant passages cuts spend and latency directly, and smaller, higher-signal context also protects answer quality by reducing the degradation that comes with bloated prompts.

Why this is the answer

  • B Ship the revision to all remaining traffic immediately, since it is currently ahead. Distractor

    Acting on a one-day lead treats a preliminary, possibly random fluctuation as a settled conclusion. Early results often reverse as more traffic and more varied query types flow through, so shipping now risks deploying a change that is no better, or worse, than the baseline.

  • C Run the test until the predetermined sample size and significance criteria are met. Correct · you chose this

    A small early lead can easily be noise, and stopping the moment one arm pulls ahead systematically inflates false positives. Deciding the required sample size and significance criteria in advance, then running the test to completion over representative traffic, gives the observed difference real evidential weight. This is the core discipline of controlled experimentation.

  • D Stop the test now and revert, treating the small margin as random noise. Distractor

    Abandoning the experiment is as premature as shipping on it; a small margin at day one is inconclusive in both directions. The test exists precisely to distinguish a real improvement from noise, and that distinction requires letting it accumulate enough data.

Why this is the answer

An A/B test is a quantitative measurement method: it compares a candidate against a baseline on live traffic so that a decision rests on measured evidence rather than impression. The mental model to hold is that early results are draws from a noisy distribution. The statistical failure mode here has a name, peeking: if you check results continuously and stop the first time one arm looks better, you dramatically raise the odds of declaring a winner that is not one.

The remedy is to fix the experiment's parameters before it starts: the primary metric, the minimum sample size needed to detect the effect you care about, and the significance threshold that will count as a win. The test then runs to completion, and only afterwards is the decision made. This is why disciplined teams pair every experiment with agreed launch thresholds tied to their success criteria and evaluations: the criteria define what "better" means, and the experiment supplies the evidence.

The other responses each break the experiment in a different way. Shipping immediately converts an inconclusive fluctuation into a production decision. Reverting immediately makes the opposite error from the same inconclusive data; the honest state at day one is "not yet known." Broadening the revision mid-test destroys the variant's integrity: the arms are no longer stable, comparable treatments, and whatever result eventually emerges cannot be attributed to any specific change, which also undermines the iterative-improvement loop the test was meant to serve.

A core principle of evaluation design is to prioritize volume over per-case grading quality: a large number of test cases with slightly lower-signal automated grading provides a more trustworthy picture than a small number of carefully hand-graded ones. Why this is the answer

Good success criteria are specific, measurable, achievable, and relevant, and this applies even to seemingly subjective dimensions like safety. The mental model is that a launch gate must be checkable by running an evaluation and comparing the result to an agreed number. "Safe outputs" is an aspiration; "fewer than 0.1% of outputs flagged for harm by our content filter over 10,000 trials" is a metric, because it names the measurement method (the filter), the dataset (a fixed test set of known size), and the threshold (0.1%). That structure is what lets a team say, defensibly, whether the requirement is met before any user is exposed.

The distractors each fail one part of that structure. A qualitative commitment has no measurement method or threshold, so any evaluation result can be argued either way. A published model benchmark measures the wrong object: it characterizes the base model in isolation, while safety failures in production usually arise from the interaction of the model with the application's prompts, retrieved content, and input distribution. Post-launch complaint counts fail on timing; they are a lagging signal that arrives only after the harm the requirement was meant to prevent, and they conflate output safety with users' willingness to report.

In practice, teams pair a threshold metric like this with a graded severity rubric and adversarial test cases, since a binary flag rate says nothing about how bad the flagged outputs are. See Define success criteria for Anthropic's guidance on quantifying hazy topics such as safety, and Develop test cases for building the evaluation set the metric runs against.
