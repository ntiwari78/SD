Developer Productivity & Operational Enablement
Core idea
Give Claude a way to verify its own work, and scope what it is allowed to touch.
  • Memory loads in layers: files from the working directory upward load at launch, while a CLAUDE.md in a subdirectory is lazy-loaded only when a tool touches that directory.
  • Permissions, hooks, and subagents are the enforcement surface. Hooks run deterministically around tool calls; prompt instructions do not.
  • A verification loop (tests, a linter, a type checker) is the single highest-leverage thing you can hand the agent, because it converts guessing into checking.
  • Headless invocation plus a schema is the pattern for CI. Keep the generation step and the enforcement step separate.

Solution Design & Architecture
Core idea
Pick the simplest pattern that fits, and know why the others do not.
  • Anthropic's taxonomy is the backbone: the augmented LLM, prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer, and finally autonomous agents.

Integration
Core idea
The model requests; your application executes and enforces.
  • The Messages API is stateless. Every turn is reconstructed by resending the conversation, so state, truncation policy, and replay all live in your code.
  • In the tool-use loop Claude emits a tool-use request and stops. Your application runs the tool and returns a tool result. Nothing is enforced inside the model, which is why authorization, validation, and rate limiting belong at that seam.
  • Distinguish client tools (your code runs them) from server tools (Anthropic runs them inside a server-side loop). They surface different stop reasons and need different handling.
  • Branch on the documented stop reason rather than guessing when a loop is finished, and give each value its own handler.

Evaluation, Testing & Optimization
Core idea
Decide what success means, in numbers, before you build.

Core idea
Guarantees are per feature and enforced in the application, never in the prompt.

Core idea
Everything in the request competes for the same window; curation beats capacity.

Q01 Architecture Answered correctly Select two

An architect is deciding which parts of a document-processing pipeline to route to the Message Batches API rather than synchronous Messages API calls. Which TWO routing recommendations are sound?

  • A Route requests that must stream partial output to users into batches. Distractor

    This is incorrect. Streaming partial output to a waiting user is a real-time, interactive requirement served by synchronous API calls. Batch jobs return completed results after asynchronous processing, so there is no live stream to surface to a user.

  • B Batch conversational turns where each request depends on the previous response. Distractor

    This is incorrect. When the next request cannot be constructed until the prior response returns, the requests cannot all be submitted up front, which batch processing requires. Note the distinction: a fully constructed multi-turn conversation history can be included in a batch request, but a live sequence of dependent future turns cannot.

  • C Batch high-volume requests that are independent of one another. Correct · you chose this

    This is correct. The Batch API is designed for submitting large volumes of independent requests in a single job, and it discounts token costs relative to synchronous calls. Independence matters because batched requests are processed without any guaranteed ordering between them.

  • D Route jobs whose results can arrive hours later to batch processing. Correct · you chose this

    This is correct. Batch processing is asynchronous with a processing window measured in hours, so it fits workloads where nobody is waiting on an immediate response. Tolerance for delayed results is the primary signal that a workload belongs in a batch pipeline.

Why this is the answer

Choosing between synchronous and batch processing is a foundational decision in the processing stage of an end-to-end architecture, and it turns on two questions: who is waiting for the result, and can every request be constructed before submission. The Message Batches API accepts a large set of requests, processes them asynchronously within a defined window, and charges 50% of standard token prices. That discount is the tradeoff the feature exists to make: you surrender latency guarantees and interactivity in exchange for cheaper, higher-throughput processing. Workloads like quarterly archive analysis, bulk classification, nightly document extraction, or large evaluation runs match this profile exactly: high volume, mutually independent requests, and consumers (dashboards, reports, downstream databases) that read results long after generation.

The disqualifying characteristic is not conversational content itself but unresolvable dependence between requests. Multi-turn conversations whose full history is already assembled can be included in batch requests, since each such request is still self-contained and independent of the others in the batch. What does not fit is a live sequence where request N cannot exist until response N-1 arrives: those turns cannot all be submitted up front, so they belong on the synchronous Messages API, with the application resending accumulated context each turn. Even agentic patterns are not categorically excluded; server tools run inside batch requests, and a paused turn can be continued in a follow-up request, batch or synchronous. Likewise, streaming partial output to a live user presumes someone is watching the response arrive in real time, which is precisely the latency-sensitive, interactive pattern batch processing gives up. An architect who sorts workloads along these axes early avoids both overpaying for synchronous capacity on offline jobs and mis-fitting interactive experiences onto an asynchronous pipeline.

Q02 Architecture Answered correctly

A mortgage lender wants to use Claude to speed up pre-approval reviews. Regulations require that a named human underwriter remain accountable for each approval decision. How should the architect position Claude within the workflow?

  • A Limit Claude to reformatting decisions the underwriter has already made so it cannot influence outcomes. Distractor

    This is incorrect because it confines Claude to cosmetic work after the slow part, the review itself, is finished. It preserves accountability but delivers almost none of the speed improvement the business asked for.

  • B Run an autonomous agent that approves applications directly and logs every decision for later audit. Distractor

    This is incorrect because a post-hoc audit log does not make a human accountable for the decision at the time it is made; the AI would be the effective decision-maker. Full automation of a regulated approval decision is an anti-pattern when the requirement is human accountability, not merely traceability.

  • C Have Claude analyze each application and draft a recommendation that the underwriter reviews and approves. Correct · you chose this

    This is correct because it captures the efficiency gain (Claude does the analysis and drafting work) while keeping the accountable human as the decision-maker before any approval takes effect. A draft-plus-review checkpoint satisfies the regulatory accountability requirement without giving up the speed benefit.

  • D Keep Claude out of the approval workflow because regulated decisions cannot include AI-generated analysis. Distractor

    This is incorrect because the regulation as stated requires human accountability for the decision, not the absence of AI assistance. AI-drafted analysis reviewed and owned by a human underwriter is compatible with that requirement.

Why this is the answer

This question is about translating a compliance constraint into an architectural position for the model, which is one of the core judgments an architect makes when scoping a Claude-based solution. The business goal (faster reviews) and the regulatory constraint (a named human remains accountable for each decision) are not in conflict; they simply determine where in the workflow the model sits. The draft-and-review pattern, often called human-in-the-loop, places Claude on the analysis and drafting side of the decision boundary: it reads the application, assembles the relevant evidence, and produces a recommendation with rationale, and the underwriter exercises judgment on that prepared output. Most of the review time in processes like this is spent gathering and synthesizing information, so the pattern delivers a real throughput gain while the human retains decision authority.

The distinctions among the wrong answers are worth internalizing. An autonomous agent with a post-hoc audit log substitutes traceability for accountability: the log records what happened, but no human stood behind the decision before it took effect, which is what the stated regulation demands. Restricting Claude to reformatting finished decisions preserves accountability but abandons the business objective, a common failure of over-cautious scoping. Excluding Claude entirely misreads the constraint: requiring human accountability is not the same as prohibiting AI-generated analysis, and treating every regulatory clause as a ban forfeits value the constraint never took off the table.

A useful mental model: draw the decision boundary first, place the accountable human at that boundary, and then let Claude absorb as much of the work on either side of it as evaluations show it handles reliably. Once the workflow position is settled, model choice within it becomes a standard tradeoff among capability, speed, and cost; see Choosing a model for how Anthropic frames that selection.

Q03 Stakeholders Answered correctly

During discovery for an assistant that will draft clinical discharge summaries, stakeholders expect the solution to "save clinicians significant time," but no one has measured how long summaries currently take. What should the architect do?

  • A Measure the current process to establish a baseline before defining improvement targets. Correct · you chose this

    This is correct because a claimed improvement can only be demonstrated against a measured starting point. Capturing baseline effort during discovery makes the success criteria concrete and gives the post-launch reporting something to compare against.

  • B Accept the stakeholders' time-saving expectation and quantify the results after the system launches. Distractor

    Measuring only after launch leaves nothing to compare the results against, so the promised time savings can never be proven or disproven. It also lets the project proceed on an assumption that was never validated.

  • C Proceed straight to design, since time savings will become self-evident once the assistant is live. Distractor

    Value is rarely self-evident in production; without a documented baseline, stakeholders will dispute whether anything actually improved. Skipping the measurement also removes the evidence needed to sustain sponsorship later.

  • D Set an industry-standard time-saving target drawn from published AI productivity benchmarks. Distractor

    External benchmarks describe other organizations' processes, not this one's, so a target built on them says nothing about whether this deployment improved anything. The relevant comparison is this team's own current-state performance.

Why this is the answer

Structured discovery is not only about hearing what stakeholders want; it is about making their expectations testable. When a sponsor's goal is expressed as an improvement over today ("save significant time," "reduce errors," "resolve tickets faster"), the improvement is only meaningful relative to a baseline: a measurement of how the current process performs before the AI system exists. If no one knows how long a discharge summary takes today, then "significant time savings" is unfalsifiable, and every post-launch report becomes an argument rather than an evidence review.

The mental model is that discovery produces two linked artifacts: agreed, measurable success criteria and the current-state measurements those criteria will be judged against. Anthropic's guidance on defining success criteria emphasizes making criteria specific, measurable, and tied to the business problem; a baseline is what converts a criterion like "faster" into "reduce median drafting time from 25 minutes to under 10." That number then flows through the whole lifecycle: it shapes model and architecture choices, sets the bar for evaluation, and anchors the outcome reporting that keeps executive sponsorship alive after launch.

The alternatives all fail the same test. Deferring measurement until after launch destroys the comparison, because the pre-deployment state can no longer be observed. Treating value as self-evident invites exactly the stakeholder disputes a baseline exists to prevent. Importing an industry benchmark substitutes someone else's process for the client's, producing a target that neither reflects local reality nor proves local improvement.

Q04 Models & Context Answered correctly

An application reuses a large, static system prompt with prompt caching enabled. Traffic arrives in bursts separated by long quiet periods, so the cache expires and the first request after each lull pays full prompt-processing latency. Which strategy most directly addresses this first-request penalty?

  • A Shorten the system prompt so uncached requests are processed faster after each lull. Distractor

    Trimming the prompt only reduces the size of the cache miss rather than preventing it, so the first request after every lull still pays an uncached processing cost. It also risks discarding instructions the application needs.

  • B Send scheduled warm-up requests that write the prompt to the cache before traffic resumes. Correct · you chose this

    Correct. Pre-warming issues a request ahead of real user traffic so the static prefix is already stored in the cache, meaning the first genuine request reads the cache instead of paying the full processing cost. Repeating the warm-up within the cache lifetime keeps the entry fresh through quiet periods.

  • C Add more cache breakpoints inside the prompt so cached segments outlast the expiration. Distractor

    Breakpoints control cache granularity and reuse boundaries, letting sections be cached and reused independently; they do not extend how long an entry lives. Each cached entry still expires according to its configured cache duration, such as the default 5-minute TTL or the extended 1-hour TTL, so adding breakpoints does not make anything survive a lull.

  • D Route the first request after each quiet period to a smaller, faster model. Distractor

    A smaller model still processes the entire uncached prompt on that first request, and caches are not shared across models, so this does not remove the cache-miss cost. It also introduces inconsistent behavior between the first response and the rest of the burst.

Why this is the answer

A prompt cache entry is not permanent: it is written when a request processes the marked prefix, refreshed each time it is read, and deleted after a period of inactivity (a minimum of five minutes by default, or one hour with the extended duration). This design keeps the cache cheap and fresh for steady traffic, but it means bursty workloads hit a predictable failure mode: the entry evaporates during a lull, and the first request of the next burst reprocesses the entire prefix at full input price and full latency.

The direct remedy is cache pre-warming: send a request ahead of real user traffic whose purpose is to populate or refresh the cached prefix, so the static content is already stored when the first genuine request arrives and reads it at the far cheaper cache-read rate. Scheduling these warm-ups at startup or on an interval shorter than the cache lifetime keeps the entry alive through quiet periods; for longer gaps, the one-hour cache duration is the complementary tool, since a single write can then cover an hour of inactivity.

The alternatives miss the mechanism. Shortening the prompt shrinks the miss but does not prevent it, and sacrifices context to do so. Routing the first request to a smaller model still processes the whole uncached prefix, and cache entries are model-specific, so the detour builds no reusable state for the main model while making behavior inconsistent. Adding breakpoints changes cache granularity, letting sections that change at different rates be cached independently, but each entry still expires according to its configured cache duration (the default 5-minute TTL or the extended 1-hour TTL, which can be mixed within a request under documented ordering constraints); more breakpoints do not extend any entry's lifetime or make it survive a lull. See Prompt caching for the pre-warming pattern and cache lifetime details.

Q05 Stakeholders Answered correctly

An architect is writing the build-path section of an architecture document for a solution with two workloads: a latency-sensitive assistant that needs a custom agent loop with fine-grained control, and long-running asynchronous research tasks. Which guidance should the document give?

  • A Document both paths as interchangeable and let each implementing engineer choose freely. Distractor

    The two paths are distinct product surfaces with different strengths, not interchangeable options. Leaving the choice to individual preference abdicates the architectural decision the document exists to record and invites inconsistent, poorly matched implementations.

  • B Recommend the Messages API for the custom agent loop and Claude Managed Agents for the asynchronous work. Correct · you chose this

    This matches each workload to the surface designed for it. The Messages API gives direct prompting access and fine-grained control over a custom agent loop, while Claude Managed Agents provide a pre-built, configurable harness running in managed infrastructure, suited to long-running and asynchronous tasks.

  • C Recommend Claude Managed Agents for both workloads, since the managed harness minimizes custom infrastructure. Distractor

    Managed Agents trade fine-grained control for a pre-built harness, which conflicts with the first workload's stated need for a custom agent loop with fine-grained control. Reducing infrastructure effort does not satisfy a requirement the harness cannot meet.

  • D Recommend the Messages API for both workloads, since direct access always gives finer-grained control. Distractor

    Finer-grained control is not what the long-running asynchronous workload needs; it would force the team to build and operate its own harness for work Anthropic already offers managed infrastructure for. Good architecture documentation matches each workload to the surface designed for it rather than defaulting to maximum control.

Why this is the answer

Anthropic documents two distinct ways to build with Claude, and an architecture document should name which one each workload uses and why. The Messages API is direct model prompting access: your code owns the loop, decides what goes into context on every request, executes tools, and manages state. That control is exactly what a latency-sensitive assistant with a custom agent loop requires. Claude Managed Agents are the opposite trade: a pre-built, configurable agent harness running in Anthropic-managed infrastructure, documented as best for long-running tasks and asynchronous work, where you would otherwise have to build and operate your own harness, retries, and lifecycle management.

The mental model is a spectrum of ownership. With the Messages API you own everything between the user and the model, which buys flexibility at the cost of engineering effort. With Managed Agents, Anthropic owns the loop and you configure it, which buys operational simplicity at the cost of fine-grained control. A document that recommends one surface for everything, or presents the two as interchangeable, either forces the wrong trade on one workload or leaves the decision undocumented, which is precisely the ambiguity an architecture document exists to remove. Recording the mapping, and the reasoning behind it, gives implementing engineers guidance they can follow consistently and future maintainers a rationale they can revisit when requirements change.

Q06 Governance Answered correctly

An insurance intake agent classifies and routes thousands of documents daily. Misroutes are low-impact and easily corrected downstream. The business wants human oversight of routing quality. Which oversight approach best fits this action profile?

  • A Route documents automatically and have humans review a random sample on a regular cadence. Correct · you chose this

    Sampled retrospective review is the right control for high-volume, low-risk, reversible actions. It produces a systematic quality signal that catches drift and error patterns without destroying throughput, and it keeps human attention meaningful rather than diluting it across thousands of trivial approvals.

  • B Have a second model instance approve each routing decision to satisfy the oversight requirement. Distractor

    A second model can be a useful quality layer, but it is not human oversight and does not satisfy a requirement for it. Model reviewers can share failure modes and blind spots with the primary model, so systematic errors can pass both checks undetected.

  • C Require a human to approve each routing decision before the document is dispatched. Distractor

    Pre-execution approval is the appropriate control for irreversible or high-impact actions, not for thousands of easily corrected routing decisions per day. Gating every decision destroys the efficiency case and drives reviewers into rubber-stamping, which erodes the value of the review itself.

  • D Review individual routing decisions only after a downstream team reports a misroute. Distractor

    Complaint-driven review is purely reactive and only surfaces errors someone happens to notice and report. Silent misroutes and gradual quality drift produce no complaints, so this approach gives no systematic signal about how well the agent is actually performing.

Why this is the answer

Human-in-the-loop validation is not a single mechanism but a family of controls, and the architect's job is to match the control to the action profile: how frequent the action is, how severe a mistake is, and how easily it can be undone. Pre-execution approval gates spend scarce human attention one decision at a time, so they belong where individual decisions are irreversible or high-impact: issuing payments, deleting data, pushing to shared systems. Anthropic's agent guidance reflects this same principle, recommending confirmation before actions that are hard to reverse or affect shared systems while letting reversible, local work proceed automatically.

Routing documents is the opposite profile: high volume, low individual impact, and cheap to correct. Gating every decision here fails twice. It throttles throughput, and it manufactures reviewer fatigue, because a human asked to approve thousands of near-identical low-stakes decisions per day stops genuinely evaluating them. The oversight requirement is better read as a need for a quality signal, which sampled retrospective review provides: humans periodically grade a random slice of production decisions, giving a measurable accuracy rate, early detection of drift, and evidence for compliance, all without sitting in the request path.

The remaining options fail for distinct reasons. A second model instance reviewing each decision is automation reviewing automation; it may improve quality but it is not the human oversight the business asked for, and correlated model failure modes can slip past both layers. Complaint-driven review is detective control at its weakest: it depends on downstream users noticing and reporting errors, so silent misroutes never generate a signal. See Anthropic's prompting guidance on confirmation for risky actions and How tool use works for where oversight controls sit in a tool-using architecture.

Q07 Evaluation Answered correctly

Users of a production assistant intermittently report very slow responses, yet the team's latency dashboard, which displays mean response time, looks healthy. Which monitoring change most directly surfaces the problem?

  • A Track latency at high percentiles, such as p95 and p99, segmented by request type. Correct · you chose this

    Intermittent slowness affecting a minority of requests lives in the tail of the latency distribution, which a mean actively hides. High-percentile metrics expose exactly what the slowest requests experience, and segmenting by request type points to where the tail comes from.

  • B Monitor the API endpoint's uptime percentage to detect availability degradation sooner. Distractor

    Uptime measures whether the service responds at all, not how long responses take. An endpoint can report perfect availability while a fraction of requests are unacceptably slow.

  • C Increase the dashboard's refresh rate so brief slowdowns appear between update intervals. Distractor

    Refresh frequency changes how often the same aggregate is redrawn, not what it measures. A mean recomputed every few seconds still averages away a slow minority of requests, so the tail remains invisible.

  • D Alert on daily token consumption deviations to catch abnormal request volume early. Distractor

    Token consumption is a cost and volume signal, not a latency signal. Slow responses for some users can occur at completely normal aggregate token usage, so this alert would not fire on the reported problem.

Why this is the answer

A mean is the wrong aggregate for diagnosing intermittent slowness because it is dominated by the majority of fast requests. If 2% of requests take twenty times longer than typical, the mean barely moves, yet those users have a genuinely bad experience. Percentile metrics (p50, p95, p99) describe the distribution directly: p99 tells you what the slowest 1% of requests actually experience, which is precisely the population that files the complaints. This is why tail-latency percentiles, not averages, are the standard operational signal for latency in production systems.

LLM-backed systems have unusually heavy latency tails, which makes this distinction even more important than in conventional services. Response time varies with output length, whether the request triggered extended thinking, how many tool-call round trips an agentic request needed, and whether upstream retries occurred. Segmenting percentiles by request type (for example, short classification calls versus long agentic sessions) turns the metric from a symptom into a diagnosis, showing which workload owns the tail.

The distractors each monitor something real but orthogonal. Refreshing an average more often still displays an average; the problem is the statistic, not its staleness. Token-consumption anomaly alerts guard cost and volume, and endpoint uptime guards availability; neither moves when a slice of requests is slow but successful. The general principle: choose the signal whose definition matches the failure mode you need to see. Q08 Integration Answered correctly

A document-review assistant connects a third-party MCP server that exposes 40 tools, but the assistant's workflow uses only five of them. Since the server was connected, tool-selection accuracy has dropped and per-request token usage has grown. What should the architect change?

  • A Wrap the server behind a single free-text tool that proxies every command. Distractor

    A generic free-text proxy discards the typed interfaces that make tool calls validatable, so malformed or wrong-intent calls become harder to catch rather than easier. It hides the bloat inside an opaque layer instead of removing it.

  • B Move to a more capable model tier that handles larger tool catalogues. Distractor

    A stronger model may tolerate a larger catalogue somewhat better, but it treats the symptom at higher cost per request. The unneeded definitions still consume tokens on every call, and the root cause, an oversized tool surface, remains in place.

  • C Configure the server connection to enable only the five tools the assistant needs. Correct · you chose this

    This is correct because the 35 unneeded tools are pure capability bloat: their definitions consume input tokens on every request and enlarge the surface over which the model must choose. Scoping the connection to the required subset removes both the confusion and the token cost at the integration boundary, and the MCP connector supports exactly this kind of selective tool enablement.

  • D Add system prompt instructions telling the assistant to ignore the unneeded tools. Distractor

    Prompt instructions do not remove tool definitions from the request, so all 40 definitions still consume input tokens and still compete for the model's attention during selection. This adds context to work around a problem that configuration can eliminate outright.

Why this is the answer

This scenario is capability bloat introduced at an integration boundary. When you connect an MCP server, every enabled tool's name, description, and input schema becomes part of the request, and those definitions are billed as input tokens whether or not the tool is ever called. They also expand the set of options the model must discriminate between on each turn, which is why selection accuracy degrades as the catalogue grows. The mental model an architect should hold is that a tool definition is not a dormant capability sitting harmlessly on a shelf; it is live context with a per-request cost and an attention cost.

The MCP connector is designed for this situation: rather than accepting a server's full tool surface, you can enable all tools, allowlist a specific subset, or denylist unwanted ones, and configure individual tools. Enabling only the five tools the workflow actually uses removes 35 definitions from every request, cutting token consumption and shrinking the selection space in one configuration change. This is the same least-surface principle that governs tool catalogues generally: the right tool set is the minimum needed for the task.

The alternatives all fail structurally. Prompt instructions to ignore tools leave every definition in context, so nothing is saved and the model can still be confused by them. A free-text proxy tool trades typed, schema-validated interfaces for an opaque command string, making errors harder to detect and doing nothing about the underlying sprawl. Upgrading the model tier raises cost per request while leaving the wasted tokens and the oversized catalogue untouched. Q09 Governance Answered correctly Select two

An insurer deploys a Claude-based system that automatically approves or declines claims for EU policyholders without human involvement. Which TWO measures most directly address GDPR obligations for automated decision-making?

  • A Retain complete decision logs for seven years so regulators can audit outcomes. Distractor

    Long retention supports after-the-fact auditability but gives policyholders no human review and no way to contest a decision. Keeping personal data longer than the purpose requires can also cut against GDPR's storage limitation principle rather than help compliance.

  • B Provide a route to human review for policyholders affected by a decision. Correct · you chose this

    Where solely automated decisions with legal or similarly significant effects are permitted under a GDPR Article 22 exception, individuals must be able to obtain human intervention. Approving or declining a claim is such a decision, so a human review path is an architectural requirement rather than an optional enhancement.

  • C Reduce randomness in the model's sampling settings so claim decisions are more consistent. Distractor

    Output consistency is a technical property, not a legal safeguard. Even a highly consistent automated decision still lacks the human intervention, transparency, and contest rights that GDPR attaches to consequential automated decisions.

The context window is a single shared budget: the system prompt, tool definitions, every message, every tool result, and the new output all count toward it. In tool-heavy agent workflows, the fastest-growing component is usually tool results, and most of them are consumed once and never needed again. The scenario adds a constraint that rules out coarser remedies: only the stale tool output should go, while the conversation's messages remain unmodified.

Context editing is the mechanism built for this kind of selective curation. Its tool result clearing strategy removes old tool results server-side once the conversation grows past a configurable threshold, keeping a set of recent results while discarding the rest. Because the editing happens on the server before the prompt reaches Claude, the client keeps its full, unmodified history; nothing needs to be synced or rewritten locally. This differs from server-side compaction, which addresses context growth by summarizing earlier parts of the conversation rather than surgically removing one category of content. When the requirement is to keep the actual messages intact and shed only stale tool output, selective clearing is the closer fit.

The distractors reflect common mental-model errors. Prompt caching changes the price of repeated prefix tokens (cache reads cost a fraction of base input), but cached tokens still occupy the context window in full; caching is a cost and latency tool, not a capacity tool. Telling the model to ignore old results removes nothing: the tokens are still transmitted, still counted, and still able to dilute attention, the phenomenon known as context rot. Why this is the answer

Skills use progressive disclosure to make reusable expertise cheap to carry: at startup, only each Skill's name and description are loaded into the system prompt, while the full instruction body stays on the filesystem until the Skill is actually triggered. This design lets an environment hold many Skills without a context penalty, but it makes the description the single gatekeeper for automatic use. Claude compares each incoming request against the descriptions it can see, so a description must convey both what the Skill does and when it should be used, including the trigger phrases and situations users are likely to mention. A capabilities-only description gives Claude nothing to match user intent against, which produces exactly the silent undertriggering in this scenario.

The distractors each misunderstand where the failure occurs. Inlining the instructions into every system prompt works mechanically but is an anti-pattern here: it pays the full token cost on every request and discards the reuse benefit that justified the Skill. Temperature governs sampling randomness, not Skill matching, so raising it changes output variability without changing delegation behavior. And shortening the instruction body optimizes content that only enters context after triggering, so it cannot influence a triggering decision that never happens. The general lesson for architects is that on-demand loading mechanisms (Skills, modular prompts, tool descriptions) shift the design burden onto their discovery metadata: the small, always-loaded surface must carry enough signal for the model to know when to reach for the rest.

See Agent Skills overview for how metadata, instructions, and bundled resources load in stages, and Prompt caching for the complementary strategy of reusing content that must appear in every request.
