Q6

Passing Runtime Findings to a Subagent

Agentic Architecture & Orchestration✓ Correct
Scenario A · Developer productivity agent (Agent SDK)

You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

The main agent maps a legacy module's conventions over several turns, then spawns a code-generation subagent with the prompt "Generate adapters following the conventions identified above." The subagent ignores them. Conventions vary per module. What should change?

  1. Incorrect

    Resuming continues a subagent's own earlier conversation, not the parent's. The investigation happened in the main conversation, and this is the subagent's first invocation, so there is no prior subagent history to continue. Resuming cannot give the subagent findings it never had.

  2. Correct

    A non-fork subagent starts with a fresh context and receives nothing from the parent except the delegation prompt. "The conventions identified above" points at content the subagent has never seen. Putting the actual conventions and file paths into the prompt is the only channel that delivers them.

  3. Incorrect

    Subagents do load the project CLAUDE.md, so this mechanism is real. It fails here because the question states that conventions vary per module; one shared file would apply a single module's rules to every module. CLAUDE.md suits stable project-wide conventions, not findings discovered at runtime for one task.

  4. Incorrect

    A system prompt is a sound place for rules that stay the same across tasks. Here the question states that conventions vary per module, so a fixed definition written ahead of time cannot carry findings discovered at runtime. The per-task findings must travel in the delegation prompt instead.

Correct answer: B

Overall explanation

In the Claude Agent SDK, a subagent is a separate agent instance with its own context window. Unless the subagent is a fork, that window starts fresh, with no parent conversation in it. The subagent gets its own system prompt, its tool definitions, applicable CLAUDE.md content, and the Agent tool prompt the parent wrote when delegating. It does not get the parent's history, the parent's tool results, or the parent's system prompt. So a prompt that says "the conventions identified above" refers to text the subagent cannot see. The fix is to copy the actual findings, including file paths and concrete rules, into the delegation prompt itself.

This isolation is a deliberate tradeoff. Fresh context keeps the subagent focused and keeps its verbose work out of the main conversation. The cost is that every handoff must be explicit: if a fact is not in the prompt, it does not exist for that subagent.

The other options place the knowledge in the wrong surface. An AgentDefinition system prompt is written before runtime, so it fits stable expertise, not findings that change with every module. Resuming a subagent continues that subagent's own prior conversation; it never imports the parent's history, and a first invocation has no history to resume. A shared CLAUDE.md does reach subagents, but it is a static project-wide file; the question says conventions differ per module, so one file cannot carry the right rules for each spawn.

A nightly CI job runs claude -p to produce a report on legacy code. When the agent requests a Bash command, the step stalls until it times out. The report does not need Bash, and policy forbids auto-approving Bash in CI. Which change fixes the hang?

  1. Incorrect

    Allow-listing is a sound way to stop permission prompts for tools the job should run. It fails here because the question states that policy forbids auto-approving Bash in CI, and allow-listing auto-approves it.

  2. Correct

    This flag tells Claude Code not to consult or wait for any approval source. Unresolved permission requests are denied and the run continues. The job never stalls, Bash is not auto-approved, and the report still gets produced.

  3. Incorrect

    A permission prompt tool is a real mechanism for handling approvals programmatically in unattended runs. Here it would auto-approve Bash, which the stated policy forbids, and the report does not need Bash anyway.

  4. Incorrect

    A -p run is non-interactive and does not read approval answers from standard input. The stall is a pending permission request inside Claude Code, not a terminal prompt, so piped input never reaches it. It would also auto-approve Bash, against policy.

Correct answer: B

Overall explanation

The -p flag makes Claude Code run non-interactively: it processes the prompt, prints the result, and exits. But non-interactive mode does not remove the permission system. Piping text into standard input does nothing in a -p run, because the stall is an unresolved permission request inside Claude Code, not a terminal waiting for keystrokes.

The mental model for unattended runs: decide in advance how every permission request resolves. Pre-approve the tools the job genuinely needs, and use --permission-prompts none so everything else is denied instead of blocking.

Q14

Finding Literal Function Calls with Grep

Tool Design & MCP Integration✗ Incorrect
Scenario A · Developer productivity agent (Agent SDK)

You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

You need to locate every literal call to cache.flushAll( and inspect the matching lines with their line numbers. The Grep invocation returns only file paths, so you cannot review the call sites. Which adjustment is appropriate?

  1. Correct

    Grep's content mode returns the matching lines, including line numbers. Since Grep uses ripgrep regular-expression syntax, the literal function call must escape the dot and opening parenthesis: cache\.flushAll\(.

  2. Incorrect

    The default files_with_matches mode returns paths of files that contain a match. Glob matches file names and paths; it does not return the matching source lines or their line numbers. Combining the two does not solve the inspection requirement.

  3. Incorrect

    Count mode reports the number of matches per file and a total. It is useful for estimating the scope of a change, but it does not return the source lines and line numbers needed for a line-by-line review.

  4. Incorrect

    Reading every file before searching fills the context window with code that may be irrelevant. The search-first workflow narrows the candidate files and then reads only the relevant content.

Correct answer: A

Overall explanation

Claude Code's built-in tools are designed for incremental investigation. Grep searches file contents and, by default, returns only the paths of matching files (files_with_matches mode). That default exists for a reason: the intended workflow is to search first, then Read only the files that matter. The agent builds understanding in loops: find where a symbol is defined, read that file, find where it is imported or called, read those consumers, and repeat until the flow is clear.

This pattern protects the context window. Reading dozens of files before answering fills the context with code that is mostly irrelevant. Listing files with Glob and reading each one has the same problem; Glob matches names, not relevance. Reading a single entry file is too little instead of too much: relevant information may pass through modules the agent never loads, so its answer becomes a guess.

Search-first is necessary but not sufficient; the search must target the right code. Grep uses ripgrep regular-expression syntax, not literal text matching or POSIX grep syntax. A dot matches any character, and an unescaped parenthesis opens a regular-expression group. To find the literal call cache.flushAll(, escape both metacharacters: cache\.flushAll\(.

The scenario needs the matching lines themselves plus their line numbers. That is exactly what content mode returns. Count mode answers a different question—how often something appears—and is better suited to a quick impact estimate. See the Claude Code tools reference for the Grep output modes and options.
