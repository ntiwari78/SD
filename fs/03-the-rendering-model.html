The Rendering Model

React is not a collection of hooks. It is one idea — describe the UI as a function of state, and let the library work out the DOM operations — plus the consequences of that idea. Learn the consequences and the API stops needing to be memorised.

01 / WHY

The problem React was built to delete

Before asking how React works, ask what it replaced — because the cost it charges you only makes sense against that.

Consider a modest feature from the capstone: a scholarship list with a search box, a loading state, an empty state, an error state, and a selected row. Written imperatively — the way the deck's slide 21 writes it with the DOM API, and the way jQuery-era code wrote everything — you do not describe the UI. You describe the transitions between UIs.

And there are a lot of them. Loading → ready. Ready → empty. Empty → ready. Ready → error. Error → loading. Selected → different row selected. Search text changed while loading. Each transition is code you write, and — this is the part that kills you — each one must undo whatever the previous state left behind. Miss one and you get the bug everyone has seen: an empty-state message still on screen underneath a table full of rows.

The number of transitions grows roughly as the square of the number of states. The number of descriptions grows linearly. That is the entire trade.

Imperative — describe the transitions

function showLoading() {
  list.innerHTML = "";
  empty.hidden = true;
  error.hidden = true;          // must remember to hide
  spinner.hidden = false;
}
function showResults(rows) {
  spinner.hidden = true;
  error.hidden = true;
  empty.hidden = rows.length > 0;
  list.innerHTML = rows.map(rowHtml).join("");
  // …and re-attach every event listener you just destroyed
}
// showError, showEmpty, clearSelection, restoreSelection, …

Declarative — describe the states

function ScholarshipList({ result, selectedId }) {
  if (result.status === "loading") return <Skeleton />;
  if (result.status === "error")   return <ErrorPanel …/>;
  if (result.data.length === 0)    return <Empty />;
  return (
    <ul>
      {result.data.map(s =>
        <Row key={s.id} row={s} selected={s.id === selectedId} />)}
    </ul>
  );
}
// There is no transition code. There is nothing to forget to undo.

Notice that the declarative version is not merely shorter. It is impossible to leave in an inconsistent state, because no state is left over from the previous render — the function computes the whole answer from its inputs every time. That is the guarantee you are buying, and everything difficult about React is the price.

What you are paying

  • Re-running your components a lot. If the UI is a function of state, then a state change means calling the function again. React's bet — and it is a bet that mostly pays — is that calling JavaScript functions is cheap and touching the DOM is expensive, so it will do a lot of the former to minimise the latter.
  • Purity as a requirement, not a style. A render must not mutate anything outside itself, because React reserves the right to call it more often than you expect, discard the result, or call it twice on purpose (Strict Mode does exactly that, to find the components that lied).
  • An escape hatch problem. Focus, scroll position, media playback, a chart library that owns its own DOM — these are all outside the model, and every one of them is why useRef and useEffect exist. Both are covered in module 05 and 06 as what they are: doors out of the model, to be used deliberately.

Where your deck starts, and where this stage starts

The Eazy Bytes deck builds the same page three ways — plain HTML, then vanilla DOM manipulation, then React via CDN — which is a genuinely good way in, and it is roughly slides 18 to 22. It then moves to JSX syntax. 02 / PIPELINE

What happens after setState

One click changes one CSS class. How many of your component functions just ran?

The single most useful mental correction for people coming to React from anywhere else: “re-render” does not mean “update the DOM”. They are separate phases, and the expensive one is not the one you think.

  1. Trigger. A state setter is called. React marks the owning component as needing work and schedules it — it does not run anything yet.
  2. Render. React calls the owning component's function, and then the functions of its children, and their children. This produces a tree of plain objects describing what the UI should be. No DOM is touched. This phase must be pure.
  3. Reconcile. React compares the new tree against the previous one, position by position. Same component type in the same position means the existing DOM node is kept and updated; a different type means the subtree is destroyed and rebuilt, state and all.
  4. Commit. The minimum set of DOM mutations is applied, synchronously. Refs are attached, useLayoutEffect runs, and only then does the browser get to paint.

The three findings hiding in those toggles

  1. Children re-render because their parent did, not because their props changed. This surprises almost everyone. A Row whose props are byte-identical still has its function called, because React does not compare props unless you ask it to. That is usually fine — the render is cheap and the commit is empty.
  2. Lifting state higher costs you the whole subtree. Move selectedId to App and watch the header, the sidebar and the filter panel start re-rendering on every row click. State belongs at the lowest common ancestor that needs it, and “lift it up just in case” is a real performance decision made carelessly.
  3. React.memo without stable props does nothing at all. Turn on memo and leave the callback inline: the rows still re-render, because onSelect is a brand-new function object every render and memo's shallow comparison sees a changed prop. You have added a comparison cost and bought nothing. Turn on useCallback too and the bailout finally works. This pairing is the single most common ineffective optimisation in React codebases.

Experiment

Set the owner to App, turn both optimisations off, and count the components that run to change one CSS class. Then turn memo and useCallback on and count again. Then ask the question that matters: was any of this ever slow? For eight components it is nanoseconds, and the memo version is more code and more comparisons. Module 07 is about knowing when this stops being true.

03 / SNAPSHOT

State is a snapshot, not a variable

You call setCount(count + 1) three times in one handler. What is the count afterwards?

The answer is one, and every explanation that involves the word “asynchronous” is wrong in a way that will hurt you later. count is a const in the current render's scope. It has a value — say 0 — and nothing can change it, because it is a const in a function that has already returned. All three calls therefore compute 0 + 1.

This is the closure model from Stage 2, and it is not a wart. A render is a snapshot: every value in it is frozen for the lifetime of that render, which is precisely what makes a render a pure description of one state of the world.

Update queue

Interactive · run the handler

Two rules that follow

  • When the next value depends on the previous one, pass a function. setCount(c => c + 1) is not a style preference — it is the only form that is correct when updates can queue, which includes every handler that fires more than once and every update issued from an interval or a subscription.
  • Never mutate state. rows.push(newRow); setRows(rows) passes React the same array reference, so Object.is says nothing changed and no re-render happens. This is the shallow-copy trap from Stage 2 landing in React: setRows([...rows, newRow]), and for nested structures either copy each level or reach for Immer, which Redux Toolkit already bundles — your deck covers that on its final slides.

Batching, precisely

React 18 and later batch every update in the same tick — including those after an await, inside a setTimeout, or in a native event handler. Before 18 only React event handlers were batched, which is why older answers on this topic are misleading. Batching means the three setter calls above produce exactly one render, not three, and the intermediate values are never rendered at all. If you genuinely need to escape it, flushSync exists — and needing it is nearly always a sign that a measurement should have been a layout effect.

✕Reading state right after setting it

setOpen(true); console.log(open); logs the old value, always. open belongs to this render; the new value belongs to the next one. If you need the value you just computed, you already have it — you passed it to the setter.

✕Deriving state into state

const [total, setTotal] = useState(0) plus an effect that recomputes it from rows. Now there are two sources of truth and one render where they disagree. Anything computable from existing state or props should be computed during render — const total = rows.reduce(…) — and memoised only if profiling says so.

✕Putting props into state “so they can be edited”

useState(props.name) captures the prop once, at mount, and then ignores it forever. When the parent sends a different student, the form keeps showing the old one. Either lift the edit state up, or reset the subtree deliberately with a key — which is module 04's mechanism used on purpose.

04 / IDENTITY

Keys are identity, and identity owns state

The deck says “don't use the array index as a key”. Here is what actually happens when you do.

A key is not a React bookkeeping detail and it is not for performance. It answers one question during reconciliation: is this element in the new tree the same thing as that element in the old tree? Everything that lives in a DOM node but not in your props — typed text in an uncontrolled input, focus, scroll position, an in-progress CSS transition, a video's playback position, and the entire state of every component inside it — follows the answer.

Type something into the rows below, then prepend, delete or reorder, and watch where your text ends up.

Key identity, live

Interactive · type, then reorder

These inputs are uncontrolled — their text lives in the DOM node, not in React state. That is exactly the state a key decides the fate of.

What the reconciler is doing

With key={index}, the element at position 0 in the new tree has the same key as the element that was at position 0 before. React concludes they are the same component, keeps the DOM node, and only updates the props that differ. Your typed text stays at position 0 while the data moves out from under it.

With key={row.id}, React matches by identity regardless of position. It moves the existing DOM node — with everything inside it — to the new position. Your text follows the row it belongs to, because it belongs to the row.

Index keys are correct in exactly one case: a list that is append-only and never reordered, filtered or deleted from. Since almost no list stays that way, the rule of thumb “always use a stable id” is right — and now you know what it is protecting.

The same mechanism, used deliberately

// A key on a single element is a reset button for its entire subtree.
// Switch students and the edit form starts completely fresh — no stale
// draft, no leftover validation errors, no scroll position.
<ApplicationForm key={studentId} student={student} />

This is the clean answer to the “props into state” mistake from module 03. Rather than syncing with an effect, tell React the component is a different instance now.

✕key={Math.random()} to silence the warning

Every render produces new keys, so React destroys and recreates every row, every time — losing focus mid-typing, restarting animations, and doing the maximum possible DOM work. It is strictly worse than the index key it was meant to improve on.

✕Assuming keys must be globally unique

They only need to be unique among siblings. Two different lists may both use key 1. What they must be is stable — the same item gets the same key across renders.

✕Changing an element's type or nesting to “refactor”

Reconciliation matches by position and type. Wrapping a subtree in a new <div>, or swapping <Table> for <Grid> at the same position, unmounts everything below it and remounts it fresh — all state gone, all effects re-run. Cosmetic-looking changes to the tree shape are not cosmetic.

05 / EFFECTS

You probably do not need an effect

Most useEffect calls in most codebases should not exist. Is yours one of them?

useEffect has one job: synchronise with something outside React. A subscription, a browser API, a chart library, a WebSocket, an analytics SDK. That is the whole remit. It is not a lifecycle hook, it is not “run this after render”, and it is not where data transformation goes.

Using it for anything else buys you an extra render pass, a state that is briefly wrong, a dependency array to maintain, and a class of bugs — races, stale closures, double-fetches — that simply do not exist in the alternatives. Work through what you are actually trying to do.

Why Strict Mode mounts twice, and why you should want it

    
In development, React 18+ mounts every component, runs its effects, runs the cleanups, and runs the effects again. It is not a bug and it cannot be “fixed” by removing the double invocation. It is a test: an effect that is correct is one whose cleanup fully undoes it, and running it twice proves that. If your component breaks under Strict Mode — a doubled request, two WebSockets, a listener added twice — it would also break in production the moment React remounted it, which it does whenever a key changes, a parent conditionally renders it, or a future feature restores state on back-navigation.

    
Every effect that acquires something must return a cleanup that releases it. A subscription needs an unsubscribe, a listener needs a removal, an interval needs a clear, a fetch needs an AbortController.

    
// The race this cleanup prevents is not hypothetical: type "de", then "del",
// and the slower first response can arrive last and overwrite the newer one.
useEffect(() => {
  const ac = new AbortController();
  apiGet(`/scholarships?q=${query}`, listSchema, { signal: ac.signal })
    .then(setResult)
    .catch(e => { if (e.name !== "AbortError") setResult(errorOf(e)); });
  return () => ac.abort();      // ← the entire point
}, [query]);

    
And then the honest note: you should not be writing that at all. Stage 5 replaces it with TanStack Query, which handles the abort, the race, the cache, the retry, the deduplication and the stale-while-revalidate for you. Fetching in an effect is worth understanding precisely so that you can recognise everything a query library is doing on your behalf.

  


  
Architecture connection

    
Every effect is a seam between React's world and something else. Stage 1's request lifecycle, Stage 2's promises and abort signals, Stage 5's server-state cache and Stage 9's token refresh all live on the far side of one. Counting your effects is a decent proxy for counting your integration points — and a component with five of them is usually one component doing five jobs.

The rules, and the reason behind them

    
Hooks must be called at the top level, in the same order, on every render — never inside a condition, loop or nested function. The deck states this correctly. The reason is worth knowing, because it makes the rule obvious rather than arbitrary: React identifies your hooks by call order, not by name. There is no registry mapping "count" to a value; there is a list, and the third useState call gets slot three. Wrap one in an if and on some renders slot three is your count and on others it is your search query.

07 / MEMOISATION
When memoising is a net loss

  
useMemo is not free. What does it cost, and when does the cost exceed the saving?


  

    
Memoisation is a cache, and every cache has three costs: memory to hold the entry, time to compute the key, and the risk of the entry being wrong. In React the key comparison is a shallow scan of the dependency array on every render, and the entry is wrong whenever a dependency is a fresh object — which, as module 02 showed, is the default for anything you write inline.

    
Move the sliders and watch the arithmetic. The point is not that memoisation is bad. It is that whether it helps is an empirical question with a number attached, and you can only answer it after measuring.

The order to work in

    
    
      
  1. Measure. React DevTools Profiler, with CPU throttling on. “It feels slow” is not a measurement, and neither is a render count.
    2. 
      
  2. Fix the structure. Move state down to the component that needs it. Pass expensive subtrees as children so a state change in the wrapper cannot re-render them. Split the component. These are free at runtime and usually make the code better; memoisation makes it worse.
    3. 
      
  3. Then memoise, and re-measure. If the number did not move, take it back out. Dead memoisation is not neutral — it is comparison cost, retained memory, and a dependency array that will be wrong within two sprints.
    4. 
    

    
Two cases genuinely need useMemo regardless of profiling, because they are about correctness rather than speed: a value used in another hook's dependency array (an unstable object there causes an infinite loop, which is a bug, not a slowdown), and a genuinely expensive pure computation — parsing, sorting thousands of rows, building a lookup — where the cost is visible in a single render.

    
The React team's own compiler exists precisely because this reasoning is hard to do by hand at scale; where it is available, it applies these optimisations automatically and the right amount of manual memoisation drops close to zero. Treat that as the direction of travel, not as permission to stop understanding the mechanism.

  


  

    
✕Wrapping every component in React.memo as a policy
      
You have added a shallow prop comparison to every component in the tree, and bought a bailout only for those whose props are stable — which, with inline objects and callbacks, is few of them. Net negative, and it makes every future prop addition a performance question.

    
✕useCallback on a handler passed to a plain DOM element
      
<button onClick={handleClick}> — a DOM element has no memo comparison to satisfy. The useCallback does nothing except cost a dependency array. It only pays when the consumer is a memoised component, a dependency array, or a context value.

    
✕Memoising to fix a render loop instead of finding the cause
      
An effect that runs forever is telling you a dependency is unstable. useMemo can silence it, but so can removing the object from the dependencies entirely, or moving it outside the component where it never changes. Silencing a symptom leaves the unstable reference in place to cause the next one.

08 / EXTRACTION
Custom hooks: behaviour, not indirection

  
Your deck mentions custom hooks once, as a naming rule. What are they actually for?


  

    
A custom hook is a function that calls other hooks. That is the entire definition — there is no registration, no special runtime, nothing magic. The use prefix exists so the linter can enforce the rules of hooks on it.

    
What makes one worth writing is that it extracts stateful behaviour, not markup and not a pure function. If your candidate hook calls no hooks, it should be a plain function. If it only returns JSX, it should be a component.

    
The test that keeps them honest: a custom hook should have a name that describes a capability, and two callers. useDebouncedValue, useMediaQuery, useLocalStorage, useIntersectionObserver, useScholarshipFilters — each names a thing a component can do. A useStudentPageLogic that exists once, to make one component's file shorter, has moved code without abstracting anything, and has made the data flow harder to follow in exchange.

    
// Two capabilities the capstone needs everywhere, extracted once.

export function useDebouncedValue<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);   // cleanup cancels the superseded timer
  }, [value, delay]);
  return debounced;
}

// Filters that live in the URL, so a filtered view is a shareable link
// and the back button works. Stage 5 calls this "URL state".
export function useScholarshipFilters() {
  const [params, setParams] = useSearchParams();
  const filters = useMemo(() => ({
    q:      params.get("q") ?? "",
    cohort: Number(params.get("cohort")) || undefined,
    status: params.get("status") as Status | null,
    page:   Number(params.get("page")) || 0,
  }), [params]);                     // memo needed: this object feeds a query key

  const setFilter = useCallback((patch: Partial<typeof filters>) => {
    setParams(prev => {
      const next = new URLSearchParams(prev);
      for (const [k, v] of Object.entries(patch)) {
        v == null || v === "" ? next.delete(k) : next.set(k, String(v));
      }
      if (!("page" in patch)) next.delete("page");   // changing a filter resets paging
      return next;
    });
  }, [setParams]);

  return { filters, setFilter };
}

    
Note what the second one does not do: it holds no state of its own. The URL is the state. That is a Stage 5 idea arriving early, and it is the reason this hook is worth extracting — every consumer gets the same rules about resetting pagination, dropping empty values, and typing the result.

    
What hooks do not share

    
Two components calling useScholarshipFilters get two independent pieces of state. A custom hook shares logic, never state. When you want shared state, the answers are lifting it up, context, or a store — which is the whole of Stage 5.

  


  
Challenge

    
The capstone's search box needs to debounce input, keep the query in the URL, reset to page 0 whenever the query changes, and cancel the in-flight request when the query changes again. Write it as composed custom hooks and decide, explicitly, which piece of state lives where — component, URL, or server cache. Then compare your answer with Stage 5's classification. The disagreements are the interesting part.
