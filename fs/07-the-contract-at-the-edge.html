Full-Stack Atlas · Stage 07 · Level 3 Backend

The Contract at the Edge

An API is the one part of your system you cannot refactor unilaterally. Everything inside is yours to change; everything at the edge is a promise to somebody else's code. This stage is about making promises you can keep — and about the three the deck never teaches you to make: one error shape, an idempotency key, and a document a partner could integrate against.

01 / RESOURCES

Nouns are easy until the operation is a verb

“Use nouns, not verbs” is where most REST advice stops. Then someone asks you to bulk-approve forty applications.

Resource modelling is straightforward for CRUD and immediately awkward for everything else — which is unfortunate, because everything else is where the business logic lives. The trick that resolves almost all of it: when an operation does not fit a noun you already have, look for the noun the operation creates. Awarding is a verb; an award is a thing. Reviewing is a verb; a review is a thing. Sending is a verb; a delivery is a thing.

That reframing gives you a resource to POST to, an identifier to return, a record you can GET later, and — usefully — somewhere to hang an audit trail. Work through the ones the capstone actually needs.

Where on the maturity model you should actually stop

Richardson's model describes four levels: a single endpoint (0), resources (1), HTTP verbs and status codes used properly (2), and hypermedia controls that tell the client what it can do next (3). Almost every good API in production sits at level 2, and this stage will get you there deliberately.

Level 3 — HATEOAS, and Spring HATEOAS exists to build it — is genuinely valuable in a narrow band of cases: long-lived public APIs with many independent clients you cannot coordinate with, and workflows where the available next actions are non-obvious and change per record. For a first-party React front end that ships from the same repository as the backend, it adds a link-parsing layer to solve a coordination problem you do not have. Say that out loud when someone raises it, rather than either adopting it reflexively or dismissing it.

And one honest note: some things are not resources and should stop pretending. Authentication endpoints follow OAuth conventions (/oauth2/token) because interoperability beats purity; a health check is /actuator/health because that is what your monitoring expects. Consistency with a widely-understood convention outranks consistency with your own model.

02 / BOUNDARY

Never return an entity

Your deck covers the DTO pattern and gives three good reasons. Here is the fourth, which is the one that ends careers.

Returning a JPA entity from a controller is the most common shortcut in Spring applications and it fails in four independent ways at once. Three are architectural and one is a data breach. Switch between the options and read what actually goes over the wire.

What crosses the boundary

Interactive · compare

Separate DTOs in, out, and per view

One record is rarely enough, and the instinct to reuse a single class in both directions produces the second-most-common API bug: a field the client can set that it should not be able to.

// ✗ One shared class. The client can now send "status": "AWARDED"
//   and "id": 1, and your mapper will cheerfully bind them.
public record ApplicationDto(Long id, String studentName, long amount,
                              ApplicationStatus status, Instant createdAt) {}

// ✓ Request: only what a caller is permitted to supply.
public record CreateApplicationRequest(
    @NotBlank @Size(max = 120) String studentName,
    @Email @NotBlank          String email,
    @Positive                 long amount,
    @NotNull @Min(2000) @Max(2100) Integer cohort
) {}

// ✓ Response: only what this caller is permitted to see.
public record ApplicationResponse(Long id, String studentName, long amount,
                                   ApplicationStatus status, Instant createdAt) {}

// ✓ And a narrower one for the list screen from Stage 4 — a row does not
//   need the full record, and sending less is both faster and safer.
public record ApplicationRow(Long id, String studentName,
                              ApplicationStatus status, LocalDate deadline) {}

The mapping between them is boring code, and boring is the point — it is the place where a field is either deliberately exposed or deliberately not. Write it by hand for a small API; reach for MapStruct (compile-time, no reflection) when the count grows past comfort. Avoid runtime reflection mappers such as ModelMapper: they are convenient exactly until they silently map a field you did not intend, which is the failure you were trying to prevent.

Note also what the DTO boundary buys you in the other direction. Because the response record is not the entity, Stage 8 can rename a column, split a table, or add a join without a single client noticing. That freedom is the whole reason the layer exists.

Architecture connection

This is the server half of Stage 2's rule. The client parses at its boundary with Zod so it never trusts a response; the server projects at its boundary with DTOs so it never leaks an entity. Both sides own their own shape, and the OpenAPI document in module 07 is what keeps the two shapes agreeing.

03 / VALIDATION

Four layers, and which one should catch it

A bad payload arrives. Where it gets caught decides the status code, the message, and whether anyone can debug it.

Validation is not one step. A request passes through four gates on its way to the database, each capable of rejecting it, each producing a different exception and — if you are not deliberate — a different error shape. Send some bad payloads through and watch where each one stops.

The rule for deciding which layer owns a check

    
    
      
  • Bean Validation owns anything checkable from the payload alone: presence, length, range, format, pattern. It is declarative, it is documented in the OpenAPI schema automatically, and it fails before your code runs.
    • 
      
  • The service layer owns anything that needs other data: is this cohort's budget exhausted, does the applicant already have an award, is the deadline past, may this reviewer act on this record. These are business rules and they belong with the business logic, not in an annotation.
    • 
      
  • The database owns invariants that must hold no matter which code path wrote the row: unique constraints, foreign keys, check constraints. This is the last line and it must exist even when the service already checks — because the service check and the insert are not atomic, and two concurrent requests will both pass it. Stage 8 makes that concrete.
    • 
    

    
A validation that lives in two layers is not duplication; it is defence in depth with different guarantees. A uniqueness check in the service gives a friendly message; the unique index guarantees correctness. You want both, and you want the service to catch DataIntegrityViolationException and translate it rather than letting a constraint name reach the client.

    
// @Valid triggers Bean Validation on the request body. Without it,
// the annotations on the record are decoration.
@PostMapping
ResponseEntity<ApplicationResponse> create(
        @Valid @RequestBody CreateApplicationRequest request,
        UriComponentsBuilder uri) {

    var created = service.create(request);       // business rules live in here

    return ResponseEntity
        .created(uri.path("/api/v1/applications/{id}").build(created.id()))
        .body(created);                            // 201 + Location header
}

// Validating a @RequestParam or @PathVariable needs @Validated on the class
// — a different mechanism, and a different exception, which module 04 handles.
@Validated
@RestController
class ApplicationController {

    @GetMapping
    Page<ApplicationRow> list(@RequestParam @Min(2000) @Max(2100) int cohort, …) { … }
}

  


  

    
✕Annotating the entity instead of the request record
      
Constraints on an entity run at flush time, inside a transaction, producing a ConstraintViolationException from Hibernate at an arbitrary later point — often after other work has already been done. Validate the request at the boundary, where the caller is still on the line and the error can name their field.

    
✕Returning the constraint name to the client
      
uk_application_email_cohort means nothing to a user and tells an attacker your schema. Catch DataIntegrityViolationException, map the constraint name to a human message in one place, and return a 409 with a field reference.

    
✕Trusting the client's validation
      
Stage 4 built the same rules in Zod, and they are a courtesy for the user's benefit. They run on a machine the user controls. Every rule that matters exists twice, and only the server's copy counts.

04 / ERRORS
One error shape, for every failure

  
Your deck teaches @RestControllerAdvice and stops. What it does not give you is the shape to put in it.


  

    
An API with a different error envelope per endpoint forces every client to write a branch per endpoint. There is a standard for this — RFC 9457 Problem Details for HTTP APIs — and Spring Framework 6 and later support it natively through ProblemDetail and ErrorResponseException. Adopting it costs nothing and means your errors are machine-readable by anything that has ever read an HTTP API.

The five fields, and the two you must add

    
RFC 9457 defines type (a URI identifying the kind of problem — the stable, machine-readable part), title (a short human summary that does not vary per occurrence), status, detail (specific to this occurrence), and instance (a URI for this occurrence). The specification explicitly allows extensions, and two are worth adding to every response:

    
    
      
  • errors — a per-field array for validation failures, which is what Stage 4's setError maps back onto inputs. Without it, a form with five bad fields gets one sentence.
    • 
      
  • traceId — the correlation ID from Stage 1. It turns “it failed at 14:32” into a single trace in Stage 12, and it is the only technical detail that should ever be shown to a user.
    • 
    

    
Note the discipline that goes with it: clients branch on type and status, never on detail. The moment a client parses your prose, you cannot reword a message without breaking someone. Publish the type URIs as part of your contract and treat them as seriously as your paths.

    
@RestControllerAdvice
class ApiExceptionHandler {

    // A domain exception carries the shape; the handler only translates it.
    @ExceptionHandler(BudgetExhaustedException.class)
    ProblemDetail onBudgetExhausted(BudgetExhaustedException e) {
        var pd = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, e.getMessage());
        pd.setType(URI.create("https://scholarships.org/problems/budget-exhausted"));
        pd.setTitle("Cohort budget exhausted");
        pd.setProperty("cohort", e.cohort());
        pd.setProperty("traceId", MDC.get("traceId"));
        return pd;
    }

    // The catch-all. Log the cause; never let it reach the client.
    @ExceptionHandler(Exception.class)
    ProblemDetail onUnexpected(Exception e) {
        var traceId = MDC.get("traceId");
        log.error("Unhandled exception [traceId={}]", traceId, e);   // stack trace to the log
        var pd = ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
                "Something went wrong on our side.");               // nothing else to the client
        pd.setTitle("Internal error");
        pd.setProperty("traceId", traceId);
        return pd;
    }
}

    
That last handler is the one people leave out, and it is the one that decides whether a bug becomes an incident or a stack trace in a browser. A default Spring error response leaks the exception class, the message, and sometimes the path of a file on your server. Catch Exception, log everything, return almost nothing.

  


  
Challenge

    
Write the type-URI registry for the capstone: every distinct problem an API client can encounter, with its URI, status, and whether it is retryable. Then check it against Stage 4's error UI — every entry should map to exactly one of the six surface states, and any that maps to none is either a problem you do not actually have or a screen you have not built.

The three defaults to change on day one

    
// application.yml — a size cap the client cannot exceed.
spring.data.web.pageable:
  default-page-size: 20
  max-page-size: 100        # requests above this are silently clamped
  one-indexed-parameters: false

// And a whitelist, because "sort" is a column name supplied by the caller.
private static final Set<String> SORTABLE =
    Set.of("id", "studentName", "amount", "deadline", "status");

private Pageable sanitise(Pageable p) {
    var safe = Sort.by(p.getSort().stream()
        .filter(o -> SORTABLE.contains(o.getProperty()))
        .toList());
    if (safe.isUnsorted()) safe = Sort.by("deadline").ascending();
    return PageRequest.of(p.getPageNumber(),
                           Math.min(p.getPageSize(), 100),
                           safe.and(Sort.by("id").ascending()));   // stable tiebreaker
}

    
Each line there prevents a specific failure. The size cap stops ?size=1000000 from loading a million rows into heap. The whitelist stops a caller sorting by a property they should not be able to observe — sorting by passwordHash leaks information about it one page at a time, and sorting by an association triggers a join you never intended. The tiebreaker stops rows appearing on two pages, which is the bug from Stage 4 seen from the server side: without a total order, the database is free to return equal rows in a different sequence for each page.


    
Page or Slice?

    
A Page<T> carries totalElements and totalPages, and that costs a second SELECT count(*) on every request. At the capstone's scale that is free. At millions of rows with a filtered count it is the slowest part of the endpoint, and the count is often not even displayed. Slice<T> fetches size + 1 rows instead and reports only whether there is a next page — enough for infinite scroll, and cheap. Choosing between them is a Stage 4 UI decision (do you show page numbers?) resolved with a Stage 8 query plan, which is a good example of why these stages are ordered the way they are.

    
And for genuinely deep pagination, offset is the wrong tool entirely: OFFSET 40000 makes PostgreSQL produce and discard forty thousand rows. Keyset pagination — “give me the twenty after (deadline, id)” — is constant time and is what every infinite scroll should use.

06 / IDEMPOTENCY
The double-award, fixed properly

  
Stage 5 showed two clicks debiting the budget twice, and said the client fix was a courtesy. This is the correctness fix.


  

    
POST is not idempotent, which means the network is allowed to deliver your request twice and neither the browser, the load balancer, nor your retry library is doing anything wrong when it does. A dropped response, a proxy retry, a double click, a mobile network handover — the server sees two requests and has no way to know they were one intent.

    
Unless you give it one. An idempotency key is a caller-generated identifier for an intent, sent as a header; the server records it, and a repeat of the same key returns the original result instead of acting again. This is how payment APIs work, and it is not complicated.

What makes it work, and what breaks it

    
@PostMapping("/applications/{id}/awards")
ResponseEntity<AwardResponse> award(
        @PathVariable long id,
        @RequestHeader("Idempotency-Key") @NotBlank String key,
        @Valid @RequestBody AwardRequest request) {

    return idempotency.execute(key, request, () -> service.award(id, request));
}

// The store, simplified. Everything hinges on the unique index.
@Transactional
<T> ResponseEntity<T> execute(String key, Object request, Supplier<T> action) {
    var fingerprint = sha256(request);           // same key, different body = a bug
    try {
        repository.insertInProgress(key, fingerprint);   // UNIQUE(key) — the whole mechanism
    } catch (DuplicateKeyException e) {
        var existing = repository.find(key);
        if (!existing.fingerprint().equals(fingerprint))
            throw new IdempotencyKeyReusedException(key);      // 422
        return existing.isComplete()
            ? replay(existing)                                  // the stored response
            : ResponseEntity.status(409).header("Retry-After", "1").build();
    }
    var result = action.get();
    repository.complete(key, 201, serialise(result));
    return ResponseEntity.status(201).body(result);
}

    
Three details do the real work. The unique index is what makes two concurrent requests resolve deterministically — one insert wins, the other gets a constraint violation, and no application-level check could have done that safely. The request fingerprint catches a client that reuses a key for a different payload, which is a client bug worth reporting rather than silently honouring. And the in-progress state means the loser of the race gets a 409 with Retry-After rather than a duplicate or a hang.

    
Which endpoints need one

    
    
      
  • Yes: any POST that creates something or moves money, budget or state — award, submit, upload, send. Anything a client might reasonably retry.
    • 
      
  • No: GET, HEAD, PUT and DELETE, which are already idempotent by definition. This is the practical payoff of the method-properties table from Stage 1: PUT /applications/8891 can be retried on a timeout without a second thought, and that is a reason to prefer it where it fits.
    • 
      
  • Consider: PATCH, which is not idempotent in general. {"credits": "+3"} applied twice is a bug; {"status": "AWARDED"} applied twice is not. Know which kind yours is.
    • 
    

    
Give the keys a TTL — twenty-four hours is typical — and delete expired rows, or the table becomes the largest thing in your database.

07 / EVOLUTION
What breaks a client, and what does not

  
Versioning is not a strategy you pick once. It is what you do when the answer below is “breaking”.


  

    
Your deck lists four versioning mechanisms — URI path, query parameter, custom header, media type — and that list is the easy part. The decision that matters comes earlier: is this change breaking at all? Most are not, and a new version for a non-breaking change costs you two code paths forever.

The versioning decision, made once

    

      

        
MechanismLooks likeTrade-off

        
          
URI path/api/v1/applications
            Obvious in logs, in a browser, in a support ticket, and trivially routable at the gateway. Purists object that the resource has not changed identity — which is true and, in practice, does not cost anything. Recommended here.

          
Media typeAccept: application/vnd.…v2+json
            The most theoretically correct: one URI per resource, negotiated representations. Also the hardest to test by hand, to cache correctly, and to explain to an integrator at 2 a.m.

          
Custom headerX-API-Version: 2
            Keeps URLs clean and is invisible in a browser address bar — which cuts both ways. Easy to forget, and caches ignore it unless you configure Vary.

          
Query parameter?version=2
            Simple, and it muddles the resource identifier with a protocol concern. Rarely the best answer.

          
No versioningadditive changes only
            The best option when you control every client and can deploy them together — which is exactly true of the capstone's React app, and exactly false the moment a partner NGO integrates.

        
      

    

    
The recommendation for this application: URI path versioning, one version, and a hard commitment to additive change. Start at /api/v1 so the shape exists, then work extremely hard never to need /v2. A version bump is not a technical event, it is an organisational one — every consumer must be found, notified, migrated and confirmed, and until the last of them moves you are running both.


    
Contract-first, and why it matters more than the mechanism

    
Springdoc generates an OpenAPI document from your annotations, which is the code-first workflow and the one your deck teaches. It works, and the document is only ever as truthful as the annotations. The stronger discipline is to treat the document as an artefact in its own right:

    
    
      
  • Generate the client's types from it. The React app should not hand-write its API types — it should generate them from the published document (openapi-typescript), so a field rename on the server becomes a TypeScript error in the front end at build time. That is Stage 2's boundary rule enforced across the repository boundary.
    • 
      
  • Diff it in CI. Commit the generated document and fail the build when a change is breaking. This is exactly the analyser above, automated — and it is the only thing that reliably stops a breaking change reaching a partner, because reviewers do not notice a removed field in a diff of a hundred files.
    • 
      
  • Document the errors too. An OpenAPI document that lists only happy paths is half a contract. Every endpoint should declare its problem types, and module 04's type-URI registry is what you list.
    • 
    

    
@Operation(summary = "Award a scholarship to an application")
@ApiResponses({
    @ApiResponse(responseCode = "201", description = "Award created"),
    @ApiResponse(responseCode = "409", description = "An identical request is in flight",
                 content = @Content(schema = @Schema(implementation = ProblemDetail.class))),
    @ApiResponse(responseCode = "422", description = "Cohort budget exhausted",
                 content = @Content(schema = @Schema(implementation = ProblemDetail.class)))
})
@PostMapping("/applications/{id}/awards")
ResponseEntity<AwardResponse> award(…) { … }

08 / OUTBOUND
When Spring Boot is the client

  
Your service calls a document-verification API that is having a bad day. What does your user see?


  

    
Every outbound call is another Stage 1 request lifecycle, with one difference that changes everything: you are now the one holding a thread while somebody else's system decides how to feel about it. The failure this produces is not an error page — it is your entire application becoming unresponsive because every request thread is parked waiting on a partner who never replies.

    
The defence is a timeout budget: every layer in the chain has a limit, and they must be ordered so that the inner ones fail first. Set the numbers and see who gives up first.

What a competent outbound call looks like

    
// RestClient is the modern synchronous client — RestTemplate is in maintenance,
// and WebClient brings a reactive programming model you do not otherwise need.
@Bean
RestClient verificationClient(RestClient.Builder builder, VerificationProperties props) {
    var factory = new SimpleClientHttpRequestFactory();
    factory.setConnectTimeout(Duration.ofSeconds(2));    // never leave these unset
    factory.setReadTimeout(Duration.ofSeconds(3));
    return builder
        .baseUrl(props.baseUrl())
        .requestFactory(factory)
        .defaultHeader("Idempotency-Key", …)             // you are somebody's client now
        .build();
}

// Resilience4j: retry only what is retryable, and stop calling a dead service.
@Retry(name = "verification")            // 5xx and timeouts only — never a 4xx
@CircuitBreaker(name = "verification", fallbackMethod = "unverified")
VerificationResult verify(String documentId) {
    return client.get().uri("/documents/{id}", documentId)
                 .retrieve().body(VerificationResult.class);
}

// The fallback is a product decision, not a technical one: what is the
// application allowed to do when this answer is unavailable?
VerificationResult unverified(String documentId, Throwable cause) {
    log.warn("Verification unavailable for {} — queuing for later", documentId, cause);
    return VerificationResult.pending();
}

    
Four rules

    
    
      
  • Never leave a timeout unset. The default for most Java HTTP clients is infinite, and infinite means one slow partner exhausts your thread pool and takes down endpoints that have nothing to do with them.
    • 
      
  • Retry only idempotent operations, and only retryable failures. Retrying a POST after a timeout is how you create two awards — unless you sent an idempotency key, which is module 06 paying off in the other direction. A 4xx will not become a 2xx by asking again.
    • 
      
  • Jitter your backoff. Synchronised retries from many instances are how a partner's brief blip becomes their outage, and then yours.
    • 
      
  • Have an answer for “unavailable”. A circuit breaker without a designed fallback just fails faster. Decide, per integration, whether the right behaviour is a queue, a cached answer, a degraded response, or an honest error — and note that this is the server-side twin of Stage 4's six surface states.
    •

The capstone increment

    
    
      
  • The full API surface — scholarships, applications, documents, awards and reviews, modelled as resources, with sub-resources for the operations that are not CRUD.
    • 
      
  • Three DTO families — request, response and row records, mapped explicitly, with entities never crossing the controller boundary.

    •

    •

    •
