The Cost of Every Query

This is the largest gap in your course deck and the one that costs most. It builds against H2 in memory, never teaches SQL, never mentions an index or a query plan, never names the N+1 problem, and has no migrations at all. Everything below is the half that decides whether the API from Stage 7 is still fast at a hundred thousand rows.

01 / CONSTRAINTS

The database is the only thing that is actually true

Your service checks that a student has not already applied. Two requests arrive four milliseconds apart. What happens?

Stage 7 said a uniqueness rule must exist in both the service and the database. This is the demonstration, because the argument only lands once you have watched the interleaving.

The service check is a SELECT followed by an INSERT, and those are two statements. Between them, anything can happen — including the identical pair of statements from another request on another thread on another instance. No amount of care in application code closes that window, because the window is created by the gap between reading and writing.

What belongs in the schema

    
The rule is not “put everything in the database”. It is: an invariant that must hold no matter which code path wrote the row belongs in the schema. That includes every rule your future self might violate from a migration script, a batch import, a support engineer's psql session, or a second service written next year.

    
    
      
  • NOT NULL on everything that is genuinely required. This is free, and it removes an entire category of null-handling from your Java. If you cannot decide, the answer is NOT NULL with a default.
    • 
      
  • UNIQUE for identity rules. Note the composite case — UNIQUE (email, cohort) — and the partial case, which PostgreSQL supports and most people never discover: CREATE UNIQUE INDEX … WHERE deleted_at IS NULL gives you “unique among non-deleted rows”.
    • 
      
  • FOREIGN KEY for every reference. An application row pointing at a deleted NGO is corruption, and the only reliable prevention is the database refusing it. Choose ON DELETE behaviour deliberately: RESTRICT by default, CASCADE only where the child genuinely cannot exist alone.
    • 
      
  • CHECK for value rules — amount > 0, deadline > created_at, status IN (…). Cheap, and they document the domain in the place people actually look.
    • 
    

    
What does not belong: anything requiring a decision, a lookup across many rows, or a policy that will change. “A reviewer may not approve an application from their own NGO” is a service rule; the database has no business knowing about roles.


    
Normalisation, briefly and practically

    
Third normal form is worth reaching and rarely worth agonising over. The practical version: store each fact once. If an NGO's name appears in the application table, you now have two places to change it and a guaranteed drift. Denormalise deliberately and only with a measurement in hand — a materialised count, a cached display name — and when you do, write down what keeps it in sync.

    
The exception worth knowing: historical facts are not the same fact. An application's awarded_amount must be stored on the award row, not read through a join to the scholarship, because the scholarship's amount may change next year and the award happened at a specific one. Confusing “the current value” with “the value at the time” is the most common data-modelling bug in financial and academic systems alike.


    
Choosing a primary key

    

      

        
StrategyGoodBad

        
          
bigint GENERATED … AS IDENTITY
            Small (8 bytes), sequential so index inserts land on the same page, fast joins, readable in logs.
            Guessable and enumerable — never expose it in a URL without an authorization check, and Stage 9's object-level rule assumes you did not.

          
uuid (v4, random)
            Generated by the client, safe to expose, no coordination needed across services.
            16 bytes, and randomness scatters inserts across the whole B-tree — page splits, cache misses, and a measurably slower write path on large tables.

          
uuid (v7, time-ordered)
            The modern compromise: opaque like v4, sequential like an identity column, so inserts stay clustered.
            Still 16 bytes, and it leaks a creation timestamp — which is usually harmless and occasionally is not.

          
Natural key
            No surrogate to maintain; the key means something.
            Natural keys change. An email address, a registration number, a national identifier — every one of them has an edge case where it must be updated, and then you are cascading a key change through six tables.

        
      

    

    
The recommendation for the capstone: bigint identity as the primary key, plus a separate uuid public identifier on anything exposed in a URL. Internal joins stay small and fast; external references stay opaque and non-enumerable. It costs one extra column and one unique index.

The SQL worth being fluent in

    
-- Aggregation. Every non-aggregated column must be in GROUP BY;
-- HAVING filters groups, WHERE filters rows, and the difference matters
-- because WHERE runs first and is therefore much cheaper.
SELECT n.name, count(*) AS applications, sum(a.amount) AS requested
FROM   application a
JOIN   ngo n ON n.id = a.ngo_id
WHERE  a.cohort = 2026                -- filters rows, before grouping
GROUP  BY n.id, n.name
HAVING count(*) > 10                  -- filters groups, after
ORDER  BY requested DESC;

-- Window functions: aggregate without collapsing rows. This is the tool
-- most people reach for a loop in Java instead of, and it is not close.
SELECT id, student_name, amount,
       rank() OVER (PARTITION BY cohort ORDER BY amount DESC) AS rank_in_cohort,
       amount - avg(amount) OVER (PARTITION BY cohort)        AS vs_cohort_avg
FROM   application;

-- A CTE for readability. In PostgreSQL 12+ these are inlined by the planner
-- unless you write MATERIALIZED, so they are free to use for clarity.
WITH awarded AS (
    SELECT application_id, sum(amount) AS total
    FROM   award GROUP BY application_id
)
SELECT a.id, a.student_name, coalesce(w.total, 0) AS awarded
FROM   application a
LEFT   JOIN awarded w ON w.application_id = a.id;

    
Two habits worth forming immediately. Never SELECT * in application code — it transfers columns you do not need, breaks when someone adds a column, and prevents index-only scans. And always alias your tables, because a three-table join without aliases is unreadable and a self-join without them is impossible.

03 / PLANS
Indexes, and reading what the planner decided

  
240,000 applications. The list endpoint from Stage 4 takes 340 ms. Which index fixes it, and how would you know?


  

    
An index is a sorted structure that lets the database find rows without reading the table. That is the whole idea, and everything interesting follows from three consequences: an index can only help if the query's predicate matches its leading columns, an index that also covers the ORDER BY removes the sort entirely, and every index makes every write slower.

    
Pick a query, add indexes, and read the plan. The numbers are modelled on a 240,000-row table.

Reading a plan, in the order that matters

    
Read it inside out — the most indented node runs first — and look at four things before anything else:

    
    
      
  • Seq Scan on a large table with a selective filter. Usually means no usable index, occasionally means the planner correctly decided a scan is cheaper. On a small table it is right and you should leave it alone.
    • 
      
  • The gap between rows= and actual rows=. The first is the planner's estimate, the second is reality. A large divergence means the statistics are stale (ANALYZE) or the data is correlated in a way the planner cannot see — and every bad plan downstream follows from a bad estimate here.
    • 
      
  • A Sort node with a large Sort Method: external merge Disk. The sort spilled out of work_mem. Either index the ordering away or give the sort more memory.
    • 
      
  • Rows Removed by Filter. This is wasted work made visible: rows the database read and then discarded. A big number next to a small result is the signature of a missing or wrong index.
    • 
    

    
Use EXPLAIN (ANALYZE, BUFFERS), not bare EXPLAIN. ANALYZE actually runs the query and reports real timings; BUFFERS shows how many pages came from cache versus disk, which is what separates “slow query” from “cold cache”. Be aware that ANALYZE executes the statement — wrap a write in a transaction you roll back.


    
Composite index column order

    
The single most useful rule in this module: equality columns first, then the range or sort column. An index on (cohort, status, deadline) serves WHERE cohort = ? AND status = ? ORDER BY deadline perfectly — it seeks straight to the matching block and reads it already in order. The same columns as (deadline, cohort, status) serve it not at all, because the leading column is not in the predicate. Same columns, same size, completely different index.


    
What indexes cost

    
Every index is a second structure that must be updated on every INSERT, UPDATE of an indexed column, and DELETE. Eight indexes on a hot table means every write does nine writes. They also consume memory that would otherwise cache the table, and they must be maintained during migrations. The discipline is to add indexes in response to measured queries, and to periodically look for unused ones — PostgreSQL's pg_stat_user_indexes tells you which have never been scanned, and dropping those is one of the cheapest performance wins available.

  


  
Experiment

    
Run the list-endpoint query with only idx_status enabled, then swap it for idx_cohort_status_deadline. The first gives you a bitmap scan over seventy thousand rows and a sort; the second returns twenty rows without sorting anything. Then enable the covering index and watch the plan lose its heap access entirely — an Index Only Scan, which is the fastest thing in this module and the reason INCLUDE exists.

04 / N+1
The problem your deck never names

  
One endpoint, twenty rows on the page. Forty-one queries went to the database. Nothing in your code says “forty-one”.


  

    
This is the most common performance bug in JPA applications, it is invisible in code review, and it does not appear in your course material at any point — including in the slides that teach lazy loading, which is the mechanism that causes it.

    
The setup is ordinary: an endpoint returns twenty applications; each has a student (a @ManyToOne) and some documents (a @OneToMany); the mapper reads both while building the response DTO. Every one of those reads on a lazy association is a separate SELECT. Try the strategies.

How to notice it before production does

    
An N+1 is undetectable by reading the code and trivially detectable by counting queries. Three ways, in increasing order of how much you should trust them:

    
    
      
  1. spring.jpa.show-sql in development. Crude, noisy, and enough to spot forty-one statements where you expected one.
    2. 
      
  2. Hibernate statistics — spring.jpa.properties.hibernate.generate_statistics=true logs the query count per session. Better, because it gives you a number rather than a wall of text.
    3. 
      
  3. An assertion in your tests. This is the one that actually holds the line: a test that fails when an endpoint issues more queries than it should. Libraries exist for it, and Stage 10's Testcontainers setup is where it belongs. An N+1 that cannot reappear is worth more than one you fixed.
    4. 
    


    
The pagination trap

    
The single nastiest interaction in this module, and it deserves its own warning. Combine a JOIN FETCH of a collection with a Pageable and Hibernate logs this:

    
HHH90003004: firstResult/maxResults specified with collection fetch;
             applying in memory

    
It is telling you that it loaded every matching row into heap and paginated in Java. Page 1 of 240,000 applications is now a full table load. It is a warning, not an error; the endpoint works, returns correct data, and destroys the server under load. The fix is two queries — page the ids first, then fetch the collections for that page — which is exactly what @BatchSize or a two-step repository method does for you.


    
The strategy that ends most of this

    
Notice which row in the counter above is best on every axis: the DTO projection. It selects exactly the columns the response needs, in one query, with no entities, no lazy associations, no dirty checking, and no persistence context to manage. Stage 7 already established that entities must not cross the controller boundary — this is the same decision paying off again, because once the response is a record, there is no reason to load an entity graph at all.

    
// One query, one row per application, only the columns that get serialised.
public interface ApplicationRepository extends JpaRepository<Application, Long> {

    @Query("""
        select new org.scholarships.web.ApplicationRow(
                 a.id, s.fullName, a.status, a.deadline, count(d.id))
        from   Application a
        join   a.student s
        left   join a.documents d
        where  a.cohort = :cohort and a.status = :status
        group  by a.id, s.fullName, a.status, a.deadline
        """)
    Page<ApplicationRow> findRows(@Param("cohort") int cohort,
                                 @Param("status") ApplicationStatus status,
                                 Pageable pageable);
}

// Keep entities for the write side, where you need dirty checking and
// the domain model. Use projections for the read side, where you do not.
// That split is the useful half of CQRS, and it costs nothing — Stage 15.

  


  

    
✕Setting FetchType.EAGER to “fix” it
      
It moves the problem rather than solving it: every query that touches the entity now loads the association, including the ones that did not want it, and collections are still fetched with separate selects. EAGER is a global decision made to satisfy one local case. Keep everything LAZY and fetch explicitly per query — which is the reverse of what many tutorials suggest, and is the consensus of every team that has maintained a JPA application for two years.

    
✕Two JOIN FETCHes on collections in one query
      
MultipleBagFetchException, or — if you use Set instead of List and dodge the exception — a silent cartesian product: twenty applications × three documents × four reviews is 240 rows to build 20 objects. Fetch one collection per query, and use @BatchSize for the rest.

    
✕Open Session In View
      
Spring Boot enables it by default, and it hides N+1 problems by keeping the persistence context — and a database connection — open for the whole request, including while Jackson serialises. That is a connection held during work that has nothing to do with the database, which Stage 11 will show you is exactly how a connection pool gets exhausted. Set spring.jpa.open-in-view=false on day one and fix the LazyInitializationExceptions it reveals: each one is a place you were loading data outside a transaction without meaning to.

05 / TRANSACTIONS
Isolation, and the anomalies you are choosing to allow

  
Your deck teaches @Transactional's mechanics well. It does not mention that the default isolation level permits three distinct ways to be wrong.


  

    
A transaction gives you atomicity and durability whatever you do. Isolation is the part you configure, and the default — READ COMMITTED in PostgreSQL, which is also Spring's default — is a deliberate trade of correctness for concurrency. It is the right default. It is not a guarantee that concurrent transactions behave as if they ran one after another, and the gap is where a class of bugs lives that testing almost never finds.

Two things about PostgreSQL specifically

    
Dirty reads never happen. PostgreSQL's READ UNCOMMITTED behaves as READ COMMITTED; its multi-version storage makes uncommitted data invisible by construction. So the classic four-anomaly table you may have memorised has one row that simply does not apply here.

    
REPEATABLE READ also prevents phantoms. The SQL standard permits them at that level; PostgreSQL's snapshot isolation does not, because the whole transaction sees one consistent snapshot. What it does not prevent is write skew — two transactions each reading a condition, each finding it satisfied, and each writing something that invalidates it for the other. That is what SERIALIZABLE and its predicate locking exist for.

    
The practical consequence: at REPEATABLE READ and above, your transaction can fail with a serialization error at commit time and that is normal. The application must be prepared to retry it — which means the transaction must be idempotent or retryable, which is the same design pressure as Stage 7's idempotency key, arriving from a different direction.


    
Locking, and which one to reach for

    
// Optimistic — the default choice. A version column, checked on write.
// No locks are held; a conflict is detected at flush and becomes a 409.
@Entity
class Application {
    @Version private long version;      // Hibernate manages this
}
// UPDATE application SET …, version = 4 WHERE id = ? AND version = 3
//   → 0 rows updated → OptimisticLockingFailureException → Stage 7's 409

// Pessimistic — take the lock up front. Correct when a conflict is likely
// and a retry is expensive, and dangerous because locks are held for the
// whole transaction and can deadlock.
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select b from CohortBudget b where b.cohort = :cohort")
Optional<CohortBudget> findForUpdate(@Param("cohort") int cohort);
// SELECT … FOR UPDATE — other transactions block here until you commit.

// Often better than either: let the database do the arithmetic atomically.
// No read, no version, no lock held across application code.
@Modifying
@Query("update CohortBudget b set b.remaining = b.remaining - 1 " +
       "where b.cohort = :cohort and b.remaining > 0")
int tryConsume(@Param("cohort") int cohort);   // returns 0 if it failed

    
That last form deserves emphasis, because it is the one people reach for last and should reach for first. UPDATE … WHERE remaining > 0 returning a row count is a compare-and-swap: it is atomic, needs no isolation level above the default, holds no lock across your code, and cannot lose an update. When a business rule can be expressed as a conditional write, express it as one.


    
Transaction scope

    
Three rules that follow from Stage 6's proxy trace. Transactions belong on the service, not the controller and not the repository — one business operation, one transaction. Keep them short: a transaction that spans an HTTP call to a payment provider holds a database connection for the duration of somebody else's outage. And mark read-only work @Transactional(readOnly = true), which lets Hibernate skip dirty checking and lets PostgreSQL route to a replica if you have one.

06 / MIGRATIONS
Changing a schema that is being used right now

  
Your deck has no migrations at all — the schema comes from Hibernate's ddl-auto and a data.sql. That works exactly until there is data you cannot lose.


  

    
Two things need saying before the mechanics. First: spring.jpa.hibernate.ddl-auto must be validate in every environment above your laptop, and never update. update makes changes it thinks are safe, never removes anything, cannot be reviewed, cannot be rolled back, and behaves differently depending on what the schema already happened to be. It is not a migration tool and was never intended as one.

    
Second: the schema is code. It belongs in version control, in numbered files, applied in order, with a checksum so a file that changed after being applied is an error rather than a mystery. That is what Flyway does, and the whole of it is four conventions.

    
src/main/resources/db/migration/
  V1__initial_schema.sql
  V2__add_cohort_budget.sql
  V3__add_application_status_index.sql
  V4__backfill_public_ids.sql
  R__reporting_views.sql        # repeatable — re-applied whenever it changes

    
Flyway records each applied version in a flyway_schema_history table with a checksum, runs pending migrations at startup inside a transaction where the database supports it (PostgreSQL does, for DDL), and refuses to start if history and files disagree. Combined with ddl-auto: validate, Hibernate then checks that the entities match the schema Flyway produced — so a mismatch fails at boot rather than on the first request.

    
The interesting part is not writing migrations. It is knowing which ones lock the table.

Expand and contract

    
Every genuinely breaking schema change becomes safe when you split it across releases, and the pattern is always the same four steps. Renaming student_name to full_name:

    
    
      
  1. Expand. Add full_name as nullable. Deploy. Nothing reads it yet.
    2. 
      
  2. Backfill and dual-write. Copy existing values in batches; change the application to write both columns and read the old one. Deploy.
    3. 
      
  3. Switch reads. Read full_name, still write both. Deploy. This is the release you can roll back without losing data.
    4. 
      
  4. Contract. Stop writing the old column, then drop it in a later migration.
    5. 
    

    
Four deploys instead of one, and at no point is there a moment where a running instance of either version is broken. That matters because a rolling deploy runs both versions simultaneously — which is the fact that makes “just rename it” wrong, and which Stage 14 will make unavoidable.

    
Two more habits worth adopting now: never edit an applied migration (Flyway's checksum will catch it, and the fix is a new file), and separate schema changes from data backfills — a V5__add_column.sql that also updates ten million rows holds a transaction open for an hour, bloats the table, and cannot be reasoned about. Backfill in batches, from application code or a separate job, with a commit per batch.

07 / REDIS
The second data store, and the four jobs it is for

  
Redis appears nowhere in your deck. It appears in your target architecture, so here is what it is actually for.


  

    
Redis is an in-memory data structure server. That phrasing matters: it is not “a cache”, it is a set of primitives — strings, hashes, sorted sets, atomic counters, expiry, pub/sub — that happen to be excellent for four jobs a relational database is bad at. Pick one.

  


  

    
What goes in Redis
Interactive · pick a job

    

      

      

    

  


  

    
The rule that keeps a cache honest

    
A cache must be able to disappear without the application becoming incorrect. If losing Redis loses data, it was not a cache — it was your primary store, chosen by accident. Session state is the usual place this line gets crossed, and it is a legitimate crossing as long as you have decided it deliberately: sessions in Redis means a Redis failure logs everybody out, which is an availability decision with a product consequence, not a technical detail.

    
The corollary is that every cache read must have a fallback path, and every cache write must be allowed to fail silently. A @Cacheable method whose cache is unreachable should hit the database and log, not return a 500.


    
What your deck taught, and where it stops

    
Slides 355–361 cover Spring's cache abstraction properly — @EnableCaching, @Cacheable, @CachePut, @CacheEvict, and Caffeine with a TTL. That abstraction is the right one, and switching from Caffeine to Redis is a dependency and a configuration block, not a code change. The distinction the deck does not draw is the one that decides which you want:

    
    
      
  • Caffeine is in-process. Nanosecond reads, zero network, and a separate copy per instance. Three instances means three caches that can disagree, and an eviction on one does nothing to the other two. Correct for immutable reference data; wrong for anything a mutation must invalidate.
    • 
      
  • Redis is shared. A network hop per read — hundreds of microseconds rather than nanoseconds — in exchange for one truth across every instance, invalidation that actually works, and survival across restarts and deploys.
    • 
    

    
Most systems want both: Caffeine in front of Redis in front of PostgreSQL, with the in-process layer holding only things that never need invalidating. Reaching for that arrangement before you have measured anything is, however, exactly the mistake Stage 11 is about.

    
// The same annotations from your deck, now backed by Redis and shared
// across every instance. Note the eviction: a mutation must invalidate,
// and this is the line people forget until the data goes stale in production.
@Cacheable(value = "scholarships", key = "#id")
Scholarship find(long id) { return repository.findById(id).orElseThrow(); }

@CacheEvict(value = "scholarships", key = "#s.id")
Scholarship update(Scholarship s) { return repository.save(s); }

// Configure per-cache TTLs — one global TTL for every cache is a smell,
// because reference data and a user's dashboard do not decay at the same rate.
@Bean
RedisCacheManagerBuilderCustomizer ttls() {
    return b -> b
        .withCacheConfiguration("scholarships",
            RedisCacheConfiguration.defaultCacheConfig().entryTtl(Duration.ofMinutes(10)))
        .withCacheConfiguration("ngos",
            RedisCacheConfiguration.defaultCacheConfig().entryTtl(Duration.ofHours(6)));
}
