Knowing When Not To

Your deck names microservices and Spring Cloud twice, in passing, and develops neither. That is closer to right than most treatments — but for the wrong reason, since it never asks the question. This stage asks it properly: what does a decomposition buy, what does it cost, who pays the cost at 3am, and what is the smallest structure that gets the benefit without the bill. The honest answer for the capstone is a modular monolith, and the point of the stage is to be able to argue that rather than assert it.

01 / SHAPES

Three architectures, one change

Architecture arguments are usually conducted with diagrams. They are settled by asking what happens to the code when a specific thing changes.

Your deck teaches the three-layer arrangement on slide 125 — controller, service, repository — and it is a perfectly reasonable default. The alternatives are not more sophisticated versions of it; they answer a different question, which is which direction the dependencies point.

Layered: each layer depends on the one below, so the service layer depends on the repository, which depends on JPA, which depends on PostgreSQL. Hexagonal — Cockburn's ports and adapters — inverts that: the application defines an interface it needs, and the database adapter implements it, so the arrow points inward. Clean architecture is the same inversion stated as a general rule; Robert Martin's Dependency Rule is that source code dependencies can only point inwards.

What Cockburn actually said, since it is usually misquoted

The intent, in his words, is to “allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases.” Note what is absent: any claim about six sides, and any claim about swapping databases. The motivation is testability and multiple drivers — the hexagon is drawn with six sides because a shape with several edges suggests several ports, and Cockburn says as much.

That matters because the usual justification offered for hexagonal architecture — “we could swap PostgreSQL for MongoDB” — is one almost nobody exercises, and it makes the pattern sound like insurance against an event that will not happen. The benefit you actually collect is that the domain can be tested without a database, without a web layer and without Spring, which Stage 10 valued at about twenty-five milliseconds a test.

My recommendation, and it is deliberately unfashionable

Use the layered arrangement your deck teaches, and invert exactly the dependencies that hurt. Full hexagonal on a CRUD-heavy module produces a port, an adapter, a mapper and two model classes where one entity would have done, and every future reader pays for that. Where a module has real business rules — the eligibility engine, the award calculation — define the interfaces it needs and let infrastructure implement them, because those are the classes where fast tests and framework independence pay back immediately.

The general principle: architecture is not a property of a codebase, it is a property of each module. A system where the scholarship-rules module is hexagonal and the document-upload module is three plain layers is not inconsistent; it is proportionate.

02 / BOUNDARIES

Where the seams are, and how you find them

A bounded context is not a folder. It is a region within which one word means one thing — and the reliable way to find one is to notice where a word stops meaning what it meant.

Domain-driven design gets taught as a vocabulary — aggregates, repositories, value objects — and the vocabulary is the least useful part. The load-bearing idea is bounded context: the recognition that, as Fowler puts it, total unification of the domain model for a large system is not feasible or cost-effective, so you deliberately let the same word mean different things in different places and make the translation explicit.

The capstone has a worked example built into it. Pick a word.

One word, several meanings

Interactive · pick a term

Aggregates, in the one sentence that matters

An aggregate is a cluster of domain objects treated as a single unit, with one root that is the only thing outside code may hold a reference to. The reason it earns its place is not modelling elegance — it is that the aggregate is the transaction boundary and the consistency boundary. Inside one, invariants hold immediately. Across two, they do not, and you need one of Stage 08's mechanisms.

That gives a concrete design test, which is more useful than any amount of aggregate theory: if two things must be consistent within the same transaction, they belong to the same aggregate. If they may be briefly inconsistent, they must not. An application and its documents are one aggregate; an application and the NGO's remaining budget are not, and pretending otherwise is how you end up with a lock on a row every reviewer needs.

Finding boundaries without a two-day workshop

  • Follow the language. Where a term changes meaning, or acquires a qualifier — “student” becoming “applicant”, “reviewer's student”, “alumnus” — you are standing on a seam.
  • Follow the transactions. Things that must commit together are one context. Things that never appear in one transaction probably are not.
  • Follow the change. Look at six months of commits and see which files change together. Modules that always change together are one module pretending to be two; modules that never do are candidates for separation.
  • Follow the people. Conway's law is not a warning, it is a prediction: the boundaries that survive are the ones that match how the organisation communicates. A boundary no team owns will erode.

What not to do: draw boundaries around nouns, which produces an “entity service” for every table and maximises the number of calls per request. If your proposed services are named after your tables, you have decomposed the schema rather than the domain.

03 / ENFORCE

A boundary nothing checks is a comment

Every monolith that became a big ball of mud had a module diagram. What it did not have was a build that failed when someone drew a line through it.

This is the argument that decides the whole stage. The usual case for microservices is that they enforce boundaries — you cannot accidentally reach into another service's tables, because the network is in the way. That is true, and it is worth noticing that the network is being used as a compiler: an extremely expensive way to get a check you can have for free.

A modular monolith gets the same enforcement from a test. Turn the rules on and see what the build says.

Module verification

Interactive · pick a violation

Spring Modulith is a Spring project, currently on its 2.x line, and it is the concrete answer. By default each direct sub-package of your application package is a module; everything in that module's own root package is its API, and sub-packages are internal. One test enforces it:

class ModularityTests {

    static final ApplicationModules modules = ApplicationModules.of(ScholarshipsApplication.class);

    @Test
    void verifiesModularStructure() {
        modules.verify();      // fails the build on a violation
    }

    @Test
    void writesDocumentation() {
        new Documenter(modules)
            .writeModulesAsPlantUml()          // C4 component diagram
            .writeIndividualModulesAsPlantUml()
            .writeModuleCanvases();            // aggregates, published events, config
    }
}

verify() checks exactly three things, and knowing them precisely is the difference between using the tool and hoping: no cycles between modules; no references into another module's internal packages; and, where a module declares allowedDependencies, no dependency outside that list. That is a small, sharp set — it is not a general architecture linter, and for layer rules within a module you still want ArchUnit.

The documentation generation deserves a mention on its own. The module canvas lists, per module, its Spring components, its aggregate roots, the events it publishes and the events it listens to — generated from the code, so it cannot drift. A module diagram that is derived rather than drawn is the only kind that stays true.

The claim this module is making, stated plainly

A modular monolith with enforced boundaries gets you most of what people want from microservices, at a fraction of the cost. Strong module boundaries: yes, checked by the build. Independent deployability: no — and that is the one real difference, which module 04 is about. Technology diversity: no, and for a team of this size that is a benefit rather than a loss. If you cannot maintain module boundaries inside one process, where a test can check them in two seconds, distributing them across a network will not help — it will convert compile errors into 500s. — My recommendation, and the through-line of the stage.

04 / DECOMPOSE

Three benefits, three costs, and who pays them

Fowler's list is short enough to memorise and specific enough to argue with, which is why it is worth using instead of a feeling.

The benefits: strong module boundaries, independent deployment, technology diversity. The costs: distribution, eventual consistency, operational complexity. Six items, and the whole decision is which ones apply to you.

Notice immediately that module 03 obtained the first benefit without paying any of the costs — which leaves a decision between one benefit you may not need and three costs you certainly will. Set your situation below.

Decomposition trade-off

Interactive · describe the situation

Prerequisites, which are not optional

Fowler's list of what you need before you begin is three items and a culture: rapid provisioning — a new server in hours, not weeks; basic monitoring — detecting serious problems quickly; rapid application deployment; and close collaboration between development and operations. Stages 12, 13 and 14 of this curriculum are, in order, those three prerequisites. That ordering was not accidental.

The popular phrasing “you must be this tall to ride” is community folklore rather than a Fowler quotation, and the underlying point stands without it: a team that cannot deploy a monolith reliably will not be rescued by having eight things to deploy.

What the evidence actually supports

This is worth stating carefully, because the internet is loud about it in both directions. DORA's research programme identifies loosely coupled teams as a core capability — architecture that lets teams test, deploy and change systems without depending on other teams — and finds it predicts delivery performance regardless of technology used. Their own language is pointed: microservices architectures are supposed to enable these outcomes, and in practice many so-called service-oriented architectures do not permit testing and deploying services independently.

So the researched property is independent deployability, not microservices. A modular monolith one team deploys on its own schedule satisfies it. A dozen services that must be released together do not, and have all the costs anyway — which is the specific failure mode worth naming, because it is the common one.

On the “everyone is going back to monoliths” story: be careful. The most-cited case study is a single Amazon audio/video monitoring service, and its original post is no longer available at its canonical URL, so it should not be cited as a live primary source. What is citable is stronger and older — Fowler's MonolithFirst and Microservice Premium from 2015, and Chris Richardson, who literally wrote the microservices pattern language, stating in 2024 that monolithic architectures remain valid and valuable for many contexts and advocating well-designed modular monoliths.

05 / TALK

What a call between modules costs when it becomes a call between machines

In one process a method call cannot half-happen. Across a network every call has a third outcome — you do not know — and every design decision downstream comes from that.

The same interaction, expressed four ways, with a failure injected. Watch what each one does to the caller.

Coupling and failure

Interactive · break something

The rule that comes out of it

Synchronous between contexts is a decision to share their availability. If the notification service is down and application submission calls it synchronously, submission is down — and no amount of retrying changes that, because the retry is also synchronous. Stage 11 gave the arithmetic: sequential calls add latency and multiply failure probability.

So the default between bounded contexts should be asynchronous, in the direction of “I have done something” rather than “please do something”. An application was submitted; whoever cares can react. That framing is choreography, and it keeps the publisher ignorant of its consumers, which is the coupling you were trying to remove.

The counter-case is real and worth stating: when the caller genuinely needs the answer to proceed — an eligibility decision, an authorization check — asynchrony is not available and you should make a synchronous call with a timeout, a fallback and a circuit breaker, exactly as Stage 07 described. Async is not a synonym for better; it is a different set of problems, and module 06 is that set.

06 / DELIVER

What a message broker actually promises

“Exactly once” is the most over-claimed phrase in distributed systems, and Kafka's version of it is real, narrow, and almost never what people think it means.

Kafka's own documentation names three semantics. At most once — messages may be lost but are never redelivered. At least once — never lost, may be redelivered. Exactly once — each message processed once and only once. The third is available and its scope is specific: it is atomic consume-transform-produce within Kafka, achieved with an idempotent producer and transactions, with consumers reading committed data and offsets committed inside the same transaction.

What it does not cover is the thing people want it for: a consumer that reads a message and writes to PostgreSQL or calls an HTTP API. Those side effects are outside the transaction, so the guarantee does not extend to them. For any consumer that touches the outside world, you are on at-least-once and your handler must be idempotent — which is Stage 07's idempotency key, arriving in a new context.

Delivery semantics

Interactive · configure, then fail

Two configuration facts that catch people

enable.idempotence defaults to true in current Kafka — and it silently switches itself off if you set a conflicting option. Kafka's own wording: idempotence is enabled by default if no conflicting configurations are set, and if conflicting configurations are set and idempotence is not explicitly enabled, idempotence is disabled. So a developer who sets acks=1 to make things faster has quietly turned off duplicate protection and will get no warning. Idempotence requires acks=all.

Ordering is per partition and nothing else. Kafka guarantees that a consumer of a given topic-partition reads that partition's events in the order they were written — and says nothing about ordering across partitions. This makes ordering a keying decision: events with the same key go to the same partition, so keying by application id gives you per-application ordering, which is almost always the ordering you actually need. Keying by something with few distinct values gives you a hot partition; keying by something unique gives you no ordering at all.

Kafka, RabbitMQ, or neither

Kafka is a distributed, partitioned, replayable log. Its distinguishing properties are retention and replay — a new consumer can read history from the beginning — and very high throughput. It is the right tool when events are facts you may want to reprocess, or when you need multiple independent consumers of the same stream.

RabbitMQ is a message broker with rich routing, per-message acknowledgement and dead-letter handling. It is the right tool for work queues where messages are commands to be executed once and then gone.

Neither is the right answer for the capstone at its current size, and it is worth saying why rather than just saying it: a broker is an additional stateful system to run, monitor, back up, upgrade and reason about, and everything it does for a single-process application can be done by a database table plus a scheduled poller. That is module 07's outbox, and it scales considerably further than people expect. Add Kafka when you have a genuine multi-consumer stream or a throughput requirement a table cannot meet — not because event-driven sounds like the mature choice.

07 / CONSISTENCY

The two-generals problem, with a database and a broker

Save the application and publish the event. Two systems, no shared transaction, and the process can die between them. Everything in this module follows from that one gap.

Stage 12's module 05 flagged this bug in passing — an email sent inside a transaction that then rolls back. Here it is as a design problem, because the general form has no clean solution and three standard mitigations.

Kill the process at each point and see what survives.

Dual write

Interactive · crash the process

Why two-phase commit is not on the list

Chris Richardson states it flatly in the saga pattern's forces — 2PC is not an option — and gives the reasons elsewhere: many databases and brokers do not support it, and distributed transactions are best avoided because of the CAP theorem. The practical version is that a coordinator holding locks across two systems turns two independent availabilities into one shared, lower one, which is the opposite of what a decomposition was for.

The outbox, and what Spring gives you

The transactional outbox writes the message into the database, in the same transaction as the business data, and a separate process relays it to the broker. One transaction, so there is no gap; the relay is at-least-once, so consumers must be idempotent. It is the standard answer and it is simple enough to implement in an afternoon.

Be precise about the Spring support, because two things get conflated. @TransactionalEventListener(phase = AFTER_COMMIT) makes an in-process listener run only after a successful commit — which fixes the rollback bug and does not survive a crash between commit and delivery. One sharp gotcha: if no transaction is running, the listener is not invoked at all, because Spring cannot honour the semantics; set fallbackExecution = true if you want it to run anyway. People assume it degrades to an ordinary listener. It does not, and the symptom is an event that silently never fires in a code path someone forgot to make transactional.

Spring Modulith's event publication registry is a genuine outbox for application events: publishing writes one row per interested listener as part of your transaction, an aspect marks each complete on success, and incomplete entries survive a crash. Two details worth knowing — republishing on restart is opt-in (spring.modulith.events.republish-outstanding-events-on-restart=true), and the registry is for in-process events, with externalisation to a broker as a separate feature. It is not a Kafka outbox by default.

// Module 03's recommended listener annotation, and what it expands to:
//   @Async + @Transactional(REQUIRES_NEW) + @TransactionalEventListener
@ApplicationModuleListener
void on(ApplicationSubmitted event) {
    notifications.notifyReviewers(event.applicationId());
}

// The registry persists one entry per listener inside the publishing transaction,
// so a crash before this method completes leaves an incomplete entry to resubmit.
spring.modulith.events.republish-outstanding-events-on-restart=true

Sagas, in the shape you will actually meet them

A saga is a sequence of local transactions, each publishing something that triggers the next, with compensating transactions to undo earlier steps when a later one fails. Choreography has no coordinator: each participant reacts to events. Orchestration has one component that tells participants what to do and collects replies.

Choreography is simpler to start and becomes very hard to reason about at around four participants, because the flow exists nowhere — you reconstruct it by reading every listener. Orchestration puts the flow in one readable place at the cost of a component that knows about everyone. My recommendation: choreography for two or three steps, orchestration the moment you cannot describe the flow from memory — and note that “compensating transaction” is a business decision, not a technical one. Undoing an award means notifying a student that they no longer have it, and nobody but the domain expert can tell you what that should say.

08 / QUERY

When the read model and the write model stop being the same shape

CQRS is a real solution to a real problem and is applied, most of the time, to systems that do not have that problem.

Fowler's definition is one sentence: you can use a different model to update information than the model you use to read it. His caveat is longer and is the part worth memorising — “You should be very cautious about using CQRS. Many information systems fit well with the notion of an information base that is updated in the same way that it's read, adding CQRS to such a system can add significant complexity.” He also insists it belongs to specific bounded contexts rather than a whole system.

Below are five read requirements from the capstone. Some want CQRS. Most want something cheaper.

Does this need CQRS

Interactive · pick a read requirement

The ladder, cheapest first

  1. A better query. Stage 08's instrument. A join and an index solve most “this screen is slow” problems and add nothing to the system.
  2. A projection in the same database — a materialised view, or a summary table maintained on write. Still one store, still one transaction, still consistent, and now fast.
  3. A read replica. Physically separate reads without changing the model at all. Buys throughput; costs replication lag and nothing else.
  4. A denormalised read store, updated by events — the search index the capstone actually needs. This is CQRS, and by the time you reach it you should be able to say precisely which query could not be served from steps 1 to 3.
  5. Event sourcing. A different thing that often arrives in the same conversation: storing the sequence of events as the source of truth rather than the current state. It is powerful, it is a large commitment, and it is not required by CQRS.

The distinction worth keeping straight: Fowler's CQRS is about separate read and write models. Richardson's microservices framing is about querying across services with a view database maintained from events. They share a name and solve different problems, and blurring them is how people end up building the second while quoting the first.

The capstone increment — and the last one

  • Five enforced modules — identity, students, scholarships, documents, notifications — as direct sub-packages, with public API in each module root and everything else internal, verified by ApplicationModules.verify() in the test suite so the build fails on a violation.
  • A generated module canvas and dependency diagram, committed, so the architecture documentation is derived from the code rather than drawn beside it.
  • Cross-module communication by application events, not by injecting one module's service into another — with @ApplicationModuleListener and the event publication registry, republishing on restart enabled.

Where your deck helps, and where it stops

Slide 125's three-layer arrangement and slide 176's DTO rationale are correct and are the foundation this stage builds on — the DTO discussion in particular is the beginning of the boundary idea, arriving one layer down. Microservices and Spring Cloud appear on slides 107 and 146 and are not developed, and there is no clean or hexagonal architecture, no domain-driven design, no modular monolith, no gateway, messaging, saga, outbox or CQRS anywhere in the 391 slides.

The generous reading, which I think is the right one: a course that teaches a working three-layer application and does not attempt distributed architecture has made a defensible choice about scope. The gap is not that it fails to teach microservices; it is that it never establishes the vocabulary for deciding, so a graduate has no way to evaluate the advice they will receive. That vocabulary is what this stage is for.

And the atlas, in one paragraph

Fifteen stages, from a single HTTP request to the question of whether to split a system apart. The thread running through all of them is the same one: find out what is actually happening before deciding what to do about it. Stage 01 decomposed a request. Stage 08 read a query plan. Stage 10 asked which test would have caught it. Stage 11 refused to optimise without a breakdown. Stage 12 built the instruments. Stage 14 measured the delivery system. And this stage applies it to the largest decision on the list, where the temptation to skip the measuring is strongest because the diagrams are so attractive.

The capstone is one application, built incrementally across all fifteen. If you have followed the increments, you have a production-shaped system with tests that catch the right things, telemetry that answers real questions, a pipeline that ships it safely and an architecture you can defend in writing. That last part is the one that transfers: the specific technologies here will change, and the discipline of measuring before deciding will not.

Experiment

Add ApplicationModules.of(Application.class).verify() as a single JUnit test to the capstone, run it, and read the failures. On any codebase that was not built with modules in mind there will be several, and they are worth reading one at a time rather than fixing in a batch — each one is a place where a boundary you believed in does not exist. Then do the harder half: pick the largest failure, and before repairing it, write two sentences on which module should own the concept. Most module violations are not import mistakes; they are a question about ownership that nobody had to answer until the test asked.

Challenge

Write the architecture decision record this stage keeps referring to — one page, for the capstone, arguing that it stays a modular monolith. It must contain: the decomposition trade-offs from module 04 with your numbers rather than the defaults; the one benefit a monolith cannot give you, named; the prerequisites from Stages 12–14 you actually have and the ones you do not; the single module you would extract first and the evidence you would need to see before extracting it; and the specific conditions under which you would revisit the decision. Then do the thing that makes it a record rather than an essay — give it to someone who disagrees, and keep their objection in the document, unanswered, if you cannot answer it. A decision record that contains only the winning argument is a press release.

Architecture connection

Every earlier stage turns out to have been an architecture stage in disguise. Stage 05's racing mutation is module 07's dual write with one machine instead of two. Stage 07's idempotency key is module 06's at-least-once consumer. Stage 08's conditional update is what makes a saga's compensation safe to retry. Stage 09's data-protection rules are why module 02's consent boundary is legal rather than aesthetic. Stage 10's fast unit test is the everyday payoff of module 01's dependency inversion, and Stage 11's sequential-latency arithmetic is precisely what module 05 charges you for a synchronous call between contexts. Stages 12 to 14 are, in Fowler's framing, not adjacent good practice but the prerequisites — which is why they came first here, and why this stage refuses to reach a verdict without them.

Where to go next

There is no Stage 16, and the honest next step is not another curriculum. It is to take the capstone and run it somewhere real, for someone real, for six months — because every stage here describes a problem that only becomes legible under actual load, actual data volume and actual users doing things you did not anticipate. Read the four books this stage cites (Evans, Vernon, Fowler's Refactoring, and Kleppmann's Designing Data-Intensive Applications) alongside that, not instead of it. And return to the hub whenever a decision comes up: the labs are meant to be re-run with your own numbers, which is the only way any of these trade-offs stop being abstract.
