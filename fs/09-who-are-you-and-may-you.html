01 / THE CHAIN

Every request walks the same corridor

Your CORS configuration is correct and the browser still reports a CORS error. Your @PreAuthorize is correct and the response is 401 rather than 403. Both answers are in the filter order.

Spring Security is a chain of servlet filters that runs before your controller exists. Your deck covers the components — AuthenticationManager, AuthenticationProvider, UserDetailsService, SecurityContextHolder — and this is the part after that: the order they run in, and what each one does to a request that fails. Almost every confusing security symptom is a filter making a decision earlier than you expected.

Four things that only make sense once you have seen the order

  1. CORS runs before authentication, but only if you register it with Spring Security. A preflight OPTIONS carries no credentials by design. If CorsFilter is not in the chain, the request falls through to the authorization filter, gets a 401, and the browser reports a CORS failure that has nothing to do with your CORS configuration. This is Stage 1's most common mystery and its cause is one line.
  2. ExceptionTranslationFilter decides between 401 and 403, and it decides by asking whether the current principal is anonymous. Same AccessDeniedException, two different statuses, depending on whether anyone was authenticated. That is exactly Stage 1's distinction, implemented.
  3. AuthorizationFilter is last. URL rules are evaluated after every authentication mechanism has had its turn, which is why an authentication failure and an authorization failure look so different in the logs.
  4. Your JWT filter goes before UsernamePasswordAuthenticationFilter — addFilterBefore(...) — because it must populate the security context before anything downstream asks who the caller is.
@Bean
SecurityFilterChain api(HttpSecurity http, JwtAuthFilter jwt) throws Exception {
    return http
        .securityMatcher("/api/**")
        .cors(Customizer.withDefaults())              // ← without this, preflights 401
        .csrf(csrf -> csrf.disable())                 // stateless bearer tokens: no CSRF surface
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(a -> a
            .requestMatchers(HttpMethod.GET, "/api/v1/scholarships/**").permitAll()
            .requestMatchers("/api/v1/admin/**").hasRole("PLATFORM_ADMIN")
            .anyRequest().authenticated())
        .addFilterBefore(jwt, UsernamePasswordAuthenticationFilter.class)
        .exceptionHandling(e -> e
            .authenticationEntryPoint(problemDetailEntryPoint())   // 401 as RFC 9457
            .accessDeniedHandler(problemDetailDeniedHandler()))    // 403 as RFC 9457
        .build();
}

Note the last block. By default Spring Security writes its own error body, which is not the problem-detail shape Stage 7 established — so the two most security-relevant responses in your API are the two that do not match your error contract. Wiring the entry point and the denied handler to produce ProblemDetail is a ten-line fix that most projects never make.

02 / PASSWORDS

Deliberately, expensively slow

Your deck explains hashing, salts and BCrypt properly. The part it leaves out is the number — and the number is the whole control.

A password hash is not a hash function used for passwords. It is a function tuned so that one verification is cheap enough for your login endpoint and expensive enough that a stolen database is not a password list. Every parameter is a dial between those two, and the only way to set it is with figures.

Interactive · set the parameters

Beyond the hash

Three login-endpoint failures that a strong hash does nothing about, and that your deck does not reach:

  • User enumeration. “No account with that email” and “Wrong password” tell an attacker which addresses are registered — and so does a response-time difference, if you skip hashing when the user does not exist. Return one message for both, and hash a dummy value on the miss so the timing matches.
  • Credential stuffing. Attackers do not guess; they replay username/password pairs from other breaches. A strong hash is irrelevant because the password is correct. The defences are rate limiting per account and per IP (module 08), a compromised-password check at registration — which your deck covers well with HaveIBeenPwnedRestApiPasswordChecker on slide 305 — and, above all, a second factor.
  • Lockout as a denial of service. Locking an account after five failures lets anyone lock any account they can name. Prefer exponential backoff and a CAPTCHA on the source, and reserve hard lockout for cases where you can notify the owner.

And the recommendation, stated plainly: use Spring Security's DelegatingPasswordEncoder, which is what PasswordEncoderFactories.createDelegatingPasswordEncoder() gives you. It stores the algorithm as a prefix — {bcrypt}$2a$12$… — so an existing database can be migrated to a stronger algorithm transparently: verify with the old one, re-hash with the new one on the next successful login. Hard-coding new BCryptPasswordEncoder() works and quietly commits you to bcrypt forever.

03 / TOKENS

The half your deck never shows: the server side

Slides 289–292 explain a JWT's three parts. Slides 293–297 have React store one. Nothing in between issues or verifies it.

A JWT is a signed statement. That is the entire idea: the server says something about the caller, signs it, and hands it over; the caller returns it; the server checks the signature and believes its own statement. The signature is the security — the payload is base64, not encryption, and anyone holding the token can read every claim in it.

Issuing one, for real

// Spring Security's OAuth2 resource server does the verification for you.
// This is the whole of the issuing side.
@Service
class TokenService {
    private final JwtEncoder encoder;

    String issueAccessToken(UserPrincipal user) {
        var now = Instant.now();
        var claims = JwtClaimsSet.builder()
            .issuer("https://api.scholarships.org")      // who minted it
            .audience(List.of("scholarships-api"))       // who may accept it
            .subject(user.publicId().toString())         // never the database id
            .issuedAt(now)
            .expiresAt(now.plus(15, ChronoUnit.MINUTES)) // the blast radius
            .id(UUID.randomUUID().toString())            // jti, for the denylist
            .claim("roles", user.roles())
            .claim("ngoId", user.ngoId())                // ownership check, module 06
            .build();
        return encoder.encode(JwtEncoderParameters.from(
            JwsHeader.with(SignatureAlgorithm.RS256).build(), claims)).getTokenValue();
    }
}

// And the verifying side is configuration, not code:
http.oauth2ResourceServer(o -> o.jwt(j -> j.decoder(jwtDecoder())));

@Bean
JwtDecoder jwtDecoder(RSAPublicKey pub) {
    var decoder = NimbusJwtDecoder.withPublicKey(pub).build();
    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
        new JwtTimestampValidator(Duration.ofSeconds(30)),   // clock skew allowance
        new JwtIssuerValidator("https://api.scholarships.org"),
        new JwtClaimValidator<List<String>>("aud", a -> a.contains("scholarships-api"))));
    return decoder;
}

RS256 or HS256?

HS256 is symmetric: one secret both signs and verifies. Simple, fast, and it means every service that must verify a token can also mint one. Fine for a single monolith that issues and consumes its own tokens.

RS256 is asymmetric: a private key signs, a public key verifies. Verifiers cannot forge. This is what you want the moment a second service, a gateway, or a partner needs to validate your tokens — and it is what every identity provider issues, so choosing it now means module 05 is a configuration change rather than a rewrite. Recommended for the capstone. Publish the public key at a JWKS endpoint, give keys an ID (kid), and rotate them by publishing the new one before you start signing with it.

Where the token lives, settled

Stage 1 recommended this and here is the reasoning in full. localStorage is readable by any script on the page, so a single XSS becomes total account takeover with a token the attacker can use from anywhere, for as long as it lives. An HttpOnly cookie is unreadable by JavaScript — but is attached automatically to every request to your origin, which is precisely the CSRF condition your deck describes at length on slides 321–334.

The arrangement that avoids both: the access token in a JavaScript variable in memory (gone on refresh, never in storage, never automatically attached), and the refresh token in an HttpOnly; Secure; SameSite=Strict cookie scoped to the refresh endpoint alone. XSS cannot read either; CSRF cannot use the refresh cookie for anything except refreshing, and SameSite=Strict blocks even that cross-site. The cost is a silent refresh on every page load, which module 04 builds.

✕Putting anything secret in the payload

It is base64, not encryption. Every claim is readable by the holder and by anyone who sees the token in a log, a proxy, a browser history entry or a screenshot. Put an identifier in it, never an email, never a phone number, never anything you would redact.

✕Long-lived access tokens “so users are not logged out”

A 30-day access token is a 30-day window for anyone who steals it, and there is no way to close it without building the revocation infrastructure you were trying to avoid. Short access token plus refresh rotation is the same user experience with a bounded blast radius — module 04.

✕Trusting alg from the token

The header is attacker-controlled. A verifier that reads alg and picks its algorithm accordingly can be told none, or told to verify an RS256 public key as an HS256 shared secret. Pin the expected algorithm in configuration. Nimbus and Spring's decoder do this correctly by default, which is a strong argument for not hand-rolling verification.

04 / LIFECYCLE

Refresh, rotation, and catching a theft

Stateless tokens cannot be revoked. So how do you log somebody out?

You do not revoke the access token — you make it so short-lived that revoking it would not matter, and you revoke the thing that mints new ones. That is the whole design, and refresh-token rotation adds a property most implementations miss: it turns a stolen token into a detectable event.

What each piece buys

  • A short access token bounds the damage of a theft to its remaining lifetime. Fifteen minutes is a common choice; the right number is however long you can tolerate a stolen credential working.
  • Rotation — every refresh invalidates the old refresh token and issues a new one — means a stolen refresh token can be used once, and the legitimate client's next refresh will present an already-used token.
  • Reuse detection turns that into a signal. A token presented twice means either the client or the attacker has a copy that should not exist, and you cannot tell which — so you revoke the whole family and force a fresh login. That is deliberately blunt, and it is correct: a false positive costs one login, a false negative costs an account.
  • A jti denylist for the access token, held in Redis with a TTL equal to the token's remaining life, closes the last gap — immediate logout, and immediate ejection when an administrator disables an account. It reintroduces a lookup per request, which is the honest cost of revocation and the reason Stage 5 said sessions in Redis remain a respectable answer.
// The refresh endpoint, with rotation and reuse detection. Note that the
// entire decision is a database update guarded by a unique constraint —
// Stage 8's lesson, applied to security.
@PostMapping("/auth/refresh")
ResponseEntity<TokenResponse> refresh(@CookieValue("rt") String presented,
                                     HttpServletResponse response) {
    var stored = refreshTokens.findByHash(sha256(presented))
        .orElseThrow(() -> new BadCredentialsException("Unknown refresh token"));

    if (stored.usedAt() != null) {                      // ← the theft signal
        refreshTokens.revokeFamily(stored.familyId());     // every session in the family
        auditLog.securityEvent("refresh_reuse", stored.userId(), stored.familyId());
        throw new BadCredentialsException("Refresh token reuse detected");
    }

    refreshTokens.markUsed(stored.id());
    var next = refreshTokens.issue(stored.userId(), stored.familyId());   // same family
    response.addHeader(HttpHeaders.SET_COOKIE, refreshCookie(next).toString());
    return ResponseEntity.ok(new TokenResponse(tokens.issueAccessToken(stored.user())));
}

Architecture connection

Notice how much of this is Stage 8 wearing a different hat. Reuse detection is a uniqueness invariant enforced by the database. Family revocation is one UPDATE. The denylist is a Redis key with a TTL, which is module 07 of that stage. Security work is rarely novel infrastructure — it is the same primitives, applied where being wrong is expensive.

05 / DELEGATE

OAuth 2.1 and OIDC: not building any of the above

Everything in modules 02 to 04 is work you could avoid entirely. When should you?

Two terms first, because they are constantly conflated. OAuth 2.0 is an authorization framework — it lets an application obtain limited access to a resource on a user's behalf. OpenID Connect is a thin identity layer on top of it that adds an id_token: a JWT that says who the user is. If you want to know who someone is, you want OIDC; OAuth alone was never designed to answer that, and using it as if it were is a well-documented class of vulnerability.

What OAuth 2.1 removed, and why it matters to you

  • The implicit flow is gone. It returned the access token in the URL fragment — into browser history, into Referer headers, into anything watching the address bar. PKCE makes the authorization code safe to use in a public client, so implicit has no remaining purpose.
  • The resource owner password credentials grant is gone. Sending a user's password through your application to the identity provider defeats the entire point of federated identity, and it makes multi-factor authentication impossible. If a tutorial shows you this, it predates 2021.
  • PKCE is required for every public client, not just mobile. A single-page application cannot keep a client secret, so proof of possession of a one-time verifier is what stops an intercepted code from being redeemed by somebody else.

Build or delegate — the decision

Build it yourselfDelegate to an IdP
You own Registration, hashing, reset flows, lockout, MFA, session revocation, audit, breach response. A redirect, a token validation, and a user record keyed by the provider's subject claim.
Good when Identity is part of the product; you need full control of the sign-up experience; there is no external identity your users already have; or a compliance regime forbids the alternative. Users already have an organisational identity — which is exactly true for school staff and NGO reviewers on Microsoft Entra ID. Also when you want MFA, conditional access and offboarding to be someone else's problem.
The hidden cost Everything above, forever, including the parts you have not thought of. Password reset alone is a security-critical flow most teams get subtly wrong. An availability dependency, a per-user price, and a mapping problem when the same human has two identities. Offboarding becomes automatic, which is a benefit and a surprise.

The recommendation for the capstone: both, deliberately. Students and guardians authenticate with a local account, because many will not have an organisational identity and the sign-up experience is part of the product. School staff, NGO reviewers and platform administrators authenticate through Microsoft Entra ID, because they already have work identities, because their access must be revoked the day they leave, and because the privileged roles are exactly the ones that should have MFA you did not have to build. Spring Security supports both in one filter chain, and Stage 14 will point the second at Azure.

06 / AUTHORIZATION

The role check that passes and the breach that follows

A reviewer at NGO 46 requests application 8891, which belongs to NGO 45. Every role check passes. What stops them?

Your deck covers authorities and roles thoroughly — hasRole, hasAuthority, access() with SpEL, the ROLE_ prefix. All of that is function-level authorization: may this kind of user call this kind of endpoint. It is necessary and it is the easy half.

The half that produces breaches is object-level authorization: may this specific user act on this specific record. OWASP ranks broken object-level authorization first in its API security list, and the reason it is so common is visible in the tester below — the request looks completely legitimate at every layer except the one nobody wrote.

Where the check has to live

    
Not in the controller, and not in the front end. Stage 4 already said a route guard is a user-experience control; this is the other half of that sentence. The check belongs at the service layer, on the method that loads or mutates the record, because that is the one place every caller must pass through — the REST controller, a GraphQL resolver added next year, a batch job, an admin tool.

    
// Method security, enabled once:
@EnableMethodSecurity
class SecurityConfig { … }

// ✗ Function-level only. The role is right. The record may not be.
@PreAuthorize("hasRole('NGO_REVIEWER')")
Application forReview(long id) { return repository.findById(id).orElseThrow(); }

// ✓ Function level AND object level, in one expression.
@PreAuthorize("hasRole('NGO_REVIEWER') and @acl.canReview(#id, authentication)")
Application forReview(long id) { return repository.findById(id).orElseThrow(); }

// ✓✓ Better still where it fits: make the query itself unable to return
//    another NGO's row. No check to forget, and it costs nothing.
@Query("select a from Application a where a.id = :id and a.ngo.id = :ngoId")
Optional<Application> findForNgo(@Param("id") long id, @Param("ngoId") long ngoId);

    
That last form deserves emphasis. A filter that lives in the WHERE clause cannot be bypassed by a code path that forgot to call the checker, and it degrades to “not found” rather than “forbidden”, which is frequently the response you want anyway. For a genuinely multi-tenant system, PostgreSQL's row-level security can enforce the same thing at the database, so even a raw SQL console is constrained — that is heavier machinery, and it is the right answer when the tenants are separate organisations whose data must never mix.


    
403 or 404?

    
A deliberate choice, per resource. 403 says “this exists and you may not have it”, which is honest and leaks the existence of the record. 404 says nothing, at the cost of a slightly confusing experience for a legitimate user who genuinely lost access. For the capstone: 404 for anything belonging to another organisation — a reviewer must not be able to enumerate other NGOs' applications by watching status codes — and 403 for operations the user is simply not permitted, where the record's existence is not itself a secret. Write the rule down; the inconsistent version is worse than either.

Why React is safe by default, and the four ways out of that

    
React escapes every value interpolated into JSX, which is why the deck's claim on slide 27 that JSX “prevents injection” is broadly true. It is not unconditionally true, and the exceptions are worth memorising because each is a real pattern people reach for:

    
    
      
  1. dangerouslySetInnerHTML — the name is the documentation. If the content is user-supplied, it must go through a sanitiser such as DOMPurify first, and the sanitiser must run on the same content that gets rendered.
    2. 
      
  2. A URL in href or src — React escapes the text, not the scheme. javascript:alert(1) in a user's “personal website” field is a working XSS. Validate the scheme against an allowlist of https: and mailto:.
    3. 
      
  3. Spreading user data into props — <div {...userSuppliedProps}> can set event handlers.
    4. 
      
  4. Rendering user content as markdown without disabling raw HTML, which is the same hole as the first item with an extra library in front of it.
    5. 
    

    
And the defence that survives all four: a Content Security Policy. Module 08 turns it on. A strict CSP with no unsafe-inline means an injected <script> does not execute even when your escaping failed, which is the definition of defence in depth.


    
SQL injection through the door Stage 7 opened

    
Parameter binding makes injection structurally impossible, and Spring Data uses it everywhere by default — which is why this is rarer than it used to be, and why the remaining cases are all in the same few places. The one worth naming again: a sort parameter cannot be bound. Column names are structure, not data, so ORDER BY " + sortColumn is the one place a modern JPA application still concatenates user input into SQL. Stage 7's whitelist is not a tidiness measure; it is the injection defence.

Rate limiting, briefly

    
Stage 8 built the mechanism with Redis; the security question is where to apply it. Three tiers, and you want all three: per IP at the edge (Azure Front Door, a WAF) to shed volumetric attacks before they cost you a thread; per account on authentication endpoints with exponential backoff, which is the credential-stuffing defence; and per API key or tenant on write endpoints, which is what stops one partner's runaway loop from degrading everyone. Return 429 with Retry-After in Stage 7's problem-detail shape, and remember that a request you rejected inside your application still consumed a thread — which is why the outermost tier matters most.


    
Secrets

    
The rule is short: a secret must never be in the repository, in an image, in a log, in an error message, or in a configuration file that ships with the application. Stage 6's property precedence is the mechanism — environment variables beat every file, which is exactly how a platform injects them. Stage 14 replaces those with Azure Key Vault and a managed identity, so the application authenticates as itself and never holds a credential to fetch its credentials.

    
Two habits worth forming now. Scan for committed secrets in CI — the failure mode is a key pushed to a public repository and found by an automated scanner within minutes, and detection after the fact is the difference between a rotation and an incident. And make rotation routine rather than exceptional: a system where changing a database password requires a deploy and a maintenance window is a system where the password never changes.


    
The checklist that catches what a stage cannot

    
The OWASP Top 10 and its API companion are the right reference precisely because they are ranked by what actually goes wrong rather than by what is interesting. Work through them against the capstone once, and note how much of this stage they cover: broken access control is module 06, cryptographic failures are 02 and 03, injection is 07, insecure design and security misconfiguration are 08, identification and authentication failures are 02 through 05. The two neither this stage nor your deck addresses — vulnerable and outdated components and security logging and monitoring failures — belong to Stage 14 and Stage 12 respectively, and are worth flagging now so they do not fall between the two.
