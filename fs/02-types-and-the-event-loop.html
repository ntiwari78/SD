Types and the Event Loop

You already know how to program. What you need from JavaScript is its two genuinely unusual ideas — a single thread with a queue, and objects whose shape is their type — and what a type system built on top of that can and cannot promise you. This is the stage your course deck declares a prerequisite and never teaches.

01 / EXECUTION

One thread, two queues

Why does a setTimeout(fn, 0) run after a promise that resolved later than it was scheduled?

Almost every JavaScript surprise you will meet in React comes from one fact: there is exactly one thread, and it does not interleave. Your function runs to completion. Nothing — not a timer, not a network response, not a click — can interrupt it mid-statement. Everything that “happens later” is a callback sitting in a queue, waiting for your code to get out of the way.

What makes this non-obvious is that there are two queues with different priorities, and the difference between them decides the order of your logs, the timing of your renders, and whether your UI freezes.

Call stack

What is executing right now. Synchronous, one frame at a time. While anything is on it, nothing else in the page runs — no timer, no paint, no click handler.

Microtask queue

Promise callbacks, await continuations, queueMicrotask. Drained completely the moment the stack empties — and if a microtask queues another microtask, that one runs too, before anything else gets a turn.

Macrotask queue

setTimeout, setInterval, I/O, DOM events. One per loop turn, and only after the microtask queue is empty. Rendering happens around these, never during your code.

Under the hood

One turn of the loop is, roughly: run the current task to completion → drain the entire microtask queue → let the browser render if it wants to → take the next macrotask. Two consequences follow, and both matter more in React than anywhere else.

Microtasks can starve everything. A promise chain that keeps queueing another promise never yields. Timers never fire, clicks never dispatch, the page never paints. It looks exactly like an infinite loop, because functionally it is one.

Your synchronous code blocks the paint. Set some state, then run 300 ms of synchronous work in the same handler, and the user sees nothing until both are done — React's update is queued, and the browser cannot paint while your function is on the stack. This is precisely what Interaction to Next Paint measures, and why the fix is to break the work up or move it to a worker, never to “optimise the render”.

Architecture connection

Stage 1 showed you where the milliseconds go across the network. This is the other half: where they go inside the browser. Parse + boot React and React render + paint in that waterfall were both a single thread doing synchronous work, and every one of them blocked the user's next frame. Stage 11 gives you the instruments; this is the mechanism.

Experiment

Run the Microtask starvation program and watch the timer callback sit in the macrotask queue while microtasks keep jumping the line. Then change the mental model: replace Promise.resolve().then(loop) with setTimeout(loop, 0). The work still happens — but now the browser gets a turn between each iteration, and the page stays alive. That one substitution is the whole technique behind chunking expensive work.

02 / SCOPE

Closures, and what a function actually captured

Your useEffect logs a count of 0 forever, even though the counter is clearly at 7. Where is the 0 coming from?

A closure is not a JavaScript curiosity. It is the single mechanism behind every custom hook you will write, every event handler that “remembers” something, and the most-reported bug in React — the stale closure. A function does not capture variables by name at call time; it captures the environment record it was created in, and holds it alive for as long as the function is reachable.

The classic demonstration is a loop, and it is worth watching rather than reading, because the difference between var and let here is not stylistic — they create a different number of environments.

Closure inspector

Interactive · environments

The React version of the same bug

This is not a loop problem. It is a “the function was created in a render that has since been replaced” problem, and it shows up like this:

// Broken: the interval callback closed over count from the first render,
// where count was 0. It will log 0 forever.
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []);                       // [] says "never recreate me" — including my closure

// Fix 1: depend on what you close over. Honest, and usually right.
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, [count]);

// Fix 2: don't close over it at all — read the latest value from the updater.
setCount(c => c + 1);         // c is always current; no capture involved

The dependency array is not bureaucracy. It is a declaration of which environment this function is allowed to remember, and the lint rule that complains about it is almost always right.

What you should be fluent in, and why

  • const by default, let when you reassign, var never. var is function-scoped and hoisted; let/const are block-scoped with a temporal dead zone that turns “used before defined” into an error instead of undefined.
  • Arrow functions have no this of their own. They inherit it lexically, which is exactly what you want in a callback and exactly wrong in an object method that needs the receiver.
  • Closures keep memory alive. A handler that captures a large object and is never removed is a leak. In React, that is a missing cleanup function; in a plain page, a missing removeEventListener.
✕Silencing the exhaustive-deps lint rule to “fix” an infinite loop

The loop is telling you a dependency is a new object on every render — an inline object, array or function. The fix is to stabilise it (useCallback, useMemo, or hoisting it out of the component), or to restructure so the effect does not need it. Removing it from the array does not remove the dependency; it just hides it and gives you a stale closure instead of a loop.

✕Assuming a captured variable updates because the variable updated

Each render creates new bindings. A function created in render #1 sees render #1's bindings forever. This is not a flaw — it is what makes React's model coherent, because a render is meant to be a pure snapshot. Once you accept that, stale-closure bugs stop being mysterious.

Ten expressions worth being certain about

You know what these probably do. In production, “probably” is where the bug lives.

Modern JavaScript's ergonomics — destructuring, spread, optional chaining, nullish coalescing — are what make React code readable. Each also has an edge that produces a bug you will not spot in review because the code looks correct.

Predict the result before you open each one. The ones you get wrong are the ones worth remembering.

On modules, briefly

Prefer named exports. A default export can be imported under any name, so a rename never propagates and your codebase quietly accumulates three names for one component. Named exports also give bundlers a reliable graph for tree-shaking. ES module bindings are live — importing a let and watching it change is legal, and a source of confusion; export functions and constants, not mutable state.

04 / CONCURRENCY

The await in your loop is costing you seconds

Twelve independent API calls, 90 ms each. How long should that take — and how long does your code actually take?

A promise is a value that will exist later; await is “suspend this function until it does, and let everything else run meanwhile”. That second half is the part people forget. Awaiting inside a loop does not make your program slow because awaiting is slow — it makes it slow because you have serialised work that had no reason to be sequential.

This is the code-level version of the round-trip lesson from Stage 1. Same arithmetic, different layer.

Concurrency timeline

Interactive · timeline

The four shapes, and when each is correct

// Sequential — correct only when call N+1 genuinely needs call N's result.
for (const id of ids) results.push(await fetchStudent(id));

// Parallel — the default for independent work. Rejects on the first failure,
// and the others keep running; you just stop hearing about them.
const results = await Promise.all(ids.map(fetchStudent));

// Every outcome, never rejects. Use when partial success is meaningful —
// a dashboard where one dead widget must not blank the page.
const settled = await Promise.allSettled(ids.map(fetchStudent));
const ok = settled.filter(r => r.status === "fulfilled").map(r => r.value);

// Bounded concurrency — because 500 parallel requests will exhaust the
// browser's connection pool, your gateway's rate limit, or Hikari's pool.
async function pool(items, limit, fn) {
  const out = [], running = new Set();
  for (const it of items) {
    const p = fn(it).finally(() => running.delete(p));
    out.push(p); running.add(p);
    if (running.size >= limit) await Promise.race(running);
  }
  return Promise.all(out);
}

Two things about promises that are not obvious

  • A promise starts running when it is created, not when it is awaited. ids.map(fetchStudent) has already fired every request by the time Promise.all sees the array. That is why the parallel version works at all — and why storing promises in a variable “for later” means the work already happened.
  • An unhandled rejection is not a caught error. With Promise.all, the losing promises still reject; if nothing attaches a handler, you get an unhandled rejection warning and, in Node, a process exit. allSettled exists partly to avoid this.

Experiment

Set 16 requests at 220 ms and compare await in a loop with Promise.all. Then ask the harder question: would you actually ship Promise.all here? Sixteen simultaneous requests against one Spring Boot instance with a ten-connection Hikari pool is a self-inflicted outage. The bounded pool is usually the right production answer, and the timeline shows you what it costs.

05 / FAILURE

Where an error goes when nobody catches it

try/catch around the call, and the error still crashed the page. How?

JavaScript has three distinct failure channels and they do not connect to each other automatically. Knowing which one you are in tells you where the catch has to be.

  1. Synchronous throw — unwinds the stack to the nearest enclosing try. Ordinary and well-behaved.
  2. Rejected promise — does not unwind anything. It sits in the promise, waiting for a .catch or an await inside a try. A try/catch around a call you forgot to await catches nothing, because the function returned successfully — it returned a promise that later rejected.
  3. Callback error — a throw inside a setTimeout or an event listener happens on a completely fresh stack, long after your try block finished. Nothing you wrote is in scope to catch it.
// Catches nothing. save() returns a promise; the throw happens later.
try { save(application); } catch (e) { toast(e); }

// Catches. await connects the rejection back to this stack.
try { await save(application); } catch (e) { toast(e); }

// Also catches, without making the caller async.
save(application).catch(toast);

// Catches nothing, in any language you write it in.
try { setTimeout(() => { throw new Error("boom"); }, 0); } catch (e) { }

What to actually throw

You can throw any value, which is why catch (e) gives you unknown in TypeScript rather than Error. Always throw an Error subclass — you get a stack trace, and instanceof becomes a usable dispatch mechanism. For an API client, model the server's problem-detail response as a class, so that every layer above can ask precise questions:

export class ApiError extends Error {
  constructor(
    readonly status: number,
    readonly problem: ProblemDetail,   // RFC 9457 body from Spring Boot
  ) {
    super(problem.title ?? `HTTP ${status}`);
    this.name = "ApiError";
  }
  get isAuth() { return this.status === 401; }
  get isForbidden() { return this.status === 403; }
}

// Now the React layer can branch on meaning, not on string matching:
if (err instanceof ApiError && err.isAuth) refreshTokenAndRetry();

That 401 versus 403 distinction is the one from Stage 1, and this is where it becomes code. A 401 means refresh and retry; a 403 means stop. A client that retries on 403 loops forever.

Architecture connection

Every error your React app can show a user originates in one of four places: the network never reached the server, Spring Security rejected the request, your service threw, or the browser threw. Stage 7 gives all four a single wire format (Problem Details), Stage 9 makes the auth cases precise, and Stage 12 makes them traceable back to the exact request. The class above is the seam where those meet the UI.

06 / TYPES

What a type system is actually for

You have shipped large systems without TypeScript. What does it buy that discipline and tests do not?

The wrong answer is “it catches typos”. The useful answer is that a type is a machine-checked claim about the whole program, enforced at every call site including the ones you have not written yet. A test proves one path works; a type proves an entire class of paths cannot be written. Rename a field on a DTO and the compiler hands you the complete list of everything that must change — which is the difference between refactoring and rewriting.

Structural, not nominal — and that is not the Java model

Coming from Java, this is the adjustment worth making explicitly. In Java, a class implements an interface because you declared that it does. In TypeScript, a value satisfies a type because its shape matches. There is no declaration and no inheritance involved:

interface Awardable { id: number; amount: number }

function disburse(a: Awardable) { /* … */ }

const grant = { id: 7, amount: 50_000, currency: "INR" };
disburse(grant);   // ✓ legal. grant was never declared Awardable —
                   //   it simply has the required members.

Two things follow. First, you almost never need adapter classes to make one library's type fit another's. Second, the compiler will not stop you passing an object with extra fields — with one deliberate exception, excess property checking, which fires only on object literals assigned directly:

disburse({ id: 7, amount: 50_000, currency: "INR" });
// ✗ Object literal may only specify known properties.
//   TypeScript assumes a literal with an unexpected key is a typo,
//   not a design. Assign it to a variable first and it compiles.

Infer aggressively, annotate at the boundaries

The idiom that separates pleasant TypeScript from noisy TypeScript: annotate function parameters, return types on exported functions, and anything crossing a module boundary. Let inference do everything else. Annotating every local variable adds no safety and doubles the diff on every change.

// Noise — the type is already known and now must be maintained twice.
const names: string[] = students.map((s: Student): string => s.name);

// Same guarantees, nothing to keep in sync.
const names = students.map(s => s.name);

interface or type?

Practically: interface for object shapes you expect others to extend or that model a domain entity; type for unions, intersections, mapped and conditional types, and function signatures — things interface cannot express. Interfaces also merge across declarations, which is what makes library augmentation possible and what makes accidental merging a real if rare hazard. Team consistency matters more than the choice.

The one rule that decides whether TypeScript is worth it

Turn on strict on day one, and treat any as a bug. any is not “a type I have not decided yet” — it is a hole through which type checking stops for everything downstream of it. One any at your API boundary silently un-types your entire data layer, and you get the compile times of TypeScript with the guarantees of JavaScript. When you genuinely do not know a shape, the honest annotation is unknown, which forces you to narrow before use. That is the whole difference: any disables the checker, unknown defers to it.

07 / NARROWING

Unions, and making illegal states unrepresentable

Four booleans give you sixteen states. How many of them are real?

Here is the highest-value idea in this entire stage, and it costs nothing to adopt. Most React components model async data like this:

interface State {
  loading: boolean;
  error: string | null;
  data: Scholarship[] | null;
}

That is eight combinations, of which three are meaningful. The other five — loading and error, data and error, nothing at all — are states your rendering code must nonetheless handle, and the bug you eventually ship is the one where a stale error renders next to fresh data. A discriminated union removes them from the language:

type Result =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "error"; error: ApiError }
  | { status: "ready"; data: Scholarship[] };

Now there are exactly four states, error exists only when there is an error, and data exists only when there is data. Click through the walker to see what the compiler knows at each line.

How the compiler narrows

  • typeof for primitives, Array.isArray, instanceof for classes — including your ApiError.
  • Literal comparison on a discriminant — if (r.status === "ready"). This is why the discriminant must be a literal type, and why widening it to string silently destroys every narrowing in the file.
  • in — if ("error" in r), for unions without a shared tag.
  • User-defined type guards — function isReady(r: Result): r is Extract<Result, {status:"ready"}>. Note that these are assertions: the compiler believes you. A wrong guard is a silent lie, which is exactly the argument for module 09.
  • Exhaustiveness via never — the trick below turns “someone added a case and forgot a branch” from a runtime bug into a compile error, which is the entire point of doing this.
function render(r: Result) {
  switch (r.status) {
    case "idle":    return <Empty />;
    case "loading": return <Skeleton />;
    case "error":   return <ErrorPanel problem={r.error.problem} />;
    case "ready":   return <Table rows={r.data} />;
    default: {
      const _exhaustive: never = r;   // add a 5th status → this line fails to compile
      return _exhaustive;
    }
  }
}

Intersections, and where they belong

Unions are “one of”; intersections (A & B) are “both at once”. Intersections earn their place in composition — type Props = ButtonHTMLAttributes<HTMLButtonElement> & { variant: "primary" | "ghost" } — and become a smell when used to bolt optional fields onto an entity, which is usually a union wearing a disguise.

Then write the transition function and let never prove you covered every case.

Generics and utility types

Generics in Java are erased at runtime. What are TypeScript's, and what can you do with them that you cannot do in Java?

TypeScript's generics are erased too — they exist only at compile time. But because the type system is structural and has mapped and conditional types, generics are used less for containers and more for describing relationships between types. Hover any call below to see what the compiler infers.

Two techniques worth stealing immediately

satisfies checks a value against a type without widening it. You get the validation of an annotation and the precision of inference — the difference between a config object whose keys are string and one whose keys the compiler knows exactly:

const routes = {
  students:    "/students",
  scholarships:"/scholarships",
} satisfies Record<string, `/${string}`>;

routes.students;   // type: "/students"  ← literal preserved
// With  : Record<string, string>  instead, it would be  string
//   and  routes.typo  would compile.

Deriving types from a source of truth rather than declaring them twice. A hand-written interface next to a Zod schema will drift within a sprint; a derived one cannot:

type Application = z.infer<typeof applicationSchema>;
type Status     = Application["status"];          // indexed access
type ListRow    = Pick<Application, "id" | "studentName" | "status">;

The same discipline applies across the network boundary: generate your API types from the OpenAPI document Spring Boot already publishes (Stage 7), rather than typing them by hand on the client. A backend field rename then becomes a red build instead of a production undefined.

09 / BOUNDARY

Your types stop at the network

const data = await res.json() as Scholarship[] — what exactly did you just verify?

Nothing. Not one thing. as is an instruction to the compiler to stop asking, and res.json() returns any, which means the object graph flowing through your entire application has been typed by an act of faith. Every type in your React app is a compile-time fiction about data that arrives at runtime from another process, over a network, from a Spring Boot version that may have been deployed twenty minutes ago.

So there is exactly one rule, and it is the deliverable of this whole stage: parse at the boundary, then trust the types inside it. Validate once, where the data enters — and from that point on, the compiler's guarantees are real, because something checked them.

What this looks like in the capstone

// One schema. The TypeScript type is derived from it, so they cannot drift.
export const applicationSchema = z.object({
  id:            z.number().int().positive(),
  studentName:   z.string().min(2),
  cohort:        z.number().int().min(2000).max(2100),
  email:         z.string().email(),
  guardianEmail: z.string().email().optional(),
  status:        z.enum(["DRAFT","SUBMITTED","UNDER_REVIEW","AWARDED","REJECTED"]),
  documents:     z.array(z.object({ type: z.string(), url: z.string().url() })),
  submittedAt:   z.string().datetime().nullable(),
});

export type Application = z.infer<typeof applicationSchema>;

// One place where unknown becomes known.
export async function apiGet<T>(url: string, schema: z.ZodType<T>): Promise<T> {
  const res = await fetch(url, { headers: authHeaders() });
  if (!res.ok) throw new ApiError(res.status, await res.json());
  const raw: unknown = await res.json();          // unknown, not any
  const parsed = schema.safeParse(raw);
  if (!parsed.success) {
    reportSchemaDrift(url, parsed.error);            // this is a monitoring event
    throw new Error(`Contract violation from ${url}`);
  }
  return parsed.data;                              // genuinely typed from here on
}

Note reportSchemaDrift. A validation failure at the boundary is not a user error and it is not really a client bug — it is the two sides of a contract having disagreed, and it should page someone. This is the cheapest contract test you will ever deploy, and it runs in production against real traffic.

Where else the boundary is

The API is the obvious one. The others catch people out: localStorage (written by a version of your app that no longer exists), URL query parameters (typed by whoever pasted the link), environment variables (all strings, all optional, all capable of taking production down at boot), form input, third-party webhooks, and anything crossing postMessage. Each deserves a schema. Environment variables in particular are worth validating at startup so a missing key fails the deploy rather than the checkout page.

✕Writing the interface by hand next to the schema

Two sources of truth, and only one is enforced. They agree today. Derive the type with z.infer and the question cannot arise.

✕Validating in every component instead of at the boundary

Defensive checks scattered through the render tree are the symptom of not trusting your own types — and they never cover everything. Parse once at the edge; inside, use the types with confidence. If you cannot, the edge is in the wrong place.

✕Using as to make a type error go away

as does not convert anything at runtime. It suppresses the compiler's objection, which was the only thing standing between you and the bug. The legitimate uses are narrow: as const, and asserting a type the compiler cannot possibly know but you have just proven — after a validation, not before.

Architecture connection

This module is the client half of a contract; Stage 7 builds the server half. Spring Boot publishes an OpenAPI document, Jakarta Bean Validation enforces the same constraints on the way in, and RFC 9457 problem details describe failures in one shape. When both halves are generated from one contract, a breaking change surfaces in CI (Stage 14) instead of in a user's browser. Everything after this stage assumes the boundary is guarded.
