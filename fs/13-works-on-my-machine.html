Works On My Machine

Docker appears on your deck's agenda slide, is named once more in passing, and never appears again — no Dockerfile, no image, no compose file, nothing. This is the whole subject: what an image actually is, why the order of four lines decides your build time, how a system of five containers comes up in the right order, where configuration and secrets live, and what happens between the moment you push and the moment traffic arrives.

01 / LAYERS

Four lines in the wrong order cost you three minutes a build

An image is not a machine. It is a stack of read-only filesystem diffs, and almost everything that matters about building one follows from that single fact.

Each instruction in a Dockerfile produces a layer: a diff against the layer below, stored and addressed by content. Stacking them with a union filesystem gives you the container's root, and a running container adds one thin writable layer on top which is discarded when it exits.

Three consequences do all the work. Layers are cached, so an instruction is skipped if its inputs are unchanged. The cache is positional, so a miss invalidates everything after it. And layers are shared, so a layer you already pushed is never pushed again. Which means: put the things that rarely change at the bottom, and the things that change on every commit at the top.

The Spring Boot part, which changed recently and matters

A Spring Boot fat JAR is one file containing your ten kilobytes of code and your ninety megabytes of dependencies. Copied as a single COPY app.jar, every commit invalidates all ninety megabytes. The fix is to unpack it into layers ordered by how often each changes.

The mechanism was renamed. Every tutorial you will find says -Djarmode=layertools; that mode is removed in Spring Boot 4.1. The current form is:

java -Djarmode=tools -jar application.jar extract --layers --destination extracted

The four default layers are unchanged, and their order is the whole point: dependencies (changes when you edit the build file), spring-boot-loader (changes with the Boot version), snapshot-dependencies, and application — your code, a few hundred kilobytes, the only layer most commits touch.

# syntax=docker/dockerfile:1
FROM bellsoft/liberica-openjre-debian:25-cds AS builder
WORKDIR /builder
COPY target/application.jar application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

FROM bellsoft/liberica-openjre-debian:25-cds
WORKDIR /application
COPY --from=builder /builder/extracted/dependencies/ ./
COPY --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder /builder/extracted/application/ ./
USER 1001
ENTRYPOINT ["java", "-jar", "application.jar"]

That is close to Spring's own reference Dockerfile, and two details in it are worth noticing. It uses BellSoft Liberica rather than Temurin — Spring's example does, and the -cds tag matters for module 03. And the extracted layout is what makes the AOT cache work at all; a fat JAR cannot use one.

Modern Dockerfile features that are stable and under-used

  • Cache mounts. RUN --mount=type=cache,target=/root/.m2 mvn package keeps the dependency cache between builds without putting it in a layer. This is the single biggest win for build time on a cold CI runner, and it is stable, not experimental.
  • Secret mounts. RUN --mount=type=secret,id=npmrc … makes a secret available during one instruction and leaves nothing in the image. Module 05 explains why ARG is not an alternative.
  • Bind mounts. --mount=type=bind,source=.,target=/src reads the build context without copying it into a layer.
  • Heredocs, COPY --link, COPY --parents and COPY --exclude are all stable in current Dockerfile syntax. Pin the frontend with # syntax=docker/dockerfile:1 and BuildKit fetches the latest 1.x before building.
  • A .dockerignore, which is the cheapest of all of these: without one, your target/, node_modules/ and .git/ are uploaded to the daemon as build context on every single build.

Two things that are already true and that people configure anyway

BuildKit is the default builder, and docker build is now an alias for docker buildx build — they are the same command, so DOCKER_BUILDKIT=1 is a no-op you can delete. And provenance attestations are generated by default at mode=min, while SBOM generation is not; --sbom=true opts in. Worth knowing before you add flags that do nothing.

02 / BASE

What you inherit by choosing a first line

The base image decides your image size, your patch cadence, your attack surface, and whether an attacker who reaches your container finds a shell waiting for them.

FROM is the highest-leverage line in the file and it is usually copied from a blog post. Below are the choices that actually exist for a Java 25 service, with real published sizes, and what each one costs you in the columns nobody puts on a comparison table.

Base image chooser

Interactive · pick a base

The size arithmetic, from published figures

A JDK image is about 150 MB compressed; the JRE variant of the same distribution is about 110 MB; the Alpine JRE is about 72 MB. So a naive single-stage build that ships the JDK is paying roughly 40 MB for a compiler it will never run, and moving to Alpine saves another 40. For comparison, nginx:alpine is about 25 MB and bare alpine is under 4.

Two corrections worth making, because the received wisdom is out of date. Temurin does publish Alpine JRE images for Java 25 — the old advice that no Alpine JRE exists is stale. And distroless has moved on: the current Java image is gcr.io/distroless/java25-debian13, not the Debian 12 / Java 21 tag most guides still cite.

What distroless actually removes, and why it matters

A distroless image contains your application, its runtime, and nothing else — no shell, no package manager, no curl, no cat. Two consequences pull in opposite directions and you should feel both. An attacker who achieves code execution has no shell to pivot with and no package manager to install one, which removes an entire stage of most intrusions. And you have no shell either: docker exec -it … sh fails, so debugging happens through logs, traces and a separately-tagged :debug variant. That trade is usually right for production and frequently wrong for the first month of a project.

Non-root is not optional, and it is one line

By default a container process runs as root — a constrained root, but root, and one kernel vulnerability or a mistakenly mounted host path away from mattering. Adding USER 1001 costs nothing and removes a class of escalation. Pair it with the runtime flags that make the container hostile to whoever gets in:

docker run \
  --user 1001:1001 \
  --read-only --tmpfs /tmp \        # nothing can be written outside /tmp
  --cap-drop=ALL \                  # drop every Linux capability, add back only what is needed
  --security-opt no-new-privileges \ # setuid binaries cannot escalate
  scholarships-api:2026.08.29

Note the tag. :latest is not a version — it is a mutable pointer that makes two deployments of "the same image" different, and makes a rollback impossible to specify. Tag with something immutable: a build number, a date, or the commit SHA. In the Dockerfile itself, Docker's guidance goes further and suggests pinning the base by digest (FROM alpine:3.21@sha256:…), which fixes the bytes exactly while still letting a scanner tell you an update exists.

Scanning, and the one flag that makes it a gate

docker scout cves is the current first-party path — it analyses an image, a directory or an SBOM. The flag that turns it from a report into a control is --exit-code, which returns non-zero when vulnerabilities are found, so a pipeline step can fail. Combine with --only-severity critical,high so the gate is about things you will actually act on.

Worth naming as the current hardened-base answer: Docker Hardened Images, minimal distroless-style images maintained by Docker with signed SBOMs and SLSA Build Level 3 provenance, with a free Community tier. Docker's own React guide now offers them alongside the official images.

03 / STARTUP

Four seconds, or eighty milliseconds

Startup time is invisible in development and decisive in production: it sets how fast you can roll out, how quickly you recover, and whether scale-to-zero is a feature or a latency bug.

A Spring Boot service on a plain JVM starts in a few seconds, and most of that is not your code — it is class loading, verification, and the JIT compiler starting from nothing. Four techniques attack that, they are not equivalent, and one of them is new enough that most material has not caught up.

Startup strategies

Interactive · pick an approach

    

  


  

    
Why the AOT cache supersedes CDS, in one paragraph

    
Class Data Sharing writes a class archive at exit and memory-maps it on the next start, which removes class loading and verification. The JVM AOT cache, from Project Leyden and available on Java 25, does that and also carries profiling and pre-resolved state, so the JIT starts warm rather than cold. Spring's documentation is explicit: it supports both, and recommends the AOT cache whenever possible. Both require the extracted layout from module 01 — with a fat JAR they have no effect at all, which is a quiet failure mode worth knowing about.

    
If you build with buildpacks, one environment variable does the whole thing: BP_JVM_AOTCACHE_ENABLED=true makes Paketo perform the training run and bake the cache into the image.


    
Native images, honestly

    
GraalVM native compilation gives startup around eighty milliseconds and a much smaller memory footprint, with no JVM in the image at all. The price is a closed world: the classpath is fixed at build time, reflection, resources, serialisation and dynamic proxies must be declared, and Spring's own documentation notes two restrictions that surprise people — @Profile and profile-specific configuration are limited, and @ConditionalOnProperty switches that change which beans exist are not supported, because the beans were decided when the binary was built. Add build times measured in minutes and a separate testing story, and this is a real architectural commitment rather than a compiler flag.

    
My recommendation for the capstone, stated plainly: JVM with the AOT cache. It gets most of the startup benefit, keeps profiles and conditional configuration working, keeps your debugging and profiling tools, and costs one training step in the build. Choose native when cold-start latency is the product — a function that runs for two hundred milliseconds and exits — and accept the constraints deliberately.


    
Buildpacks, as the other way to get here

    
mvn spring-boot:build-image produces an OCI image with no Dockerfile at all, using Cloud Native Buildpacks. The current default builder is paketobuildpacks/builder-noble-java-tiny, images run as non-root by design, and it still requires a Docker daemon. It is genuinely good: it makes layering, JRE selection, memory calculation and the AOT cache someone else's problem, and the result is usually better than a hand-written first Dockerfile.

    
The trade is control and legibility. When you need a system package installed, a specific base image for compliance, or an unusual entrypoint, you are configuring a builder rather than editing a file you can read. Start with buildpacks; move to a Dockerfile when you need something it will not give you — and note that you will need to understand layers either way, because that is what you will be debugging.

04 / COMPOSE
Five containers, and the order they come up in

  
The capstone's promise is that docker compose up brings the whole platform online on a clean machine. The distance between that and a crash loop is one word in one line.


  

    
depends_on without a condition means “start this one first”, which is almost never what you want — a PostgreSQL container starts in a hundred milliseconds and a PostgreSQL server is ready several seconds later. The API starts in the gap, fails to connect, and exits. Docker restarts it, and it does the same thing.

      interval: 10s
      start_period: 40s

  web:
    build: ./web
    depends_on:

Four things in there worth stopping on

    
    
      
  • start_period is what stops a slow-starting service being marked unhealthy while it is legitimately still starting. Failures inside the window do not count toward retries — so a forty-second Spring Boot start is fine with start_period: 40s and a restart loop without it.
    • 
      
  • Service names are hostnames. jdbc:postgresql://db:5432/… works because Compose puts every service on a network with DNS. This is also why localhost inside a container means that container, which is the second most common Compose confusion after depends_on.
    • 
      
  • Named volumes are how data survives docker compose down. Without pgdata the database is empty on every restart, which people discover after seeding it.
    • 
      
  • The condition needs a healthcheck to exist. condition: service_healthy against a service with no healthcheck block and no HEALTHCHECK in its image waits forever, because the container never reports healthy.
    • 
    


    
Compose has moved, in a way that is easy to misread

    
The current release line is Compose v5, which is described by Docker as functionally identical to v2 with an official Go SDK added — the command is still docker compose and the file format is still the Compose Specification. What has genuinely gone is the Python docker-compose v1 binary, which is no longer among the supported versions. And version: "3.9" at the top of your file is obsolete: Compose validates against the latest schema regardless and warns that the key means nothing.

    
Two additions worth knowing about. develop: watch gives you a real inner loop — sync copies changed files into the running container, rebuild triggers an image rebuild, and sync+restart does both for config changes — run with docker compose up --watch. And include lets you compose compose files, which is how you keep one file per concern rather than one four-hundred-line file.


    

      
Experiment

      
Take your capstone's compose file, remove every condition: service_healthy, and run docker compose up on a machine with a cold image cache — a fresh clone, or after docker system prune -a. The failure only appears when the database has to initialise from scratch, which is exactly the case a new team member hits on their first day and you never hit again. Then put the conditions back and confirm the ordering in the timeline above matches what you see.

05 / CONFIG
The same image, in every environment

  
If your staging image is a different image from your production image, you have not tested the thing you deployed. Which means every difference between environments has to arrive from outside the image.


  

    
This is the third of the twelve factors — store config in the environment — and it is the one with the sharpest test. Could you open-source your image right now? If not, there is a credential in it, and the same credential is in every layer cache, every registry, and every laptop that pulled it.

    
Eight pieces of configuration, five places they could live. Not all combinations are wrong, and the ones that are wrong are wrong for different reasons.

Why ARG is not a secret channel, concretely

    
A build argument feels transient — it is not baked into a layer the way ENV is — and people use it for tokens. Two things defeat that. docker history shows build arguments for the layers that used them. And BuildKit's provenance attestation at mode=max includes build-argument values, so a token passed as an ARG ends up in metadata attached to the pushed image, in a registry, for anyone with pull access.

    
The supported mechanism is a secret mount, which exists precisely for this:

  



# syntax=docker/dockerfile:1
FROM node:24-alpine AS build
WORKDIR /src
COPY package*.json ./
# The token is readable during this instruction and is in no layer afterwards.
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci
COPY . .
RUN npm run build

# Build with:  docker build --secret id=npm_token,env=NPM_TOKEN .


  

    
Runtime secrets, and an honest note about Docker's own

    
Worth being precise, because the naming misleads: Docker secrets are a Swarm feature. They are mounted at /run/secrets/<name> on an in-memory filesystem and flushed when the task stops, and they are not available to standalone containers. Compose can declare a secret from a file, which is a reasonable local-development pattern and is not a production secret store.

    
For production, the mechanism should be one the platform provides and your application never sees a file for: Azure Key Vault reached through the Secrets Store CSI driver with workload identity on AKS, Container Apps secrets and managed identity on Container Apps, or the equivalent elsewhere. The property that makes these different in kind is not encryption — it is that the application authenticates as itself rather than holding a credential that authenticates it, so there is no long-lived secret to leak or rotate.


    
The file-versus-environment question

    
Spring Boot reads configuration from many sources, and two are worth using deliberately in a container. Environment variables map onto properties through relaxed binding — SPRING_DATASOURCE_URL becomes spring.datasource.url — which is how twelve-factor config reaches a Spring application without any code. And for anything multi-line or awkward as a variable, Spring Boot reads config trees: point spring.config.import=configtree:/run/secrets/ at a directory of files whose names are property names, which is exactly the shape both Kubernetes secrets and the CSI driver produce.

    
Profiles remain useful for behaviour that genuinely differs — an in-memory mail sender locally, a real one in production — but resist encoding values in profile-specific files that get baked into the image. The rule that keeps this clean: profiles select behaviour, the environment supplies values.

06 / PROBES
The health check that takes down the fleet

  
Point your liveness probe at the database and the next database hiccup restarts every instance you have, simultaneously, while the database is already struggling.


  

    
Three probes, three different questions, and conflating them causes outages that look like infrastructure problems.

    
    
      
  • Liveness — is this process still working, or is it wedged? Failure means restart the container. It must depend on nothing outside the process.
    • 
      
  • Readiness — can this instance serve traffic right now? Failure means remove it from the load balancer, without restarting it. This is where dependency checks belong.
    • 
      
  • Startup — has it finished starting? While it is failing, the other two are suspended. This exists so a slow start does not look like a liveness failure.
    •

What Spring Boot gives you, and the sentence to remember

    
Actuator publishes two dedicated endpoints when probes are enabled: /actuator/health/liveness and /actuator/health/readiness. They are backed by two state machines — LivenessState is CORRECT or BROKEN, ReadinessState is ACCEPTING_TRAFFIC or REFUSING_TRAFFIC — and Spring's documentation is unusually blunt about the difference:

    
Liveness “should not be based on external checks (databases, Web APIs, external caches)”, because a failing external dependency would cause cascading restarts.

    
Liveness becomes CORRECT as soon as the application context has refreshed. Readiness becomes ACCEPTING_TRAFFIC after the runners have finished. You can read the current state by injecting ApplicationAvailability, listen for changes with @EventListener on AvailabilityChangeEvent, and — the useful part — publish a change yourself when your application knows something the framework does not.

  



@Component
class QueueDepthReadiness {

    private final ApplicationEventPublisher events;

    // The export queue is saturated: keep serving in-flight work, take no new traffic.
    void onQueueSaturated() {
        AvailabilityChangeEvent.publish(events, this, ReadinessState.REFUSING_TRAFFIC);
    }

    void onQueueDrained() {
        AvailabilityChangeEvent.publish(events, this, ReadinessState.ACCEPTING_TRAFFIC);
    }
}


  

    
One configuration note: Spring Boot enables the probe endpoints automatically when it detects Kubernetes, which it does by looking for *_SERVICE_HOST and *_SERVICE_PORT in the environment. Outside Kubernetes — on Container Apps, or in Compose — set management.endpoint.health.probes.enabled=true explicitly, or the paths will not exist and your probes will get 404s that look like failures.


    
Docker's own HEALTHCHECK, briefly

    
The instruction has five options — --interval, --timeout, --start-period, --start-interval, --retries — and one rule that catches people: the command must exit 0 for healthy and 1 for unhealthy, and 2 is reserved. A script that returns 2 on error is not reporting unhealthy; it is doing something undefined. Container status moves starting → healthy | unhealthy, and that status is exactly what Compose's condition: service_healthy from module 04 waits on.


    

      
A platform restriction that will shape your probes on Azure

      
Container Apps supports all three probe types, and does not support exec probes or gRPC probes, allows only one probe of each type per container, and requires integer ports. So the design is fixed for you: httpGet against /actuator/health/liveness and /actuator/health/readiness, on the port your application listens on. Worth knowing before you write a shell-script health check that cannot be used.

07 / STATIC
Why the deep link 404s

  
Your React router handles /applications/8891 perfectly. Paste that URL into a fresh tab and the server — which has never heard of it — returns 404, correctly.


  

    
A single-page application is one HTML file plus assets. Every route it knows about exists only after that file has loaded and JavaScript has run. So a first request for any path other than / reaches a web server that has no such file, and the fix is to tell the server to serve index.html for anything it cannot find — after which the router sees the URL and does its job.

The configuration, which is short enough that every line should be understood:

  



server {
    listen       8080;                     # 8080, not 80 — a non-root process cannot bind 80
    root         /usr/share/nginx/html;

    # Hashed assets: the filename changes when the content does, so cache forever.
    # Note: the `expires` directive cannot emit `immutable` — add_header is required.
    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
        try_files $uri =404;               # a missing asset is a real 404, not the app shell
    }

    # The shell is the one file that must never be cached, or users get last week's app.
    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    # Anything the router owns falls through to the shell.
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Same origin for the API removes the CORS problem from Stage 1 entirely.
    location /api/ {
        proxy_pass         http://api:8080;
        proxy_set_header   Host $host;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_set_header   traceparent $http_traceparent;   # Stage 12's context, preserved
    }
}


  

    
The two-line rule that makes deploys safe

    
The caching pair above is doing more work than it looks. Vite emits assets with a content hash in the filename, so index-a3f21c.js is immutable by construction — if the content changes, the name changes. Caching those for a year is therefore not a risk but a correctness statement. index.html is the opposite: it is the file that names the current asset filenames, so caching it means a user's browser keeps pointing at the previous deploy's JavaScript, which is either 404s or a subtly old application.

    
Get these backwards and deploys break in the most confusing available way: it works for you, because you hard-refreshed, and it is broken for anyone whose browser held the old shell.


    
The Dockerfile, and a detail Docker itself changed

  



# syntax=docker/dockerfile:1
FROM node:24-alpine AS build
WORKDIR /src
COPY package*.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build

# Docker's own React guide now uses the unprivileged image, which listens on 8080
# and runs as a non-root user with no configuration from you.
FROM nginxinc/nginx-unprivileged:stable-alpine
COPY --from=build /src/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 8080


  

    
Two decisions embedded there. The multi-stage split means Node — several hundred megabytes of it — is present for the build and absent from the shipped image, which is about 25 MB of Nginx plus your assets. And nginx-unprivileged, published by NGINX and used in Docker's own React guide, is the plain nginx image reworked to run as a non-root user: it listens on 8080, drops the user directive, and writes its PID and temp files under /tmp. It is the shortest path to a non-root front end.


    
Nginx, or Spring Boot serving the assets

    
You can put the built React output in Spring Boot's static/ directory and ship one container. It is simpler, it removes a moving part, and it gives you the same origin for free. The costs are real though: your front end now redeploys whenever the API does, static files are served by a JVM thread from the pool you sized in Stage 11, and you cannot scale or cache the two independently. For the capstone I would keep them separate, because the front end and the API have genuinely different release cadences — and would happily ship a combined image for an internal tool where they do not.

08 / ROLLOUT
The gap between “deployed” and “serving”

  
Stage 12 gave you an error budget. A deploy that drops four hundred requests spends some of it, every time, for no reason anyone chose.


  

    
A rolling update replaces instances one at a time so the service stays up. Whether it actually does depends on four settings, and the failure is quiet: a small number of dropped requests per deploy, attributed to nothing, showing up as a sawtooth in the error rate that everyone learns to ignore.

The four settings, and what each one is for

    
    
      
  • A readiness probe stops traffic reaching an instance that is still starting. Without it the orchestrator's only definition of “ready” is “the process exists”, and a Spring Boot application exists for several seconds before it can answer anything.
    • 
      
  • Surge before terminate — bring the new instance up and ready before taking the old one down, rather than after. Costs one instance's worth of capacity for the duration of the rollout, and it is the difference between reduced capacity and no capacity gap at all.
    • 
      
  • Graceful shutdown — server.shutdown=graceful in Spring Boot, with spring.lifecycle.timeout-per-shutdown-phase. On SIGTERM the server stops accepting new connections and lets in-flight requests finish. Without it, the requests being handled at that instant are simply cut.
    • 
      
  • A pre-stop delay — a few seconds between “remove from the load balancer” and “send SIGTERM”. This looks superstitious and is not: endpoint removal propagates asynchronously, so for a moment after an instance is marked terminating, some proxies are still sending it traffic. Kubernetes has a preStop sleep for exactly this.
    • 
    


    
Where to run it, on Azure

    
Azure Container Apps is Microsoft's current default recommendation for containerised microservices, and their Java guidance points Spring applications at it specifically. It is Kubernetes underneath — with KEDA for scaling, Dapr, and Envoy — without your having to operate Kubernetes: revisions with traffic splitting, scale to zero, and event-driven autoscaling on HTTP concurrency, TCP connections, or any KEDA scaler.

    
App Service remains the right answer for a straightforward web application or a traditional application server. AKS is for when you genuinely need the Kubernetes API — custom operators, complex networking, or an existing platform team.

    
One important correction, because a lot of Spring material still points there: Azure Spring Apps is retired. No new customers since March 2025 and full end of support in March 2028, with Container Apps and AKS as the documented migration targets. Do not start anything on it.

    
And one Container Apps trap worth knowing before it bites: if ingress is disabled and you set neither minReplicas nor a custom scale rule, the app scales to zero with nothing able to start it again. Scale-to-zero is a genuine cost feature for a background worker and a latency decision for an API — a cold start is a cold start, and Stage 11's numbers about startup time are what determine whether your users notice.


    

      
Challenge

      
Put a constant load on your capstone — one request a second is enough — and deploy a new version while watching the error rate. Count the failures. Then add the four settings above one at a time, redeploying between each, and count again. The number should reach zero, and the exercise is worth more than reading about it because the intermediate states are surprising: graceful shutdown alone often makes things look fine while the pre-stop gap is still dropping a handful of requests. Then connect it to Stage 12: at ten deploys a week, what fraction of your error budget was this spending?

The capstone increment

    
    
      
  • A multi-stage Dockerfile per service — extracted Spring Boot layers in dependency order, a JRE (not JDK) runtime base, USER 1001, a .dockerignore, and cache mounts on the dependency step.
    • 
      
  • The React image built and served properly — Node in the build stage only, nginx-unprivileged on 8080 in the runtime stage, SPA fallback, an /api proxy, and the caching pair the right way round.
    • 
      
  • The AOT cache wired up — a training run in the build, the cache in the image, and a before-and-after startup measurement recorded. If you use buildpacks, BP_JVM_AOTCACHE_ENABLED=true and the same measurement.
    • 
      
  • One compose.yaml that brings everything up on a clean machine — PostgreSQL, Redis, the API, the front end and an OTLP collector, with healthchecks on the data services, condition: service_healthy on their dependents, named volumes, and Flyway migrations applied on start. Test it by pruning your images and running it.
    • 
      
  • Not one credential in any image. Environment for values, secret mounts for build-time tokens, a config tree or platform secrets at runtime, and the open-source test applied honestly to every layer.
    • 
      
  • Probes that mean different things — /actuator/health/liveness checking nothing external, /actuator/health/readiness checking what the instance needs to serve, a startup probe sized to your measured start time, and management.endpoint.health.probes.enabled=true because you are not on Kubernetes locally.
    • 
      
  • An image tagged immutably, scanned with docker scout cves --exit-code --only-severity critical,high as a pipeline gate, with provenance attached.
    • 
      
  • A zero-downtime rollout — readiness gate, surge before terminate, server.shutdown=graceful, and a pre-stop delay — verified by deploying under load and counting the failures, which should be none.

Where your deck helps, and where it stops

    
It does not help here at all. Docker is on the agenda slide and is mentioned once more in passing; there is no Dockerfile, no image, no compose file, no discussion of layers or configuration or deployment anywhere in the 391 slides. This is the largest gap after testing, and it is a consequential one, because everything the deck does teach — the application, the database, the security configuration — has to reach a server somehow, and the mechanism by which it does is where a surprising share of production problems live.

    
The one place the deck's material connects is profiles: its treatment of application-{profile}.yml is correct and is exactly the mechanism module 05 asks you to use carefully. Profiles select behaviour; the environment supplies values. Read that section with this module in mind and the two fit together.
