The Container and the Language

Two things stand between you and productive Spring Boot. The first is that Java in 2026 reads almost nothing like the Java most tutorials were written for. The second is that the container is a lifecycle with a definite order — and once you can trace it, half of Spring's error messages stop being mysterious.

Java, as it actually reads now

Your deck lists Java as a prerequisite and teaches none of it. Most Java material online predates half of what you should be writing.

You already program, so this is not a language tutorial. It is a list of the constructs that changed what idiomatic backend Java looks like, because reading a 2018 Spring tutorial and writing 2018 Java is the most common way an experienced engineer produces code that looks dated to a Java team.

The version question, settled

Java 25 is the current long-term-support release, and Spring Boot 4.1 supports 17 through 26. Nothing above requires the newest release — records and text blocks landed in 16 and 15, sealed types and pattern matching for switch are in 21, and virtual threads went final in 21. If your organisation is on 21, every construct here is available to you. If it is on 17, everything except pattern matching for switch and virtual threads is.

The one genuinely new habit worth adopting deliberately: immutability by default. Records, List.of, final fields and constructor injection all push the same way, and the payoff arrives in Stage 15 when you start reasoning about concurrency and shared state. A mutable entity passed between threads is a bug you have not found yet.

02 / MODELLING

Sealed types: the compiler as a reviewer

Stage 2 made illegal states unrepresentable in TypeScript. Java can do the same thing, and enforce it harder.

A sealed interface declares a closed set of implementations. The compiler knows the complete list, which means a switch over it can be checked for exhaustiveness — and a new implementation added six months from now breaks the build at every place that failed to handle it. That is the same guarantee as Stage 2's never trick, except that here it is a language feature rather than a clever assignment.

This matters most for exactly the thing the capstone is full of: state machines with per-state data.

Where each modelling tool belongs

  • record — a value defined entirely by its data. DTOs, coordinates, money, query criteria, events. Immutable, with equals, hashCode and toString generated correctly. Add a compact constructor for validation and the invariant holds for every instance ever created.
  • enum — a fixed set of constants that may carry behaviour. Java enums are full classes: give them fields, methods, and per-constant overrides rather than writing a switch over them somewhere else.
  • sealed interface — a closed set of shapes, where each alternative carries different data. This is what an enum cannot do and what you want for application states, command types, and the result of an operation that can fail in several distinct ways.
  • interface (unsealed) — a genuine extension point where third parties or future code should be able to add implementations you do not know about. If you cannot name the implementations you want to allow, do not seal it.
  • abstract class — increasingly rare. Reach for it only when you need shared mutable state or a protected constructor; default methods on interfaces cover most of what abstract classes used to be for.

The one caution: sealing is a commitment. A sealed hierarchy in your own domain is a gift to your future self; a sealed type in a published library is a promise that nobody will ever extend it, and that promise is harder to keep than it looks.

Challenge

You modelled the application lifecycle as a TypeScript discriminated union in Stage 2. Model it again as a sealed interface with records, so that rejectionReason is unreachable on an awarded application and awardedAmount is unreachable on a draft. Then write the transition method and confirm that removing one case is a compile error rather than a runtime surprise. Compare the two versions: same idea, two type systems, and one of them checks it at build time on the server.

03 / STREAMS

Streams are lazy, and that is the whole point

Eight applications, four pipeline stages. How many elements does filter actually see?

The common mental model of a stream — “it filters the list, then maps the result, then collects” — is wrong in a way that matters. A stream does not process the collection stage by stage. It pulls one element at a time all the way through the pipeline, which is why a short-circuiting terminal operation can finish after examining three of eight elements, and why an infinite stream is a sensible thing to write.

When a stream is the wrong tool

Streams are not universally better than loops, and treating them as a style rule produces some genuinely awful code. Use a plain for loop when you need to break out early with complex conditions, mutate an index, modify the source, or throw a checked exception from the body — that last one is the single most common reason a stream turns into an unreadable knot of wrapper exceptions. Use a stream when the pipeline reads as a description of the transformation rather than as machinery.

// Reads as a description. Good.
Map<ScholarshipStatus, List<Application>> byStatus = applications.stream()
    .filter(a -> a.cohort() == 2026)
    .collect(Collectors.groupingBy(Application::status));

// Fighting the abstraction. A loop would be clearer and would let the
// checked exception propagate normally.
List<Document> docs = ids.stream()
    .map(id -> {
        try { return storage.fetch(id); }
        catch (IOException e) { throw new UncheckedIOException(e); }
    })
    .toList();

The performance note, honestly

Sequential streams are usually within noise of a loop, and occasionally slower on very hot, very small collections because of the pipeline setup. That difference almost never matters, and Stage 11 will show you it is never the bottleneck you are looking for. parallelStream(), on the other hand, is a genuine hazard: it uses the shared fork-join pool, it helps only for large, CPU-bound, side-effect-free work over splittable sources, and it hurts badly for anything I/O-bound. In a Spring application handling concurrent requests, the answer is almost always no.

✕Side effects inside map or filter

Saving to a repository inside a map works by accident until something reorders or short-circuits the pipeline. Intermediate operations must be pure; do the writing in the terminal operation or in a loop over the result.

✕Using Optional as a field or a parameter

Optional was designed as a return type, to make “there may be no answer” explicit at the call site. As a field it adds an allocation and breaks serialisation; as a parameter it means the caller must wrap a value they already have. Prefer an overload or a nullable parameter with a clear name.

✕.collect(Collectors.toList()) in new code

.toList() since Java 16 is shorter and returns an unmodifiable list, which is almost always what you wanted. Use Collectors.toCollection(ArrayList::new) when you genuinely need a mutable one — and notice how rarely that is.

04 / CONTAINER

Inversion of control, as a lifecycle you can trace

Your deck explains IoC and DI well. This is the part after that: what the container actually does, in what order, between main() and your first request.

Dependency injection is easy to explain and easy to half-understand. The half that gets skipped is when — and almost every confusing Spring behaviour lives in the gap. Why is a field null in the constructor. Why does @Transactional silently do nothing. Why does a circular dependency fail with constructor injection but not with field injection. Why does the bean you get back not have the class you wrote.

All four have the same answer: something happened at a different point in the lifecycle than you assumed. So trace it.

The four things worth carrying out of that trace

    
    
      
  1. Definitions come before instances. Scanning registers metadata — class, scope, dependencies, whether it is lazy. Nothing is constructed until the container starts pre-instantiating singletons. This is why a BeanFactoryPostProcessor can rewrite a definition and why property placeholders are resolved before any of your code runs.
    2. 
      
  2. Dependencies are resolved depth-first. To build the controller the container must first build the service, which must first build the repository, which must first build the data source. The creation order is not the order you wrote the classes in; it is a topological sort of the dependency graph.
    3. 
      
  3. The proxy is created after initialisation, by a BeanPostProcessor. This is the single most load-bearing fact in Spring. Your @PostConstruct runs on the raw object; everything injected elsewhere receives the wrapper. It explains why @Transactional, @Cacheable, @Async and @PreAuthorize all fail in exactly the same three situations — module 05.
    4. 
      
  4. Constructor injection makes cycles impossible. Not “discouraged” — impossible, because neither object can be constructed without the other already existing. Field injection permits the cycle by leaving a half-built object lying around, which is worse: the failure moves from startup to some later moment when the field is read. Spring 2.6 onwards refuses circular references by default for exactly this reason.
    5. 
    

    
And the corollary for how you write beans: constructor injection, final fields, no @Autowired annotation needed. Since Spring 4.3 a class with a single constructor gets it injected automatically. The class is then immutable, obviously testable with new, and impossible to leave half-constructed.

    
@Service
class ScholarshipService {
    private final ScholarshipRepository repository;   // final: assigned once, in the constructor
    private final AuditService audit;

    ScholarshipService(ScholarshipRepository repository, AuditService audit) {
        this.repository = repository;                  // no @Autowired — one constructor is enough
        this.audit = audit;
    }
}

// In a unit test there is no container at all:
var service = new ScholarshipService(new FakeRepository(), new RecordingAudit());

The proxy rule, in one sentence

    
Spring's annotations work by wrapping your bean in a proxy that intercepts incoming external calls to public methods. Everything that fails does so for one of three reasons: the call never left the object (this.method()), the method could not be intercepted (private, final, static), or the caller has the raw object rather than the proxy (self-injection, new, a nested class). Learn that sentence and you have pre-solved every @Transactional, @Cacheable, @Async and @PreAuthorize mystery you will ever meet.

  







  
06 / AUTO-CONFIG
Auto-configuration is a long list of if statements

  
Spring Boot is not magic. It is a few hundred conditional configuration classes evaluated at startup, and it will tell you exactly what it decided.


  

    
This is the demystification that makes Spring Boot comfortable rather than uncanny. @SpringBootApplication includes @EnableAutoConfiguration, which loads a list of configuration classes shipped inside the starter jars. Each one is guarded by conditions — is this class on the classpath, has the user already defined this bean, is this property set — and the ones whose conditions hold contribute beans. That is the entire mechanism.

    
The most important condition is @ConditionalOnMissingBean, and it is the reason Spring Boot never fights you: every auto-configured bean steps aside the moment you define your own. “Overriding” Spring Boot is just declaring the bean yourself.

Three habits that follow

    
    
      
  • When a bean you expected does not exist, run with --debug. The condition evaluation report lists positive matches, negative matches with the reason, and exclusions. It answers the question directly instead of by inference.
    • 
      
  • To change Spring Boot's mind, declare the bean. Not @Primary gymnastics, not excluding the auto-configuration unless you genuinely want none of it — just define your own and @ConditionalOnMissingBean does the rest.
    • 
      
  • Starters are curated dependency sets, not code. spring-boot-starter-web is a pom.xml with no classes in it: Spring MVC, Jackson, validation and an embedded Tomcat, at versions the parent BOM has already tested together. Adding a starter is how you make conditions become true.

07 / CONFIG
Configuration, profiles, and which value actually wins

  
The same property is set in four places. Production is reading a value you cannot find in any file.


  

    
Spring Boot resolves a property from a strictly ordered list of sources, and the whole list is worth internalising because the one that surprises people — environment variables beat every file — is exactly the one your container platform will be using in Stage 13.

Reading configuration: three ways, one recommendation

    
// ✗ @Value — untyped, no validation, scattered across the codebase,
//   and a typo in the key is a startup failure at best.
@Value("${app.scholarship.max-amount}")
private long maxAmount;

// ✗ Environment — imperative, stringly-typed, hard to test.
long max = env.getProperty("app.scholarship.max-amount", Long.class, 100_000L);

// ✓ @ConfigurationProperties — typed, validated, documented, injectable,
//   and a record makes it immutable for free.
@ConfigurationProperties(prefix = "app.scholarship")
@Validated
public record ScholarshipProperties(
    @Positive long maxAmount,
    @NotBlank String currency,
    @DurationMin(seconds = 60) Duration reviewSla
) {}

// Enabled once, and injected like any other bean.
@ConfigurationPropertiesScan
@SpringBootApplication
public class ScholarshipsApplication { … }

    
The advantage that matters is not tidiness. A @ConfigurationProperties record with validation fails the application at startup when a required value is missing or malformed — before it takes traffic. A @Value in a lazily-created bean fails on the first request that touches it, in production, at an arbitrary time. This is Stage 2's parse-at-the-boundary rule, applied to configuration.


    
Profiles, and the trap in them

    
Profiles select which property files and which beans participate: application-prod.yml layers over application.yml, and @Profile("!prod") keeps a bean out of production. Two cautions worth stating before you rely on them:

    
    
      
  • Profiles are not a secrets mechanism. An application-prod.yml in the repository is a database password in the repository. Secrets come from the environment, and in Stage 14 from Azure Key Vault. The profile decides which keys, never which values.
    • 
      
  • Profile-specific beans make production a different application. A @Profile("dev") stub that replaces the payment gateway means the path you tested is not the path that runs. Prefer configuring the same beans differently over swapping beans wholesale, and reserve bean-swapping for genuine infrastructure boundaries.
    • 
    


    
The layering, and what each layer is forbidden from knowing

    
Your deck's slide 125 gives the three layers correctly. The useful version adds the prohibitions, because a layered architecture that nobody enforces is just three package names:

    
web/        @RestController   HTTP in, DTOs out. Knows about status codes and
                                requests. Must not know about entities, JPA, or SQL.
              ↓  (DTOs only)
service/    @Service          Business rules, transaction boundaries, orchestration.
                                Must not know about HttpServletRequest or Jackson.
              ↓  (domain types)
repository/ @Repository       Persistence. Entities, queries, mapping.
                                Must not contain business rules.
domain/                         Entities, value objects, sealed state types.
                                Knows about nothing — no Spring, no annotations
                                beyond JPA's.

    
The transaction boundary belongs on the service, not the controller and not the repository — one business operation is one transaction, and the service is the only layer that knows where an operation begins and ends. Stage 8 will make that concrete, and Stage 15 will show you what happens to this structure when the application gets large enough to need modules.
