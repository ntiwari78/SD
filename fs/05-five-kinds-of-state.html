Five Kinds of State

“Which state library should I use?” is the wrong first question, and answering it first is how applications end up with a Redux store full of API responses. The right first question is what kind of state you are holding — because four of the five kinds have an obvious home once you have named them.

01 / CLASSIFY

Name it before you store it

Most “global state” problems dissolve the moment you notice the state is not global and not yours.

The reason state management feels hard in React is that the word covers five genuinely different things, with different owners, different lifetimes, and different failure modes. Treating them as one problem is what produces a 4,000-line store that nobody can reason about.

Local UI state
Ephemeral, belongs to one component, dies with it. Is the menu open, which tab is active, is this row hovered.
useState · useReducer
Server state
Owned by the backend. You hold a copy that is stale the instant it arrives, shared by many components, and can change without you.
TanStack Query · RTK Query
Global client state
Genuinely yours, genuinely app-wide, and not derivable from the server. Theme, the access token in memory, a command palette.
Zustand · Redux Toolkit · Context
URL state
Anything a user should be able to bookmark, share or reach with the back button. Filters, sort, page, the open record.
useSearchParams · route params
Form state
In-progress edits, plus touched, dirty and validity. Short-lived, high-frequency, and its own problem.
React Hook Form

The claim this stage rests on: in a typical CRUD application, seventy per cent of what people put in a global store is server state. It got there because there was no other name for “data several components need”, and once there, it has to be manually kept in sync with a source of truth that does not know your store exists. That manual synchronisation is where the bugs live.

Classify these fourteen pieces of the capstone before reading further. The two that catch nearly everyone are worth the exercise on their own.

02 / SERVER

Server state is a cache, and caches have rules

Your deck never names this category. It is the largest single gap in it, and the one that costs the most.

Here is the distinction that reorganises everything. Client state you own: you set it, you know it is correct. Server state you do not own — PostgreSQL does. What lives in your browser is a copy that was correct at the moment it arrived and has been decaying ever since, possibly changed by another user, another tab, or a background job while you read this sentence.

That means server state comes with problems client state simply does not have, and each of them is a decision you make whether or not you notice:

  • Staleness — how long is a copy good enough to reuse without asking again?
  • Deduplication — three components mount and all want the scholarship list. One request, or three?
  • Revalidation — the user switched tabs for ten minutes and came back. Is the number on screen still true?
  • Races — Stage 2's problem, at the data layer: the response to the older request arrives last.
  • Garbage collection — the component unmounted. Keep the data for the back button, or free it?
  • Retries and backoff — a 500 might be transient; a 403 never is.

Put server data in a Redux slice and you have signed up to solve all six by hand, in application code, forever. Use a query cache and they become configuration. Drive the machine below and watch what each setting actually does.

The two settings that matter, and the one people confuse

staleTime is how long the data is considered good enough to serve without a background refetch. It defaults to zero, which means “refetch on the next trigger, always” — the safest default and the reason a query library looks chatty until you tune it. Reference data that changes weekly deserves minutes; a live queue deserves zero.

gcTime is how long an unused entry survives in memory after its last observer unmounts. It is not about freshness at all. Setting staleTime when you meant gcTime is the single most common misconfiguration; the giveaway is “why is my data gone when I navigate back” (that is gcTime) versus “why is it refetching so often” (that is staleTime).

Notice what the counters are and are not saying. A query cache does not simply make fewer requests — driven for long enough it may well make more, because it revalidates on refocus and after every mutation. What it makes is the right requests: none when several components ask for the same thing at once, none when the copy it holds is still within staleTime, and one whenever something has happened that could have made the copy wrong. The naive version fires exactly once per mount, forever, and its data is stale from that moment until the component happens to remount.

The query key is the identity

Everything above hangs on one design decision: the key. It must contain every input that changes the result — which, if you followed Stage 4, is exactly the URL's search parameters.

const { filters } = useScholarshipFilters();          // from the URL — Stage 3

const { data, isPending, isFetching, error } = useQuery({
  queryKey: ["scholarships", filters],                // identity = the inputs
  queryFn:  ({ signal }) => apiGet(`/scholarships?${qs(filters)}`, pageSchema, { signal }),
  staleTime: 30_000,
  placeholderData: keepPreviousData,   // page 2 keeps page 1 on screen while loading
});

// isPending  → no data at all yet          → skeleton   (Stage 4, module 02)
// isFetching → refreshing behind data       → stale mark
// error      → the ApiError from Stage 2    → error panel

Because the key is derived from the URL, the cache, the browser history and the shareable link are the same thing. Change a filter and you get a different key, a different cache entry, and — with keepPreviousData — the old table stays on screen while the new one loads instead of flashing a skeleton. All three of Stage 4's loading treatments fall out of this one hook.

✕Copying query data into useState so you can edit it

Now there are two copies and one of them is silently wrong. If you need an editable draft, that is form state — initialise the form from the query and let the mutation write back. The cache is not your working copy.

✕A query key that omits an input

["scholarships"] for a filtered request means every filter shares one cache entry, so switching filters shows the previous filter's rows and the cache never notices. If it changes the response, it belongs in the key. This is a cache-invalidation bug disguised as a typo.

✕Disabling refetch-on-focus globally because it “looks noisy”

You have turned off the feature that keeps a long-lived tab honest. If it is genuinely too chatty, raise staleTime — that is the knob for “this data does not change that fast”. Turning off revalidation is the knob for “I would rather show stale numbers”, which is rarely what anyone means.

03 / CONTEXT

Context is dependency injection, not a state manager

Your deck teaches Context well. It does not mention the thing that makes people abandon it at scale.

Context solves exactly one problem: getting a value to a deep descendant without threading it through every component in between. It is a transport mechanism. It holds nothing, updates nothing, and optimises nothing — the state still lives in a useState or useReducer somewhere above.

The consequence people meet in month three: every consumer of a context re-renders whenever the context value changes, with no way to subscribe to part of it. Put user, theme and notifications in one context and a notification arriving re-renders every component that only wanted the theme.

Interactive · change one slice

Three fixes, in the order to try them

  1. Memoise the provider value. <Ctx.Provider value={{ user, theme }}> creates a new object on every render of the provider, so every consumer re-renders even when nothing changed. Wrap it in useMemo. This is a bug, not an optimisation — turn the toggle off above to see how bad it is.
  2. Split by change frequency, not by topic. A value that changes on every keystroke and a value that changes twice a session do not belong in the same context. Two providers is not duplication; it is the correct granularity.
  3. Separate the value from the setters. A StateContext and a DispatchContext — the pattern your deck's useReducer slides are one step away from — means components that only dispatch never re-render when the state changes. That is often the single biggest win, because there are usually more dispatchers than readers.

Past that, you have outgrown Context, and the honest move is a store with selector subscriptions rather than a fourth clever workaround. Note what Context still does better than any store: it is scoped. Two <WizardProvider>s on one page hold two independent wizards, which a module-level store cannot do without keys and manual cleanup.

Experiment

Two runs worth doing. First: Split contexts with the memo toggle off — splitting bought you nothing, because each provider still hands out a fresh object every render. Second: set the slice to notifications and uncheck alters the derived unread count. Both Context architectures wake UnreadBadge; the store does not, because the number it selects did not change. That gap — subscribing to what you read rather than to the container — is the whole of what a store buys you here.

How to choose, stated as a rule

  • Start with Context + useReducer. Zero dependencies, scoped to a subtree, and if the value is small and changes rarely — theme, the auth object, a wizard — it may be the last answer you need.
  • Move to Zustand when consumers are re-rendering for slices they do not use, when you want the store outside React (an interceptor reading the token), or when the ceremony of Context providers is the thing you are actually tired of. It is roughly a hook with a subscription, which is why it is the smallest step up.
  • Choose Redux Toolkit for a large team on a long-lived application where the value is the discipline: one mutation vocabulary, time-travel debugging, a serialisable action log you can attach to a bug report, and middleware as a real extension point. Your deck teaches RTK properly, and RTK Query would fold module 02's job into the same store — a legitimate alternative to TanStack Query if you are already on Redux.

What should not decide it: how many lines each version takes on a slide. RTK looks verbose at one slice and looks like structure at forty, and the boilerplate argument that killed classic Redux was largely addressed by createSlice. Judge these at the size you will actually be, not at the size of the example.

And the recommendation for the capstone, stated as one: TanStack Query for server state, Context for auth and theme, Zustand only if a third genuinely-global concern appears. No Redux — not because it is worse, but because with server state properly homed, what remains is too small to earn a store's overhead. That is an architectural judgement about this application, and a team already fluent in RTK should weigh it differently.

05 / MUTATION

Writing, and the four ways it goes wrong

The reviewer clicks Award. When should the UI change — and what happens when the server says no?

Reads are the easy half. The moment you write, you have two copies of the truth diverging in real time, and every design in this space is a different answer to “how long am I willing to lie to the user?”

Invalidate or write into the cache?

After a successful write you have two options and they are not equivalent.

  • invalidateQueries marks the affected entries stale and refetches the visible ones. It costs a round trip and it is always correct, because the server recomputes everything your write touched — the derived counts, the audit entry, the recomputed remaining budget. Make this your default.
  • setQueryData writes the server's response straight into the cache with no round trip. It is right when the response already contains the complete new state of that entry, and wrong the moment a write has side effects elsewhere — which, in a domain with budgets, audit logs and notification counters, is most writes.
const award = useMutation({
  mutationFn: (id: number) => apiPost(`/applications/${id}/award`, {}, applicationSchema),

  // 1 · before the request: apply the lie, and keep the truth to undo it
  onMutate: async (id) => {
    await qc.cancelQueries({ queryKey: ["applications"] });   // stop an in-flight refetch
                                                              // from overwriting us
    const prev = qc.getQueryData(["applications"]);
    qc.setQueryData(["applications"], (old) => markAwarded(old, id));
    return { prev };                    // the rollback token
  },

  // 2 · it failed: put the world back exactly as it was
  onError: (_err, _id, ctx) => qc.setQueryData(["applications"], ctx.prev),

  // 3 · either way, let the server have the last word
  onSettled: () => qc.invalidateQueries({ queryKey: ["applications"] }),
});

Three details in that snippet are the difference between an optimistic update that works and one that produces ghosts. cancelQueries stops a refetch that started before your write from landing after it and undoing it. The context object is the only record of the pre-write state, so it must be captured before the mutation, not reconstructed after. And onSettled runs on both paths, because after a failure the cache should be re-synchronised from the server rather than trusted.

When to be optimistic at all

Optimism is a bet that the write will succeed, paid for in credibility if it does not. Take it when the action is frequent, low-stakes and reversible — a checkbox, a like, a reorder — where the latency is more annoying than the rare rollback. Do not take it when the action is rare, consequential or irreversible: awarding a scholarship, deleting a document, submitting an application. There, a disabled button and a spinner for 300 ms is honest, and a UI that shows “Awarded” and then takes it back is worse than one that made the user wait.

Architecture connection

Every failure mode here has a server-side counterpart. The racing clicks are why Stage 7 gives you idempotency keys — with one, the second request is recognised as a duplicate rather than creating a second award. The stale-refetch overwrite is why Stage 8 uses optimistic locking with a version column, so a write based on a stale read is rejected with a 409 instead of silently winning. Client-side state management is one half of a conversation; the other half is the API contract.

The two entries worth arguing about

The signed-in user is server state. This surprises people, because “current user” feels like the definition of global. But it comes from GET /me, the server owns it, and it can change without you — an admin revokes a role and the next revalidation should reflect that. Cache it with a long staleTime and refetch on focus. What genuinely belongs in a global store is only the access token, and only because an HTTP interceptor outside React needs to read it.

The unread notification count is server state too, not a number you increment locally. Increment it yourself and it drifts from the badge the user sees on their phone within a day. Derive it from the cached notifications query, and let a mutation invalidate that query.

The pattern behind both: if the server could tell you the answer, the server owns it. Anything you compute and store locally instead is a second source of truth you have volunteered to maintain.

07 / CLOSING

What you should now be able to do

Self-check

  1. Name the five kinds of state and the default tool for each.
  2. Why is server state different in kind — not just in origin — from client state? Name three problems it has that client state does not.
  3. staleTime versus gcTime: which one explains “it refetches constantly” and which explains “my data vanished when I navigated back”?
  4. What belongs in a query key, and what goes wrong when something is missing from it?
  5. Why does every consumer of a Context re-render, and what are the three fixes in order?
  6. When does React.memo fail to stop a context-driven re-render? (Stage 3's answer applies — say why.)
  7. Give an action you would update optimistically and one you would not, with the reasoning.
  8. After a successful write: invalidateQueries or setQueryData? When is each wrong?
  9. Why is the signed-in user server state and the access token global state?

The capstone increment

  • TanStack Query for every read, with query keys derived from the URL filters built in Stage 3, staleTime set deliberately per resource, and the apiGet wrapper from Stage 2 as the only queryFn — so every response is still schema-validated at the boundary.
  • Mutations for apply, award, reject and document upload — pessimistic on the consequential ones, optimistic with rollback on the reversible ones, each invalidating the right keys.
  • An AuthContext holding the access token in memory plus a useCurrentUser() query for the profile and roles, with the refresh-token flow from Stage 1's recommendation.
  • A theme context persisted to localStorage, and nothing else global unless a third concern earns it.
  • The state map committed to the repository as a markdown table, and a review rule: a pull request that adds state to a category the map does not justify has to update the map.
