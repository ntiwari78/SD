Where Did the 900 Milliseconds Go

Your deck teaches Spring's caching annotations well and then applies them without a bottleneck ever having been found — which is the single most common way performance work goes wrong. This stage inverts the order: measure, locate, decide, and only then optimise. Every lab here is a measurement instrument, and several of them will tell you that the fix you were about to make would have done nothing.

01 / BUDGET

The fix that saves nothing

Scholarship search takes 900 ms at p95. You have one week. Which of eight plausible optimisations is worth doing, and how much of that can you know before writing any code?

Performance work has an arithmetic that decides most of it in advance, and it is not complicated. If a segment accounts for 5% of your latency, making it infinitely fast saves 5%. That is Amdahl's law, and its practical form is blunter: your ceiling is set by the segment you chose, before you write a line of code.

Which is why the first artefact of any performance effort is a breakdown, not a plan. Below is a real-shaped one: a p95 request through the capstone's scholarship search, decomposed into the seven places time actually goes. Turn optimisations on and watch what each one buys.

Four things the arithmetic settles

  1. The biggest segment is almost never the one you were going to fix. Everyone's instinct is to reach for the thing they most recently learned about — a cache, a memo, an index. The breakdown is what converts that instinct into a decision, and it takes an afternoon to produce.
  2. Two segments hide inside “server”. Time queueing for a connection or a thread is not time doing work, and no amount of query tuning touches it. Modules 06 and 08 are about that half.
  3. Round trips are additive and unavoidable by optimisation. If the client makes three sequential requests, you have three times the network segment no matter how fast each one is. That is fixed by changing the shape of the interaction, not by making anything faster.
  4. An optimisation with a real cost and no measurable effect is worse than nothing, because it also has to be maintained, reasoned about, and eventually removed by someone who cannot tell whether it matters.

How to produce the breakdown for your own request

  • Client segments from Chrome DevTools' network panel and performance trace, or programmatically from the PerformanceNavigationTiming and PerformanceResourceTiming entries — which give you DNS, TLS, request, TTFB and transfer as separate numbers rather than one bar.
  • Server segments from a distributed trace. Stage 12 sets this up properly with OpenTelemetry; the minimum viable version today is Spring Boot's Actuator http.server.requests timer plus a timer around the repository call, which already separates “in the controller” from “in the database”.
  • Database segments from EXPLAIN (ANALYZE, BUFFERS) — Stage 8's instrument. Note that a plan tells you about one query; the N+1 from Stage 8 shows up as a small plan repeated 340 times, which the plan itself cannot reveal. For that you need the query count.
  • Everything, in one picture, from a profiler. On the JVM, an async-profiler flame graph over a load test shows you where CPU time actually goes, including the parts nobody instrumented — and it routinely names something surprising, like JSON serialisation or logging.

The discipline, stated as a rule

Never optimise anything you have not measured, and never claim an improvement you have not measured twice — once before and once after, under the same load, on the same data volume. “It feels faster” is not a result, and neither is a stopwatch on a laptop with a warm cache and forty rows in the table. The capstone deliverable for this stage is exactly one artefact: a before-and-after with numbers. — My recommendation, and the only part of this stage I would call non-negotiable.

02 / TAIL

The average is the one number that cannot help you

Mean response time 140 ms, and a quarter of your users think the application is broken. Both statements are true simultaneously, and the reason is arithmetic.

Latency is not normally distributed. It is heavily right-skewed: a dense cluster of fast responses and a long tail of slow ones caused by cache misses, garbage collection, connection waits, cold code paths and the occasional retry. A mean over that distribution describes a request that essentially never happens.

Worse, the mean is insensitive to exactly the thing you care about. Add a slow path taken by 1% of requests and the mean moves by a few milliseconds while the 99th percentile doubles. Turn the sources of tail latency on below and watch the two numbers diverge.

Then it gets worse, because pages are not requests

A user does not experience one request. The reviewer dashboard makes nine calls to render: the application list, the counts, the filters, the current user, the notification badge, and four lazily-loaded panels. If each one independently has a 1% chance of being slow, the chance that the page contains at least one slow call is not 1%. It is:

1 − (1 − 0.01)9 = 8.6%

This is the same multiplication as Stage 10's flaky suite, in a different domain, and it has the same shape of consequence: per-component reliability that sounds excellent produces whole-experience reliability that is not. Jeff Dean and Luiz Barroso named this “the tail at scale”, and the practical version of their argument is that in any fan-out system the p99 of a component becomes something much more common at the level of the page.

Two corollaries that change how you design. First, reducing fan-out is a latency optimisation, often a bigger one than making any individual call faster — which is a real argument for a purpose-built endpoint over nine generic ones, and one of the honest points in favour of GraphQL or a backend-for-frontend. Second, a timeout is a latency control, not just an error control: capping a call at 250 ms and rendering a degraded panel converts a tail event into a visible, bounded one.

Which percentile, and measured where

  • p50 tells you whether the common case is healthy. It is the number that moves when you fix an algorithm.
  • p95 / p99 tell you what your unluckiest users get, and they are the numbers that move when you fix queueing, contention, cold caches and GC. Most production pain lives here.
  • p99.9 is where you find the pathological case — the one request that hit a lock, a retry and a GC pause together. Worth watching, dangerous to chase.
  • Never average percentiles. The mean of each instance's p95 is not the fleet's p95, and averaging a percentile over a time window is not a percentile of that window. Aggregate the underlying histogram, which is why Micrometer publishes histogram buckets rather than pre-computed quantiles when you ask it to.

And measure in the field, not only in the lab. A synthetic run on a fast machine over a fast network is a useful regression check and a poor description of your users — which is precisely why Google's Core Web Vitals are assessed at the 75th percentile of real visits rather than on a lab score. That is module 03.

03 / VITALS

Three numbers a user can feel

Your Lighthouse score is 94 and your users complain the page is sluggish. Lighthouse ran once, on your machine, with a warm cache. Neither of you is lying.

Core Web Vitals are an attempt to reduce “is it fast” to three things a person actually perceives: how long until the main content appears (LCP), how long until it responds when I touch it (INP), and does it move under my finger (CLS). Each has a published threshold with a documented derivation, and each is assessed at the 75th percentile of real user visits over a rolling 28-day window — not at a lab score.

The thresholds, current as of writing: LCP good at or under 2.5 s, poor above 4 s. INP good at or under 200 ms, poor above 500 ms. CLS good at or under 0.1, poor above 0.25. Two useful diagnostics that are deliberately not Core Web Vitals: TTFB, good at or under 800 ms, and FCP, good at or under 1.8 s.

The reason each metric is worth learning is that each decomposes, and the decomposition tells you what to fix. Pick one.

Fixes

INP is the one this stack gets wrong

LCP is mostly a delivery problem and CLS is mostly a layout-discipline problem, but INP is a JavaScript execution problem, and a React application with a data layer is exactly the shape that produces bad INP. The mechanism is worth stating precisely: an interaction is slow when the main thread is busy, and the main thread is busy because your event handler synchronously triggered a state update that re-rendered a large tree before the browser was allowed to paint.

The three components — input delay, processing duration, presentation delay — point at three different fixes, and they are not interchangeable. Input delay means the thread was already busy when the user touched the screen: the culprit is something else, often a third-party script or a poorly timed effect. Processing duration means your handler is doing too much. Presentation delay means the render and layout that follow are too expensive, which is module 05's subject.

Two platform features are directly relevant and both are recent enough to be worth naming. The Long Animation Frames API (PerformanceObserver on long-animation-frame, in Chromium since Chrome 123) attributes a slow frame down to the specific script and character position that blocked it — this is how you diagnose INP from field data rather than guessing. And scheduler.yield() lets a long task yield to the main thread and resume with priority, which setTimeout(0) notably does not: a continuation scheduled with setTimeout queues behind every task that arrived in the meantime. It is in Chrome and Firefox but not Safari, so feature-detect or use the official polyfill.

// Report the real thing, from real users. web-vitals v5, attribution build.
import { onLCP, onINP, onCLS } from "web-vitals/attribution";

const send = (metric) => navigator.sendBeacon("/api/v1/vitals", JSON.stringify({
  name: metric.name, value: metric.value, rating: metric.rating,
  attribution: metric.attribution        // v5 folds LoAF data into INP attribution
}));

onLCP(send); onINP(send); onCLS(send);

// And the yield that actually helps, where it exists:
async function processLargeList(items) {
  for (const chunk of chunks(items, 50)) {
    render(chunk);
    if ("scheduler" in window && "yield" in scheduler) await scheduler.yield();
    else await new Promise(r => setTimeout(r, 0));   // worse, but portable
  }
}

Lab scores and field data answer different questions

Lighthouse is a lab tool: one load, one device profile, simulated throttling, and — importantly — no user, which means it cannot measure INP at all. What it reports instead is Total Blocking Time, a proxy. That makes Lighthouse excellent for catching a regression in CI and unable, in principle, to tell you what your users experience.

Field data comes from real visits: the Chrome User Experience Report for the aggregate, and your own web-vitals beacon for the detail — the latter being the only one that can tell you which route and which interaction. My recommendation for the capstone is to run both and to treat them as answering different questions: Lighthouse in the pipeline as a budget gate, field data on a dashboard as the truth.

Experiment

Open the reviewer dashboard, start a Chrome performance recording, and interact with the filter control. Find the long animation frame in the trace, expand it, and read the three phases directly. Then do the same thing with the CPU throttled to 4× slowdown — which is roughly a mid-tier Android phone. The number that was 90 ms becomes 360 ms, and the fix you would have chosen from the unthrottled trace is usually not the one the throttled trace points at.

04 / DELIVERY

Every kilobyte of JavaScript is paid for twice

Once to download, and again — more expensively, on a slower processor — to parse, compile and execute. The second cost is the one nobody budgets for.

A 900 KB JavaScript bundle over a good connection is about a second of transfer. On a mid-tier Android phone it is another second and a half of parsing, compiling and executing before anything can happen — and that second and a half is main-thread time, which means it is also blocking the first interaction. This is why bundle size is not a vanity metric and why compressing harder does not fix it: compression reduces transfer and does nothing to execution.

The order to do this in

  1. Measure the bundle first. You cannot reason about a number you do not have, and the number is almost always larger than the guess. Vite 8 ships first-party tooling for this — Vite DevTools with the Rolldown plugin gives module graphs, chunk treemaps and build-to-build diffs — and rollup-plugin-visualizer still works if you prefer it.
  2. Split by route. This is the single largest win available and it is nearly free. Note a change worth knowing: in React Router v7's framework mode, each route module is its own bundler entry point and is code-split automatically — React.lazy is unnecessary there, and Split Route Modules further separates clientLoader from the component so both can be fetched in parallel. In data or declarative mode you still do it yourself, with a route-level lazy or React.lazy.
  3. Remove or replace the heavy things. A date library that ships every locale, an icon package imported as a namespace, a charting library used for one sparkline, a component library imported without tree-shakeable paths. This is where the surprising numbers live, and the treemap is what finds them.
  4. Then, and only then, compress and preload. Brotli over gzip is a real but bounded win, and <link rel="preload"> on the LCP image or the critical font moves work earlier without making it smaller.

Two mistakes with the same shape

Splitting too finely turns one big request into forty small ones, and on a high-latency connection the round trips cost more than the bytes saved. Split at route boundaries and at genuinely deferred features — a rich text editor, a PDF viewer, an admin panel — not at component boundaries.

Lazy-loading something the first screen needs converts a bundle cost into a waterfall: the browser downloads the shell, executes it, discovers it needs a chunk, and only then starts fetching. The result is a worse LCP than shipping it in the main bundle. The rule is that a route's own code is not a candidate for lazy loading; the code for routes the user has not visited is.

A version note, since it changes the advice

Earlier stages of this atlas pinned Vite 7. Vite 8 is now current and makes Rolldown the default bundler, replacing both esbuild and Rollup with one Rust implementation — the rolldown-vite opt-in package that guides describe was the pre-8 preview and is no longer how you get it. Build times improve substantially; more relevant here, the analysis tooling changed, so a guide that tells you to reach for rollup-plugin-visualizer as the only option predates the first-party alternative.

05 / RENDER

A re-render is free until it is not

Four hundred components re-rendering in 3 ms is fine. Forty components re-rendering in 90 ms is a dropped frame. The count was never the number that mattered.

Stage 3 established why React re-renders and Stage 5 established where state should live. This module is the measurement layer over both: when does a re-render actually cost something, and what is the correct order of interventions?

The frame budget is the anchor. At 60 Hz a frame is 16.7 ms, and the browser needs part of that for style, layout, paint and compositing — so your JavaScript has roughly 8–10 ms if you want to stay smooth. Anything longer is a dropped frame; a handler that takes 200 ms is twelve of them, and the user sees the interface stop.

Interventions, in the order you should try them

The order matters more than the tools

  1. Move the state down. If only the toolbar reads the filter text, the filter text belongs in the toolbar. This is free, removes the problem rather than mitigating it, and makes the component easier to read. It is the first thing to try and the thing people try last.
  2. Split the context. A context re-renders every consumer when any part of its value changes. Two contexts — one for the value that changes on every keystroke, one for the value that changes twice a session — is usually a five-line change with a large effect. Stage 5's lab showed the mechanism; this one shows the cost.
  3. Defer the expensive consequence. useDeferredValue lets the input stay responsive while the expensive list catches up, and startTransition marks an update as interruptible. Both are the right tool when the work genuinely has to happen and just must not block the keystroke.
  4. Do less work per item. Virtualise a long list so you render the visible thirty rows rather than all four hundred. This is the intervention that changes the asymptotics, and it beats every amount of memoisation on a large enough list.
  5. Memoise, last. React.memo, useMemo and useCallback are real tools with a real cost — every memo is a comparison on every render plus retained memory — and they are frequently applied to trees where the render was never the problem.

What the React Compiler does and does not change

React Compiler reached 1.0 and does automatic memoisation at build time, which removes most of the reason to write useMemo and useCallback by hand. Two things to be precise about, because the enthusiasm outruns the guidance. First, React's own advice for an existing codebase is not to strip existing memoisation wholesale — removing it can change what the compiler produces, so leave it or test carefully. Second, and more important here: the compiler memoises; it does not move your state. If the filter text lives in App and every component reads it, the compiler will faithfully memoise a tree that should not have been re-rendering at all. Interventions one and two above are outside its reach, and they are the ones that matter most.

Worth knowing alongside it: React 19.2's Performance Tracks in Chrome DevTools add a Scheduler track (work by priority) and a Components track (render, effect mount, and what blocked rendering), so the profiling story is now in the same timeline as the browser's own. And <Activity mode="hidden"> pre-renders and preserves UI without competing with visible work — a better answer than {isVisible && <Page/>} for a tab or a route you will come back to.

Challenge

Open the reviewer dashboard with React DevTools' Profiler, record a single keystroke in the filter box, and read the flame chart. Write down two numbers before changing anything: total commit duration, and the number of components that rendered. Then apply interventions one and two only — move the state, split the context — and record again. My claim, which you should check rather than accept: for a typical dashboard those two changes alone recover more than every memo you were about to add, and they remove code instead of adding it.

06 / POOL

The counter-intuitive one: fewer connections, more throughput

Your database is at 40% CPU, your pool is exhausted, and requests are queueing. The instinct is to raise the pool size. The instinct makes it slower.

This is the most reliably surprising result in backend performance, so it is worth stating before you play with it: past a certain point, adding connections reduces throughput. Not “has diminishing returns” — actively reduces. HikariCP's documentation puts the reason in one line: “Once the number of threads exceeds the number of CPU cores, you're going slower by adding more threads, not faster.”

The mechanism is that a database connection is a server-side process or thread that competes for the same finite CPU cores, disk queue and lock manager. Twenty connections on eight cores means context switching, cache-line contention and lock waits, all of which inflate the service time of every query, including the ones that would otherwise have been fast. You have not added capacity; you have added contention and moved the queue from a place where it was visible to a place where it is not.

The formula, and what it is really saying

The PostgreSQL project's rule of thumb, which HikariCP adopts:

connections = ((core_count × 2) + effective_spindle_count)

Core count excludes hyperthread siblings. Effective spindle count is the number of disks the working set actually has to reach — which on modern hardware with a working set that fits in the page cache is zero. So for an eight-core database server with a cached working set, the answer is about 16 connections, and it does not go up because your application has two hundred concurrent users. Pool size tracks the server's ability to do work in parallel, not the client's demand for it.

The evidence HikariCP cites for this is worth repeating because the magnitude is hard to believe. In an Oracle Real-World Performance demonstration, reducing a connection pool from 2048 to 96 took response time from around 100 ms to around 2 ms — a fifty-fold improvement, from removing connections and changing nothing else.

What to set on the other side

  • PostgreSQL's max_connections defaults to 100 and is a start-time parameter that sizes shared memory, so raising it costs fixed resources whether or not the connections are used. Set it slightly above the sum of your pools, leaving headroom for maintenance and monitoring — not at some large round number.
  • A pooler becomes necessary when you have more application instances than the database can host connections for. Four instances at 16 connections each is 64, which is fine. Forty instances is not, and that is where PgBouncer in transaction mode belongs — PostgreSQL deliberately ships no built-in pooler, and nothing in recent releases changes this. PostgreSQL 18's headline is asynchronous I/O, which is a genuine storage-read improvement and not a connection-scalability one.
  • connectionTimeout is the number that decides what a saturated pool looks like. Too high and requests pile up invisibly until threads are exhausted; too low and you shed load aggressively. Two to five seconds is a reasonable starting point, and the resulting exception should be treated as a load signal, not a bug.
  • leakDetectionThreshold is worth enabling in non-production. A connection held across an HTTP call, or leaked by a missing @Transactional boundary, presents as pool exhaustion under load and is nearly impossible to find without it.

The diagnosis this module is really teaching

When latency rises under load but the database CPU is not saturated, the time is being spent waiting, not working — and waiting is invisible to query tuning. Look at hikaricp.connections.pending and hikaricp.connections.acquire in Actuator before you look at a query plan. If acquisition time is a large fraction of request time, no index will help you, and neither will a bigger pool.

07 / CACHE

Four tiers, and the question that picks between them

Your deck adds @Cacheable to a service method. That is the last decision, not the first — and on three instances it produces three different answers.

A cache is a deliberate trade of correctness for latency, and the whole skill is in knowing exactly which correctness you traded. The annotation is easy; the questions it silently answers are not. How stale may this be? Who else has a copy? What happens when it is wrong? Who invalidates it, and what happens to the ones they cannot reach?

The distinction that catches everyone: per-instance versus shared

    
Caffeine is an in-process cache. Three application instances means three caches, filled at different times, evicted at different times, and holding different values. For a slow-moving reference list that is completely fine and is the cheapest cache available — a hash-map lookup, no serialisation, no network. For anything a user just changed it is a bug with a specific and infuriating symptom: refresh the page and the old value comes back, intermittently, depending on which instance answered.

    
Redis is shared, so all instances agree, and you pay a network round trip plus serialisation for that agreement — sub-millisecond in the same availability zone, and not free. The decision between them is not about speed. It is about whether divergence between instances is acceptable for that particular piece of data, and that question has a different answer for the scholarship catalogue than it does for a student's own draft.


    
Invalidation, honestly

    
Three strategies, in increasing order of how much they ask of you.

    
    
      
  • Time-based expiry is the only one that always works, because it requires no knowledge of what changed. Choose the TTL by asking how stale this may be, and write the answer in the code as a comment; the number is a product decision that has been delegated to an engineer.
    • 
      
  • Explicit eviction on write — Spring's @CacheEvict — is correct when every path that mutates the data goes through your application. It becomes wrong the moment something else writes: a batch job, an admin tool, a database migration, another service.
    • 
      
  • Versioned keys sidestep invalidation altogether: include something that changes with the data in the key, and stale entries become unreachable rather than needing removal. This is what a content hash in an asset filename does, and it is the most robust of the three where it fits.
    • 
    


    
Two Caffeine details that matter more than they look

    
expireAfterWrite removes the entry, so the next reader blocks while it is reloaded — which means every expiry is a latency spike for whoever is unlucky, and for a hot key under load it is a stampede: every concurrent reader misses at once and they all hit the database together. refreshAfterWrite behaves differently: the entry becomes eligible for reload, and the next reader gets the stale value immediately while the reload happens asynchronously. Combining both is the pattern worth learning — refresh keeps hot keys warm without a stall, expiry caps how stale a cold key can get.

    
The practical trap: refreshAfterWrite cannot be expressed in the spring.cache.caffeine.spec string, because it needs a CacheLoader and a string cannot carry one. You supply a Caffeine bean and a CacheLoader bean instead — and note that Spring then applies that loader to every cache in the manager, which is a real footgun if your caches load differently.

  



@Configuration
class CacheConfig {

    // Slow-moving reference data: per-instance is fine, and it is the fastest thing available.
    @Bean
    Caffeine<Object, Object> caffeineConfig() {
        return Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofMinutes(30))    // caps staleness for cold keys
            .refreshAfterWrite(Duration.ofMinutes(5))    // keeps hot keys warm, no stall
            .recordStats();                              // exposed via Actuator — measure the hit rate
    }

    @Bean
    CacheLoader<Object, Object> cacheLoader(ScholarshipRepository repo) {
        return key -> repo.findCatalogueEntry((Long) key);
    }
}

@Service
class ScholarshipCatalogue {

    @Cacheable(cacheNames = "catalogue", key = "#id")
    public CatalogueEntry find(long id) { … }

    // Correct only because every write to a scholarship goes through this method.
    @CacheEvict(cacheNames = "catalogue", key = "#entry.id()")
    public void update(CatalogueEntry entry) { … }
}


  

    
One line in that configuration is doing disproportionate work: recordStats(). Without it you have no hit rate, and without a hit rate you have a cache you cannot evaluate. A cache at 12% hits is not helping and is adding a memory cost and a staleness risk for nothing; a cache at 97% hits is load-bearing and should be on a dashboard. Spring exposes Caffeine's statistics through Actuator's cache.gets metrics, tagged by result — which makes “is this cache worth having” a question with an answer rather than an opinion.

Stage 8 identified the N+1 on the reviewer dashboard and Stage 10 pointed out that no correctness test catches it. Notice that a cache would also have “fixed” it — the second page load would have been fast, the metric would have improved, and the 340 queries would still be there, now firing on every cache miss and every deploy. 08 / THREADS
What runs out first

  
Two hundred platform threads, a downstream call that slows from 40 ms to 900 ms, and your service stops answering requests it could have answered. Virtual threads change which resource runs out — not whether one does.


  

    
A classic Spring MVC application is thread-per-request on a bounded pool: Tomcat's default is 200. Each in-flight request occupies one thread for its whole duration, including the time it spends blocked on a database or an HTTP call doing nothing at all. When a downstream dependency slows down, threads accumulate in the blocked state, the pool exhausts, and requests that never needed that dependency start queueing behind ones that do. This is the mechanism behind most “the whole service went down because one integration was slow” incidents.

    
Virtual threads change the economics of that: a blocked virtual thread unmounts from its carrier and costs almost nothing, so blocking stops being expensive. Run the scenario both ways.

Turning it on, and the two things that surprise people

    
In Spring Boot it is one property — spring.threads.virtual.enabled=true, on Java 21 or later. It switches the auto-configured task executor to SimpleAsyncTaskExecutor on virtual threads and the scheduler to SimpleAsyncTaskScheduler, which covers @Async, MVC async request handling, scheduling and several other integration points. Note that once it is on, pool-sizing properties such as spring.task.execution.pool.max-size are silently ignored — there is no pool to size, and the property does not warn you.

    
The first surprise is what happens to your database. Unbounded request concurrency meeting a pool of sixteen connections does not mean sixteen requests and 984 errors; it means 984 requests waiting on connectionTimeout. Oracle's own guidance is unusually direct about this: the recommended way to limit concurrency under virtual threads is a semaphore, and a connection pool already is one — “there is no need to add an additional semaphore on top of the connection pool.” What changes is the shape of the failure: it stops looking like thread starvation and starts looking like connection-acquisition timeouts, so that is the metric to watch and the timeout to tune.

    
The second surprise is that a common piece of advice is now obsolete. Until recently, a virtual thread that blocked inside a synchronized block pinned its carrier thread, which could deadlock a service under load — hence years of guidance to rewrite synchronized as ReentrantLock. JEP 491 removed that in JDK 24, so on Java 24 and later synchronized no longer pins. What still pins is a native method or a foreign-function call that blocks. If you are reading a virtual-threads guide that leads with the ReentrantLock rewrite, it predates the fix.


    
Virtual threads or reactive, since you will be asked

    
Reactive — WebFlux, Reactor — achieves the same non-blocking goal by restructuring your code into a pipeline of operators. It works, it is mature, and it demands a great deal: every library in the path must be non-blocking, stack traces become unhelpful, debugging is harder, and the mental model is genuinely different. In exchange you get backpressure as a first-class concept, which virtual threads do not give you.

    
Virtual threads get most of the scalability benefit while letting you keep ordinary sequential code, ordinary stack traces, ordinary debuggers and ordinary blocking JDBC. For a system shaped like the capstone — a REST API in front of a relational database, with modest fan-out — that trade is strongly favourable, and it is what I would build on. Reactive earns its complexity when you are genuinely streaming, when backpressure is a real requirement, or when you are fanning out to many slow services at once.


    
And the JVM underneath, briefly

    
Enough to read a problem rather than to tune one, since most JVM tuning is a way of avoiding a fix.

    
    
      
  • G1 is the default on any server-class machine — which the JVM defines as at least two processors and about 1.75 GB of memory — and it is the right default for a typical Spring service. It is a pause-time-targeted collector, and its pauses are usually a few tens of milliseconds.
    • 
      
  • ZGC is the low-pause alternative, generational-only now that the non-generational mode was removed in JDK 24, and documented for heaps from a few hundred megabytes to sixteen terabytes. Generational Shenandoah is also GA, though not Shenandoah's default mode. There is no published core-count or heap-size threshold at which you should switch collectors — if a guide gives you one, it is folklore. Switch when you have measured a pause-time problem G1 cannot meet, and measure again afterwards.
    • 
      
  • Compact object headers (-XX:+UseCompactObjectHeaders) became a product feature rather than an experimental one, and the reported gains on a standard benchmark are around 22% less heap and 8% less CPU. It is not on by default, so it is a deliberate flag — and one of the few JVM flags with a large, well-documented, low-risk payoff for an object-heavy service.
    • 
      
  • What to look at first is not a flag. It is the GC log (-Xlog:gc*) answering one question: are pauses long, or are they frequent? Long pauses point at heap size or collector choice. Frequent pauses point at allocation rate, which is a code problem — usually something creating garbage per row in a loop — and no collector setting fixes it.

The capstone increment

    
    
      
  • A load test that produces a distribution, not an average — k6 or Gatling against the scholarship search at realistic data volume, reporting p50, p95 and p99 and the request rate at which they degrade. Realistic volume means the row counts you expect in year two, not the forty rows in your seed data.
    • 
      
  • A latency breakdown for the slowest endpoint, produced before any optimisation: client segments from Navigation Timing, server segments from Actuator timers, database from EXPLAIN (ANALYZE, BUFFERS), and a flame graph over the load test.
    • 
      
  • One optimisation, chosen by the breakdown, with the before-and-after numbers recorded. One is enough. The discipline of choosing by evidence is the deliverable; the speedup is a side effect.
    • 
      
  • Field vitals — a web-vitals beacon posting LCP, INP and CLS with attribution to your own endpoint, broken down by route, so you can see which screen is slow for real users rather than which screen is slow on your laptop.
    • 
      
  • Bundle budgets in the pipeline — a maximum initial-route transfer size that fails the build when exceeded, plus route-level splitting and a treemap you have actually read.
    • 
      
  • A sized pool, derived from the formula rather than guessed, with connection-timeout and leak-detection-threshold set deliberately and hikaricp.connections.pending on a dashboard.
    • 
      
  • A cache with a written justification — which tier, what TTL, why divergence between instances is or is not acceptable, how it is invalidated, and its measured hit rate. If you cannot write those five things down, the cache is premature.
    • 
      
  • Virtual threads enabled, with the connection-acquisition metric watched rather than the thread-pool one, and a load test that demonstrates the service surviving a slow downstream dependency instead of collapsing.

Where your deck helps, and where it stops

    
Slides 355–361 on Spring's caching abstraction are solid: @EnableCaching, the difference between @Cacheable, @CachePut and @CacheEvict, and a Caffeine configuration with TTL and maximum size. The material is correct and you should read it. What is missing is everything that comes before it — the deck never finds a bottleneck, never measures anything, and never asks whether the method it is annotating was slow. Cached-by-default is presented as a good property rather than as a trade with a cost.

    
Beyond caching there is nothing: no profiling, no load testing, no connection pooling or thread-pool discussion, no JVM or GC, no code splitting, no bundle analysis, no Core Web Vitals, and no Redis at all despite it appearing in the stack list. The useMemo material is presented as a rendering-cost argument without a rendering cost ever being measured, which is the frontend version of the same gap. Read the caching slides; get the discipline from here.
