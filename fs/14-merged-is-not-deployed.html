Merged Is Not Deployed

Stage 13 assumed a person typing docker build and docker push, which works until there are two of you. This stage is the machinery in between: what runs on every commit and in what order, why the pipeline must build the artefact exactly once, how a runner authenticates to Azure without holding a credential, what a release actually looks like when it can be undone in ninety seconds, and how you know whether any of it is getting better.

01 / ORDER

How long until it tells you no

A pipeline's job is not to run everything. It is to find the failure as early and as cheaply as possible, and only then to spend money proving the rest.

Stage 10 sorted tests by what they cost and what they catch. A pipeline is that ordering made executable: cheap, broad checks first, so that ninety per cent of failures are reported in ninety seconds; expensive, narrow ones last, so you only pay for them on code that has already survived.

Reorder the pipeline below and watch the number that matters — time to first failure — rather than the total.

Pipeline shape

Interactive · pick a failure, pick a shape

The ordering rule, and the two exceptions to it

Sort by (probability of catching a failure) ÷ (time to run). Compilation and linting are seconds and catch a large share of mistakes. Unit tests are tens of seconds. Slice tests are a minute. Container-backed integration tests are several. End-to-end journeys against a deployed environment are the most expensive thing you own and should run last, on an artefact that has already passed everything else.

Two things override the ordering. Anything that gates on a human should be as late as possible, because a review request that arrives before the build has passed wastes the reviewer's attention. And a security scan that blocks the build belongs before the push, not after — publishing an image with a critical vulnerability and then failing the pipeline leaves the image in the registry.

Two settings that pay for themselves immediately

name: ci

on:
  push: { branches: [main] }
  pull_request:

# Cancel a run when a newer commit arrives on the same branch. On a busy repo
# this halves runner spend and stops you reviewing results for stale code.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

# Least privilege by default; grant more per job only where needed.
permissions:
  contents: read

jobs:
  verify:
    runs-on: ubuntu-latest        # currently Ubuntu 24.04
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v5
        with:
          distribution: temurin
          java-version: '25'
          cache: maven            # GitHub's documented path — no hand-rolled actions/cache
      - run: mvn -B verify

Dependency caching through the setup actions is what GitHub itself recommends: setup-java understands maven and gradle, setup-node handles npm, Yarn and pnpm — and as of its current major, npm caching is on by default. Worth knowing the limits behind it: a repository gets 10 GB of cache, and entries not read for seven days are evicted, so a cache on a branch nobody has touched in a fortnight is not there any more.

Version drift is a real cost, and it has a fix

The core actions moved a major version when the runner's Node moved to 24 — checkout@v7, setup-node@v6, cache@v5, upload-artifact@v7, download-artifact@v8. Any workflow copied from a tutorial written a year ago will be on the previous majors, and the Node 20 runtime they depend on is being removed. The durable answer is not to chase versions by hand: let Dependabot update your action references, which it does even when they are pinned to commit SHAs — which module 02 argues they should be.

02 / TRUST

Your pipeline is a machine that runs other people's code with your credentials

Every third-party action in your workflow executes on a runner that can see your secrets and push to your registry. That is the deal, and there are four settings that make it survivable.

In March 2025 a widely-used action was compromised: an attacker with stolen credentials retagged every one of its version tags — v1.0.0 through the current release — to point at a single malicious commit that dumped runner memory, including secrets, into build logs. Tens of thousands of repositories referencing @v44 or @v1 were running attacker code within minutes, with no change to their own files.

Nothing about that attack was novel; the mechanism is that a Git tag is a movable pointer. Below, four hardening measures against five attacks.

Workflow hardening

Interactive · pick an attack
Hardening in place

The four, stated plainly

  • Pin actions to a full commit SHA. GitHub's own wording is that this is “currently the only way to use an action as an immutable release”, because forging a matching SHA would require a SHA-1 collision on a valid Git object. Put the version in a trailing comment so a human can read it, and let Dependabot bump both.
  • Set permissions to least privilege. Default the workflow to contents: read and grant more per job. A compromised step in a job that cannot write cannot tag a release or push a commit.
  • Use OIDC instead of stored cloud credentials, which is module 03 — there is then no long-lived secret in the repository for an exfiltration step to find.
  • Keep secrets in environments rather than at repository scope, so they are only available to jobs that request that environment and only after its protection rules pass.

The fork problem, and the trigger not to reach for

Workflows triggered by a pull request from a fork run without your secrets — GitHub withholds everything except a read-only GITHUB_TOKEN, which is exactly right, because the code in that pull request is written by a stranger. The temptation is then pull_request_target, which runs in the context of the base repository with secrets. GitHub's guidance is blunt about it: avoid it if it is not necessary, prefer workflow_run for privilege separation, and above all such a workflow must not check out the untrusted code. A workflow that uses pull_request_target and then checks out the pull request's head is the classic full compromise, and it is a two-line mistake.

Attestations, and what they actually prove

An artifact attestation is a signed statement, produced by the build, that this artefact came from this commit, in this repository, through this workflow. GitHub's attest-build-provenance action produces an in-toto statement with a SLSA provenance predicate, signed through Sigstore, and gh attestation verify checks it. Be precise about the level: using the action gets you SLSA Build Level 2; Build Level 3 additionally requires that the build run through shared, vetted reusable workflows, which is an organisational change rather than a step you add.

The value is not abstract. It is what lets a deployment refuse an image that was not built by your pipeline — turning “we think this is the right image” into something checkable.

# Pinned by SHA, with the human-readable version in a comment. Dependabot updates both.
- uses: actions/checkout@08c6903cd8c0fde910a37f88322edcfb5dd907a8   # v7.0.0

# Only this job gets the extra permissions, and only the two it needs.
build:
  permissions:
    contents: read
    id-token: write        # OIDC — module 03
    attestations: write    # provenance
  steps:
    …
    - uses: actions/attest-build-provenance@v4
      with:
        subject-name: ghcr.io/${{ github.repository }}/api
        subject-digest: ${{ steps.push.outputs.digest }}
        push-to-registry: true

03 / IDENTITY

A credential you do not have cannot leak

The conventional way to let a pipeline deploy to Azure is to create a service principal, put its secret in the repository, and rotate it annually if anyone remembers. There is a better mechanism and it has been the recommendation for a while.

Workload identity federation inverts the trust. Instead of Azure holding a password that GitHub knows, Azure is told to trust tokens issued by GitHub's OIDC provider for one specific repository, on one specific branch or environment. At deploy time the runner asks GitHub for a short-lived token describing itself, and Azure exchanges it for an access token. Nothing long-lived exists anywhere.

Credential blast radius

Interactive · pick a scenario

The workflow side is four lines of permissions and three values that are not secrets — a client id, a tenant id and a subscription id. They are stored as secrets out of habit and convention rather than necessity; none of them authenticates anything on its own.

permissions:
  id-token: write        # without this, no OIDC token is issued and login fails
  contents: read

steps:
  - uses: azure/login@v3
    with:
      client-id:       ${{ secrets.AZURE_CLIENT_ID }}
      tenant-id:       ${{ secrets.AZURE_TENANT_ID }}
      subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      # note: no client-secret, and no `creds:` blob

  - uses: azure/cli@v2
    with:
      inlineScript: |
        az containerapp update -n scholarships-api -g rg-scholarships \
          --image $ACR.azurecr.io/api:${{ github.sha }}

On the Azure side you add a federated credential to an app registration or a user-assigned managed identity, with a subject that names exactly what you will accept — repo:org/repo:ref:refs/heads/main, or better repo:org/repo:environment:production, so that only a job running in the protected production environment can obtain production access.

A documentation inconsistency worth being warned about

Microsoft's own Container Apps + GitHub Actions page still shows azure/login@v1 with a creds: service-principal JSON blob generated by az ad sp create-for-rbac --json-auth, and actions/checkout@v3. The azure/login repository itself is on v3 and labels OIDC as recommended. Follow the action's own documentation, not that page's YAML — this is a good general habit when a platform doc and a tool's own README disagree.

And the same idea, one layer down

The pattern repeats between the running application and its dependencies. A container that holds a database password is the same shape of problem as a pipeline that holds a service-principal secret. On Container Apps the answer is a managed identity: grant it the Key Vault Secrets User role, and reference the secret by its Key Vault URI. Leave the version out of the URI and the platform picks up rotations within about thirty minutes, restarting active revisions. The same identity is what pulls from your container registry — which is why the registry's admin account, which Microsoft describes as being for a single user and mainly for testing, should stay switched off.

04 / PROMOTE

Build once, or test something you never ship

If staging and production are built from separate pipeline runs, they are different artefacts — and every hour of testing you did in staging was about a build that no longer exists.

The rule has a name and it is worth stating as an absolute: build the artefact exactly once, then promote that artefact through environments. Not the commit, not the tag, not “the same Dockerfile” — the identical image, addressed by digest.

The failure mode is quiet, which is why it survives. Two builds from the same commit differ in a dozen invisible ways: a transitive dependency that published a new patch, a base image that moved, a build-time timestamp, a different runner image. Most of the time nothing breaks, which teaches everyone that rebuilding is fine, right up until the once that matters.

Promotion or rebuild

Interactive · what changed between environments

What promotion looks like in practice

Build once and tag with something immutable — the commit SHA. Push. Capture the digest, not the tag, because a tag can be moved and a digest cannot. Every subsequent environment deploys that digest.

build:
  outputs:
    digest: ${{ steps.push.outputs.digest }}     # the identity of the artefact
  steps:
    - id: push
      uses: docker/build-push-action@v6
      with:
        push: true
        tags: ${{ env.ACR }}/api:${{ github.sha }}

deploy-staging:
  needs: build
  environment: staging
  steps:
    - run: az containerapp update -n api-staging -g rg-scholarships \
             --image ${{ env.ACR }}/api@${{ needs.build.outputs.digest }}

deploy-production:
  needs: [build, deploy-staging]
  environment: production        # protection rules gate this job — module 05
  steps:
    - run: az containerapp update -n api-prod -g rg-scholarships \
             --image ${{ env.ACR }}/api@${{ needs.build.outputs.digest }}

Note @sha256:… rather than :tag in the deploy steps. It is slightly uglier and it means the thing running in production is provably the thing that passed staging.

The corollary, which people resist: if the artefact is identical everywhere, every difference between environments must come from configuration — which is Stage 13's module 05, and the reason that module comes before this one. A pipeline that promotes a single image is only possible if the image contains no environment.

05 / GATES

Who is allowed to press it, and what has to be true first

A pipeline that anyone can run against production is not a pipeline, it is a shared root shell with better logging.

GitHub's environments are the mechanism, and they do two things that repository secrets cannot. They hold secrets that are only released to jobs targeting that environment, and they enforce protection rules before the job starts — required reviewers, a wait timer, and a policy restricting which branches may deploy at all.

Configure an environment and try to deploy to it.

Choosing the rules rather than collecting them

Each rule answers a different question and there is a cost to every one. Required reviewers (up to six people or teams, optionally preventing self-review) buy human judgement and spend calendar time — the right control for a production database migration and the wrong one for a copy change. A wait timer buys a window in which someone can cancel, and is genuinely useful in front of an irreversible step. A deployment branch policy is the cheapest and most valuable of the three: it makes “production can only be deployed from main” a property of the platform rather than a convention.

My recommendation for the capstone: branch policy on production always; required reviewers only on the deploy job, never on the build; no wait timer unless something downstream is irreversible. And put the OIDC federated credential's subject on the environment — repo:org/repo:environment:production — so that the platform's protection rules and Azure's trust are the same control rather than two things that can disagree.

Branching, briefly, because it decides how much of this you need

Trunk-based development — one main, short-lived branches that live hours or days, merged behind a review and deleted — is what makes a pipeline like this coherent: every merge is a release candidate, so the pipeline runs constantly and stays fast because everyone feels it. Long-lived release branches produce the opposite: rare, large, frightening merges, and a pipeline that is exercised least when it matters most.

The honest counter-argument, and Martin Fowler makes it in his branching-patterns article: feature branching suits contributors you cannot trust with main — open-source drive-bys, contractors — where a review gate before integration is the point. For a committed team building one product, continuous integration wins, and the thing that makes it possible for large changes is not a branch but a feature flag: ship the code dormant, turn it on separately. Azure App Configuration provides this as a managed service with filters for user groups, time windows and percentage rollouts, and it decouples deploy from release — which is the same distinction this whole stage is about.

06 / RELEASE

Shifting traffic, not swapping servers

On Container Apps a deployment creates a revision, and every release strategy you have heard of is a different pattern of weights across revisions.

This is a genuinely clarifying model. A revision is an immutable snapshot of an app version; ingress splits incoming traffic across revisions by weight; and blue/green, canary and rolling are three ways of moving those weights. Nothing is being installed or swapped.

The three, and when each is right

    
    
      
  • Single revision mode is the default and is already safe: the platform provisions the new revision, scales it, waits for its startup and readiness probes, and only then moves traffic — and if it never becomes healthy, traffic stays where it is. For most changes this is the correct amount of ceremony, and Stage 13's four rollout settings are what make it seamless.
    • 
      
  • Blue/green keeps both versions running with labels, so you can hit the new one on its own hostname — https://app---green.… — and verify it under real conditions before it serves anyone. The switch is one command and so is the rollback. The cost is running two full copies.
    • 
      
  • Canary sends a small percentage to the new revision and increases it as evidence accumulates. It is the only one of the three that finds problems proportional to exposure, and it is only meaningful if you are watching the right thing — which is Stage 12's error budget and burn rate, on the new revision specifically.
    • 
    

    
One syntax correction worth having: --traffic-weight is deprecated. The current flags are --revision-weight and, for labelled revisions, --label-weight. Weights must total 100, and latest is a valid target.


    

      
Experiment

      
Do a blue/green release of the capstone and, before shifting any traffic, open the green revision's own label FQDN and click through the three journeys from Stage 10. That is the whole value of blue/green in one action: production configuration, production data, production identity, zero production users. Then shift to 100, and — this is the part that matters — practise the rollback immediately, while nothing is wrong. A rollback you have executed once is a ninety-second operation; one you have only read about is an incident.

07 / UNDO
The number that decides how brave you can be

  
How long from “this is wrong” to “this is no longer serving traffic”? Everything about how a team ships follows from that one figure.


  

    
A team whose recovery time is forty minutes deploys carefully, rarely, and with a change-advisory meeting. A team whose recovery time is ninety seconds deploys ten times a day, because the cost of being wrong is ninety seconds. The deployment frequency is downstream of the rollback time, and teams that want the first without fixing the second get neither.

    
Something has gone wrong. Time the recovery.

The one that is not reversible, and what to do about it

    
A container revision rolls back in seconds. A database migration does not. Rolling back the application while the schema has moved forward gives you an old binary talking to a new schema, which is a different and usually worse failure.

    
This is why Stage 8's expand-contract discipline is a deployment concern rather than a database one. Expand: add the new column, nullable, and deploy code that writes both and reads the old. Migrate the data. Deploy code that reads the new. Only then, in a later release, contract: drop the old column. Every intermediate state is one where both the old and new application versions work — which is precisely the property that makes rollback safe, and the reason the sequence takes three releases instead of one.

    
The rule that follows: never ship a schema change and the code that requires it in the same release. It sounds pedantic until the first time you need to roll back at 2am and cannot.

08 / MEASURE
Five numbers that describe a delivery system

  
Every claim in this stage — order the pipeline, promote one artefact, make rollback cheap — is a claim about these numbers. They are how you find out whether any of it worked.


  

    
DORA's research programme identified a small set of measures that distinguish high-performing delivery organisations, and — worth knowing, because most material has not caught up — the set is now five, and three were renamed. Two describe throughput and three describe instability.

What the correlations actually say

    
The counter-intuitive finding, and the one worth internalising: throughput and stability move together, not against each other. Teams that deploy more often have lower change failure rates and recover faster. The intuition that says “we deploy rarely because we are careful” has the causation backwards — deploying rarely makes each release larger, which makes each release riskier, which justifies deploying more rarely.

    
The mechanism is batch size. A release containing one change has one thing to bisect when it breaks. A release containing forty changes has forty, plus their interactions, and its rollback removes thirty-nine things that were fine.


    
Measuring them without a platform

    
    
      
  • Deployment frequency — count successful production deployment runs. GitHub's deployments API already has this.
    • 
      
  • Change lead time — first commit on the branch to production deploy. A join between the commit timestamp and the deployment timestamp; twenty lines of script.
    • 
      
  • Change fail rate — deployments requiring a fix or rollback, over total deployments. This one needs a convention: label the pull request or the incident, or it cannot be computed.
    • 
      
  • Failed deployment recovery time — from the failed deployment to the resolving one. Module 07's number, measured rather than estimated.
    • 
      
  • Deployment rework rate — the newest of the five, and the one that catches “we deploy constantly” teams whose deploys are mostly fixing the previous deploy.
    • 
    

    
My recommendation is to compute them crudely and early rather than accurately and later. A weekly script that prints five numbers into a channel changes behaviour; a dashboard project that takes a quarter does not. And treat them as a diagnostic for the system, never as a target for the team — deployment frequency is trivially gamed by deploying nothing repeatedly, and the moment a metric becomes a target that is what happens to it.

The capstone increment

    
    
      
  • A pipeline ordered by feedback speed — lint and compile, unit, slice, container-backed integration, image build, scan, then journeys — with concurrency cancelling superseded runs and setup-action dependency caching.
    • 
      
  • Every action pinned by commit SHA, a version comment beside each, Dependabot configured for actions, Maven and npm, and workflow-level permissions: contents: read.
    • 
      
  • No cloud credential in the repository — a federated credential whose subject is repo:…:environment:production, id-token: write on the deploy job only, and azure/login with no client-secret.
    • 
      
  • One build, promoted by digest through staging and production, with the digest carried as a job output and every deploy step referencing @sha256:….
    • 
      
  • Environments with real rules — a branch policy restricting production to main, required reviewers on the production deploy job, and environment-scoped secrets.
    • 
      
  • Provenance attestation on the pushed image, and a verification step that refuses to deploy an image your pipeline did not build.
    • 
      
  • A blue/green release using revision labels, verified on the green label's own FQDN before any traffic shifts.
    • 
      
  • A rollback you have actually performed, timed, written down, and repeated until it is boring — plus one expand-contract migration executed across three releases to prove the schema path works too.
    • 
      
  • Five numbers, weekly, computed from the deployments API and posted somewhere visible.
