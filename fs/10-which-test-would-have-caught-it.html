Which Test Would Have Caught It

Testing appears in none of your deck's 391 slides. “Unit testing” shows up once, as a claimed benefit of constructor injection, and never again. This stage is the whole subject, and it is organised around a single question you can ask about every bug you have ever shipped: which test would have caught this, how long would it have taken to run, and was that a good trade?

01 / THE QUESTION

Start from the bug, not from the coverage number

Coverage tells you which lines ran. It does not tell you which failures you are insured against. Those are different questions, and only one of them is worth money.

The usual way into testing is a taxonomy: here are unit tests, here are integration tests, write some of each. It produces suites that are simultaneously large and useless, because nothing in the taxonomy tells you what a given test is protecting you from.

Here is the other way in. Take thirteen bugs — every one of them a real thing that happens in an application shaped like your capstone — and for each one ask which level of test would have caught it, and what that level costs to run. The answers are not evenly distributed, and the pattern in them is the strategy.

Bug triage board

Interactive · pick a bug

What the pattern says

  1. Most bugs have exactly one cheapest level that catches them, and it is usually not the one people reach for. Validation annotations need the framework. Pagination stability needs a real database. A double-submitted form needs a rendered DOM. Nothing about the bug's severity tells you which level that is — only the mechanism does.
  2. Some bugs are caught at every level and should therefore be tested at the cheapest one. The eligibility rule is a pure function of its inputs. Testing it through an HTTP request costs you three orders of magnitude and tells you nothing extra.
  3. Some bugs are caught at no level. Configuration that differs per environment, and performance regressions that produce correct output, are not test-shaped problems. Pretending otherwise is how suites grow without getting safer. Those belong to deployment verification and to observability — Stages 13 and 12.
  4. The negative case is the test nobody writes. Four of these thirteen are only caught by a test that asserts a request fails. There is no coverage tool that will tell you the test is missing, because the happy-path test already executed every line.

Which is why coverage is a floor, not a target

A test suite can execute 100% of your lines and assert nothing meaningful about any of them. Coverage measures whether a line ran; it cannot measure whether the test would have noticed if the line were wrong. That gap has a name and a tool: mutation testing. A mutation tester such as PIT deliberately breaks your code — flips a > to >=, replaces a return value with a default, removes a method call — and reruns the tests. A mutant that survives is a change to your production code that no test objected to.

That number, the mutation score, is the honest one. It is also expensive to compute, so the practical use is not to chase it continuously but to run it once on the code you actually care about — the eligibility rules, the award calculation, the authorization checks — and look at the survivors. Every survivor is a sentence: “you can change this and nothing will tell you.”

A recommendation, stated as one

Set a coverage floor in CI (60–70% is plenty) purely to stop whole modules arriving untested, and never set a target above it. A team told to reach 90% will reach 90%, and the last twenty points will be tests written to execute lines rather than to check behaviour — which cost real time to run and real time to maintain, and catch nothing. Spend the same effort on mutation-testing your three most consequential classes instead. — This is my architectural recommendation, not a rule from any documentation.

Three habits that produce useless suites

✗Writing one test per method

Methods are an implementation detail; behaviours are not. evaluate() has one method and about nine behaviours — under age, over income, missing guardian consent, expired document, all rules passing, no active rules, and the boundary of each numeric rule. A single evaluateTest() that exercises the happy path gives you 100% coverage of the method and protection against none of the other eight.

The shape that follows from this is the parameterised test: one method, a table of cases, one row per behaviour. In JUnit that is @ParameterizedTest with @CsvSource or @MethodSource; in Vitest it is test.each. Adding the ninth case then costs one line.

✗Asserting that a mock was called

verify(repository).save(any()) asserts that your code did the thing your code does. It will pass for as long as the line exists and fail the moment you restructure it, which is precisely backwards: it is insensitive to bugs and sensitive to refactoring. Module 03 makes this measurable.

There is one honest use for verify: a side effect at a true boundary that has no observable return value — an email actually being dispatched, a message actually being published, an audit row actually being written. There, the interaction is the behaviour.

✗Treating the test suite as write-only

Tests are code with no tests of their own, so the only thing keeping them honest is that you read them. The two symptoms of a suite that stopped being read: assertions that cannot fail (assertNotNull(result) on a method that cannot return null), and tests that were quietly disabled and never re-enabled.

A useful discipline: when a test fails, before fixing the code, break the code differently and confirm the test still fails. A test that only fails one way is often not testing what its name says.

02 / SHAPE

How many of each, and what it costs you

The pyramid and the trophy disagree about the middle. They agree about the top, and the disagreement turns out to be about economics rather than principle.

The test pyramid — Mike Cohn's, popularised by Martin Fowler — says: many fast unit tests, fewer service tests, very few UI tests. The testing trophy — Kent C. Dodds' — says: static analysis at the base, some unit tests, mostly integration tests, few end-to-end. They are drawn as different shapes and are usually presented as rival camps.

They are not really rivals. Both say the same thing about the top of the diagram, and they differ in the middle because an integration test costs a different amount in each ecosystem. In a React application, an “integration” test renders several real components into jsdom with the network stubbed: it crosses no process boundary and takes forty milliseconds. In a Spring application, an integration test boots a container, starts a database and builds an application context: it takes eight seconds. Advice calibrated in one of those worlds does not transfer to the other, and a full-stack engineer needs both calibrations at once.

So put numbers on it. Below, allocate a suite and watch what it buys.

Read the ice-cream cone carefully

It is not a straw man. It is what a suite becomes when tests are added in response to incidents, at whatever level the incident was observed. Every individual decision was reasonable — “this broke in production, let me add an end-to-end test for it” — and the aggregate is a suite that takes twenty minutes, is red a third of the time for no reason, and covers fewer distinct failure modes than a suite a tenth its size.

The three numbers that actually constrain you

  • Feedback latency. How long from pushing to knowing. Under two minutes and people wait for it; past ten and they context-switch, which means every failure now costs a re-entry as well as a fix. This is the number to optimise, and it is why parallelism is not a luxury.
  • Failure precision. When it goes red, how many places could the cause be? A unit test failure names one class. An end-to-end failure names a journey and leaves you to bisect. The pyramid is, in large part, an argument about debugging cost rather than running cost.
  • Flake exposure. The probability the suite goes red when nothing is wrong. It compounds multiplicatively with test count, which is the arithmetic in module 08, and it is the mechanism by which a suite stops being believed.

Where I would put this stack

Concretely, and stated as a recommendation rather than a finding: on the backend, pyramid-shaped with an unusually fat slice layer, because Spring's slices are the cheapest place to test the thing that actually breaks — the boundary where JSON, validation, status codes and security rules meet. On the frontend, trophy-shaped, because a React “integration” test is nearly as cheap as a unit test and vastly more meaningful, and because unit-testing a component in isolation mostly tests React. End-to-end, a fixed small number chosen by revenue — for the capstone: apply, review, award. Three journeys, not thirty, and their job is to prove the pieces are wired together, not to check business rules.

Experiment

Set the preset to Pyramid, note the feedback latency, then drag the end-to-end slider from 6 to 40 and watch three numbers move at once: latency, flake exposure, and — the surprising one — bug classes covered, which barely moves. Then put the E2E count back to 6 and spend the same wall-clock budget on slice tests instead. The comparison is the entire argument for the pyramid, expressed as arithmetic rather than as a diagram.

03 / UNIT

Test the behaviour, or test the code you happened to write

A test that fails when you rename a private method is not protecting you. It is charging you rent.

Everyone agrees that tests should be resilient to refactoring and sensitive to bugs. Nobody disagrees with that sentence, and suites full of brittle tests get written anyway, because the sentence is not actionable — it does not tell you which line in your test file is the problem.

So here is the same claim as an experiment. One service, four ways of testing it, five changes applied to the production code. Four of the changes are meant to be behaviour-preserving; one deliberately changes what the system does. A good test style produces no failures on the harmless changes and a failure on the real one. Watch which styles manage it.

The system under test, in full — this is the whole of what the four styles are testing:

public record EligibilityDecision(boolean eligible, List<String> reasons) { }

public interface Rule {
    String code();
    boolean test(Application app, LocalDate today);
}

public class IncomeRule implements Rule {
    static final BigDecimal MAX_HOUSEHOLD_INCOME = new BigDecimal("250000");
    public String code() { return "INCOME"; }
    public boolean test(Application app, LocalDate today) {
        return app.householdIncome().compareTo(MAX_HOUSEHOLD_INCOME) <= 0;
    }
}

@Service
public class EligibilityService {
    private final RuleRepository rules;
    private final Clock clock;                    // injected, never LocalDate.now()

    public EligibilityDecision evaluate(Application app) {
        var today = LocalDate.now(clock);
        var failed = new ArrayList<String>();
        for (Rule r : rules.findAllActive()) {
            if (!r.test(app, today)) failed.add(r.code());
        }
        return new EligibilityDecision(failed.isEmpty(), List.copyOf(failed));
    }
}

The rule that falls out of it

Mock what you do not own and cannot run. The payment gateway, the email sender, the identity provider, the wall clock. Construct what you do own. IncomeRule is a class you wrote with no dependencies and a microsecond runtime — replacing it with a mock buys you nothing and costs you the ability to notice when its threshold changes.

The clock is the clean example of the other side. LocalDate.now() called directly inside a rule makes the rule untestable at boundaries — you cannot write “a student turning 18 on the deadline” without changing the system clock. Injecting java.time.Clock and passing Clock.fixed(Instant.parse("2026-08-29T00:00:00Z"), ZoneOffset.UTC) in the test makes every date-boundary case an ordinary parameterised row. This is a design change that testing forces, and it is a better design regardless — which is the usual sign that the test was telling you something.

The shape a rules test should have

@ParameterizedTest(name = "{0}: income {1} at age {2} → {3}")
@CsvSource({
    "under both limits,      180000, 17, true",
    "income exactly at cap,  250000, 17, true",     // boundary: <= not <
    "income one over cap,    250001, 17, false",
    "age exactly at cap,     180000, 18, true",     // boundary: eligible on the day
    "age one day over,       180000, 19, false"
})
void decidesEligibility(String name, BigDecimal income, int age, boolean expected) {
    var app = anApplication().withIncome(income).aged(age).build();
    assertThat(service.evaluate(app).eligible()).isEqualTo(expected);
}

Five behaviours, one method, and the two boundary rows are the ones that would have caught bug 1 in module 01. Adding a sixth rule costs one line. Compare that with five separate @Test methods sharing a copy-pasted arrange block — same coverage, five times the surface to maintain, and a strong disincentive against adding the sixth.

Running Mockito on a modern JDK — a current, unobvious requirement

Mockito's default (inline) mock maker attaches a Java agent to the running JVM. Since JEP 451, dynamically loading an agent into a running JVM warns, and the JDK has signalled that it will eventually be disallowed. On Java 21 and above you will see:

Mockito is currently self-attaching to enable the inline-mock-maker.
This will no longer work in future releases of the JDK.

Mockito's own documentation gives the fix, and it is a build change rather than a JVM flag. With Maven and the resolved-artifact syntax:

<plugin>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <argLine>@{argLine} -javaagent:${org.mockito:mockito-core:jar}</argLine>
  </configuration>
</plugin>

You will also see -XX:+EnableDynamicAgentLoading suggested widely, and it does silence the warning. Mockito's documentation lists it only as an alternative and notes that the option is not standardised, so a future JDK may refuse it. Prefer the -javaagent form: it is the one that will still work.

Versions, checked against the current documentation

Two of these will contradict most tutorials you find. JUnit 6 is the current generation — 6.1.x at the time of writing, with Spring Boot 4.1 managing Jupiter 6.0.x. The org.junit.jupiter.* package names and the annotations are unchanged from JUnit 5, so migration is essentially a version bump; what changed is that Platform, Jupiter and Vintage now share one version number instead of the old 1.x / 5.x split, and a handful of deprecated modules were removed. Mockito is 5.23.x, still mockito-core; mockito-inline is no longer published because inline became the default in 5.0.

If you are reading a guide that pins junit-jupiter:5.10 and junit-platform:1.10 as separate versions, it predates this change. The test code in it is still correct.

04 / SLICES

Boot the smallest thing that can fail

Every distinct combination of test annotations is a separate ApplicationContext. Ten variants means ten boots, and nobody tells you.

Spring Boot's test slices exist because the two obvious options are both bad. Testing a controller with plain JUnit and new MyController(mockService) tests a method call, not an endpoint: no JSON serialisation, no validation, no status-code mapping, no security — which is to say, none of the parts that break. Testing it with @SpringBootTest boots your entire application, including the database connection pool and every scheduled job, to check a 400.

A slice boots a named subset of the auto-configuration. @WebMvcTest starts the web layer — the dispatcher, the argument resolvers, the message converters, the exception handlers, the security filter chain — and nothing else. Your service layer is absent, so you supply it with @MockitoBean. The context is small, it boots in around a second, and it exercises exactly the machinery that produces HTTP-shaped bugs.

The context cache, which is the thing that actually determines your suite's runtime

    
Spring's test framework caches application contexts across the whole test run, keyed by the full configuration: which classes, which profiles, which properties, which bean overrides, which initialisers. Two test classes with identical annotations share one context and one boot. Two test classes where one adds a single @TestPropertySource get two contexts and two boots.

    
This is why a suite that “only has forty integration tests” can take six minutes: it has forty tests spread across eleven distinct context configurations, and it is paying eleven startups. The fix is nearly always to consolidate — one shared base test class with the annotations on it, deviations only where genuinely required — and it can turn six minutes into ninety seconds without deleting a single test. Turn the toggle above off and on to see the difference on a hundred-test suite.

Two more Boot 4 changes that will bite

    
    
      
  1. @MockBean and @SpyBean are removed, not deprecated. The replacements are Spring Framework's @MockitoBean and @MockitoSpyBean, from org.springframework.test.context.bean.override.mockito.     2. 
      
  2. @SpringBootTest no longer auto-configures MockMvc. You must add @AutoConfigureMockMvc explicitly. In Boot 3 this was implicit, so the symptom is an existing test suite failing to inject MockMvc immediately after an upgrade.

MockMvcTester, and why the assertions read better

    
Classic MockMvc chains Hamcrest matchers: mvc.perform(get("/x")).andExpect(status().isOk()). It still works and is still documented. Boot now also auto-configures MockMvcTester when AssertJ is on the classpath, which gives you ordinary AssertJ assertions on the exchange — the practical benefit being that failures print the actual response rather than a matcher mismatch, and that you can assert on a deserialised body without a second parse step.

  



@WebMvcTest(ApplicationController.class)
@Import(SecurityConfig.class)                     // slices exclude your @Configuration
class ApplicationControllerTests {

    @Autowired MockMvcTester mvc;
    @MockitoBean ApplicationService service;      // not @MockBean — removed in Boot 4

    @Test
    @WithMockUser(roles = "STUDENT")
    void rejectsAnApplicationWithNoGuardianEmail() {
        assertThat(mvc.post().uri("/api/v1/applications")
                .contentType(APPLICATION_JSON)
                .content("""
                    { "studentId": 221, "guardian": { "email": null } }
                    """))
            .hasStatus(HttpStatus.UNPROCESSABLE_ENTITY)
            .bodyJson()
            .extractingPath("$.errors[0].field").isEqualTo("guardian.email");
    }

    @Test
    void requiresAuthentication() {                // the negative case nobody writes
        assertThat(mvc.get().uri("/api/v1/applications")).hasStatus(HttpStatus.UNAUTHORIZED);
    }
}


  

    
Three things are being tested there that no unit test can reach: that @Valid is actually wired to the argument resolver, that your @RestControllerAdvice produces the problem-detail shape from Stage 7 with the field path the React form expects, and that the security rules from Stage 9 deny an anonymous request. All three are configuration, and configuration only exists once the framework runs.


    

      
Challenge

      
Take the error contract you designed in Stage 7 and write a single parameterised @WebMvcTest that asserts its shape for all four failure classes: a validation failure (422), a missing resource (404), an authorization denial (403) and an unhandled server error (500). Assert on type, title, status and the presence of an instance identifier. That one test file is the executable version of your API's error documentation — and it will fail the day someone adds a controller that throws an exception nobody mapped.

05 / REAL
H2 is a different database

  
Your deck's application runs on H2 and mentions PostgreSQL once, in a production-profile example. Every test that passes on H2 is a test about H2.


  

    
The argument for an in-memory database in tests is speed, and it was a good argument when the alternative was a shared development server that three people were also using. It is a much weaker argument now, because the alternative is a container that starts in about eight seconds once per suite.

    
The argument against is not that H2 is bad software. It is that H2 is a different database, and the differences are concentrated in exactly the features you reach for when a query stops being trivial. Stage 8 was largely about those features. Every one of them is a place where an H2-backed test tells you something true about H2 and nothing at all about production.

The honest case for H2, so this is not one-sided

    
If a repository test only exercises save, findById and a derived query over indexed columns, H2 will give you the same answer as PostgreSQL and will do it in fifty milliseconds instead of eight seconds. For a suite of two hundred such tests that is a real difference, and a team that runs them on every save rather than every push is getting genuine value from the speed.

    
The problem is that nothing marks the boundary. There is no warning when a query crosses from “H2 agrees” to “H2 is guessing”, and the crossing usually happens as a small edit to an existing passing test. My recommendation is therefore the blunt one: use the real database for every test that touches SQL, accept the eight seconds once per suite, and spend the saved uncertainty elsewhere. If you keep H2 for a fast inner loop, treat it as a linter — useful, not authoritative — and never let it be the only thing that runs before a merge.


    
Testcontainers, and a breaking change you will hit immediately

    
Testcontainers 2.0 renamed everything. Module artifacts gained a testcontainers- prefix, container classes moved into per-module packages, JUnit 4 support was dropped, and the no-argument module constructors were removed — you must name the image. Any guide written before this will not compile, and the compile error points at the import rather than at the cause.

  



<!-- Maven. Note the artifactId prefix: this is Testcontainers 2.x -->
<dependency>
  <groupId>org.testcontainers</groupId>
  <artifactId>testcontainers-postgresql</artifactId>   <!-- was: postgresql -->
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>com.redis</groupId>                        <!-- Redis has no official module -->
  <artifactId>testcontainers-redis</artifactId>
  <scope>test</scope>
</dependency>



import org.testcontainers.postgresql.PostgreSQLContainer;   // was o.t.containers.*
import com.redis.testcontainers.RedisContainer;

@SpringBootTest
@Testcontainers
abstract class IntegrationTestBase {

    @Container @ServiceConnection
    static final PostgreSQLContainer POSTGRES =
        new PostgreSQLContainer("postgres:17-alpine");

    @Container @ServiceConnection
    static final RedisContainer REDIS =
        new RedisContainer("redis:7-alpine");
}


  

    
Two details in that snippet carry most of the value.

    
@ServiceConnection replaces @DynamicPropertySource. You are no longer writing registry.add("spring.datasource.url", postgres::getJdbcUrl) for every property; Boot derives the connection details from the container itself. Less code, and — more usefully — it cannot drift out of sync with the property names when Boot renames one.

    
static on an abstract base class is the performance decision. A static container starts once for the JVM and is shared by every test class that extends the base. A non-static @Container field starts and stops a container per test method, which turns an eight-second cost into an eight-second-per-test cost. This single keyword is the difference between a two-minute integration suite and a forty-minute one, and it is the most common Testcontainers mistake by a wide margin.

    
Container reuse — withReuse(true) plus testcontainers.reuse.enable=true in ~/.testcontainers.properties — keeps the container alive between runs and makes the local loop feel instant. It remains explicitly experimental in the documentation, it requires per-developer opt-in by design, and it should not be enabled in CI, where a fresh container is the point.


    
What to do about the data

    
Two rules that prevent most integration-test pain. Run your real Flyway migrations against the container, from empty, in order, on every run — that is what turns bug 6 in module 01 from a 3am deployment failure into a red build. And make each test responsible for its own data, either by rolling back (@Transactional on the test, which Spring rolls back by default) or by truncating between tests. Shared fixture data that accumulates is how a suite becomes order-dependent, and order-dependence is the flakiness that is hardest to diagnose because the failing test is never the guilty one.


    

      
Architecture connection

      
The pagination bug from Stage 8 — page 2 repeating a row from page 1 because the sort was not total — is the cleanest demonstration in this stage of why the database has to be real. On H2 the rows come back in insertion order and the test passes indefinitely. On PostgreSQL, with enough rows to make the planner choose a parallel sequential scan, the same query returns rows in an order the planner is entitled to change. The bug is not in your code; it is in an assumption your code makes about a freedom the database has. Only the database that has that freedom can tell you.

06 / QUERIES
Find the element the way a user would

  
A test that breaks when you rename a CSS class is testing your stylesheet. A test that breaks when you replace a button with a div is testing something real.


  

    
React Testing Library is built on one claim, and it is worth quoting because everything else follows from it: “The more your tests resemble the way your software is used, the more confidence they can give you.” In practice that is a statement about how you find elements. The library deliberately gives you no way to select by class name or component name, because a user cannot perceive either.

    
The consequences are easiest to see as a survival test. Six ways of finding the same two elements; six changes to the component. Some of the changes are cosmetic, one is an accessibility regression, and one is an accessibility fix — and the interesting result is that the good selectors distinguish between them.

The priority order, and the reasoning behind it

    
Testing Library documents a query priority, and it is not arbitrary — it is ordered by how closely each query resembles how someone actually finds the thing.

    
    
      
  1. getByRole, with the accessible name. This is what assistive technology sees, so a test written this way fails exactly when the element stops being reachable. It is the only query in the list that doubles as an accessibility assertion.
    2. 
      
  2. getByLabelText for form fields — the same argument, specialised to inputs.
    3. 
      
  3. getByPlaceholderText, getByText, getByDisplayValue — visible text, which real users do use, but which is also the thing that changes when copy or language changes.
    4. 
      
  4. getByTestId, last and deliberately so. It survives everything, which sounds like a virtue and is actually the problem: it survives the button becoming a div. It is the right choice when there is genuinely nothing perceivable to grab — a chart container, a virtualised row — and the wrong choice everywhere else.
    5. 
    

    
Note what is missing from the list entirely: querying by CSS class, by tag, or by component. Those are not slow or discouraged; they are unavailable, and that constraint is the library's main contribution.


    
userEvent, not fireEvent

    
fireEvent.click(el) dispatches one click event. A real click also moves the pointer, fires pointerdown, mousedown, focus, pointerup, mouseup and click, and will not happen at all if the element is disabled or covered. userEvent.click(el) simulates the sequence, which means it catches a class of bug fireEvent cannot: a handler that depends on focus, or a button that a test can click but a user cannot.

    
user-event v14 is asynchronous and requires a setup call. This is the shape:

  



import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("cannot submit twice", async () => {
  const user = userEvent.setup();                 // v14: set up per test
  const onSubmit = vi.fn();
  render(<ApplicationForm onSubmit={onSubmit} />);

  await user.type(screen.getByLabelText(/household income/i), "180000");
  const submit = screen.getByRole("button", { name: /submit application/i });

  await user.click(submit);
  await user.click(submit);                        // the impatient double-click

  expect(submit).toBeDisabled();
  expect(onSubmit).toHaveBeenCalledTimes(1);        // bug 8 from module 01
});


  

    
Waiting, and the two things people get wrong

    
getBy* throws immediately if the element is absent. queryBy* returns null and is the only correct choice for asserting absence. findBy* is asynchronous and retries until a timeout, and is what you want after anything that resolves — a fetch, a transition, a suspense boundary. The common error is await waitFor(() => expect(screen.getByText("Saved")).toBeInTheDocument()), which works but is a longer spelling of await screen.findByText("Saved"). The other common error is asserting absence with getBy*, which throws rather than failing, producing a confusing message.

    
The act(...) warning, when it appears, almost always means state updated after the test finished — usually an un-awaited promise. It is a real signal about a race in your component, not a formality to silence.


    
Snapshot tests, evenly

    
The case for: a snapshot of a serialiser's output, or of a rendered error page, is a cheap regression net over something with many fields and no interesting logic. The case against, for components: a snapshot asserts nothing in particular, so when it fails the reviewer has no basis for deciding whether the diff is a bug or a change, and the reliable outcome is that snapshots get updated rather than read. My position is that they belong to data, not to UI — and that a component test asserting three specific things a user can perceive is worth more than a snapshot of the whole tree.


    

      
Install-time gotcha worth knowing before you hit it

      
@testing-library/react v16 moved @testing-library/dom from a dependency to a required peer dependency. If you install only @testing-library/react, nothing resolves and the error names a module you never asked for. Install all three: @testing-library/react, @testing-library/dom and @testing-library/user-event. TypeScript users also need @types/react-dom separately. React 19.2 is supported — the published peer range accepts React 18 and 19.

    


    
And a Vitest 4 note, since most guides predate it

    
Vitest 4 removed the workspace configuration in favour of projects declared inside vitest.config.ts; there is no vitest.workspace.js any more. Browser mode is no longer experimental, and imports moved from @vitest/browser to vitest/browser. Coverage changed too: coverage.all and coverage.extensions are gone, and you now specify coverage.include explicitly — which, if you upgrade without noticing, silently narrows what your coverage report is measuring.

07 / BOUNDARY
Where you cut the network decides what you can catch

  
Every frontend test replaces the network with something. The only question is how far down you cut — and each depth is blind to a different class of bug.


  

    
This is the decision that determines whether a frontend suite is worth its runtime, and it is usually made by accident, by copying whatever the first tutorial did. Five plausible places to cut, six integration bugs, and the results are not close.

  


  

    
Mock boundary
Interactive · pick a bug

    

      

        

    

    

      

      

      

    

  


  

    
Why intercepting at the network is different in kind

    
When you write vi.mock("./api/applications"), your test and your production code are now two expressions of the same belief. If the belief is wrong — the path is wrong, the method is wrong, the header is missing — both are wrong together and the test passes. This is the failure mode that makes people distrust frontend tests, and it is not a discipline problem; it is structural.

    
Mock Service Worker cuts below all of your code. The request is made for real, by your real client, and is intercepted at the network layer, which means the request itself becomes an object you can assert about: its URL, method, headers and body. A wrong path is no longer invisible — it arrives at a handler that does not exist.

    
That last part only works if you turn it on. The single most important line in an MSW setup:

  



import { setupServer } from "msw/node";
import { http, HttpResponse } from "msw";

export const server = setupServer(
  http.get("/api/v1/applications/:id", ({ params }) =>
    HttpResponse.json({ id: Number(params.id), status: "SUBMITTED", awardedAt: null })
  )
);

beforeAll(() => server.listen({ onUnhandledRequest: "error" }));  // ← this line
afterEach(() => server.resetHandlers());                          // per-test overrides die here
afterAll(() => server.close());


  

    
The default is "warn", which prints to a console nobody reads. With "error", a request your handlers do not cover fails the test — so a typo in a path, a call to an endpoint you forgot about, and an accidental request to a third-party analytics script all become visible. It converts MSW from a stubbing convenience into an assertion about your application's entire network surface.


    
Testing the six states from Stage 4, properly

    
Stage 4 argued that a screen has six async states and that most bugs live in the four nobody designs. MSW is how you actually reach them, because you can override a handler for a single test:

  



test("shows the server's field errors on the right inputs", async () => {
  server.use(                                        // override, just for this test
    http.post("/api/v1/applications", () =>
      HttpResponse.json({
        type: "https://api.scholarships.org/errors/validation",
        title: "Validation failed", status: 422,
        errors: [{ field: "guardian.email", message: "Already registered" }]
      }, { status: 422 })
    )
  );

  const user = userEvent.setup();
  render(<ApplicationForm />, { wrapper: Providers });
  await user.click(screen.getByRole("button", { name: /submit/i }));

  // the assertion that catches bug 9: the message lands on the right field
  expect(await screen.findByRole("textbox", { name: /guardian email/i }))
    .toHaveAccessibleDescription(/already registered/i);
});


  

    
Four more server.use overrides give you the other states: a 500, a slow response for the loading assertion, an empty array for the empty state, and a network error for the offline case. Each is three lines, each covers a state your users will reach, and none of them requires a backend to be running.


    
The ceiling, and where contract testing starts

    
Be clear about what MSW does not fix. Your handlers are handwritten, so they encode your belief about the server's responses. If the backend renames awardedAt to awardDate, every frontend test still passes, because your handler still returns the old name. No amount of frontend testing catches that, and it is the single most common way a green frontend suite ships a broken screen.

    
Two things do fix it, and they are worth naming even though this stage does not teach them fully. Generate the types from the API's OpenAPI document — with openapi-typescript or similar — so that a renamed field becomes a TypeScript error at the moment you pull the new schema, which moves the bug down to level 0. Or write a consumer-driven contract test, with Pact or Spring Cloud Contract, where the frontend publishes the shape it depends on and the backend's build verifies it still produces that shape. The first is cheap and covers structure; the second is more work and covers semantics as well. For a two-team system, generated types plus one integration test per critical endpoint is usually the right place to stop.


    

      
Experiment

      
Add onUnhandledRequest: "error" to an existing MSW setup on a real project and run the suite. Most codebases discover at least one request they did not know they were making — a font, an analytics beacon, a health check, or an endpoint that was renamed six months ago and whose old path is still being called from one component that nobody opens. The list it prints is a genuine inventory of your application's network surface, and you cannot get it any other way this cheaply.

08 / JOURNEYS
The arithmetic of a flaky suite

  
Two hundred end-to-end tests, each 99.5% reliable, and your build is red more often than green. That is not a mood. It is 0.995 to the power of 200.


  

    
Everyone knows end-to-end tests are flaky. Almost nobody has done the multiplication, and the multiplication is the argument — because per-test reliability that sounds excellent produces suite reliability that is unusable, and the crossover happens at a suite size teams reach without noticing.

What the retry column is really buying

    
Retries fix the arithmetic completely — two retries take a 37% green rate to essentially 100% — and that is exactly why they are dangerous. A retry does not distinguish between “the browser was slow” and “there is a genuine race condition in the application that manifests once in two hundred attempts.” Both go green on the second attempt. You have not removed the flakiness; you have removed your ability to see it, and the race is still there in production, where there are no retries.

    
The defensible position, and it is the one Playwright's own guidance points at: retries are for infrastructure, not for your code. Enable them in CI where the environment is genuinely noisier, keep them off locally so you feel the problem, and — the part that makes it honest — report retried tests as a first-class signal. A test that passed on retry did not pass. Track the list, and treat a test that appears on it twice in a week as a bug ticket rather than a nuisance.


    
Why end-to-end tests flake, and what removes most of it

    
The single largest cause is a test that asserts on a moment rather than on a condition. await page.waitForTimeout(500) encodes a guess about how long something takes, and a guess that is right on your laptop is wrong on a loaded CI machine. Playwright's assertions retry by design — await expect(locator).toBeVisible() polls until it is true or the timeout expires — and swapping guesses for conditions removes most flakiness without any other change.

    
    
      
  • No waitForTimeout, ever, in a test. If you need it, you are missing an assertion about what you are waiting for.
    • 
      
  • Log in once, not per test. Authenticate in a setup project, save storageState, and load it into every test's context. This removes both the slowest step and the most frequently flaking one.
    • 
      
  • Isolate the data per worker. Two workers creating an application with the same student id will collide intermittently, and the failure will look like a UI bug. Seed per-worker prefixes, or create the data the test needs inside the test.
    • 
      
  • One browser context per test. Playwright's default already does this; the mistake is reintroducing shared state through a shared database or a module-level variable.
    • 
      
  • Assert on roles and text, not on CSS. Same argument as module 06 — getByRole works in Playwright too, and a locator tied to a class name will break on a restyle and look like flakiness.
    • 
    


    
Choosing the journeys

    
The selection rule that survives contact with a real backlog: an end-to-end test earns its place if its journey failing silently would cost money or trust. For the capstone that is three — a student completing and submitting an application, a reviewer opening and scoring one, and an award being issued and notified. Everything else — every validation rule, every filter, every empty state — is cheaper and more precisely tested one or two levels down.

    
The corollary is uncomfortable and worth stating: when an end-to-end test fails for a business-rule reason, the correct response is usually to delete it and write the rule test at a lower level, not to fix it. A suite of three journeys that is always believed is worth more than a suite of eighty that is routinely re-run until green.


    
Playwright or Cypress, without picking a winner

    
Cypress runs inside the browser alongside your application, which produces an excellent debugging experience — time-travel through every command, the DOM at each step, a very good interactive runner — and a genuinely gentler learning curve. Its architecture is also its constraint: running in-page makes multi-origin flows, multiple tabs and true parallel execution harder, and parallelisation is a paid cloud feature.

    
Playwright drives the browser from outside over the DevTools protocol. That gives real Chromium, Firefox and WebKit, multiple contexts and origins without ceremony, parallel workers in the open-source runner, and a trace viewer that records a complete run for after-the-fact debugging. The cost is that the debugging story is post-hoc rather than live, which some people find less pleasant.

    
For this stack I would choose Playwright, and the reason is specific rather than tribal: the capstone has multi-role journeys — a student submits, a reviewer scores, an administrator awards — and expressing that as three browser contexts in one test is natural in Playwright and awkward in Cypress. If your application is single-role and single-origin, that argument does not apply and the choice comes down to which runner your team will actually enjoy using, which is not a trivial criterion.


    

      
Challenge

      
Write the reviewer journey as one Playwright test with two browser contexts in the same test: the student submits an application in context A, and the reviewer — already authenticated via a different storageState — sees it appear in their queue in context B. This is the test that proves the whole stack is wired together, and it is the one thing no lower level can tell you. Then set retries: 0 locally and run it twenty times. Every failure is a real race, and finding them now is much cheaper than finding them in an incident.

Where your deck helps, and where it stops

    
It does not help here at all, and this is the largest single gap in it. Across 391 slides there is no JUnit, no Mockito, no @SpringBootTest, no MockMvc, no Testcontainers, no Vitest, no React Testing Library and no Playwright. The phrase “unit testing” appears once, on the constructor-injection slide, as a benefit that is claimed and then never demonstrated. Nothing in the deck is wrong on this subject, because the deck does not say anything about it — but a course that builds a full-stack application and never runs a test has taught the part of the job that is visible in a demo and skipped the part that determines whether the application can be changed after it ships.

    
Treat everything above as additive rather than corrective, and reread the deck's dependency-injection material with module 03 in mind: constructor injection matters precisely because it lets you construct the object under test with the collaborators you choose. That is the slide's claim, and this stage is what the claim was for.
