Full-Stack Atlas · Stage 04 · Level 2 Frontend

Screens That Survive

Stage 3 was about how React works. This one is about the decisions that decide whether an application is still pleasant to change in two years: where the boundaries go, what a screen does when there is no data, where errors land, and how a filtered list stays a shareable link.

01 / BOUNDARIES

Composition beats configuration

Every new requirement adds one boolean prop. How many components do you now have?

Component architecture rarely goes wrong at the start. It goes wrong one reasonable prop at a time. Someone needs a compact variant, so isCompact. Then a version without actions, so hideActions. Then a selected state, an icon slot, a loading skeleton. Each addition is defensible; the aggregate is a component nobody wants to touch.

The arithmetic is what makes this concrete, and it is not intuitive until you see it.

Prop surface

Interactive · add requirements

The rule underneath

Flags multiply; slots add. Six booleans describe sixty-four states, of which perhaps eight are real and two are tested. Six slots describe six insertion points that compose freely and independently, and the component never needs to know what goes in them.

This is also the answer to the old “container versus presentational” dichotomy, which has aged poorly as a filing rule and aged well as an instinct. The useful version is not two folders. It is: a component should either decide something or display something, and the ones that display should be ignorant of where the data came from. A ScholarshipCard that calls useQuery cannot be used on the print view, in a Storybook story, or in the NGO's export screen. One that takes a scholarship prop can be used everywhere, forever.

Four questions that settle most boundary arguments

  • Would I ever render this without the other part? If yes, they are two components. If never, splitting them adds a props contract for nothing.
  • Does this component know something it should not? A card that knows about pagination, a row that knows about routing, a form field that knows about your API — each is a coupling that will block reuse.
  • Is the props list growing faster than the component's job? That is the flags-multiplying smell. Convert the next flag into a slot.
  • Can I describe it in one sentence without “and”? “Shows a scholarship and handles the apply flow and tracks analytics” is three components wearing a trenchcoat.

What does not settle a boundary argument: file size. A 300-line component that does one thing coherently is better than four 80-line components that only exist together and must be read as a set.

Challenge

Take the capstone's application review screen — student summary, document list, eligibility checks, reviewer notes, approve/reject actions — and draw the boundaries twice: once optimising for reuse across the student, reviewer and admin views, and once optimising for a single reviewer screen you can read top to bottom. Then argue for one. There is a right answer, and it depends on how many of those three views actually exist yet.

02 / STATES

Every async surface has six states, not two

Your table renders data and a spinner. What does it show when the search matches nothing, or when the request 403s?

The gap between a demo and a product is almost entirely here. Demos have data. Products have a first-run user with no records, a filter that matches nothing, a reviewer who lost permission this morning, a network that dropped, and a cache that is showing yesterday's numbers while today's are fetched.

Each of these needs a different screen, and — this is the part usually missed — two of them look identical and mean opposite things. An empty list because nothing exists yet is an onboarding moment. An empty list because a filter is too narrow is a dead end the user created and can undo. Showing the same “No results” for both is how a first-run user concludes your product is broken.

Two rules that make these cheap to build

Model the states, do not infer them. Stage 2's discriminated union does the work here: a surface that receives Result<Scholarship[]> cannot render an error and data simultaneously, because the type does not permit it. The two empty states are then a plain question asked at the ready branch — were any filters applied? — rather than another flag.

Skeletons should match the shape they replace. A skeleton whose rows are a different height than the real rows causes a layout shift the moment data lands, which is a measurable Core Web Vitals failure (CLS) and a visible flinch. Build the skeleton from the same layout primitives as the row, not from a generic grey block.

// The whole surface, with every state accounted for and none possible twice.
function ScholarshipList({ result, filtersApplied, onClearFilters, onRetry }: Props) {
  switch (result.status) {
    case "loading": return <ListSkeleton rows={5} />;
    case "error":
      return result.error.status === 403
        ? <Forbidden />
        : <ErrorPanel problem={result.error.problem} onRetry={onRetry} />;
    case "ready":
      if (result.data.length === 0) {
        return filtersApplied
          ? <NoMatches onClear={onClearFilters} />    // user's doing — offer the undo
          : <FirstRun />;                             // nothing exists — offer the first step
      }
      return <Rows data={result.data} stale={result.isStale} />;
  }
}

Loading, more precisely

“Loading” is three different situations and the right treatment differs for each. A first load with no previous data gets a skeleton. A background refetch with data already on screen gets a subtle staleness marker and keeps the old data — replacing a populated table with a spinner is strictly worse than showing slightly old numbers. A user-initiated mutation gets its feedback on the control that started it, not on the whole page: the Submit button becomes busy, the form does not disappear.

✕A full-page spinner on every refetch

The user loses their scroll position, their place in the table, and any sense that the app is fast. Once you have data, keep it on screen and mark it stale. This is the default behaviour of a decent query library and it is the reason Stage 5 recommends one.

✕Error messages that quote the exception

“TypeError: Cannot read properties of undefined” tells the user nothing and tells an attacker something. Say what failed, whether it is likely to work on retry, and give them the action. Put the technical detail behind a correlation ID that your logs can find — Stage 12.

✕Treating 403 as retryable

A Retry button on a permissions failure invites the user to click it forever. Stage 1's distinction is a UI decision as much as a protocol one: 401 means refresh the credential and try again, silently; 403 means explain and offer a different route.

03 / ROUTES

Routing is architecture, not navigation

Which layouts wrap this URL, which loaders run, and in what order?

Your deck covers React Router's data APIs properly — createBrowserRouter, nested routes, Outlet, loader, action, errorElement, the navigation hooks. What it does not do is treat the route config as what it actually is: the highest-level structural decision in the front end. It decides what is shared, what is guarded, what code is downloaded when, and what a user can bookmark.

Pick a URL and a signed-in role and watch the whole match resolve.

Route config

What renders

Four things the route config buys you

  • Shared shell without prop drilling. A layout route renders the header, sidebar and toasts once and puts an <Outlet /> where its children go. Navigating between siblings does not remount the shell — the header keeps its state, the scroll container keeps its position.
  • Guards in one place. A protected layout route wrapping a subtree means every route beneath it is protected by construction, and a new page added there next month is protected without anyone remembering. The alternative — a guard inside each page — fails the moment someone forgets.
  • Parallel data loading. Loaders for every matched route in the chain start together, not in a waterfall. A page composed of three nested routes fires three requests concurrently while the code is still downloading — this is Stage 2's Promise.all lesson applied by the router on your behalf.
  • Code splitting along a boundary users already understand. lazy() on a route means the admin bundle never reaches a student's browser. Route boundaries are the one split point that is both natural and measurable.
const router = createBrowserRouter([
  { path: "/", element: <AppShell />, errorElement: <RootError />, children: [
      { index: true, element: <Dashboard /> },
      { path: "login", element: <Login />, action: loginAction },

      // One guard, protecting everything below it — including routes not written yet.
      { element: <RequireAuth />, children: [
          { path: "students", element: <StudentsLayout />, loader: studentsLoader, children: [
              { index: true, element: <StudentList /> },
              { path: ":studentId", element: <StudentDetail />, loader: studentLoader,
                children: [{ path: "documents", element: <Documents />, loader: docsLoader }] },
          ]},
          // Role guards compose: authenticated AND holds REVIEWER.
          { element: <RequireRole role="REVIEWER" />, children: [
              { path: "review", lazy: () => import("./review/route") },
          ]},
      ]},
      { path: "*", element: <NotFound /> },
  ]},
]);

The guard that is not a guard

Say this plainly, because it is the most common misunderstanding on the front end: <RequireRole> is a user-experience control, not a security control. It stops a reviewer from seeing a broken admin screen. It does not stop anyone from reading admin data, because the check runs in code the user's browser downloaded and can modify. Every route guard must have a matching authorization rule at the API — Stage 9's @PreAuthorize and object-level check. A front end without a matching backend rule is a locked door in a wall made of glass.

Architecture connection

Route boundaries, code-split boundaries, guard boundaries and cache-key boundaries want to be the same boundaries. When they are, Stage 5's query keys fall out of the URL, Stage 11's bundle budget is enforced per route, and Stage 14's deployment can serve a different admin bundle entirely. When they are not, every one of those becomes a bespoke problem.

04 / FORMS

Forms, and the render you did not need

Why does a controlled form re-render your whole component on every keystroke — and does it matter?

Your deck teaches forms exactly one way: a React Router <Form> posting to an action. That is a genuinely good pattern for a whole-page submission, and it degrades gracefully. It is not enough for the capstone's onboarding wizard, which needs per-field validation, cross-field rules, async availability checks, an unsaved-changes guard and server errors mapped back onto specific inputs.

The form below is real. Type into it, submit it, and watch the render counters.

Why the counters diverge

A controlled input keeps its value in React state, so every keystroke is a setState and therefore a render of the component holding it — and, per Stage 3, of everything beneath it. With one small form nobody notices. With a forty-field onboarding wizard containing a date picker and a document uploader, people notice.

React Hook Form keeps values in the DOM (uncontrolled, read through refs) and subscribes only the parts of your UI that actually display something derived from them. Renders happen when validation state changes, not when characters change. That is where the ratio in the counters comes from — and it is a design consequence, not a micro-optimisation.

// One schema, shared with the API client from Stage 2 — never a second copy.
const applicationForm = z.object({
  studentName:   z.string().min(2, "Enter the student's full name"),
  email:         z.string().email("That does not look like an email address"),
  cohort:        z.coerce.number().int().min(2000).max(2100),
  amount:        z.coerce.number().positive("Requested amount must be above zero"),
  guardianEmail: z.string().email().optional().or(z.literal("")),
  consent:       z.literal(true, { errorMap: () => ({ message: "Consent is required" }) }),
});

const { register, handleSubmit, setError, formState: { errors, isSubmitting } } =
  useForm<z.infer<typeof applicationForm>>({
    resolver: zodResolver(applicationForm),
    mode: "onTouched",          // validate after first blur, then live
  });

async function onSubmit(values) {
  try {
    await apiPost("/applications", values, applicationSchema);
  } catch (e) {
    // Map RFC 9457 field errors from Spring's @Valid handler back onto inputs.
    if (e instanceof ApiError && e.status === 422) {
      for (const { field, message } of e.problem.errors ?? []) {
        setError(field, { type: "server", message });
      }
      return;
    }
    throw e;                  // anything else belongs to the error boundary
  }
}

The mode question, settled

onChange validates while the user is still typing, so the first character of an email address is marked invalid — accusatory and wrong. onSubmit is polite but hides five errors until the end, then scrolls the user around hunting for them. onTouched is the right default: say nothing until the user has left a field, then correct live as they fix it. This is an interaction-design recommendation with usability evidence behind it rather than a framework requirement, and the lab above lets you feel the difference.

What the client must never own

Client validation is a courtesy — instant feedback so the user is not waiting on a round trip. It is not a rule. The same constraints live in Jakarta Bean Validation on the Spring Boot DTO (Stage 7), and those are the ones that count, because the client's copy runs on a machine the user controls. When the two disagree, the server wins and the client's job is to display the server's answer on the right field. That is what setError above is doing.

✕Two schemas — one for the form, one for the API

They will diverge, and the failure mode is a form that happily submits a payload the server rejects. Derive both from one Zod schema, as Stage 2 established; where the shapes genuinely differ (a form has a confirm-password field the API does not), express that as a transform, not a second definition.

✕Disabling submit until the form is valid

It feels tidy and it is hostile: the user sees a dead button with no explanation of what is wrong. Leave it enabled, validate on submit, and move focus to the first error. A disabled control that cannot say why it is disabled is an accessibility failure as well as a usability one.

✕Errors that are not associated with their input

Red text near a field is not an association. Screen readers need aria-invalid and aria-describedby pointing at the message, and the message needs to say what to do — “Enter the student's full name”, not “Invalid”. Stage 4 of the capstone is where accessibility either gets built in or gets retrofitted expensively.

05 / LISTS

Search, filter, sort, paginate — and the URL that carries them

A reviewer finds a useful view and sends the link to a colleague. Do they see the same thing?

This is the screen the capstone lives or dies on, and the deck never builds it. Four independent controls, one server request, and one hard rule: the query string is the state. Not component state that happens to also update the URL — the URL is where it lives, and the components read from it.

Everything good follows from that. The view is shareable. The back button works. A refresh does not lose the filters. The query key for Stage 5's cache is derived from it for free. And when a reviewer says “it was slow for me”, they can send you the exact URL.

Client-side or server-side? Decide once, with a number

    
The lab above filters in the browser because it holds twenty-four rows. That is the right call for twenty-four rows and the wrong call for four thousand. The threshold is not a matter of taste:

    
    
      
  • Filter on the client when the entire dataset is small enough to send (roughly a few hundred rows, tens of kilobytes), stable enough to cache, and the user benefits from instant response. A dropdown of NGOs, a list of document types, a settings page.
    • 
      
  • Filter on the server when the dataset is unbounded, is subject to row-level authorization, or contains data this user must not receive. This last one is decisive and often missed: filtering on the client means you sent every row first. An NGO reviewer's browser must never receive the applications belonging to other NGOs, however carefully the table hides them.
    • 
    

    
The four rules that stop the bugs

    
    
      
  1. Changing a filter resets the page to zero. Otherwise the user is on page 7 of a result set with 2 pages and sees an empty table — the single most common bug in this screen, and it is why the URL helper in Stage 3 deleted page whenever any other parameter changed.
    2. 
      
  2. Debounce the search, not the filters. Typing produces a request per keystroke without it; a dropdown change is one deliberate act and should feel instant.
    3. 
      
  3. Sort must be total. Sorting by a non-unique column with a keyset or an unstable database sort can return the same row on two pages and skip another. Always append a unique tiebreaker — sort=amount,desc&sort=id,asc.
    4. 
      
  4. Offset pagination degrades. OFFSET 40000 makes PostgreSQL walk forty thousand rows to discard them. For deep pages or infinite scroll, keyset pagination (“give me the 20 after id 8891”) is constant-time. Stage 8 shows the query plans that make this obvious.
    5. 
    

    
Note also what the response above carries: a totalElements count. That count costs the database a second aggregate query on every page load, which is fine at this scale and a real cost at millions of rows — which is why some APIs return “has next page” instead. Spring Data's Slice<T> does exactly that, and choosing between Page and Slice is a Stage 8 decision that starts as a Stage 4 design choice about whether your UI shows page numbers at all.

  


  
Experiment

    
Set a status filter, sort by amount, go to page 2, then change the search box. Watch the page reset to 0 and the URL rewrite. Then copy the URL from the bar, reset everything, and paste it back mentally — every control returns to where it was, because nothing was stored anywhere else.

06 / CONTAINMENT
Where errors land, and where they do not

  
You wrapped the app in an error boundary. Which of your errors does it actually catch?


  

    
Fewer than most people assume, and the gaps are not obvious. An error boundary catches errors thrown during rendering, in lifecycle methods, and in constructors of the tree below it. That is the documented list, and everything outside it — event handlers, asynchronous code, timers, server rendering, and errors thrown in the boundary itself — falls straight through to the window.

    
Pick a place to throw from.

The containment strategy that works

    
One error boundary around the whole app is a white screen with extra steps. The useful pattern is boundaries at the seams you already have, so a failure destroys the smallest sensible region:

    
    
      
  • Route level — React Router's errorElement on each route branch. A broken detail page keeps the shell, the navigation and the user's session.
    • 
      
  • Widget level — around anything independently fallible: a chart, a third-party embed, a dashboard tile. One dead tile should not blank the dashboard, which is the same argument as Promise.allSettled from Stage 2, expressed in components.
    • 
      
  • Never below a form the user is filling in. Unmounting a form with unsaved work loses it. Catch above, or handle the failure inline.
    • 
    

    
// Error boundaries are still class components — the only remaining case where
// a class is required. Or use react-error-boundary, which wraps this for you.
class ErrorBoundary extends React.Component<Props, { error: Error | null }> {
  state = { error: null };
  static getDerivedStateFromError(error: Error) { return { error }; }
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    reportError(error, { componentStack: info.componentStack, correlationId });
  }
  render() {
    return this.state.error
      ? this.props.fallback(this.state.error, () => this.setState({ error: null }))
      : this.props.children;
  }
}

    
Two details that matter. componentDidCatch is where the error reaches your monitoring, and it should carry the correlation ID from Stage 1 so the front-end error and the backend trace are the same incident in Stage 12. And the fallback must offer a way out — a reset that clears the error state, or navigation home. A fallback with no action is a dead end wearing an apology.

    
The one that will bite you

    
An async event handler whose rejection nobody handles produces an unhandled rejection: no boundary, no fallback, frequently no visible symptom at all. The button simply does nothing, and the user clicks it again. Every async handler needs a try/catch or a .catch — this is Stage 2's failure-channel lesson arriving exactly where it hurts.

07 / LIBRARIES
When to take the dependency

  
Every library is a permanent liability someone else maintains. When is that a good trade?


  

    
The instinct that a dependency is “free” is wrong in a specific way. What you install is not code — it is a relationship: an upgrade path, a security surface, a bundle cost, an API you did not design, and a bet that this project will still be maintained when you need it fixed. Sometimes that is an outstanding trade. Often it is not.

    
Five questions, in order:

    
    
      
  1. Is the problem genuinely hard, or just tedious? Hard means edge cases you will discover in production: time zones, internationalisation, accessible focus management, cache invalidation, virtualisation. Tedious means volume. Take the dependency for hard; write the tedious thing.
    2. 
      
  2. Would my version be wrong in ways I would not notice? A hand-rolled accessible dropdown is wrong for keyboard and screen-reader users, and your team will never notice. That asymmetry is the strongest argument for a library there is.
    3. 
      
  3. What does it cost at the boundary? Bundle size on a route students load on 3G is a user-facing cost. On an admin route behind a login it is nearly free. Measure it per route, not per app.
    4. 
      
  4. How hard is it to remove? A date formatter is a one-file swap. A state management library or a component system with theming is a rewrite. Weight the scrutiny accordingly — the reversible decisions deserve less argument than they usually get, and the irreversible ones more.
    5. 
      
  5. Is it maintained, and is the API stable? Recent releases, a clear migration story between majors, and a maintainer who is not one person. A dependency abandoned mid-project is worse than no dependency at all.
    6.

The recommendation, stated as one

    
These verdicts are an architectural recommendation for this stack and this application, not a general law — a team with deep MUI experience should weigh the component-library row differently, and a team shipping to low-end mobile in India should weigh every bundle row harder. What should not vary is the method: ask the five questions out loud, write the answer down next to the dependency, and revisit it when the answer changes. A dependency nobody can justify is a dependency nobody will dare remove.
