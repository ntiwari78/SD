Part one

Before CrewAI: what an agent actually is

Every behaviour later in this guide makes sense only against these four ideas. None of them are CrewAI-specific, and CrewAI does not change any of them — it only decides how much of each it writes for you.

The definition

An AI agent is an LLM with tools in a loop to achieve a goal.

An LLM takes input tokens, predicts likely tokens, and generates text. It does not take actions. The agent is the surrounding code that calls the model, interprets the output, decides what to do, calls tools, feeds results back, and repeats.

The boundary that matters

LLM = token generation engine. Agent = code that interprets those tokens and acts on them. The model never reaches into your computer. Your code does. Tool calling and “autonomy” are both ordinary software: prompt → tokens out → your code parses → your code executes.

Who decides the next step?

This is the single most consequential architectural choice, and CrewAI turns it into a one-line setting — so it is worth having the vocabulary first.

WorkflowAgent
Next step chosen bythe developer, at design timethe model, at runtime
Pathpredefinedopen-ended
Predictabilityhighlow
Testingconventionalneeds trajectory evaluation
Cost per taskbounded, knownvariable
If you already know the workflow, there is often little reason to ask an LLM to decide the workflow.

What every framework abstracts

Frameworks are helper libraries. They handle three things and no more:

orchestration
connecting multiple LLM calls together
tool calling
connecting an LLM to functions it can invoke
structured outputs
getting back data your code can parse

Together these make an agent loop. The useful axis between frameworks is not features but how opinionated they are — how much they decide for you. CrewAI sits firmly at the opinionated end.

Part two

CrewAI has three nouns

Learn these and you have the whole vocabulary. Everything in Part three is these three things plus one new setting at a time.

Agent — an LLM with a personality

Where a lightweight framework gives you one instructions field, CrewAI asks for three and composes the system prompt itself.

You write 
role: A compelling debater
goal: Present a clear argument
      for or against {motion}
backstory: An experienced debater
      with a knack for concise,
      convincing arguments
llm: openai/gpt-4o-mini
Crew sends 
You are A compelling debater.
Your personal goal is: Present a
clear argument for or against
{motion}
An experienced debater with a
knack for concise, convincing
arguments

…plus framework scaffolding you
never wrote

The trade: you inherit CrewAI's prompt-engineering work. You lose sight of the prompt.

Task — the unit of work

A task has a description and an expected_output, and is assigned to an agent. Functionally, it is the user prompt. CrewAI's own guidance is emphatic about where to spend your effort:

You can have good tasks with very loosely defined agents and it will still work well, but if you have a lot of detail on the agents but lousy tasks, then you're going to get lousy performance. CrewAI docs, via course transcript

Crew — agents + tasks + a process

The crew binds them and decides execution order. The process setting is where the workflow-versus-agent question from Part one reappears:

ProcessBehaviourEquivalent to
sequential tasks run in definition order, respecting declared dependencies orchestration by code
hierarchical a manager LLM decides the order and delegates orchestration by LLM

Where these live on disk

CrewAI's most-liked feature is that prompts live in YAML, separate from code. crewai create crew <name> scaffolds this for you.

project structure 
src/project/
├── config/
│   ├── agents.yaml   # role, goal, backstory, llm
│   └── tasks.yaml    # description, expected_output, agent,
│                    #   context, output_file, output_pydantic
├── crew.py           # binds YAML keys → objects; process, tools, memory
└── main.py           # inputs dict → kickoff()
Brittle seam

The function names in crew.py must match the YAML keys exactly. A typo produces an obscure key-not-found error that is hard to trace back to its cause.

Part three

Six cases, each adding one thing

These build strictly in order. Every case introduces exactly one new concept and ends with the behaviour it exposes — usually something CrewAI decided without telling you.

1

The minimal crew

Adds: nothing — this is the baseline

Two agents, two tasks, sequential. A researcher investigates a topic; a reporting analyst writes it up. This is the default scaffold, and it runs out of the box.

tasks.yaml 
research_task:
  description: Conduct research on {topic}
  expected_output: A list of 10 bullet points
  agent: researcher

reporting_task:
  description: Expand each point into a full section
  expected_output: A full report in markdown
  agent: reporting_analyst
  output_file: report.md
Behaviour exposed

You never wrote a system prompt. CrewAI composed one from role, goal and backstory, and injected its own instructions on top — including lines like “you must return the actual complete content of the final answer, not a summary.” The prompt that reaches the model is a framework artifact, not something you can read off the page.

2

Placeholders and a third task

Adds: {variables} · one agent, many tasks

A debate. Two agents — debater and judge — and three tasks. The debater both proposes and opposes; the judge decides. Curly-brace placeholders are filled from the inputs dict in main.py.

tasks.yaml · main.py 
propose:
  description: Argue in favour of {motion}. Be very convincing.
  agent: debater
oppose:
  description: Argue against {motion}. Be very convincing.
  agent: debater
decide:
  description: Review the arguments and decide which is
                 more convincing. Judge purely on the arguments.
  agent: judge

# main.py
inputs = {"motion": input("Enter the motion: ")}

It works. The judge reaches a verdict grounded in both arguments. But notice what was never written: nothing told the judge about the two prior tasks.

Behaviour exposed — the big one

When a task does not declare a context field, CrewAI silently passes it the outputs of every prior task. The judge saw the proposal and the opposition because CrewAI decided it should.

3

Tools, and context made explicit

Adds: built-in tools · the context field

A financial researcher. One agent gets web search via SerperDevTool; an analyst turns the findings into a report. Tools attach at the agent level.

crew.py · tasks.yaml 
# crew.py
from crewai_tools import SerperDevTool

@agent
def researcher(self) -> Agent:
    return Agent(config=self.agents_config['researcher'],
                 tools=[SerperDevTool()])

# tasks.yaml
analysis_task:
  description: Analyse the research findings and write a report
  agent: analyst
  context: [research_task]      # ← the new thing
  output_file: output/report.md

Here is the counter-intuitive part. You would expect context to add information. It does the opposite.

Behaviour exposed

Declaring context narrows what the task receives — from all prior task outputs down to only the tasks you named. Being explicit restricts; staying silent is the permissive option.

Why this bites

In a long crew, the implicit default grows the prompt on every task. You pay for it in tokens and in context rot, and nothing in your YAML shows it happening. Declare context even when it seems redundant — it is the only way to control what each task sees.

4

Structured outputs and a custom tool

Adds: Pydantic schemas · the @tool decorator

A stock picker. Three agents find trending companies, research them, and pick one. Free text will not survive being passed between tasks, so the first two tasks return typed objects.

crew.py 
class TrendingCompany(BaseModel):
    name: str   = Field(description="Company name")
    ticker: str = Field(description="Stock ticker symbol")
    reason: str = Field(description="Why it is trending")

class TrendingCompanyList(BaseModel):
    companies: List[TrendingCompany]

@task
def find_trending_companies(self) -> Task:
    return Task(config=self.tasks_config['find_trending_companies'],
                output_pydantic=TrendingCompanyList)

Custom tools use a decorator over a plain function — the schema is derived from the name, type hints and docstring:

tools/push_tool.py 
from crewai.tools import tool

@tool("send_push_notification")
def send_push_notification(message: str) -> str:
    """Send a push notification to the user."""
    requests.post(PUSHOVER_URL, data={...})
    return '{"notification": "ok"}'
Behaviour exposed

The docstring and type hints are the model-facing contract — they become the tool schema the LLM reads. This is identical to how lightweight frameworks do it. Tool definition is the one place CrewAI is not opinionated, and the skill transfers directly.

5

Memory

Adds: one boolean

You want the stock picker to avoid recommending the same company twice. Earlier CrewAI versions exposed four configurable memory types. Current CrewAI collapses all of it into unified memory:

crew.py 
return Crew(
    agents=self.agents,
    tasks=self.tasks,
    process=Process.sequential,
    memory=True,          # ← that is the entire API
)

Mechanically, agents are handed tools that read and write a memory store. It works. The question is what you do when it does not.

Behaviour exposed

A one-line opt-in with no visibility into what was stored or retrieved. The abstraction is total: no retrieval policy, no eviction rule, no inspection surface. Traces are the only window.

If the memory works the way you wanted to, then fabulous. If it doesn't, you can be left scratching your head trying to figure out how do I even debug this? Course transcript
6

Hierarchical — handing control to a manager

Adds: a manager agent · one changed enum

So far every crew ran tasks in the order you defined them. Switching to hierarchical hands ordering and delegation to a manager LLM.

crew.py 
manager = Agent(
    config=self.agents_config['manager'],
    allow_delegation=True
)

return Crew(
    agents=self.agents,
    tasks=self.tasks,
    process=Process.hierarchical,   # was Process.sequential
    manager_agent=manager,
)

If you omit manager_agent, CrewAI supplies a default one. Specifying your own is more predictable, because you control its prompt.

Behaviour exposed

One enum moves the system across the line from Part one — from orchestration by code to orchestration by LLM. That is a genuine strength: the most important architectural decision in agent design becomes cheap to A/B. It is also a one-line switch into unpredictability, harder testing, and variable cost.

Rule of thumb

Use LLM autonomy when autonomy provides real value — not simply because the framework makes it available.

Part four

Traces are the documentation

Every case above ended with something CrewAI did that your config did not show. There is exactly one way to see any of it.

three ways to enable 
$ crewai traces enable          # per project
CREWAI_TRACING_ENABLED=true     # in .env, all projects
Crew(..., tracing=True)          # in code, this crew

Then crewai login and read them at app.crewai.com. What you get is the per-agent, per-task breakdown: LLM calls, tool calls with inputs and outputs, and — the important tab — the actual messages sent to the model.

Use traces for two things

One: ordinary debugging — what did it call, what came back. Two, and more valuable: reverse-engineering the framework. Compare the messages tab against your YAML and you can see exactly what CrewAI added, rephrased, and forwarded.

This is the practical consequence of choosing an opinionated framework, and it changes what code review means. With a lightweight framework you can read a prompt change in a diff. With CrewAI, you have to run it and look at the trace.

Part five

Traps that cost hours

Behavioural surprises first, then environment issues. The first three are design consequences; the rest are papercuts that are merely expensive.

Implicit context

No context field means all prior task outputs are forwarded. Declaring it narrows rather than widens.

Opaque system prompts

You author role, goal and backstory. CrewAI authors the prompt. Only traces show what was actually sent.

Undebuggable memory

memory=True gives no retrieval accuracy, storage policy, or inspection surface.

Wrong Gemini key name

CrewAI looks for GEMINI_API_KEY, not GOOGLE_API_KEY. Set both to be safe.

The inner .env

crewai create crew writes a nested .env that shadows your project one. Delete it immediately.

Non-overriding dotenv

CrewAI calls load_dotenv() without override=True, so a stale machine-level API key silently wins.

YAML indentation

Misaligning llm: under the agent name instead of beside role: surfaces as a cryptic key error.

Breaking changes

Pin the version. CrewAI ships breaking changes between releases.

Part six

Choosing it, honestly

The deciding question is not features. It is how much transparency you are willing to trade for speed.

Reach for CrewAI when
  • You want a project scaffold and a large tool library on day one
  • Separating prompts into YAML is worth something — reviewable by non-engineers, editable without touching code
  • Your problem decomposes naturally into agents with assigned tasks
  • You want to A/B code-versus-LLM orchestration cheaply
Look elsewhere when
  • You need to see and control the exact prompt
  • You must reason about prompts statically — compliance, high-stakes output, prompts reviewed as artifacts
  • Fine-grained context control matters; the implicit default fights you
  • You need guardrails or sandboxing as first-class features
What the evidence does not say

No source evaluates whether role/goal/backstory beats a plain system prompt — CrewAI's defining design choice is undemonstrated. There is no sequential-versus-hierarchical comparison on the same crew, no retrieval-accuracy data for unified memory, and no benchmark against any other framework. Treat the guidance above as reasoning from documented behaviour, not from measurement.

Don't over-focus on framework selection. Different frameworks often provide different implementations of broadly similar underlying capabilities. Course transcript

The skills that transfer — writing good tool descriptions, being deliberate about context, evaluating against a real outcome, reading traces instead of guessing — are worth more than the choice itself.
