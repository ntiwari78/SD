Agents in plain Python — no framework

Just Python and a While Loop

Every agent framework abstracts three things: orchestration, tool calling, and structured outputs. Build those yourself once and the abstractions stop being magic. This guide goes from a bare model call to a bounded, observable agent in eight steps — and each step shows the naive version beside the one that survives contact with production.

Part one

What you are actually building

Four ideas. None require a framework, and skipping the framework does not change any of them.

The definition

An AI agent is an LLM with tools in a loop to achieve a goal.

An LLM takes input tokens, predicts likely tokens, and emits text. That is the whole of what it does. It has no state, no memory, and no ability to act. Everything else — the loop, the tools, the memory, the limits — is code you write.

The boundary

LLM = token generation engine. Agent = the code that interprets those tokens and acts on them. The model does not reach into your machine and run your function. Your software reads what it emitted and decides to call it.

This matters more without a framework than with one, because you are the layer. Every safety property the system has, you will have typed.

Who decides the next step?

WorkflowAgent
Next step chosen byyou, at design timethe model, at runtime
Pathpredefinedopen-ended
Predictabilityhighlow
Cost per taskbounded, knownvariable
If you already know the workflow, there is often little reason to ask an LLM to decide the workflow.

The three jobs you are taking on

A framework is a library that handles these. Without one, they are yours:

orchestration
connecting multiple LLM calls together
tool calling
describing functions, parsing requests, dispatching safely
structured outputs
getting back data your code can rely on
Why do this at all

Build it yourself once and you can read any framework's documentation and know exactly what it is doing for you — and what it is doing to you. It is also the right choice when you need fine-grained control over context, or when the harness is the product.

Part two

Eight steps from a bare call to an agent

Strictly incremental — each step adds one capability to the previous one. Where the simple version breaks under load, the hardened version sits beside it.

01

Text in, text out

Adds: nothing — the floor

The whole foundation, one line.

def simple_generate(self, user_input: str) -> str:
    """Simplest possible interaction — just pass text to the LLM."""
    return self.llm.generate(user_input)
Behaviour

Probabilistic. The same prompt twice can give different answers. Stateless. It remembers nothing between calls. No understanding. It recognises patterns in tokens and predicts likely continuations — that is the mechanism, not a metaphor.

02

Give it a role

Adds: a system prompt

Same model, same question, different behaviour — by constraint, not capability.

def generate_with_role(self, user_input: str) -> str:
    prompt = f"""{self.system_prompt}

User: {user_input}
Assistant:"""
    return self.llm.generate(prompt).strip()
Behaviour

Behaviour is not intelligence — it is constraints. You are not changing the model, you are shifting probabilities. Responses still vary, but now they vary within the bounds you set.

03

Make the output parseable

Adds: a schema, validation, retries

Free text cannot drive a program. Asking for JSON is necessary and not sufficient — the model will sometimes wrap it in prose, or emit something malformed.

Naive 
resp = llm.generate(prompt)
data = json.loads(resp)   # throws
# one bad response and
# the program dies
Hardened 
for attempt in range(3):
    resp = llm.generate(
        prompt, temperature=0.0)
    parsed = extract_json_from_text(resp)
    if parsed is not None:
        return parsed
return None

Three things doing work here: temperature 0 for determinism, tolerant extraction that finds JSON inside surrounding prose, and a bounded retry.

Behaviour — the first engineering moment

You are now treating the LLM as a fallible component: parse it, validate it, handle failure. Retries convert probabilistic behaviour into reliable behaviour. Count them — a rising retry rate is how you detect a prompt or model regression before users do.

Non-obvious

Multi-line schemas with a worked example outperform single-line ones. And a prompt edit that merely improves phrasing can increase verbosity, push the JSON past the context window, and break parsing — without changing correctness at all.

04

Let it choose

Adds: a finite action space

Instead of generating an answer, the model selects from a fixed list.

for attempt in range(3):
    parsed = extract_json_from_text(
        llm.generate(prompt, temperature=0.0))
    if parsed and "decision" in parsed:
        decision = parsed["decision"]
        if decision in choices:        # ← the load-bearing line
            return decision
return None
Behaviour — agency begins here

Selection is not generation. Constraining an infinite output space to a handful of options is the cheapest reliability win available. But the model can still return something that looks like a decision and is not in your list — which is why the membership check is not optional.

05

Let it act

Adds: tools — request separated from execution

The model emits a structured request. Your code decides whether to honour it. Keeping those two things in separate functions is the whole of tool safety. 

def request_tool(self, user_input: str) -> dict | None:
    # prompt describes: calculator(a, b, operation)
    for attempt in range(3):
        parsed = extract_json_from_text(
            self.llm.generate(prompt, temperature=0.0))
        if parsed and "tool" in parsed and "arguments" in parsed:
            return parsed
    return None

def execute_tool_call(self, tool_call: dict):
    return execute_tool(tool_call["tool"], tool_call["arguments"])

Dispatch is where the danger is. A tempting shortcut looks up the function by name in the global namespace:

Naive — do not ship this 
fn = globals()[name]
result = fn(**args)

# elegant, and it exposes
# every global function
# to the model
Hardened 
TOOL_MAP = {
  "record_user_details": record_user_details,
  "record_unknown_question": record_unknown_question,
}
fn = TOOL_MAP.get(name)
if fn is None:
    return "Error: unknown tool"
Why globals() is a vulnerability

It trusts the model to only ever name a tool you gave it. In principle the model can name exec — or anything else importable in that module — and your dispatcher will happily call it. An explicit allow-list is the boundary, and it is one dictionary.

Behaviour

Tools are interfaces, not abilities. The agent does not have the capability — you do. It describes what it wants through a structured contract you defined, and you retain the right to refuse. This is also why adding capability needs no retraining: you add a function and a description.

06

Close the loop

Adds: iteration and termination

Everything so far is a single exchange. The agent appears when you repeat: call the model, run whatever tools it asked for, append the results, call again — and stop when it answers without requesting a tool. 

while not goal_achieved:
    response = call_llm(context)

    if response_requests_tool:
        result = execute_tool(...)
        context += result          # observation goes back in
    else:
        return response          # no tool requested → done
Behaviour — this is the whole trick

The software owns the loop. The software owns tool execution. The model only emits tokens that guide the next step. Everything marketed as autonomy is this while and this if.

That version has no brakes. A loop with no bounds is the signature agent failure, and four independent limits are the fix — any one alone is insufficient:

LimitTypicalWhy it alone is not enough
Step cap20–50five expensive steps can still burn the budget
Cost ceiling$3.00a cheap loop can run for hours
Wall-clock limitper deploymenta hung tool blocks indefinitely
No-progress detectionhash last k actionsan agent can oscillate under all three
A free planning upgrade

Give the loop two extra tools — create_checklist(items) and mark_complete(index, notes) — and the model starts planning before it acts and works through items one by one. The visible to-do list in coding agents is exactly this. Nothing else changes; it is the same loop.

07

Let it remember

Adds: persistence across interactions

Say "My name is Ale" in one call and ask "What's my name?" in the next, and the model has no idea. It never did. What looks like memory is context being resupplied. 

memory_context = self.memory.get_all()
memory_str = "You remember:\n" + "\n".join(f"- {m}" for m in memory_context)

# model returns: {"reply": ..., "save_to_memory": "..." | null}
if parsed.get("save_to_memory"):
    self.memory.add(parsed["save_to_memory"])
Behaviour

Memory is data storage, not thought. It is a list you can print, edit, and delete. The model has no direct access to it — it only ever sees what you chose to put in the prompt. Distinguish context (this prompt) from memory (storage that outlives it).

Where this goes wrong

Get-all retrieval stops working once memory is large — it floods the context and costs tokens on every turn. You will eventually need relevance, recency, and an eviction rule. Start simple, but know the ceiling is low.

08

Let it plan

Adds: plans as data → typed actions → a dependency graph

Three refinements of one idea, each making the plan more executable.

First, a plan is JSON — not a thought:

{"steps": ["Research topic", "Create outline", "Write draft"]}

Because it is data, you can inspect it, edit it, validate it, and reuse it before anything executes.

Second, vague steps become typed actions. "Write draft" cannot be validated. This can:

{"action": "generate_text",
 "inputs": {"topic": "AI agents", "length": "1000 words"}}

Third, add dependencies and you have a graph:

{"nodes": [
  {"id": "1", "action": "research", "depends_on": []},
  {"id": "2", "action": "outline",  "depends_on": ["1"]}
]}

# validate BEFORE executing:
#   every depends_on id exists
#   the graph is acyclic
Behaviour

Planning is structured data generation, not reasoning. The graph is not advanced cognition — it is validation plus explicit ordering, which buys you parallel execution of independent nodes and failures contained to single nodes. By this point it feels inevitable rather than clever.

What decomposition cannot fix

Global constraints. Split a trip into flights, hotels, and food and each part is fine — but budget and dietary rules belong to no sub-task, so no sub-task checks them. Neither more decomposition nor a bigger context window solves this. Enforce global constraints in your own code, after the plan runs.

Part three

How little you actually need

The strongest evidence that frameworkless is viable is a research agent that deliberately removed almost everything.

mini-swe-agent, from the team behind SWE-bench, is roughly 100 lines for the agent class and scores over 74% on SWE-bench Verified. Four choices explain it:

No tools other than bash

Not even the model's tool-calling interface — so it runs with any model at all. Rather than implementing a tool per capability, the model uses the shell.

A completely linear history

Every step appends. The trajectory is the message list you send — nothing to reconcile when debugging or fine-tuning.

subprocess.run for every action

No stateful shell session. Each action is independent, which makes sandboxing a one-line substitution — swap in docker exec — and scaling trivial.

Termination is a message

The loop exits only on a message with role == "exit", so the reason a run ended is part of the saved trajectory rather than a side channel.

Its entire safety envelope is a config object:

the whole surface 
class AgentConfig(BaseModel):
    system_template: str
    instance_template: str
    step_limit: int = 0                     # 0 = unlimited
    cost_limit: float = 3.0                 # USD
    wall_time_limit_seconds: int = 0
    max_consecutive_format_errors: int = 3
    output_path: Path | None = None

Limits are checked before the model call and raised as typed exceptions that append an exit message. The trajectory is written in a finally block, so even a crashed run leaves a complete record.

We placed a lot of emphasis on tools and special interfaces for the agent. However, one year later, as LMs have become more capable, a lot of this is not needed at all to build a useful agent. mini-swe-agent, project README
What this is evidence for

Capability moved from the scaffold into the model. Loop complexity is not where agent performance comes from. A simple loop with good tools and honest limits is a competitive baseline — and a deliberately unopinionated one, which is why it is also the recommended starting point for fine-tuning or RL work that should not overfit to a particular scaffold.

Part four

What you still owe the system

Eight cases produce a working agent. These are the jobs a framework would have quietly done, and they are the difference between a demo and something you can operate.

A context budget

History grows linearly, so billed tokens grow quadratically. Count tokens with the real tokenizer before every call — some APIs truncate silently and your system prompt is what disappears.

Retries with backoff

Exponential backoff with jitter, applied at the tool level where failures are common and recoverable. Retried tools must be idempotent or you will send two emails.

Loop detection

Hash (tool, args) with sorted keys and look for repeats in a sliding window. On detection, escalate — do not iterate harder.

A sandbox

The one control that does not depend on the model behaving. Containers, no network by default, read-only root, CPU and memory caps. Never host privileges.

Untrusted tool output

A fetched page can carry instructions. Treat every tool result as data, never instructions, and sanitise before it re-enters context.

Graceful failure

Say what was accomplished, why it stopped, what would unblock it — and preserve state so the task can resume.

Two things to build early, not late

Evals. An eval suite is just a Python file that runs your agent and asserts nothing broke. Start with hard assertions only — JSON is valid, required fields exist, the tool name is one you offer — and five to ten golden cases per capability. Run them before every prompt change. 

# the whole idea
result = agent.generate_structured(case["input"], case["schema"])
assert result is not None
assert all(f in result for f in case["must_have_fields"])

Telemetry. Structured JSON lines, one span per operation, all sharing a trace ID. Then a failure is grep <trace_id> agent.jsonl rather than a guess. 

@dataclass
class Span:
    span_id: str
    trace_id: str        # ← links the whole interaction
    event_type: str      # llm_call | tool_call | memory_op | decision
    timestamp: str
    duration_ms: float | None = None
    data: dict | None = None
    error: str | None = None
They answer different questions

Evals run before deployment on known inputs and catch regressions. Telemetry runs during deployment on unknown inputs and explains what happened. Neither substitutes for the other.

The mistake that outranks all of these

Measuring output quality instead of outcome. An LLM is very good at producing plausible content — an email can read beautifully and sell nothing. Tie the agent to a real metric: reply rate, tickets resolved, tests passing, revenue. "Looks good" is not a result.

Part five

Staying frameworkless, honestly

Stay in plain Python when
  • You need fine-grained control over context — the usual reason teams leave a framework
  • The harness itself is your product or differentiator
  • You have strict latency or cost requirements
  • You are doing fine-tuning or RL and must not overfit to a scaffold
  • You are learning — build it once and every framework becomes legible
Take the framework when
  • You are prototyping and speed beats control
  • You need many tool integrations you would otherwise write yourself
  • Your use case fits the framework's abstractions cleanly
  • Built-in tracing, sessions, or guardrails would otherwise be your next month
What the evidence does not say

No source measures a framework's overhead against a hand-written loop, and none reports how much of end-to-end performance comes from the harness versus the model. The mini-swe-agent result is reported without the model, run count, or date. Treat the guidance here as reasoning from documented behaviour, not from measurement.

Don't over-focus on framework selection. Different frameworks often provide different implementations of broadly similar underlying capabilities. Course transcript

The skills built here — bounding the loop, allow-listing dispatch, validating before executing, treating tool output as untrusted, measuring against a real outcome — transfer to every framework and outlive all of them.
