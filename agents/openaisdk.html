OpenAI Agents SDK — a working model

What the Agents SDK Reduces To

The SDK's design bet is thinness: almost every abstraction it offers collapses into a primitive you already understand. This guide builds from agentic fundamentals through seven worked cases, and each case ends by naming the plain mechanic underneath the nice API.

Part one

Before the SDK: four ideas

Every case later depends on these. None are SDK-specific — and the SDK's whole character is that it doesn't obscure any of them.

The definition

An AI agent is an LLM with tools in a loop to achieve a goal.

An LLM takes input tokens, predicts likely tokens, and emits text. It does not take actions. The agent is the surrounding code that calls the model, parses the output, decides what to do, executes tools, feeds results back, and repeats.

The boundary

LLM = token generation engine. Agent = code that interprets those tokens and acts. The model never reaches into your machine. Your code does. Tool calling and "autonomy" are both ordinary software.

The central architectural question. It returns in Part four as a concrete choice between two SDK mechanisms.

The SDK's particular bet

Evolved from the experimental Swarm project, the Agents SDK is deliberately lightweight and code-first: few abstractions, and none of them hiding much. Its own material is blunt about it —

Framework abstractions often reduce to familiar primitives such as prompts, tool calls, and messages. Course transcript

That sentence is the thesis of this entire guide. Each case below ends by showing exactly which primitive.

Part two

Two objects and a result

This is nearly the whole vocabulary. Everything in Part three adds one setting at a time.

Agent

A model, an instruction string, and some tools. The instructions field is the system prompt — you write it, and it is what the model receives.

the shape 
agent = Agent(
    name="Jokester",
    instructions="Tell funny jokes.",   # ← this is the system prompt
    model="gpt-4o-mini",
    tools=[...],            # optional
)

Recommendation from the source: start with one agent, and introduce more only when doing so clearly improves the solution.

Runner — who owns the loop

Runner.run() executes one application-level turn: send the prompt, receive the response, call tools if requested, feed results back, continue, stop when complete. This is the loop you would otherwise hand-write. 

result = await Runner.run(agent, "Tell me a joke about agents.")

For progressive output there is Runner.run_stream(...), which the material relates to server-sent events.

The result object — two things worth knowing

result.final_output
the finished answer
result.to_input_list()
the conversation as a reusable message list — the key to Case 3
Part three

Seven cases, each adding one thing

These build in order. Every case introduces exactly one concept and ends by naming the primitive it reduces to.

01

The minimal agent

Adds: nothing — this is the baseline

An agent, a runner, an answer. Three lines of real work.

from agents import Agent, Runner, trace

agent = Agent(name="Jokester", instructions="Tell funny jokes.")

with trace("Joke workflow"):                  # wrap for observability
    result = await Runner.run(agent, "Tell me a joke.")
    print(result.final_output)
Reduces to

A system prompt, a user message, and a while loop around an API call. Runner owns the loop so you don't rewrite it — but nothing about the prompt is composed for you. What you typed is what the model sees.

02

Give it a tool

Adds: the @function_tool decorator

Hand-writing JSON tool schemas is laborious and error-prone. The decorator derives the schema from the function itself.

What you write 
@function_tool
def push_tool(message: str) -> str:
    """Send a message to the user
       as a push notification."""
    ...
What the model receives 
{
  "name": "push_tool",
  "description": "Send a message
     to the user as a push
     notification.",
  "parameters": {
    "message": {"type": "string"}
  }
}
Reduces to

The three signals that become the schema are the function name, the type hints, and the docstring. They are not stylistic — they are the model-facing contract. A vague docstring produces vague tool selection.

Why this matters

Tool descriptions are part of the prompt. Poor descriptions produce poor tool use — and this is the one area where the skill transfers unchanged to any other framework.

03

Make it remember

Adds: conversation history

Reuse the same Agent object across two runs and ask it your name. It will not know. 

await Runner.run(agent, "My name is Ed.")
await Runner.run(agent, "What's my name?")   # no idea

Two remedies. Manual, where you own the storage:

next_input = result.to_input_list()
next_input.append({"role": "user", "content": "What's my name?"})
result = await Runner.run(agent, next_input)

Or the SDK's session abstraction, which manages history across runs for you:

session = SQLiteSession("conversation_id")
result  = await Runner.run(agent, "What's my name?", session=session)
Reduces to

Resending messages. Memory is an illusion created by supplying context again. Because the manual route hands you a plain list, your history can live anywhere — a file, Postgres, S3, Mongo, application state.

04

Run three at once

Adds: concurrency

Three sales agents — professional, humorous, executive — draft the same email in different registers. Running them in sequence wastes wall-clock on I/O waits. 

results = await asyncio.gather(
    Runner.run(professional_agent, prompt),
    Runner.run(humorous_agent,     prompt),
    Runner.run(executive_agent,    prompt),
)
Reduces to

asyncio. The framework is not parallelising anything — Python's event loop is. Three I/O-bound HTTP requests progress concurrently because that is what gather does.

Pattern

Same task, different specialised prompts, N candidate outputs — then one more agent picks the best. Generate → evaluate → select.

05

Delegate, keeping control

Adds: agents as tools

A manager agent needs specialists but must stay in charge of the conversation. Any agent can be exposed to another agent as a callable tool. 

tools = [
    professional_agent.as_tool(tool_name="sales_professional", ...),
    humorous_agent.as_tool(tool_name="sales_humorous", ...),
]
manager = Agent(name="Sales Manager", instructions=..., tools=tools)

Flow: Manager → Specialist → Manager. The specialist returns a result; the manager decides what happens next.

Reduces to

A tool call whose implementation happens to be another agent loop. Nothing new is introduced — the sub-agent is a function that takes longer and costs more.

06

Delegate, giving up control

Adds: handoffs

Sometimes the specialist should own the rest of the conversation — a triage agent routing to billing, where billing finishes the job.

Reduces to

A tool call. Handoffs are exposed to the model as tools named transfer_to_<agent>. The conceptual distinction is real and useful; the mechanism is the one you already met in Case 2.

07

Constrain it

Adds: structured outputs · guardrails

Free text is unparseable and unenforceable. Two different constraints solve two different problems.

Structured outputs — a Pydantic model defines the shape of the answer:

class NameCheckOutput(BaseModel):
    is_name_in_message: bool
    name: str

guardrail_agent = Agent(..., output_type=NameCheckOutput)

The material connects this to constrained decoding: structured output is not merely "please return valid JSON" — the system can impose the schema so the result conforms.

Guardrails — validation with a hard stop. Three kinds, with defined boundaries:

GuardrailValidatesRuns on
Inputincoming user inputthe first agent
Outputfinal agent outputthe final agent
Toolfunction-tool calls and resultsindividual tool calls

A failing guardrail trips a tripwire and the SDK raises an exception — execution stops rather than continuing with bad data.

Reduces to

A schema plus an if statement. Which is exactly why the source offers a dissenting option: skip the abstraction and write agent → checker → validation → continue or stop yourself — claimed to be easier to debug and less coupled to one framework. An architectural preference, not a claim the SDK's version is wrong.

Prompting is not enforcement

In the source's own lab, the model sometimes would not call the email tool despite being instructed to. A framework setting can require tool use. When a behaviour is mandatory, use an application-level control rather than hoping the model complies every time.

Part four

Who decides the order?

Cases 5 and 6 both hand routing to the model. There is a third option the SDK does not advertise, because it needs no feature at all.

Code orchestration is just successive Runner.run() calls in an order you wrote. No handoffs, no agents-as-tools — plain Python deciding what happens next.

LLM orchestration 
manager = Agent(
  tools=[a.as_tool(), b.as_tool()],
  handoffs=[emailer],
)
# the model picks the path
Code orchestration 
plan   = await Runner.run(planner, q)
docs   = await Runner.run(search, plan)
report = await Runner.run(writer, docs)
await Runner.run(emailer, report)
SituationPreferred
Fixed business workflowcode
Business-critical decisionscode
Predictability requiredcode

Open-ended taskLLM
Agent must choose its own pathLLM
Coding agents, autonomous productsLLM
If you already know the workflow, there is often little reason to ask an LLM to decide the workflow.
The production default

Production systems favour code-driven orchestration, because businesses need predictable behaviour, clear failure modes, auditable execution and easy testing. Use LLM autonomy when autonomy provides real value — not simply because the framework makes it possible.

A caution about multi-agent

There is no new intelligence created merely by adding agents. Quality still depends on prompts, context, model capability, tool definitions, evaluation and workflow design. Under the surface, agent collaboration is message passing.

Part five

Beyond the loop

Four capabilities that sit outside the seven cases — and the one place the SDK's model-agnosticism stops.

Tracing

Built in, covering LLM calls, tool calls, handoffs and guardrails. Wrap work in with trace("name") and inspect which agents ran, in what order, what was parallel, and what each was actually sent.

Sandbox agents

SandboxAgent gives an isolated workspace — Manifest, capabilities, session, SandboxRunConfig. In the source's demo the agent found a mutable-default bug and wrote the fix to an output directory rather than editing the original.

MCP

A standard way to connect to tools and data someone else built. The compelling case: an older model that doesn't know a new API can consult a documentation MCP server and answer accurately.

Hosted tools

Web search, file search, code interpreter, hosted MCP. Fast to prototype with — and the one real coupling point.

The lock-in seam

The core — agents, tools, handoffs, structured outputs — is model-agnostic. Hosted functionality is not: it is more tightly connected to OpenAI infrastructure than the rest of the SDK. The named trade-offs are cost, provider dependence, reduced infrastructure control and ecosystem lock-in.

Debug empirically, not by narration

Don't anthropomorphize the agent. Inspect the actual prompts, outputs, and tool calls.

Rather than "the sales manager decided the humorous email was best," look at the system prompt, the user prompt, the candidates, the tool calls, the output, the trace. Then modify, rerun, compare. Agent engineering is iterative and empirical, not write prompt → done.

The biggest mistake

The source's own SDR project generates three emails, picks one with a judge, and sends it — and never proves the chosen email works. An LLM is very good at generating plausible content; plausible is not commercially effective. Measure open rate, reply rate, meetings booked, revenue. "Looks good" is not a result.

Reach for the Agents SDK when
  • You need to see and control the exact prompt
  • Guardrails, tripwires or a sandbox are requirements
  • The handoff-versus-agents-as-tools distinction maps onto your problem
  • You want minimal abstraction between your code and the model
  • Prompts are reviewed as artifacts — compliance, high-stakes output
Look elsewhere when
  • You want a project scaffold and a large tool library on day one
  • Non-engineers need to edit prompts without touching code
  • You would rather inherit someone else's prompt-engineering conventions
  • Heavy reliance on hosted tools would make provider lock-in unacceptable
What the evidence does not say

No measured comparison of agents-as-tools versus handoffs on the same task — the distinction is conceptual and the guidance is judgment. No data behind the claim that hand-written guardrails are more debuggable than the SDK's. No measurement of the SDK's overhead against a hand-written loop, and no benchmark against any other framework. Treat all of the above as reasoning from documented behaviour.

Don't over-focus on framework selection. Different frameworks often provide different implementations of broadly similar underlying capabilities. Course transcript

The transferable skill is not this API. It is writing tool descriptions that work, being deliberate about context, evaluating against a real outcome, and reading traces instead of guessing.
